CURRENT TREE / IMPORTANT EXISTING CONTRACTS

Inspect the actual tree before editing and verify these facts rather than trusting this prompt.

The supplied tree is currently around SAIPEN 7.232.0.

The project ALREADY has the important continuity primitives:

1. Work != Attempt.
   - BOARD ticket is durable Work.
   - Attempt is one bounded execution episode.
   - Attempt may end interrupted/context_limit/process_crash/deliberate_handoff/etc.
   - Attempt failure does not destroy Work identity.

2. `saipen brief` already provides a cold-handoff projection.
   - It is derived from canonical STATE + BOARD + LOG.
   - It is read-only.
   - It is never authority.
   - It must remain reconstructable from canonical state.

3. Cold handoff is already proven:
   - a cold Agent B with zero chat history can resume the SAME Work from repository state alone.

4. Disk/canonical files outrank model memory.
   - STATE / BOARD / LOG remain project truth.
   - stale remembered context must be discarded.

5. Core is single-writer.
   - one active Core Work / writer semantics must not change.
   - handover must not create concurrent Core writers.

6. Completion is evidence-based.
   - producer claims are not completion authority.
   - VERIFY / REVIEW / SHIP / closure evidence still decide DONE.

7. EXECUTION already treats the final evidence report as mandatory human-facing output.
   - progress chatter may be suppressed.
   - evidence may not be suppressed.

8. The v9 runtime research already reserves runtime ownership for:
   - resident sessions
   - queues
   - timers / scheduling
   - heartbeat / continuation policy
   - model connections
   - detachable execution
   - runtime messaging
   while Core retains state, Work, evidence and DONE authority.

9. v9 runtime implementation is gated.
   - Do not smuggle resident runtime/model switching into the current protocol before its gate opens.

THESIS

SAIPEN does NOT need a second handoff system.

It already solves correctness of cold continuation.

What may be useful is an OPTIONAL, NON-CANONICAL optimization layer:

    TRAJECTORY DELTA / CONTINUATION CAPSULE

whose only job is to reduce repeated exploration and preserve execution knowledge
that cannot be reconstructed from the repository.

The capsule is advisory acceleration.

It is NEVER required to resume.
It is NEVER project truth.
Deleting it MUST lose convenience only, not correctness or recoverability.

==================================================
PHASE 2 — CLASSIFY CONTEXT BY RECONSTRUCTABILITY
==================================================

Define a bounded three-class model.

CLASS A — RECONSTRUCTABLE / VERSIONABLE LOCAL CONTEXT

Examples:
- source files
- project docs
- repository config
- git history
- stable generated files already in the tree

Default handling:
- do NOT copy full content into the capsule;
- store a reference;
- bind the reference to freshness identity.

Useful fields may include:

{
  "path": "src/router.py",
  "range": "120-310",
  "source_identity": "...",
  "content_hash": "...",
  "purpose": "traced retry lifecycle",
  "finding": "timeout state is written before worker termination"
}

Do not require both Git object identity and byte hash if one strong existing
project identity mechanism already solves freshness. Reuse existing SAIPEN
source identity/fingerprint machinery where possible.

If current bytes no longer match the recorded identity:
- the finding becomes STALE/ADVISORY;
- the successor rereads the file;
- stale capsule data never overrides current files.

CLASS B — NON-RECONSTRUCTABLE / EPHEMERAL EVIDENCE

Examples:
- web research
- remote API responses
- transient provider errors
- browser observations
- runtime-only console output
- a test failure output whose exact state can no longer be reproduced
- external model/subagent findings not stored elsewhere

Default handling:
- preserve the minimum evidence needed to understand the result;
- include provenance/time/source when available;
- for large evidence, store a bounded artifact + reference/hash instead of
  stuffing full output into the capsule.

CLASS C — KNOWLEDGE DELTA

Examples:
- verified root cause
- decision and why
- rejected approach and why
- changed hypothesis
- exact resume point
- known unknown
- unresolved risk

Default handling:
- preserve compactly;
- distinguish VERIFIED / INFERRED / REJECTED / UNKNOWN;
- never promote an inference to evidence.

This class is the main value of the idea.

    NEVER DONE.

PHASE 7 — RED CONTROLS
==================================================

Add a focused red-control/test plan before production runtime implementation.

At minimum prove or specify tests for:

TC-01 DELETE-CAPSULE
Delete every trajectory artifact.
A cold agent still resumes correctly from `.saipen` alone.

TC-02 TAMPERED-CAPSULE
Capsule contradicts BOARD/STATE/LOG.
Canonical files win; contradiction is ignored/reported.

TC-03 STALE-LOCAL-REF
Referenced file hash/source identity changed.
Successor rereads current file; stale finding is not trusted as current evidence.

TC-04 NO-LOCAL-DUPLICATION
Large reconstructable source read is represented by reference/fingerprint,
not copied wholesale into compact capsule.

TC-05 EPHEMERAL-EVIDENCE-SURVIVES
A non-reconstructable upstream/API/runtime error required for reasoning is
preserved or artifacted with provenance.

TC-06 REJECTED-HYPOTHESIS-SURVIVES
A failed approach and its reason cross the handoff so successor does not retry
the identical dead hypothesis without a changed input/evidence/hypothesis.

TC-07 UNKNOWN-STAYS-UNKNOWN
Unknown/inferred capsule data cannot satisfy VERIFY evidence or closure.

TC-08 SINGLE-WRITER
Handoff never creates two Core writers or two active Core Attempts.

TC-09 WORK-IDENTITY
Provider/model change creates a successor Attempt on the SAME Work.
It does not create duplicate Work.

TC-10 PROVIDER-PORTABILITY
Switch Codex -> OpenCode Go -> Claude (synthetic adapters are enough at first).
Canonical STATE/BOARD/LOG remain provider-neutral.

TC-11 PARTIAL-CAPSULE-WRITE
Crash during capsule write leaves either old-valid or new-valid optional
artifact; canonical files remain valid.

TC-12 SECRET-REDUCTION
Synthetic API key/cookie/auth header is never emitted to the capsule.

TC-13 HUMAN-NO-BABYSITTING
A synthetic quota-trigger handoff reaches the successor without requiring
"copy / paste / continue" human steps.

TC-14 RESULT-AUTHORITY
A successor receiving a capsule cannot convert producer claims into DONE.
Normal VERIFY/REVIEW/SHIP evidence remains required.

TC-15 CAPSULE-ABSENCE
Runtime/adapters may operate without transcript/session access.
No transcript dependency is required for SAIPEN compatibility.
