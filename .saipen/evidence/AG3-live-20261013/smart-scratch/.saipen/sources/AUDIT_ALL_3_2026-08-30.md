[P1] [CORE-002] _SMART_VAC_CLEANER.py::CleanerEngine._plan_tree
EVIDENCE: `_plan_tree()` accumulates an entire directory's `staged_files`/`staged_dirs`, commits them to global `files`/`dirs`, recursively descends all staged directories, and only afterwards checks `len(files) > _plan_max` (lines 2395-2453). On overflow it logs "failing closed", clears the shared lists and returns only from the current recursion frame. Parent frames remain active and can recurse into later siblings, repopulating the cleared plan. Focused reproduction with `SMARTVAC_PLAN_MAX_FILES=2` and a nested tree containing three files in `a/a1`, then `a/a2/late.tmp` and sibling `b/late2.tmp`, produced `freed=1`, `n_errors=1`: after the overflow error, `a/a2/late.tmp` was still physically deleted. The three files which originally triggered the overflow survived. There is also no bound on the `dirs` list, so a directory-heavy tree can exceed the intended in-memory resource ceiling without increasing the checked counter.
DEFECT: The resource-cap abort is local rather than transaction-wide and is enforced after unbounded staging/recursion. Include directories in the resource accounting or otherwise independently bound them.
VERIFY: With a cap of 2, cover (1) one wide directory, (2) a deep branch followed by later siblings, and (3) a directory-only/deep tree. In both dry-run and delete mode, overflow must log exactly the operational failure, report zero planned/freed bytes, perform zero filesystem mutations, and create no CandidateLedger claim. At exactly the allowed bound, normal planning/apply must still work.
