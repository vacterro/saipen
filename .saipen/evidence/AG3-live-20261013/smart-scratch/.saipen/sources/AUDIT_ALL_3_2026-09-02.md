[P0] [CORE-001] _SMART_VAC_CLEANER.py:is_path_blacklisted / sanitize_roots / CustomCleaner.run_all
EVIDENCE:
- BLACKLIST_PATHS (around lines 4094-4110) contains protected roots including C:\, Windows, USERPROFILE, Program Files, SCRIPT_PATH.parent and BASE_DIR.
- is_path_blacklisted (around lines 4113-4137) states that an ancestor of a protected root is equally dangerous, but its actual relation test is candidate.relative_to(protected_root). That detects equality/descendants only; it does not detect a candidate that is an ancestor containing a protected root.
- sanitize_roots (around lines 4182-4205) and custom-rule normalization (around lines 4461-4477) rely on that one-direction predicate.
- CustomCleaner.run_all (around lines 4045-4069) validates the configured root once and, for pattern "*", calls _del_dir_contents(target, ...).
- SafetyGuard.is_safe (around lines 1865-1934) confines mutations to its cleaner base root but does not independently forbid descendants that fall inside BLACKLIST_PATHS.
- Deterministic reproduction patched BLACKLIST_PATHS to contain a protected child below a broader custom target and ran a "*" sweep. Observed:
  broad_blacklisted False
  protected_blacklisted True
  protected_exists True
  victim_exists False
  The protected directory survived only as a directory while a file inside that explicitly protected subtree was deleted.
DEFECT:
A user-supplied custom/portable root can be accepted when it is an ancestor of a protected application/system root. Once accepted, the cleaner's local SafetyGuard considers protected descendants safe because they are inside the configured base. This breaks the blacklist invariant and can delete data inside a root the program explicitly declares untouchable. The practical risk is especially direct for BASE_DIR/SCRIPT_PATH on a non-C: drive where C:\ itself does not incidentally reject the broader ancestor.
REPAIR:
For user-supplied/configured cleaning roots, reject any overlap with a protected root in either direction: candidate equal to/inside protected root OR candidate is an ancestor containing protected root. In addition, propagate protected subtrees into the guard used by user-root cleaners so a stale/directly constructed rule cannot sweep through BLACKLIST_PATHS. Do not blindly impose the same global-overlap rule on reviewed internal SystemCleaner targets, which intentionally operate beneath system roots.
VERIFY:
Add regressions proving:
1. A custom/portable target that is a parent of BASE_DIR or SCRIPT_PATH.parent is rejected.
2. pattern="*" cannot remove any descendant of a protected child even when a stale rule reaches runtime.
3. An unrelated sibling/non-system-drive root remains accepted.
4. Existing reviewed SystemCleaner targets continue to operate.
5. Run the full Windows test suite after the guard change.

Evaluate expected fingerprints only after acquiring the cross-process lock.
VERIFY:

2. A writer carrying a genuinely stale fingerprint must return false/retry rather than overwrite newer state.
3. Concurrent migration/bootstrap and GUI persistence must preserve unrelated policy fields.
4. Crash/interruption testing must still leave either old or new valid JSON, never a partial config.
