P0-A — START_PREPARED CONTRACT IS CURRENTLY BROKEN

browser_dispatch.py now requires:

    START_PREPARED -> canonical start_receipt must exist

This is correct.

But browserWorkerConsume() currently effectively does:

    ATTACHED
    -> startAuditCoreFromReadyAttachment()
    -> inspect handoff
    -> START_PREPARED without start_receipt
    -> STARTED

This violates exactly-once semantics in TWO ways:

1. START_PREPARED is reported AFTER the irreversible Send path has already run.
2. The worker does not send handoff.receipt to the Bridge.

Actual HTTP lifecycle regression currently fails with:

    missing_start_receipt
    START_PREPARED requires the canonical START receipt

The repository architecture contract already says START_PREPARED must be
acknowledged after the exact receipt exists and BEFORE any Send click.

THIS IS THE FIRST THING TO FIX.

P0-B — ACTIVE AUDIT LEASE IS NOT HEARTBEATED

browserWorkerSnapshot() currently does not include:

    dispatch_id
    lease_id

register_worker() is already able to renew an existing lease when those fields
are supplied.

Therefore an audit can enter AUDITING, perform no state transition for several
minutes, and the 180-second lease may expire even though the browser tab is
alive and working.

That is unacceptable for audits that naturally take many minutes.

Every heartbeat belonging to an active dispatch must renew its exact lease.

P0-C — BROWSER "COMPLETE" IS NOT DURABLE AUDIT COMPLETE

Auto runtime currently reaches:

    autoRuntime.stage = 'complete'

as soon as all browser responses have been captured.

But completed wave records can still be waiting in the Bridge save queue.

browserWorkerPollOnce() currently sees runtime complete and sends:

    COMPLETE

then clears browserWorkerLease.

That means transport can be marked DONE before the final audit is physically
committed to disk.

This violates the main user requirement:

    "готовый аудит готов и сохранён"

Canonical success must mean:

    campaign.json says COMPLETE
    AND campaign_run_id matches
    AND final_handoff exists
    AND final_handoff validates
    AND the expected wave count is durable.

Browser runtime completion is only FINALIZING, never authoritative DONE.

P0-D — WORKER LEASE IS CLEARED EVEN WHEN COMPLETE ACK MAY FAIL

Current worker flow clears browserWorkerLease after attempting COMPLETE.

Never destroy recovery identity before a positive Bridge acknowledgement.

P0-E — POST-START RESTART RECOVERY IS INCOMPLETE

BrowserDispatcher correctly refuses blind redispatch after START_PREPARED.

However Bridge restart currently converts post-start work to BLOCKED and there
is no complete same-worker reconciliation path back into AUDITING/COMPLETE.

Similarly browserWorkerLease is currently only an in-memory JS variable.

A browser reload, widget reload, or Bridge restart can therefore strand an
otherwise healthy audit.

P1-A — SEND AUDIT CAN USE AN OLD ZIP

_on_send_audit() currently accepts an existing archive merely because the file
exists.

Existence != freshness.

ProjectRoomModel already contains archive/source freshness knowledge.
Use a canonical ensure_fresh_archive() operation before dispatch.

Never silently audit yesterday's ZIP because it happens to be lying around.
See also the ancient human tradition of naming files "final_final2.zip".

P1-B — LIVE DISPATCH STATE IS MOSTLY INVISIBLE IN DESKTOP UI

BridgeService.status() already obtains browser dispatcher counters, but the

ProjectRoomModel has no dispatch-specific roles.

    waiting for browser
    uploading
    starting
    auditing
    saving
    done
    blocked
    failed

P1-C — WORKER SCHEDULING CAN BE DELAYED BY A GHOST FREE WORKER

This is a pull-based broker.

claim_job() additionally calls _next_worker_for_assignment() across all
registered FREE workers.

A stale-but-not-yet-TTL-expired worker can therefore be chosen as the preferred
worker even though another genuinely polling FREE worker is available.

For a pull broker, assignment should normally be:

    first eligible live polling worker atomically claims oldest queued job

Do not let a ghost worker prevent a live worker from claiming work.

P1-D — POLLING HAS AN UNNECESSARY IDLE GAP

Server long-poll can wait ~20 seconds.

Widget then sleeps another ~25 seconds before issuing the next poll.

This creates unnecessary periods where no worker is waiting on the broker.

Run essentially continuous long-poll:
    response
    -> short 250-500 ms yield
    -> next long-poll

Do not busy-loop.

The browser never receives this path, which is good, but the Bridge should

Bind submission to:

    expected output directory
    basename
    size
    sha256
