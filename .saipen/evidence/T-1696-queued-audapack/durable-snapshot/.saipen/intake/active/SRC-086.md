======================================================================
PRODUCT VISION
======================================================================

AUDAPACK already knows or is learning:

- projects;
- provider launchers;
- multiple provider accounts;
- exact launcher/profile identity;
- running agent instances;
- local CLI invocation;
- browser audit dispatch;
- captured SAIHANDOFF files;
- current project handoff identity;
- model/provider routing;
- asynchronous Bridge work.

The next product layer is a resource-aware prepared execution scheduler.

The operator should be able to prepare work in advance and say, conceptually:

"Run this when Claude 1 resets."

"At 18:00, when Codex 2 is available, start this project with this handoff."

"Start Claude 1 and Claude 2 together so their 5-hour windows become aligned."

"At 09:00, intentionally open this accounts 5-hour usage window with one
minimal safe request."

"When the limit resets, launch the latest SAIHANDOFF for this project using
model X and effort Y."

AUDAPACK should then perform the work automatically, safely, observably, and
exactly once.

The operator must not need to:

- manually remember reset times;
- repeatedly check account availability;
- manually refresh limits every few minutes;
- manually select between several accounts;
- manually copy the latest SAIHANDOFF;
- manually launch the CLI at reset time;
- manually specify model and effort again;
- manually synchronize two account windows.

======================================================================
PRIMARY PRODUCT PRINCIPLES
======================================================================

1. ACCOUNT-AWARE

AUDAPACK should understand real provider accounts/profiles, not merely launcher
button labels.

2. LIMIT-AWARE

AUDAPACK should track all useful observable limit windows for each account.

Examples may include:

- 5-hour window;
- weekly window;
- daily window;
- reserve window;
- provider-specific quotas.

Do not hard-code a universal assumption that every provider has exactly one
5-hour limit.

3. LOW-PROBE

Routine limit observation must not waste model quota.

A normal limit refresh and a deliberate usage-window-prime are two completely
different operations.

Never accidentally consume quota merely to check whether quota exists.

4. PREPARED

The operator can prepare a future job once.

AUDAPACK owns the waiting.

5. EXACTLY ONCE

A trigger must never turn into two agents, two prompts, or two audits because
the UI restarted or two processes observed the same due time.

6. PERSISTENT

Prepared jobs and observed reset information survive AUDAPACK restarts.

7. FAIL-SAFE, NOT ARTIFICIALLY BLOCKING

Unknown limit data should be represented honestly.

Do not fabricate availability.

But a stale optional limit source must not brick unrelated launchers or
unrelated prepared jobs.

8. OBSERVABLE

The operator must always be able to see:

- which accounts exist;
- which limits are known;
- when they reset;
- how fresh the information is;
- what prepared jobs are armed;
- why a job is waiting;
- what will happen next.
