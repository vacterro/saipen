IMPLEMENTATION TARGET: AUDAPACK → FREE BRAVE AUDIT WORKER DISPATCHER

Нужно расширить текущий AUDAPACK так, чтобы из desktop GUI одной кнопкой можно было отправить выбранный проект на аудит в одно из уже открытых свободных окон Brave/ChatGPT, где установлен AUDAPACK Widget и подключён локальный AUDAPACK Bridge.

Это должен быть надёжный локальный orchestration layer, а не автоматизация через SendKeys/мышь/focus.

ОСНОВНАЯ ЦЕЛЬ

Пользователь держит максимум 6 Brave окон с ChatGPT + AUDAPACK Widget.

В AUDAPACK Project Room он выбирает проект и нажимает, например:

    SEND AUDIT

После этого AUDAPACK должен:

    project selected
        -> ensure/reuse fresh ZIP
        -> create dispatch job
        -> Bridge finds FREE browser worker
        -> free Widget atomically claims job
        -> Widget receives ZIP from local Bridge
        -> Widget attaches ZIP into ChatGPT composer
        -> Widget verifies attachment READY
        -> Widget starts canonical existing audit flow
        -> existing Auto3/SUPER10 engine continues unattended
        -> Bridge tracks worker/job/run status
        -> when audit is finished, worker becomes FREE again

Maximum usable browser workers: 6.

Do NOT create a seventh audit worker/window.

If all six are busy, queue the project in AUDAPACK and dispatch it automatically when one worker becomes free.

IMPORTANT ARCHITECTURAL RULE

Do NOT implement desktop -> browser control through:

    SendKeys
    clipboard paste
    mouse automation
    window focus tricks
    HWND keystroke injection
    screen coordinates
    Selenium
    Playwright
    Chrome DevTools remote-debugging dependency
    external websocket framework

Those are fragile and unnecessary.

Use the existing localhost AUDAPACK Bridge as the control plane.

The browser must PULL work from Bridge.

Desktop:
    producer

AUDAPACK Bridge:
    broker / scheduler / lease authority

AUDAPACK_WIDGET.user.js:
    browser worker / consumer

This is deliberately pull-based because the desktop Bridge cannot reliably "push HTTP" into a browser userscript, while every Widget can already call localhost Bridge through bridgeRequest()/GM_xmlhttpRequest.

Inspect and reuse the existing implementation rather than building parallel systems:

    audapack/bridge/server.py
        existing authenticated localhost HTTP API

    audapack/services/bridge_service.py
        desktop GUI Bridge facade

    audapack/services/packing_service.py

        attachment READY detection

    audapack/instances.py
        native window discovery already exists, but it must NOT become the transport for audit commands

The new dispatcher must integrate with these canonical paths.

DO NOT create a second audit-start implementation.

--------------------------------------------------
1. BROWSER WORKER REGISTRATION
--------------------------------------------------

Each ChatGPT tab containing an active AUDAPACK Widget becomes a potential browser worker.

Give each tab a stable session worker id derived from the existing tab identity, e.g. autoTabId.

Widget reports to Bridge:

    worker_id
    widget_version
    bridge_api_version
    site
    conversation_key
    conversation_id when available
    current URL/path
    current project name if any
    current profile
    current campaign run_id if any
    worker state
    last activity time
    whether ChatGPT is generating
    whether composer has a manual draft
    whether composer has attachments
    whether auditStartInFlight/actionInFlight is active

Suggested worker states:

    FREE
    RESERVED
    PREPARING
    UPLOADING
    STARTING
    AUDITING
    BLOCKED
    OFFLINE

Bridge worker registry is ephemeral.

A worker disappears automatically after heartbeat/long-poll TTL expires.

Do not persist stale browser workers forever.

Maximum ACTIVE workers accepted by the dispatcher is 6.

Additional tabs may exist in Brave, but dispatcher must not use more than six simultaneously.

--------------------------------------------------
2. DO NOT USE AGGRESSIVE 1-SECOND POLLING
--------------------------------------------------

There may be six browser workers.

Do not create six dumb high-frequency polling loops.

Preferred implementation:

    POST /v1/browser/poll

This request performs:

    heartbeat/update worker state
    optional atomic job claim
    optional long-poll wait

Use bounded long polling, approximately 15-25 seconds, with immediate return when a job becomes available.

On failure use bounded exponential backoff.

When page is closing:

    best-effort worker release/offline signal

When Bridge restarts:

    workers simply re-register.

This keeps CPU/network usage essentially negligible even with six Brave windows.

--------------------------------------------------
3. FREE WORKER DEFINITION
--------------------------------------------------

A worker is eligible for a new audit only if the Widget itself verifies that it is safe.

FREE must mean approximately:

    ChatGPT page is usable and authenticated
    no active generation
    no auditStartInFlight
    no actionInFlight
    no unresolved START transaction
    no current running audit
    no substantive manual composer draft
    no user-owned attachment that would be overwritten
    worker owns no other dispatch lease

Do not trust only the Brave window title.

Widget runtime state is authoritative for browser availability.

A completed previous audit can become FREE again.

For a completed/old conversation, dispatcher may reuse the same TAB by navigating it to New Chat through the existing canonical openNewChatFromWidget() flow.

Do not spawn another tab just because the previous conversation is complete.

Before navigating to New Chat, preserve all existing protections against losing:

    manual draft
    active generation
    attachment
    incomplete audit
    unsaved COMPLETE result

If those protections say navigation is unsafe, worker remains BLOCKED/BUSY.

--------------------------------------------------
4. DISPATCH JOB MODEL
--------------------------------------------------

Introduce a separate browser dispatch identity.

For example:

    dispatch_id

Do NOT use dispatch_id as CAMPAIGN_RUN_ID.

This distinction is critical.

dispatch_id:
    identifies desktop -> browser delivery attempt

campaign run_id:
    identifies the actual audit campaign

The existing canonical audit engine must remain the authority for creation of campaign run_id unless architecture is deliberately changed everywhere to one shared canonical owner.

Do NOT pre-generate one run_id in desktop and accidentally let Widget create another one.

We just fixed exactly this family of bug.

Job should contain server-side fields such as:

    dispatch_id
    project_id
    project_name
    archive filename
    archive absolute path internally
    archive size
    archive sha256 if practical
    requested profile
    created_at
    state
    assigned_worker_id
    lease_id
    lease_expires_at
    attempts
    campaign_run_id once actually established
    conversation_id once actually established
    error/result

Suggested lifecycle:

    QUEUED
    -> LEASED
    -> ARTIFACT_FETCHED
    -> ATTACHED
    -> START_PREPARED
    -> STARTED
    -> AUDITING
    -> COMPLETE

Failure/recovery states may include:

    RETRYABLE
    BLOCKED
    FAILED
    CANCELLED

Transitions must be validated.

--------------------------------------------------
5. ATOMIC WORKER CLAIM
--------------------------------------------------

Two free Brave tabs must NEVER receive the same project.

Job claim must be atomic on Bridge side.

Use a lock around:

    select queued job
    select/validate worker
    issue lease
    mark LEASED

Return a unique lease token/id.

Every subsequent state-changing request for that job must include:

    dispatch_id
    worker_id
    lease_id

Reject stale owners.

Lease expiry can return a job to QUEUED only while it is still safe to retry.

--------------------------------------------------
6. EXACTLY-ONCE START SAFETY
--------------------------------------------------

This is the most important reliability requirement.

A lost HTTP response must NEVER cause Audit Core to be submitted in a second browser window.

Before START_PREPARED:
    a dead lease may safely return job to QUEUED.

After START_PREPARED:
    DO NOT blindly reassign job to another worker.

Once the Widget has created the canonical START receipt / prepared the Core transaction, that worker owns recovery of that exact send.

Reuse the existing:

    beginStartAuditHandoff()
    machine receipt
    START prepared/clicking/sent phases
    Auto lease
    recoverArmedStartSend()

Integrate dispatch ownership with that machinery.

The dispatcher must know that:

    "HTTP ACK lost"

does not mean:

    "nothing happened"

If START may already have been prepared or clicked, preserve same-worker recovery or mark the dispatch as requiring reconciliation.

Never send a duplicate Core merely because Bridge did not receive an ACK.

--------------------------------------------------
7. PROJECT ZIP DELIVERY THROUGH BRIDGE
--------------------------------------------------

The current widget already knows how to create browser File objects and inject them through DataTransfer using setNativeFileList().

Reuse this capability.

Do NOT attempt to send a Windows filesystem path to ChatGPT.

Browser cannot attach:

    V:\\some\\archive.zip

directly.

Instead:

AUDAPACK:
    creates or identifies the real ZIP

Bridge:
    owns the server-side absolute path

Widget:
    downloads the ZIP bytes from authenticated localhost Bridge

Example concept:

    GET /v1/browser/jobs/<dispatch_id>/artifact

Requirements:

    X-Bridge-Token authentication
    loopback only
    active worker lease required
    job ownership checked
    stream file, do not JSON/base64 the ZIP
    Content-Length
    Content-Type application/zip
    Content-Disposition with safe filename
    reject missing/changed archive
    optional sha256 verification

Do NOT expose an endpoint accepting arbitrary filesystem paths from the browser.

The artifact path must originate from the trusted AUDAPACK packing result/job record.

After downloading:

    Blob/ArrayBuffer
        -> new File(...)
        -> setNativeFileList(uploadInput, [file])
        -> wait for ChatGPT attachment tile
        -> wait until attachment no longer reports busy
        -> verify exact filename

Do not duplicate the existing DOM attachment logic if reusable helpers already exist.

Create a generalized helper if necessary:

    attachChatGPTLocalArtifact(file)

and let prompt-file attachment and ZIP attachment share the safe lower-level injection path where appropriate.

--------------------------------------------------

--------------------------------------------------

Once the project ZIP is visibly READY in the ChatGPT composer, do NOT construct/send Audit Core manually.

Call the existing canonical:

    startAuditCoreFromReadyAttachment()

    composer state
    attachment state
    Auto lease
    project identity
    START handoff
    receipts
    send verification
    duplicate prevention

The dispatcher is only responsible for getting a verified project archive into a safe free worker and invoking the existing START pathway.

It must not become a second Auto3 implementation.

--------------------------------------------------
10. SIX-WINDOW SCHEDULER
--------------------------------------------------

Hard upper bound:

    6 active browser audit workers.

Do not automatically create window #7.

If:

    0 free
    4 busy
    2 offline

job stays QUEUED.

When one worker reports FREE:
    oldest eligible queued job should be dispatched automatically.

Use deterministic scheduling, for example FIFO jobs + least-recently-assigned free worker.

Avoid repeatedly feeding all work into worker #1 while other workers sit unused.

Track last_assigned_at.

Do not couple scheduling to monitor position or Brave title.

--------------------------------------------------
11. QUEUE DURABILITY
--------------------------------------------------

Browser worker registry can be ephemeral.

Dispatch jobs should survive AUDAPACK/Bridge restart.

Use small local persistent state under the existing AUDAPACK runtime/state directory.

Keep it simple:

    JSON state
    atomic temp write + replace
    lock around mutations

No database dependency is needed for six workers.

On Bridge startup reconcile:

    QUEUED -> remain QUEUED

    LEASED before START_PREPARED with expired worker
        -> QUEUED

    START_PREPARED / STARTED with missing worker
        -> RECONCILE/BLOCKED, never automatically duplicate

    COMPLETE
        -> retain briefly/history, do not redispatch

Bound history/queue size.

Do not create an unbounded state file.

13. SECURITY
--------------------------------------------------

All browser-dispatch endpoints:

    Bridge token auth
    strict JSON validation
    bounded request sizes
    server-owned archive paths
    project registry binding

--------------------------------------------------
15. API DESIGN
--------------------------------------------------

Exact endpoint naming is implementation-agent choice, but keep one coherent API namespace.

A reasonable shape is:

    POST /v1/browser/poll
        heartbeat + long poll + claim

    POST /v1/browser/jobs/<id>/state
        worker ACK / lifecycle transition

    GET /v1/browser/jobs/<id>/artifact
        leased ZIP stream

    POST /v1/browser/jobs
        desktop/internal creation if HTTP is used

    GET /v1/browser/status
        GUI scheduler status

Do not add endpoints merely because they look RESTful.

Prefer the smallest coherent contract.

Desktop code may call scheduler/service classes directly rather than HTTP when running in the same AUDAPACK process.

HTTP is primarily necessary between Bridge and browser Widget.

19. PERFORMANCE REQUIREMENT
--------------------------------------------------

Six idle workers must not materially load Brave or AUDAPACK.

No broad DOM polling loops.

Use current MutationObserver/event-driven audit machinery.

Browser dispatch should use long polling or similarly bounded event-like localhost traffic.

Do not add repeated full registry scans or filesystem scans to every heartbeat.

Worker heartbeat payload must stay small.

ZIP must be streamed/downloaded only after a job is successfully leased.

DONE WHEN
--------------------------------------------------

The feature is complete only when:

A project can be selected in AUDAPACK and sent with ONE click to a FREE existing Brave/ChatGPT/AUDAPACK Widget window.

Up to six browser workers are coordinated reliably.

Busy workers are never disturbed.

No seventh worker is used automatically.

Jobs wait when all workers are busy.

A newly free worker automatically accepts queued work.

The project ZIP is transferred through authenticated localhost Bridge and attached by the Widget.

The existing canonical startAuditCoreFromReadyAttachment() pathway performs the actual audit start.

dispatch_id never competes with campaign run_id.

No duplicate Audit Core can be caused by retries, dead workers, lost ACKs, or Bridge restart.

Current Bridge audit-save functionality remains intact.

All relevant Python and Widget regression tests pass.

Do not report COMPLETE based only on unit tests if the browser transport itself was not exercised.

Preserve the existing architecture and make the smallest robust extension.
