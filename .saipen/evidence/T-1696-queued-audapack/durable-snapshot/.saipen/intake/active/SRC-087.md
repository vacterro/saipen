MILESTONE A  DURABLE EXECUTION LEASE AND FENCING
======================================================================

Current claim uniqueness prevents two fresh execution rows for one event.

That is necessary but insufficient.

Problem:

A Bridge/process crash can leave an execution in:

CLAIMED
PREPARING
LAUNCHING
DELIVERING
VERIFYING
RUNNING

with no durable takeover semantics.

The new Bridge may then leave it stranded indefinitely.

Implement recovery-aware ownership.

----------------------------------------------------------------------
A1  MONOTONIC FENCE
----------------------------------------------------------------------

Extend execution ownership with equivalent semantics to:

claim_generation
lease_owner
lease_expires_at
heartbeat_at

Exact schema may follow repository conventions.

Every mutation of an active execution must prove:

execution_id
+
current claim_generation
+
owner

A stale worker must not update a receipt after takeover.

Do not rely solely on mutable owner_id text.

----------------------------------------------------------------------
A2  RECOVERY CLASSIFICATION
----------------------------------------------------------------------

Classify crash points.

SAFE_TO_RECLAIM:

- CLAIMED before provider process creation;
- PREPARING before irreversible provider action.

AMBIGUOUS_SIDE_EFFECT:

- LAUNCHING when process creation may already have occurred;
- DELIVERING when provider may already have received input.

OBSERVABLE_RUNNING:

- process_id is known and process is still attributable.

TERMINAL:

- DONE
- FAILED_TERMINAL
- MISSED
- CANCELLED

FAILED_RETRYABLE may only auto-retry when the prior attempt is proven pre-side-effect.

----------------------------------------------------------------------
A3  SAFE TAKEOVER
----------------------------------------------------------------------

After bounded lease expiry:

if execution is CLAIMED/PREPARING

and:

- no process_id;
- no delivery_hash indicating delivery;
- no other irreversible receipt;

a new worker may take ownership of the SAME execution attempt or a canonically related retry attempt.

Do not generate unrelated duplicate work.

----------------------------------------------------------------------
A4  PROCESS CREATED
----------------------------------------------------------------------

If process_id exists:

never automatically launch another provider process merely because lease expired.

Use:

- process existence;
- InstanceMonitor identity;
- project;
- launcher;
- account;
- execution metadata.

If process still exists:

adopt/observe.

If process is definitely gone:

determine whether delivery could have completed.

If uncertain:

mark something equivalent to:

RECOVERY_REQUIRED
FAILED_AMBIGUOUS

Operator or provider-specific proof decides further action.

----------------------------------------------------------------------
A5  RETRY MODEL
----------------------------------------------------------------------

Current ONE_SHOT claim behavior effectively prevents later attempts after any prior execution.

Implement explicit attempt semantics.

A retryable pre-side-effect failure may produce attempt N+1.

An ambiguous or successful side effect may not.

Do not weaken exactly-once semantics.
