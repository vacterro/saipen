SAITULS

MISSION
Repair and extend SAISPIN into a reliable Windows startup watchdog
that detects abandoned CPU-spinning processes, reports genuinely stalled
work, and automatically terminates only targets whose recovery eligibility
has been positively established.

Primary user requirements:
1. SAISPIN must actually work on the user's Windows machine.
2. Start automatically when the user signs into Windows.
3. Detect and safely clean up genuinely abandoned or stuck processes.
4. Never terminate tests, agents, builds, renders, or other jobs that
   are still doing legitimate work.
5. Give the operator clear evidence explaining every detection,
   protection, refusal, and termination.
6. Minimize background CPU, disk, and memory overhead.

KNOWN CURRENT BEHAVIOR

The existing SAISPIN implementation is an orphan CPU-spin watchdog.

It requires:
- Consecutive hot CPU samples.
- A minimum sustained time.
- Orphan process classification.
- Explicit auto-kill enablement.
- Successful never-kill and identity checks.
- Trusted persisted history.
- Durable pre-kill audit evidence.

Current default policy:
- 80% of one logical CPU core.
- 6 consecutive hot observations.
- 30 minutes minimum sustained heat.
- 3 seconds sampling.
- 5 minutes scheduled sweep interval.
- 30 minutes stale-history boundary.
- Dry-run unless auto-kill is armed.

These are not total-system CPU percentages.

Reported real UI state:
- Scheduled: NO
- Mode: DRY-RUN
- Test sweep: Test failed

Task Manager shows concurrent Node.js, Python, PowerShell, DWM,
OBS, browser, and other processes consuming substantial resources.

These observations do not prove any individual process is hung.
Do not use raw CPU usage as sufficient proof of a runaway.

PROJECT SAFETY CONTRACT

The existing standalone SAISPIN specification explicitly prohibits
automatic termination of non-orphan processes.

Preserve this invariant in the existing orphan-spin policy.

If additional recovery behavior is introduced for explicitly managed,
proven-owned processes, isolate it into a separately gated policy
with its own positive ownership and liveness evidence.

Do not silently weaken the legacy orphan safety contract.

PHASE 1 — REPRODUCE THE BROKEN TEST SWEEP

Start with the reported GUI failure.

In Scripts/saispin_settings.ps1, the BackgroundWorker DoWork handler
uses a PowerShell scriptblock to perform external process operations
on a background .NET thread.

Investigate PowerShell runspace availability and thread ownership.

Hypothesis:
The scriptblock may execute on a thread with no usable PowerShell
runspace, throwing before the watcher can complete.

Also inspect the error callback:

$resultLabel.Text = $event.Error.Exception.Message

RunWorkerCompletedEventArgs.Error is already an Exception.
The extra .Exception access can hide the actual error message.

This is a verified suspicious source boundary.
The underlying runtime exception remains unproven until reproduced.

B. Invoke the same command through the GUI.
C. Compare exit code, stdout, stderr, and exception.
D. Compare current-user identity, environment, and working directory.
E. Test missing Python, failed CIM enumeration, and invalid configuration.
F. Test normal completion after the GUI loses foreground focus.

Repair the BackgroundWorker implementation properly.

Use a supported PowerShell runspace mechanism or another proven
nonblocking process execution design.

Never access Windows Forms controls from a worker thread.

Avoid synchronous stdout/stderr pipe deadlocks.
Use bounded execution time and deterministic child cleanup.

Keep the UI responsive during sampling.

Make all errors observable.

SPECIFIC SOURCE DEFECT

Invoke-ProvenKill() currently uses a fixed 80.0 CPU threshold during
final re-sampling.

The decision engine instead uses validated configurable thresholds.

This is a policy-consistency defect.

Make final validation use the actual effective policy of the same
process rule and decision.

Do not make the final recheck weaker than the decision gate.

Test both globally configured thresholds and stricter per-process rules.

Retain identity and parent revalidation immediately before termination.

PHASE 6 — DISTINGUISH HANGS FROM LEGITIMATE WORK

Do not treat these as equivalent:

CPU_SPIN
GUI_NOT_RESPONDING
NO_OUTPUT
WAITING_FOR_IO
WAITING_FOR_NETWORK
COMPILING
TEST_RUNNING
RENDERING
DEAD_CHILD_OWNER
ABANDONED_WORKER

High CPU can indicate useful work.
Low CPU can indicate a legitimate wait.
No console output can be normal for a long-running test.

Design a bounded multi-signal detector.

Use trustworthy evidence where available:

- Process identity and creation time.
- Parent chain and verified parent identity.
- Owner identity.
- Actual CPU history.
- Explicit task ownership.
- Validated progress or heartbeat signals.
- Known managed job state.
- Confirmed cancellation or shutdown.
- GUI responsiveness for genuine GUI processes.
- Process exit and restart behavior.

Windows GUI hung detection may use a narrowly scoped documented
mechanism such as IsHungAppWindow.

However, a GUI hung flag alone must not authorize termination.

For headless Python/Node jobs, no reliable generic Windows API can
prove useful progress.

If progress cannot be established, classify as UNKNOWN or SUSPECTED,
not automatically disposable.

Do not invent artificial certainty from heuristic signals.

PHASE 7 — PROTECT ACTIVE TESTS AND AGENTS

This is a mandatory safety gate.

Protect legitimate work including:

- pytest and unittest.
- Node test runners.
- Build and compiler processes.
- Playwright/browser test fixtures.
- Long-running Python workers.
- Active agent CLI subprocesses.
- OpenCode/Claude/Antigravity task processes.
- Media encoding and rendering jobs.
- User foreground applications.
- Ongoing managed automation workflows.

Protection must not rely only on parent PID being alive.

A parent can exit while a legitimately useful child continues working.

Implement explicit classification:

PROTECTED_ACTIVE
PROTECTED_SYSTEM
PROTECTED_USER
OBSERVE_ONLY
SUSPECTED_STALL
PROVEN_RECOVERABLE
UNKNOWN

Rules:

1. Active or unknown work is never killed automatically.
2. A missing parent is evidence, not proof of safe disposability.
3. Name-only heuristics cannot positively establish ownership.
4. Generic python.exe or node.exe identity is insufficient.
5. A test with no recent console output may still be healthy.
6. Any unreliable process or ownership data refuses termination.
7. Recovered or resumed progress resets stall evidence.
8. The watchdog must not terminate itself.
9. Do not kill an entire process tree without explicit validated
   ownership of every affected member.
10. No aggressive global process-name kill policies.

Where possible, integrate optional protection leases or explicit
managed-job ownership records through existing project interfaces.

Do not require a new global service or rewrite other applications
merely to gain these signals.

For uninstrumented jobs, remain conservative.

No action may move directly from high CPU to process termination.

The final kill gate must verify:

- Exact PID and process creation identity.
- Correct owner.
- Current eligibility.
- Current effective CPU or stall evidence.
- Current protected-work state.
- Current parent/ownership state.
- No active lease or verified heartbeat.
- Explicit auto-kill authorization.
- Durable state and audit availability.
- No forbidden process classification.

Harden system-process protection.

The current basic hardcoded never-kill list is not sufficient as
the sole guard for Windows desktop, service, and security processes.

Do not accidentally terminate DWM, Explorer, Windows services,
security components, critical desktop hosts, or unrelated applications.

Use positive eligibility rather than relying only on an expanding
denylist.

Keep the actual kill operation as narrowly targeted as possible.

No blind Stop-Process by process name.
No blanket /F /T tree termination.
No killing all Python or Node workers.

Do not invent a safe process identity from command-line substrings.
