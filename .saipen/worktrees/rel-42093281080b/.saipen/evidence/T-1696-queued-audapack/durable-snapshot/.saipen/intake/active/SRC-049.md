## Request

AUDAPACK

NEXT TARGET — MANUAL CHAT ARCHIVE PICKER / ONE-CLICK PROJECT ZIP ATTACH WITH IDEMPOTENT DUPLICATE PROTECTION

Build on the existing T-180/T-182 AUTO ZIP transport.

Do NOT create a second archive transport.

The current widget already has the correct low-level primitives:

- listRegisteredProjects()
- ensureProjectArchive(projectId)
- fetchProjectArchive(projectId)
- sha256Hex(bytes)
- setNativeFileList()
- waitForDomCondition()
- canonicalArchiveProofMatches()
- rememberCanonicalArchiveProof()
- composerArchivesForProject()
- removeComposerAttachmentTile()

Current AUTO ZIP flow already performs:

registered project
-> canonical archive ensure
-> Bridge download
-> size/SHA verification
-> File construction
-> ChatGPT native attachment injection
-> readiness proof
-> old same-project archive replacement

Reuse this implementation.

The new manual flow must additionally be aggressively idempotent:

if the exact current canonical project archive is already attached and proven,
do NOTHING.

No repack.
No redownload.
No File reconstruction.
No duplicate attachment.
No replacement dance.
No DOM churn.

Return an explicit duplicate/no-op result such as:

ALREADY_ATTACHED
DUPLICATE_NOOP

Conceptually:

duplicate detected
-> no need to upload again
-> READY

USER GOAL
==================================================

The user must be able to open ANY normal ChatGPT conversation and attach the latest AUDAPACK project archive through the Widget.

No Windows drag-and-drop.

No manually finding ZIP files.

No requirement to start an audit.

No requirement that an archive is already attached.

No requirement that Auto Audit is enabled.

No unnecessary repeated archive work when the correct archive is already present.

Desired interaction:

1. Open any ChatGPT conversation.
2. Press a compact Widget ZIP/project control.
3. If this conversation already has a bound AUDAPACK project:
   -> determine whether the current canonical archive is already proven attached;
   -> if yes: return READY / ALREADY_ATTACHED immediately;
   -> if no: ensure latest canonical archive;
   -> download only when required;
   -> attach only when required.

4. If no project is bound:
   -> show compact project picker;
   -> user chooses one registered AUDAPACK project;
   -> bind this conversation to that project;
   -> ensure/download/attach immediately if needed.

After the first selection, future presses are one-click.

==================================================
TARGET D — IDEMPOTENT DUPLICATE PROTECTION
==================================================

This is a core requirement, not an optimization.

Repeated clicks on ZIP with unchanged project state must converge to a no-op.

The system must distinguish:

1. exact canonical archive already attached;
2. older archive for the same project attached;
3. same filename but unproven bytes attached;
4. canonical archive downloaded previously but not currently attached;
5. project changed since previous canonical archive;
6. concurrent duplicate requests.

The strongest available identity should be used.

Preferred canonical identity:

project_id
+ canonical archive SHA-256
+ canonical archive byte size
+ canonical archive generation/version if available.

Filename is metadata only.

Filename alone is NEVER sufficient proof of equality.

==================================================
TARGET E — FAST NO-OP PATH
==================================================

Before downloading archive bytes, inspect current composer attachment state and remembered canonical proofs.

If the current composer contains an attachment for the selected project whose exact-tile proof matches the current canonical archive identity:

return immediately:

ALREADY_ATTACHED

Do not:

- repack;
- GET archive bytes;
- construct another File;
- call setNativeFileList();
- remove/re-add the tile;
- disturb composer text;
- update campaign state.

This must be the cheapest successful path.

If Bridge can cheaply report the current canonical archive identity without repacking, use that metadata endpoint/state.

Do not download megabytes merely to discover that the same SHA is already attached.

==================================================
TARGET F — PACK / ENSURE IDEMPOTENCY
==================================================

ensureProjectArchive(projectId) must itself behave idempotently.

If source state has not changed and a valid canonical archive already exists:

return:

reused=true

with canonical metadata such as:

- project_id;
- archive filename;
- size;
- SHA-256;
- source/archive generation;
- packed=false or equivalent.

Do not create a new timestamped ZIP containing identical project content just because the button was clicked again.

Repeated unchanged requests must not create archive churn on disk.

Desired behavior:

PACKED_NEW

subsequent unchanged request:
REUSED_EXISTING

If current archive freshness cannot be proven cheaply:

perform the normal canonical ensure.

Never guess freshness from filename timestamps alone.

TARGET G — DOWNLOAD DEDUPLICATION
==================================================

==================================================
TARGET H — ATTACHMENT DEDUPLICATION
==================================================

Before native attachment injection, check again.

Race-safe invariant:

If another concurrent request already attached the same canonical SHA while this request was waiting:

the later request becomes ALREADY_ATTACHED and performs no second injection.

The composer must never end with two identical canonical archives for the same project SHA because the user double-clicked or two flows raced.

==================================================
TARGET I — REPLACEMENT SEMANTICS
==================================================

For a selected project:

1. Resolve canonical archive metadata.
2. Check exact proven composer attachment.
3. If exact canonical SHA is already attached:
   -> ALREADY_ATTACHED;
   -> stop.

4. If not:
   -> ensure canonical archive;
   -> obtain canonical metadata;
   -> check composer again in case state changed while ensure ran.

5. Only if still absent:
   -> GET canonical archive bytes;
   -> verify byte length;
   -> verify SHA-256;
   -> construct File;
   -> inject through the existing native ChatGPT attachment path;
   -> wait until the NEW attachment tile is registered and no longer busy;
   -> record exact canonical proof.

6. Only AFTER the new canonical tile is proven ready:
   -> remove older archive attachments belonging to the SAME project.

Never remove the old same-project archive first.

Failure at any stage:

- previous attachment survives;
- composer text survives;
- unrelated attachments survive;
- no Send;
- no campaign transition;
- no false READY state.
