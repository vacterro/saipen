P0-1 — STOP THE 5-SECOND CMD POPUP
=====================================================================

VERIFIED ROOT CAUSE

audapack/ui_qt/main_window.py currently creates:

    dispatch_status_timer.setInterval(5000)

Every tick calls:

    _refresh_dispatch_status_async()

which calls:

    self._bridge.browser_jobs()
    self._bridge.status()

BridgeService.status() currently calls:

    check_bridge_health(...)
    get_autostart_status()
    is_bridge_healthy(...)
    browser_status()

get_autostart_status() calls:

    query_task()

which executes:

    schtasks /query ...

Therefore a GUI live-status timer is spawning a Windows command-line process
every five seconds.

THIS MUST STOP.

FIX ARCHITECTURE

Split Bridge status into TWO classes of operation.

A. CHEAP RUNTIME STATUS

Used by live/periodic UI:

    health endpoint
    browser worker status
    browser jobs

It MUST:
    perform HTTP only
    spawn zero processes
    invoke zero schtasks calls
    invoke zero PowerShell calls
    invoke zero cmd calls.

Example API:

    BridgeService.runtime_status()

or:

    BridgeService.status(include_autostart=False)

B. OS/AUTOSTART STATUS

Used only:
    on application startup once if needed
    when Settings -> Bridge is opened
    after user changes autostart
    after explicit Repair/Refresh

This may query Task Scheduler.

DO NOT query Scheduled Tasks from the 5-second live-status timer.

Also harden EVERY subprocess invocation in:

    audapack/components/autostart.py

On Windows use hidden process flags consistently:

    CREATE_NO_WINDOW

and, where useful:

    STARTUPINFO
    STARTF_USESHOWWINDOW
    SW_HIDE

This applies to:

    schtasks /query
    schtasks /create
    schtasks /delete
    schtasks /run
    schtasks /end

Even explicit settings operations must never flash a console.

ACCEPTANCE

Run AUDAPACK for at least 60 seconds.

Expected:

    zero CMD windows
    zero PowerShell windows
    Project Room status continues updating
    Bridge status continues updating.

Add regression coverage proving the periodic runtime-status path does not call

P0-3 — FIX THE ACTUAL ATTACHMENT REGISTRATION RACE
=====================================================================

VERIFIED ROOT DEFECT

Browser worker does:

    setNativeFileList(input, [artifact.file])

then immediately:

    waitForReadyAttachment(40000)

But waitForReadyAttachment() currently contains an early condition equivalent to:

    allTiles = ...
    if (allTiles.length === 0)
        return null

This is unsafe immediately after file injection.

ChatGPT attachment registration is asynchronous.

A successful input.files assignment/change event does NOT guarantee the
attachment tile exists on the first DOM probe.

Therefore a valid attach can be rejected milliseconds after injection as:

    attachment-not-ready

The dispatch then goes RETRYABLE and another worker may try again.

REMOVE THIS RACE.

IMPLEMENT A DEDICATED EXACT ATTACH WAIT

Do not use the generic manual START helper unchanged for dispatch delivery.

Introduce something like:

    waitForExactProjectAttachment({
        filename,
        expectedSize,
        timeoutMs
    })

Required behavior:

1. Start timer.
2. Re-resolve the LIVE composer root on every probe.
3. Allow an initial tile-appearance grace period.
4. Do NOT return failure merely because no tile exists yet.
5. Wait until timeout unless a definite fatal condition occurs.
6. When a tile appears, require exact expected filename.
7. If metadata is available, also require expected size.
8. Reject a different unexpected project attachment.
9. Return structured result:

       {
           ok,
           filename,
           reason,
           observedNames
       }

Suggested timing:

    probe every 100-250 ms
    timeout 40 s

No busy loop.

THE IMPORTANT INVARIANT:

    setNativeFileList == accepted by DOM

is NOT equivalent to:

    ChatGPT attachment == ready.

Only transition:

    ARTIFACT_FETCHED -> ATTACHED

after exact ChatGPT attachment readiness is proven.

P0-6 — PREVENT ATTACH RETRY THRASHING
=====================================================================

Current RETRYABLE behavior can rapidly expose the same job to another worker.

For attachment registration failures this can turn into worker pinball:

    worker A injects
    -> thinks attach failed
    -> RETRYABLE
    -> worker B claims
    -> injects
    -> RETRYABLE
    -> ...

Add bounded retry semantics.

Extend DispatchJob with lightweight retry information if required:

    retry_count
    next_retry_at
    last_error_code

Rules:

TRANSIENT:
    attachment tile not visible yet
    temporary composer replacement
    temporary upload registering

should first retry in the SAME worker/browser context.

Use bounded local retry/backoff before releasing the lease.

Example:

    attempt 1
    wait
    retry probe
    attempt 2
    wait
    final retry

Do NOT re-inject the ZIP every probe.

Only re-inject when the previous injected attachment is proven absent/failed.

When releasing to RETRYABLE:

    clean up only the worker-owned partial attachment if safe
    set a short backoff
    avoid instant cross-worker hammering.

After a reasonable pre-start retry bound:

    transition BLOCKED or FAILED with exact diagnostics.

Never infinite-loop.
