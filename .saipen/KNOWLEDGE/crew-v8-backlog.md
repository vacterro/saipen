# SAIPEN v8 Crew Design Backlog (gated)

This is the detailed gated Crew design backlog, moved here from the active
board's `## BLOCKED` section by T-464 (board prune). The tickets are unchanged;
only their home changed. They are all held by `HELD FOR SEQUENTIAL STABILITY`
and remain unreachable until the gate ticket T-442 reaches `## DONE`. T-442
stays on the active board and cites this file.

Everything in this file is a design ticket, not an implementation. No Crew
implementation may begin before T-442 unblocks and each ticket's own `verify:`
is met.

## T-443 [P0] Define a markdown-first SAIPEN v8 Crew contract before implementing concurrency. Preserve ordinary files, Git history, cold-agent readability and operation without SAIPENVIEW, a database, a background service or a proprietary runtime. Specify which records are canonical, which may merge, which decisions must serialize, how agents identify themselves, how stale writers are rejected, how recovery works and how v7 sequential mode remains available. Treat every proposed mechanism as a hypothesis until it kills a reproduced failure class. | needs: T-442 | verify: every new mechanism maps to a reproduced failure; every v7 invariant is preserved, strengthened or explicitly retired with evidence; no rule depends on a GUI to be understood or executed | blocker: HELD FOR SEQUENTIAL STABILITY

## T-444 [P1] Add a minimal concurrent work layer without replacing the current canonical `STATE.md`, `BOARD.md` and `LOG.md`. Agents work in isolated Git worktrees and produce durable proposals carrying proposal ID, agent, ticket, base commit, base state hash, intended logical resources, changed files, evidence and verification results. One existing Core still integrates accepted proposals sequentially. This stage must prove that useful work can run in parallel before canonical ownership becomes distributed. | needs: T-443 | verify: two agents complete independent tickets concurrently in separate worktrees; a stale proposal is refused rather than silently rebased; accepted proposals integrate one at a time; the ordinary v7 validator remains authoritative | blocker: HELD FOR SEQUENTIAL STABILITY

## T-445 [P1] Define atomic ticket and logical-resource claims in file-backed state. A claim names ticket, agent, base revision, lease epoch and logical resources such as an RFC rule, Markdown section, Python function, schema key or release operation; file paths alone are insufficient. Expanding scope requires an atomic claim update. A conflicting agent waits, chooses different work or emits a proposal without editing the claimed resource. A superseded epoch permanently loses write authority. | needs: T-444 | verify: simultaneous claims produce exactly one owner; independent claims both succeed; scope expansion conflicts fail before editing; a stale or resurrected agent cannot checkpoint, integrate or ship under an old epoch | blocker: HELD FOR SEQUENTIAL STABILITY

## T-446 [P1] Define markdown-visible waiting, dependency and deadlock behavior for concurrent agents. Every wait names the blocked ticket, required resource or dependency and current owner. Build a deterministic wait-for graph and victim rule so circular waits cannot persist. Waiting agents may perform compatible read-only work but may not silently widen their scope or edit another owner's resources. | needs: T-445 | verify: a reproduced two-agent resource cycle is detected and broken deterministically; the losing claim is preserved as a proposal or returned to the queue; no hidden overlapping edit occurs while either agent waits | blocker: HELD FOR SEQUENTIAL STABILITY

## T-447 [P1] Give simultaneous `cc`, `ee`, `qq` and `ccc` calls one durable intent model rather than treating them as unrelated text messages. Commands from one user action share an intent ID and explicit dependencies. Multiple `cc` calls claim compatible independent work. `ee` and `qq` bind their output to an exact source commit. `ccc` waits for its required Core, translation and wiki work instead of running merely because it was received. Repeated delivery of the same intent must be idempotent. | needs: T-444, T-445 | verify: one grouped command set produces a deterministic dependency graph; two compatible Core tickets run concurrently; stale translation/wiki packages are refused; duplicate command delivery creates no duplicate ticket, package or release request | blocker: HELD FOR SEQUENTIAL STABILITY

## T-448 [P1] Add a local file-first Crew monitor for progress and safe takeover of non-SHIP work. Runtime-only heartbeats, process observations and leases may live outside Git, but every recoverable checkpoint remains in normal SAIPEN files and commits. Distinguish heartbeat from actual progress and distinguish WORKING, BUSY, SUSPECT, STALLED, LIMITED, LOST and DONE without inventing a cause an adapter cannot observe. On takeover, freeze the abandoned worktree, preserve its diff, increment the epoch and continue from the last verified checkpoint or a reviewed proposal. No GUI dependency. | needs: T-445, T-446 | verify: a stalled agent is replaced without losing verified work; a known long-running process is not stolen; a resumed stale agent is denied writes; machine sleep does not trigger immediate false takeover; unknown failure is never falsely labelled as a usage limit | blocker: HELD FOR SEQUENTIAL STABILITY

## T-449 [P0] Make concurrent `ccc` safe through exactly one release captain, one independent reviewer and optional reserves. Role acquisition is atomic and epoch-bound. Only the current captain may integrate, version, tag, push or update release state. Every external side effect carries a stable release ID and is checked against the repository and remote before retry, because the previous captain may have succeeded before disappearing. SHIP takeover uses a stricter recovery path than BUILD takeover. | needs: T-447, T-448 | verify: two simultaneous `ccc` calls elect exactly one captain; another agent becomes reviewer or reserve; loss before push transfers safely; loss after push is detected remotely and does not duplicate commit, tag, wiki push or release; the stale captain cannot resume shipping | blocker: HELD FOR SEQUENTIAL STABILITY

## T-450 [P1] Decide whether canonical `STATE.md`, `BOARD.md` and `LOG.md` should remain directly authored files or become deterministic views over accepted proposals, ticket records and append-only events. Do not introduce a reducer merely because distributed systems traditionally enjoy having one. Implement generated views only if the earlier Crew stages reproduce merge failures that cannot be solved while preserving the current files. Migration must remain reversible and sequential operation must remain possible without the monitor. | needs: T-444, T-445, T-448, T-449 | verify: the decision cites real Crew runs; if a reducer is accepted, state rebuilds byte-stably, interrupted reduction cannot leave partial truth and rollback to the authored-file model is exercised; otherwise the ticket closes with evidence that authored Markdown remains sufficient | blocker: HELD FOR SEQUENTIAL STABILITY

## T-451 [P0] GOAL FLAG: SAIPEN v8 Crew Mode is achieved only after the markdown-first system survives a defined real-world soak period without SAIPENVIEW. Run it on real project work long enough to include concurrent Core tasks, translation/wiki preparation, repeated releases, agent limits, process loss, stale proposals, resource waits, application or terminal restarts and at least one automatic takeover. Record every ownership transition, epoch, proposal, checkpoint and external side effect in inspectable files. Do not call the protocol v8 merely because one demonstration succeeds. | needs: T-443, T-444, T-445, T-446, T-447, T-448, T-449, T-450 | verify: before the soak begins, record a fixed minimum duration and workload target that cannot be reduced after failures; the completed run shows no lost work, duplicated release, split brain, unresolved deadlock or unreconstructable state; killing every active agent still leaves one correct next action recoverable from the repository alone | blocker: HELD FOR SEQUENTIAL STABILITY
