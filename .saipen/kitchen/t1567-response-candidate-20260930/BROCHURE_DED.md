# SAIPEN

## Агент забыл. Проект помнит.

**SAIPEN — файловый протокол продолжения работы для ИИ-агентов.**

Он хранит память проекта не в чате, не в мутной «долговременной памяти» сервиса и не в голове конкретной модели, а прямо рядом с кодом, в обычных Markdown-файлах.

Сегодня работает Claude.
Завтра GPT.
Послезавтра Gemini, Qwen или ещё какой-нибудь электронный шаман.

Модель меняется. Контекст исчезает. Проект продолжает работу.

**Agent dies. Project remembers.**
**Agent kaob. Projekt mäletab.**
**エージェントは消える。プロジェクトは覚える。**
*[Ējento wa kieru. Purojekuto wa oboeru. Агент исчезает. Проект помнит.]*

---

## Проблема

Обычный coding agent живёт как золотая рыбка с доступом к терминалу.

Он двадцать минут изучает проект, понимает архитектуру, находит ошибку, начинает исправлять её, упирается в лимит или закрывается.

Приходит новый агент:

> Что мы делаем?
> Какие файлы важны?
> Что уже проверено?
> Что нельзя трогать?
> Продолжать?

И человек снова пересказывает историю проекта. Потом ещё раз. Потом пишет огромный `CLAUDE.md`. Потом файл превращается в священную помойку из старых решений, случайных запретов и фраз, которые модель когда-то неправильно поняла.

SAIPEN говорит:

> Хватит хранить проект в разговоре.
> Положи состояние рядом с проектом.
> Новый агент прочитает и продолжит.

# Что умеет SAIPEN

## 1. Продолжать работу без истории чата

Пользователь пишет:

```text
saipen continue
```

или коротко:

```text
cc
```

Холодный агент читает:

```text
STATE.md
BOARD.md
хвост LOG.md
human_note
```

После этого он выполняет записанный `next_action`.

Не проводит интервью.
Не просит повторить архитектуру.
Не сочиняет новый план поверх старого.
Не делает вид, что «ознакомился с контекстом», прочитав первые двадцать строк.

Он продолжает работу с конкретного места.

---

## 2. Хранить память проекта в простых файлах

SAIPEN разделяет память по назначению.

### `STATE.md`

Отвечает на вопрос:

> Что делать прямо сейчас?

Там находятся текущая фаза, активный тикет, режим работы, точное следующее действие и важные ограничения.

### `BOARD.md`

Отвечает:

> Какая работа существует?

Задачи разделены на:

```text
DOING
TODO
BLOCKED
DONE
```

У каждой задачи есть приоритет, зависимости, условия проверки и причина блокировки.

### `LOG.md`

Отвечает:

> Что реально произошло и почему мы пришли сюда?

Не «мы собираемся проверить».
Не «вероятно, исправлено».
А конкретное событие, команда, результат и связь с предыдущими решениями.

### `KNOWLEDGE/`

Отвечает:

> Что является долговечной правдой проекта?

Архитектурные решения, ограничения, соглашения и ADR не тонут в километрах временного лога.

### `kitchen/`

Рабочий верстак.

Черновики, промежуточные материалы, подготовленные пакеты и незаконченная работа остаются там, чтобы смерть сессии не превращала полчаса труда в пепел и философию.

---

## 3. Давать агенту одно точное следующее действие

Сердце SAIPEN — поле:

```yaml
next_action:
```

Агент не должен каждую сессию заново решать, что ему делать.

Проект уже знает следующий шаг:

```text
PHASE SCOUT T-399
RUN validate.py
VERIFY T-501
WAIT: destructive-op
SHIP release
```

Один state.
Одна команда.
Одна реальность.

Чем меньше агент импровизирует в управлении процессом, тем больше мозгов остаётся на саму задачу. Редкий случай, когда бюрократия не мешает работе, а не даёт нейронке убежать в лес с отвёрткой.

---

## 4. Вести работу через строгую машину состояний

Работа движется по фазам:

```text
INIT
→ PLAN
→ SCOUT
→ BUILD
→ VERIFY
→ REVIEW
→ SHIP
→ DONE
```

Также существуют специальные фазы:

```text
BLOCKED
HUNT
MARKHUNT
ADD
CLEAN
TRANSLATE
PREPARE
VALIDATE
```

Каждая фаза знает:

* что агент обязан прочитать;
* что ему разрешено менять;
* что считается завершением;
* куда переходить дальше;
* когда необходимо остановиться;
* какие доказательства оставить.

Агент не может объявить задачу готовой сразу после первого зелёного теста. Сначала BUILD, потом VERIFY, потом REVIEW, потом SHIP.

Потому что «запустилось у меня один раз» — не инженерный стандарт. Это народная примета.

---

## 5. Работать с разными моделями и инструментами

SAIPEN не принадлежит одной компании.

Он рассчитан на работу с:

* Claude Code;
* OpenAI Codex;
* Gemini;
* OpenCode;
* Aider;
* Antigravity;
* DeepSeek;
* Qwen;
* другими агентами, способными читать файлы и выполнять команды.

Для платформ существуют адаптеры и инъекторы, но основа остаётся одинаковой:

```text
обычные файлы
обычный Git
обычный Markdown
```

Никакой proprietary memory.
Никакой обязательной базы данных.
Никакого вечного фонового демона, который завтра обновится и решит, что твой проект теперь надо хранить в облачном горшке.

---

## 6. Самостоятельно выполнять длинную цель

Команда:

```text
saipen goal <objective>
```

включает Goal Mode.

SAIPEN:

1. фиксирует цель;
2. строит или перестраивает очередь;
3. выбирает следующий рабочий тикет;
4. выполняет его;
5. проверяет;
6. делает review;
7. продолжает со следующим;
8. не спрашивает после каждого шага: «Продолжать?»

Существуют safety limits по волнам и количеству тикетов. Автономность не означает бесконечное блуждание по репозиторию под луной.

Goal Mode работает до одного из честных исходов:

```text
цель достигнута;
работа заблокирована;
сработал safety valve;
исчерпан доступный объём работы.
```

---

## 7. Сам находить следующую полезную работу

Когда обычный backlog закончился, Maintenance-слой может перейти в цикл:

```text
HUNT
→ ADD
→ HUNT
```

### HUNT

Ищет:

* реальные дефекты;
* противоречия;
* сломанные проверки;
* мёртвый код;
* архитектурный drift;
* незащищённые обязательные правила;
* расхождения между документацией и поведением.

### ADD

Когда явных дефектов больше нет, предлагает следующую естественную функцию, продолжающую существующую архитектуру.

Не устраивает творческий фестиваль.

SAIPEN развивается эволюционно:

```text
существующий паттерн
→ очевидный пробел
→ минимальное расширение
→ проверка
```

А не так:

```text
агенту стало скучно
→ переписал половину проекта на Rust
→ назвал это modern architecture
```

---

## 8. Отличать аудит от ремонта

SAIPEN разделяет несколько разных действий, которые модели любят сваливать в один котёл.

### `markhunt`

Проводит широкий аудит и записывает находки.

Ничего не исправляет.

Это важно: сначала установить факт, потом менять проект.

### `hunt`

Разбирает подтверждённые находки и превращает их в нормальные задачи.

### `validate`

Проверяет структурную целостность самого SAIPEN-состояния и исправляет разрешённые повреждения.

### `test`

Запускает объявленные тесты и докладывает PASS или FAIL.

Не чинит тест тайком во время проверки.

### `clean`

Удаляет мусор, чистит доску и приводит структуру в порядок, но обязан проверять ссылки и зависимости перед перемещением или удалением файлов.

Потому что файл может выглядеть сиротой, пока его не вызывает программа в три часа ночи.

---

## 9. Требовать доказательства вместо красивого отчёта

SAIPEN построен против типичных привычек LLM:

* заявить, что файл прочитан, хотя он не прочитан;
* сказать, что тесты прошли, не запуская их;
* придумать правдоподобный путь;
* остановиться после первого зелёного результата;
* пересказать задачу вместо выполнения;
* принять последнюю реплику пользователя за новую истину проекта;
* превратить временное предположение в постоянное правило.

Поэтому работа оставляет след:

```text
изменение файла;
событие LOG;
изменение BOARD;
изменение STATE;
команда и её результат;
verification evidence.
```

Если агент ничего не сделал, он должен сказать именно это, а не сочинять отчёт о великой внутренней подготовке.

В SAIPEN фраза «готово» сама по себе весит примерно как чек из магазина без названия товара.

---

## 10. Проверять сам протокол

SAIPEN имеет собственный conformance layer.

Он проверяет:

* корректность состояния;
* допустимые переходы фаз;
* форму тикетов;
* зависимости;
* порядок событий;
* ссылки между документами;
* соответствие схемам;
* покрытие правил проверками;
* работу на PowerShell и shell;
* сценарии повреждения и восстановления;
* мутационные red controls.

Проверка должна уметь стать красной, когда правило сломано.

Если тест всегда зелёный, это не тест. Это комнатное растение.

---

## 11. Переживать обрывы и смену агента

SAIPEN использует checkpoints.

Перед опасным переходом агент сохраняет:

* текущую фазу;
* активный тикет;
* выполненную часть;
* результаты проверки;
* следующий шаг;
* состояние рабочей директории.

Если агент погиб, завис, упёрся в лимит или был закрыт, следующий не начинает археологические раскопки в чате.

Он читает checkpoint и продолжает.

**継続 — keizoku — продолжение.**

Не героическое восстановление памяти. Обычная штатная операция.

---

## 12. Не уничтожать чужую незавершённую работу

Грязный Git tree для SAIPEN — нормальное состояние проекта.

Агент обязан определить:

* какие изменения принадлежат его тикету;
* какие оставил пользователь;
* какие принадлежат другой незавершённой работе;
* что можно включить в текущий release;
* что нельзя трогать.

SAIPEN запрещает:

* неожиданные `reset`;
* откат чужих файлов;
* стирание незакоммиченной работы;
* массовую перезапись без проверки;
* притворное «очищение» проекта через удаление непонятного.

Принцип простой:

> Не знаешь, чьё это — лапами не трогай.

---

## 13. Останавливаться честно

Когда работа действительно не может продолжаться, SAIPEN использует явный `WAIT:` или переводит тикет в `BLOCKED`.

Причина должна быть конкретной:

```text
нужна ручная проверка;
требуется разрешение на разрушительную операцию;
не хватает capability;
неизвестно обязательное решение;
нужен первый publish;
существует внешний blocker;
сработал safety valve.
```

Агент не должен угадывать.

Но и блокироваться из-за собственной лени ему тоже нельзя.

Недостаток информации — stop.
Нежелание посмотреть файл — не stop.

---

## 14. Показывать реальный статус проекта

Команда:

```text
saipen status
```

работает только на чтение.

Она показывает:

* текущую фазу;
* активную задачу;
* следующую работу;
* что ждёт пользователя;
* какие результаты заявлены, но ещё не доказаны;
* когда последний раз проходила conformance-проверка;
* насколько устарело текущее состояние;
* какие задачи заблокированы.

SAIPEN не объявляет собственный проект «здоровым» или «production ready».

Он показывает факты. Вывод делает человек.

Агент, самостоятельно выдавший себе медаль, всё равно остаётся агентом, самостоятельно выдавшим себе медаль.

---

## 15. Передавать работу между специализированными фабриками

SAIPEN поддерживает изолированные producer-процессы.

Они работают отдельно от основного дерева и отдают результат через `OUTBOX.md`.

Примеры:

### `saihunt`

Ищет дефекты и подозрительные места.

Сенсор. Не ремонтник.

### `saitest`

Превращает подозрение в воспроизводимый факт или убивает ложную гипотезу.

Он создаёт adversarial scenarios:

* неправильный ввод;
* граничные значения;
* нарушение порядка;
* повторные вызовы;
* повреждённое состояние;
* resource pressure;
* hostile environment.

### `saipython`

Берёт небольшие Python-дефекты, исправляет копию в изолированном рабочем пространстве, проверяет и передаёт готовый patch.

Основное дерево самостоятельно не редактирует.

### `saitranslate`

Готовит многоязычный пакет отдельно от Core.

### `saiwiki`

Готовит документацию и wiki-пакет, привязанный к конкретному состоянию исходников.

Core принимает только свежий, проверенный и полный пакет.

Никаких:

> Я вроде там что-то сделал, посмотри в соседнем чате.

Только payload, instructions, source commit и evidence.

## 16. Проводить работу по промышленному конвейеру

Команда Crew Circuit прогоняет проект через последовательность:

```text
sense
→ reproduce
→ intake
→ build
→ verify
→ review
→ translate
→ document
→ publish
```

Каждый этап передаёт следующему не обещание, а:

```text
воспроизведение;
вердикт;
тикет;
пакет;
доказательство.
```

Если этап пуст — это фиксируется как результат.

Если этап заблокирован — конвейер останавливается.

Частичный результат не передаётся дальше с запиской «там вроде нормально».

Текущий Crew Circuit последовательный. Полноценная конкурентная Crew Mode с атомарными claims, epochs, worktrees и release captain проектируется отдельно и не выдаётся за уже решённую задачу.

---

## 17. Экономить контекст

SAIPEN использует lazy loading.

Агент сначала читает маленький BOOT kernel и INDEX.

После этого загружает только:

* документ активной фазы;
* нужное правило Core;
* специализированный документ для текущей работы;
* релевантную долговечную память проекта.

Он не обязан каждую сессию перечитывать всю конституцию, историю государства и родословную валидатора.

Это уменьшает:

* token cost;
* вероятность отвлечения;
* конфликт старых инструкций;
* влияние нерелевантных правил;
* cold-start time.

**Vähem müra, rohkem tööd.**
Меньше шума, больше работы.

---

## 18. Работать без обязательной инфраструктуры

Основа SAIPEN:

```text
Markdown
Git
файловая система
stdlib Python для полного валидатора
```

Без Python остаётся переносимый shell/PowerShell validation floor.

Проект можно открыть как Obsidian vault.

`KNOWLEDGE/` виден в графе.
Работают обычные ссылки.
Состояние читается человеком.
Git показывает всю историю изменений.

Никакой скрытой магии.

Если SAIPEN сломался, его можно открыть в блокноте и понять, что произошло.

Вот это и называется система. Всё остальное иногда называется dashboard.

# Основные команды

```text
saipen set                 принять проект
saipen continue            продолжить работу
saipen plan                создать план и тикеты
saipen goal <text>         автономно выполнить цель
saipen status              показать состояние, ничего не менять
saipen stop                сохранить checkpoint и остановиться
saipen hunt                искать дефекты
saipen markhunt            провести широкий аудит
saipen test                запустить тесты
saipen validate            проверить структуру
saipen clean               очистить проект
saipen prepare             подготовить handoff
saipen collect             принять готовый пакет
saipen translate           подготовить переводы
saipen ship                выпустить релиз
saipen crew                пройти полный производственный цикл
```

Для частых действий существуют короткие ключи вроде:

```text
cc     продолжить
sss    показать статус
ss     сохранить checkpoint и остановиться
```

Команда является всем сообщением целиком. Никакого заклинания на четыре абзаца.

---

# Чего SAIPEN не делает

SAIPEN — не новая LLM.

Он не делает слабую модель гениальной.

Он не гарантирует, что агент никогда не ошибётся.

Он не является распределённым consensus algorithm для сотни машин.

Он не заменяет тесты, Git и инженерное мышление.

Он не должен хранить секреты или пользовательские данные без необходимости.

Он делает другое:

> Ошибка становится видимой.
> Работа становится продолжимой.
> Состояние становится проверяемым.
> Агент становится заменяемым.

---

# Для кого это

SAIPEN полезен, если:

* работаешь с несколькими AI coding agents;
* постоянно упираешься в session limits;
* меняешь модели по цене, доступности или задаче;
* ведёшь проект дольше одного разговора;
* устал объяснять агенту одно и то же;
* хочешь очередь задач без ручного `continue` после каждого шага;
* хочешь видеть разницу между «сделано» и «доказано»;
* не доверяешь магической памяти чата;
* предпочитаешь открытые файлы закрытой инфраструктуре;
* хочешь, чтобы проект пережил смерть любого конкретного агента.

---

# В одной фразе

**SAIPEN превращает ИИ из забывчивого собеседника в заменяемого рабочего, который приходит в цех, читает состояние проекта, берёт следующую задачу, оставляет доказательства и не требует пересказывать ему всю жизнь завода.**

```text
Чат исчез.
Модель сменилась.
Лимит закончился.
Проект не забыл.
```

**SAIPEN. One command. Zero dependencies. Zero amnesia.**
