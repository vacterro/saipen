# T-1319 — RIPGREP-DEPENDENT SKILL STARTUP (appended)

Operator evidence: fresh OpenCode flow ran `continue` → `Skill "saipen"` →
`ripgrep execution failed`.

## RIPGREP ROOT CAUSE — `OPEN_CODE_TOOL_FAILURE`

Not a guard refusal, and not SAIPEN prose. Proven mechanically:

* the string `ripgrep execution failed` exists **only inside the OpenCode
  binary** (`opencode-ai/bin/opencode.exe`), never in SAIPEN markdown or Python;
  `grep -rn -i ripgrep saipen/ tools/` finds nothing.
* in that binary it is the *single catch-all* of the ripgrep-backed FileSystem
  service: every failure inside the scoped effect that is not already a
  `Ripgrep.Error`/`InvalidPatternError` is mapped to
  `R0("ripgrep execution failed", q)` — so the real defect is **swallowed** and
  the operator sees only the generic string.
* the service resolves its binary as: `which rg.exe` → `<data>/bin/rg.exe` →
  download `ripgrep-15.1.0-x86_64-pc-windows-msvc.zip` and extract it with
  PowerShell `Expand-Archive`.
* measured on this host: `rg` was **absent from the persistent PATH**
  (`reg query HKCU\Environment` — no manicode entry; the `rg.exe` under
  `~/.config/manicode/` is injected only into another tool's sessions), and
  OpenCode's own bin (`C:\Users\vac34\.cache\opencode\bin`) held **only the
  1.81 MB archive with no `rg.exe` beside it** — the exact stranded state the
  code leaves when the extraction step throws before its cleanup.
* `@ff-labs` (the `fff` native finder) is **not installed**, so OpenCode uses
  the ripgrep layer for `grep`/`glob`/`find` rather than the fff fast path.
* `opencode debug skill` lists the `saipen` skill **successfully with rg
  absent**, so skill *discovery* does not need ripgrep; the fault is the
  agent's host search tool during the cold route.

Sub-cause: `RIPGREP_NOT_FOUND` in the host's effective PATH combined with an
incomplete binary provisioning, hidden by a catch-all error mapping.

## RIPGREP FAST PATH

Unchanged and not owned by SAIPEN. When `rg.exe` is present the host search
layer works normally; `opencode debug rg files` lists files correctly.

## RIPGREP FALLBACK — T-1319 (the actual fix)

The structural answer is that protocol startup must not need the host search
layer at all. `tools/saipen.py` now exposes a deterministic cold-route locator:
`saipen status --json` carries a `cold_route` block naming the bound
`project_root`, `saipen_home`, `protocol_dir`, `phase`, `phase_module`, `boot`,
`style`, the protocol document set and the `.saipen/` memory files, and stating
`search_required: false`.

Bounded by construction — a fixed document-name list probed with `pathlib`
inside two known directories plus one `phases/<phase>.md` check. **No directory
walk, no drive/profile scan, no recursion into unrelated repositories, no new
dependency, no subprocess.** `saipen/SKILL.md` and `saipen/BOOT.md` now route
the cold start through it and say explicitly that a host search fault is a
**host** fault, never a SAIPEN binding failure.

`tools/test_boot_locator.py` — **10 PASS**, CASE 1–8:
