# SAIPEN

**Протокол продовження для AI-агентів кодування.**Пам'ять проекту зберігається у звичайному
файлах Markdown усередині проекту(`.saipen/`), тому будь-який сумісний холодний агент —
без історії чату, без сесійної пам'яті — може працювати`/saipen continue`, читати
збережені`next_action`, і відновлювати роботу без запиту у користувача на повторне пояснення
нічого. Стан належить проекту, а не пам'яті одного виробника моделі.

**Одна команда для відновлення. Стан у звичайних файлах. Підтверджувані машиною договори.**

Репозиторій перевіряє себе при кожному push; встановлення, стан, перевірки, і
встановлення видалення виконується локально — немає сервісу хмари, немає демона, немає бази даних.

## Що залишається

Жива пам'ять проекту зберігається в`.saipen/`— звичайні файли, які можна читати, порівнювати та
зберігати разом із кодом. Холодний агент відповідає на п'ять запитань із файлів
самостійно:

|Файл / поле|Відповіді|
|---|---|
| `STATE.md` |Що відбувається зараз?(етап, активний тікет, режим роботи, блокувач) |
| `BOARD.md` |Яка робота існує / яка активна?(граф тікетів: DOING, TODO, DONE, BLOCKED) |
| `LOG.md` |Чому проект досяг цього стану?(граф подій, що додаються тільки вперед) |
| `KNOWLEDGE/` |Які сталі факти проекту мають виживати під час сесій?|
| `next_action` (в`STATE.md`) |Яку саме дію має виконати наступний агент?|

Це контракт на контрольні точки, а не пропозиція з проектування:`saipen stop`і кожен
перехід тікета записує файли в фіксованому порядку, і результат перевіряється
валідатором. Нічого не зберігається в хостованій базі даних, і нічого не втрачається, коли
сесія закінчується.

## Швидкий старт

**1. Встановіть один раз на кожній машині**— навчає Claude Code, Codex, Gemini, OpenCode,
Aider, Antigravity, і будь-який загальний`~/.agents/skills`читач(FreeBuff, тощо.):

```bash
git clone https://github.com/vacterro/saipen
cd saipen
powershell -ExecutionPolicy Bypass -File .\bootstrap\inject.ps1     # Windows
bash bootstrap/inject.sh                                            # macOS / Linux
```

<sub>What that touches, so nothing is a surprise: it appends a marked
`<!-- SAIPEN:BEGIN -->...<!-- SAIPEN:END -->`блок до інструкції агента
файли, які ви вже маєте(`~/.claude/CLAUDE.md`, `~/.config/opencode/AGENTS.md`,
`~/.codex/AGENTS.md`, `~/.gemini/GEMINI.md`)— резервне копіювання кожного з них до`.bak`перш за все —
і копіює протокол у відповідні папки навичок. Нічого за межами цих
шляхи, без демона, без мережевих викликів.</sub>

**2. Створіть проект**— відкрийте агента в вашій папці, введіть:

> `saipen set`

**Без встановлення?**Вставте один рядок у будь-який агент:

> Прочитайте&lt;clone&gt;/saipen/BOOT.md першою(ядро холодного запуску), потім&lt;clone&gt;/saipen/INDEX.md +&lt;клонувати&gt;/saipen/STYLE.md і дотримуйте їх.

**Змінили думку?**Один командою можна повернути:

```bash
powershell -ExecutionPolicy Bypass -File .\bootstrap\uninstall.ps1  # Windows
bash bootstrap/uninstall.sh                                         # macOS / Linux
```

Вона видаляє саме позначений блок(залишаючи решту файлу без змін), зберігає
a `.uninstalled.bak`створіть копію спочатку, і видаліть теки з навичками.

## Чому не просто історію чату?

SAIPEN має на меті конкретну проблему: AI-агента для кодування, який нічого не запам'ятовує
після закінчення сесії. Інші інструменти та звички частково вирішують цю проблему:

|Підхід|Що з ним добре|Що воно не несе|
|---|---|---|
|Історія чату / пам'ять моделі|Зручно, нуль налаштувань|Залежить від сесії та постачальника; не зберігається разом із проектом, тому холодний агент ніколи не бачить його|
|Статичний`AGENTS.md`/ файл інструкцій|Тривалий стійкий правила та звичаї|Сам по собі не представляє живого стану завдання`next_action`, або історію відновлення|
|Трекер проблем / TODO|Управління завданнями та беклогом|Сам по собі не визначає семантику продовження агента — що холодний агент має читати та виконувати після відновлення|
| **SAIPEN** |Живий виконавчий стан, черга завдань, історія подій, стійкі знання, і правила продовження, перевірені машинно — у звичайних файлах поруч із кодом|Нічого; це поєднання є контрактом|

Різниця не в одному файлі. Це те, що SAIPEN виконує крок відновлення
перевірка машиною: перша дія холодного агента після`/saipen continue`це
визначається збереженим`next_action`і перевіряється валідатором, а не
відновлюється з пам'яті.

## Інженерні докази

SAIPEN поєднує нормативний протокол у звичайних файлах з виконуваним, спрямованим на помилки
перевірки. Репозиторій демонструє дизайн протоколу/машини станів, Python
інструменти, схема-орієнтовані стани, міркування про відновлення, тестування на відхилення,
межі робочих процесів з участью кількох агентів, і дисципліна специфікації.

- **Договір, розроблений.** [SPEC.md](SPEC.md)визначає файловий
модель продовження та стабільний контракт на диску;[CORE.md](saipen/CORE.md)
і[MAINTENANCE.md](saipen/MAINTENANCE.md)визначають поточну нормативну поведінку.
- **Машинно перевірений стан.**Тільки stdlib канонічний
  [валідатор](tools/validate.py)читає живий
  [СТАТУС схема](extensions/schemas/state.schema.json)і перевіряє фазу
переходи, залежності квитків, посилання на граф подій, міждокументальні
інваріанти, можливості та стан відновлення.
- **Покриття невдач.** [CONFORMANCE.md](saipen/CONFORMANCE.md)відображає
вимоги до[сценаріїв фікстур](tests/scenarios/); те
  [виконавець сценаріїв](tools/run_scenarios.py)виконує структурні тести на успіх/провал
включаючи відновлення з пошкодженим станом, недійсні переходи, цикли залежностей та
обмеження тільки для читання.
- **Контролі регресії.** [audit_checks.py](tools/audit_checks.py)змінює
відомі добре копії та доводить, що перевірки валідатора все ще можуть відмовити, замість того,
щоб вважати постійно зелену перевірку доказом.
- **Виконувальний шар.** [saipen.py](tools/saipen.py)зберігає журналізований стан
операції;[bootstrap/](bootstrap/)зберігає інсталляцію, деінсталляцію та експорт
допоміжні засоби, з необов'язковим[інсталятором хука pre-commit](tools/install_hook.py).
- **Явні компроміси.**Основний протокол стану — це звичайні файли без runtime
залежності. Канонічна валідація та інструменти CLI потребують Python, але використовують лише
його стандартну бібліотеку і не потребують`pip`інсталляції.

## Архітектура

Три шари, строго односторонні залежності:

```text
CORE            continuation / state / checkpoint / validation       required
  └─ MAINTENANCE   autonomous HUNT / ADD / CLEAN evolution           optional, on top of Core
       └─ GOAL MODE / SUBAGENTS   opt-in throughput/execution        optional
```

Ядро не залежить від обслуговування: з вимкненим автономним еволюціонуванням, SAIPEN
все ще є повною протоколом продовження — холодний агент все ще відновлюється.

- **Станова машина ядра** — `INIT → PLAN → SCOUT → BUILD → VERIFY → REVIEW → SHIP → DONE | BLOCKED`.
- **Автономне обслуговування**— плата призупинена(нічого працездатного в`## TODO`,
нічого в`## DOING`)і не`BLOCKED`? Автономні переходи`HUNT` (сканування помилок)
  → `ADD` (розвиток функцій) → `HUNT`, нічого не запитує. Сесія, що сидить на
  `BLOCKED`ніколи не виконує автоматичний пошук
  ([Обслуговування § 2.1](saipen/MAINTENANCE.md#21-autonomous-transitions)).
- **Режим цілі** — `/saipen goal <objective>`обертає дошку і запускає
об'єкт вперед через VERIFY/REVIEW, потрапляючи в автономне обслуговування
доти, доки не виконається правило завершення або не досягне ліміту(3 хвилі / 20 квитків,
потім перевіряє контрольні точки і звітує) ([Обслуговування § 2.4](saipen/MAINTENANCE.md#24-goal-mode-autonomous-execution)).
- **Зміцнення**— батчовий вхід аналізується в хірургічні квитки по одному
  (Ядро § 1.8); продовження забрудненого дерева зберігає незавершену роботу(Ядро § 1.5);
значення, подібні до секретів, видаляються з журналів(`sk-***`) (Ядро § 1.2).

## Що SAIPEN не є

- **LLM або моделлю**— це протокол, яким агенти дотримуються, а не інтелект.
- **IDE або базою даних, що зберігається на сервері**— стан — це звичайні файли в вашому проекті;
нічого не хоститься.
- **Заміна Git**— Git все ще володіє історією версій; зробіть коміт
  `.saipen/`як інший код.
- **Розподілений консенсус**— дивіться межу паралельності нижче.
- **Гарантія того, що LLM зробить правильні інженерні рішення**— він
зменшує втрату контексту та дрейф поведінки; він не робить стохастичних агентів
непомилковими.

SAIPEN має на увазі продовження/контракт стану разом із валідацією та інструментами —
передаючи наступному агенту початкову точку, перевірену машиною, а не магію.

**Границя паралельності.**Журналовані зміни стану(SAIOPS)використовуйте
оперативний блокувач, прив'язаний до проекту, і журнал відновлення([OPS § 5](saipen/OPS.md#5-locks)).
Звичайні редагування проекту та відключені автори знаходяться поза цим блокувачем. SAIPEN
це не розподілений консенсус, тому відключені автори потребують зовнішньої
координації([SPEC](SPEC.md#concurrency--distribution-boundaries)).

## Примітки до налаштувань

**Мова відповіді.**Агент відповідає на**естонською**за замовчуванням — це
налаштування, а не вимога протоколу, і нічого іншого у SAIPEN не естонське.
Протокол, код, коміти та кожен документ залишаються англійськими на кожному
етапі. Змініть це в одному місці: у`reply_language:`рядку на початку
[`saipen/STYLE.md`](saipen/STYLE.md). `et`естонською,`en`англійською,`ru`російською,
`auto`вибирається з повідомлення, яке ви надіслали.

**Адаптери.**Платформа не охоплена інжектором(DeepSeek, Qwen, standalone
OpenAI, тощо)? Примітки залежно від платформи знаходяться в`extensions/adapters/`.
