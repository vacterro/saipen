# AUDIT — `state-history-binding` read deadlock is still live at HEAD `10a2989`

An independent project (`SAIPAL`) was handed a mission and could not run a single
canonical write. Every mutating verb, the one repair verb, and the guard's own
advertised recovery route all refuse with the same error, and the only manual
workaround is forbidden by the guard. Nothing in this report is inferred from
prose: every command below was executed against the installed protocol.

This is a re-confirmation of `SAIPAL-DEADLOCK-20260916`
(`.saipen/evidence/SAIPAL-deadlock-state-history-binding-20260916/REPORT.md`)
on a **second observed project**, with the added findings that (a) the deadlock
survives the current source HEAD, (b) `saipen status` / `next` / `validate`
are inside the same loop, and (c) the START resume command the engine emits
points back at itself.

## Findings

### F1 [P0] [PROTOCOL_DEADLOCK] [reproduced] — no canonical verb can repair the state

expected: `saipen recover` reads and repairs a machine-owned checkpoint defect,
as `OPS.md` § 3 and the CORE repair contract state; `saipen status`/`next`
report the condition read-only; the guard's named recovery route is executable.

actual: every one of the following returns the **identical** refusal
`VALIDATION_FAILED: state-history-binding: invalid phase transition:
VERIFY -> DONE (RFC § 1.6). The block-parked shape requires the latest
phase-changing event through STATE.last_event to be the canonical active-block
DEC for the exact ticket still in BOARD.BLOCKED`:

```
saipen continue
saipen next
saipen recover
saipen recover --attest-legacy-done T-125
saipen ticket unblock T-125 proceed
saipen transition SHIP T-125 --dry-run
saipen context cold
```

`saipen status --json`:

```json
{"ok":false,"code":"VALIDATION_FAILED","action":"saipen status",
 "reason":"checkpoint-invalid",
 "detail":"checkpoint invalid: FLOOR: STATE.task=T-125 but BOARD DOING is empty at the raw floor; STATE proposed next_action 'None' does not start with WAIT:/saipen /PHASE /RUN:/RESUME:; STATE proposed invalid phase transition: VERIFY -> DONE (RFC § 1.6). The block-parked shape requires the latest phase-changing event through STATE.last_event to be the canonical active-block DEC for the exact ticket still in BOARD.BLOCKED",
 "recovery_pending":false,"recovery_conflict":false,
 "conflict_ops":[],"pending_ops":[]}
```

`saipen validate --json` reports four underlying errors:

```
FLOOR: STATE.task=T-125 but BOARD DOING is empty at the raw floor
STATE proposed next_action 'None' does not start with WAIT:/saipen /PHASE /RUN:/RESUME:
STATE proposed invalid phase transition: VERIFY -> DONE (RFC § 1.6). ...
STATE proposed phase DONE is not ticket-bearing but task is 'T-125'; task must be none outside a ticket-bearing phase
```

`saipen fleet prepare` classifies the condition but offers no executable exit:

```
REFUSE [BOUND_RECOVERY_REQUIRED_BLOCKED]
next: saipen recover (operator decision)
```

The refusal is therefore **not** `RECOVERY_REQUIRED`: there is no pending journal
operation to settle, and `saipen recover` itself cannot run. The validator is a
sensor here, not a repair.

### F2 [P0] [PROTOCOL_DEADLOCK] [reproduced] — START emits a self-referential resume command

expected: when START refuses, the `resume_command` it prints is an executable
next step (`BOOT.md` "Routing failures": a refusal names one exact refusal and
the executable next action).

actual: `saipen start --receipt SRC-009 --json` returns

```json
{"ok":false,"code":"VALIDATION_FAILED",
 "detail":"the request is durable as SRC-009; one operator decision is open in this project and must be answered before new Work is projected",
 "receipt":"SRC-009","ticket":null,"valve_reauthorized":false,
 "resume_command":"saipen start --receipt SRC-009",
 "reconciliation":{"ok":false,"code":"VALIDATION_FAILED",
   "detail":"state-history-binding: invalid phase transition: VERIFY -> DONE (RFC § 1.6). ..."}}
```

The only "operator decision" that would clear `preserved` is a reconciliation
decision, and reconciliation fails with the same F1 refusal. So the printed
`resume_command` is the command that just refused, and the durable receipt
(`SRC-009`) can never be projected as Work — the mission's own delivery path is
unreachable.

### F3 [P1] [PROTOCOL_VIOLATION] [reproduced] — the guard closes the manual exit

expected: a bound agent that hits a machine-owned checkpoint defect has at least
one route to recovery.

actual: the OpenCode guard refuses the two remaining human routes:

- every non-`saipen` consequential tool → `SAIPEN_GUARD_REFUSAL: NO_ACTIVE_WORK`
  (`admission.py:783`, exactly one `## DOING` Work required; `## DOING` is empty);
- a direct write/delete of `.saipen/STATE.md` → `SAIPEN_GUARD_REFUSAL:
  PROTECTED_CANONICAL_NAMESPACE` (`admission.py:1023`/`1111`,
  `PROTECTED_CANONICAL_NAMESPACES` at `admission.py:59`).

The guard correctly exempts canonical `saipen` verbs as the repair path
(`admission.py:1386`), but that path is exactly what F1 breaks. The loop is
closed: sanctioned repair unreachable, manual edit forbidden.

## Root cause (exact sources)

1. `tools/saipen_engine/operations.py:320-322` — `_read` raises unconditionally:

   ```python
   parked_error = block_parked_evidence_error(state, board, snapshot.events)
   if parked_error is not None:
       raise CheckpointError(f"state-history-binding: {parked_error}")
   ```

2. `tools/saipen_engine/fast_check.py:170` — `block_parked_evidence_error`
   returns `None` only for a legal park or a pair it does not own. Here
   `source=VERIFY`, `destination=DONE`, so it proceeds and requires the newest
   phase-changing event at/before `STATE.last_event` to satisfy `is_active_block`
   (`taxonomy == DEC`, `op_id` starting `ticket-`, text starting
   `ticket block via SAIOPS (active)`, ticket present in `BOARD ## BLOCKED`).
   `E-950`/`E-951` have `op_id == null`, no active block exists, so it returns
   the error string.

3. `tools/saipen_engine/reconcile.py:1671` — the one repair operation calls the
   same reader:

   ```python
   docs, state, _board, log_tail = _read(project_root, allow_malformed_state=True)
   ```

   `_read` has three escape hatches (`allow_dead_home`, `allow_malformed_state`,
   `allow_illegal_log`), and **none covers the parked-evidence gate**.
   `grep allow_parked_evidence` over both the install and the clone returns
   nothing. The deadlock is structural, not incidental.

**Why the state got here.** `E-950`/`E-951` were appended without the SAIOPS
operation layer, so they carry no `[op: ...]` marker and the parked-evidence
gate cannot bind the `VERIFY -> DONE` pair to a canonical active block. The
authoring defect is a hand-edit after the migration boundary; the protocol
defect is that the resulting state has no repair route.

## Impact

- The project cannot `status`, `next`, `continue`, `recover`, `transition`,
  `claim`, `checkpoint`, or `ticket unblock`.
- `saipen start` projects no Work: every new request is captured as a durable
  receipt and never materialized (four orphan receipts now sit in this project:
  `SRC-006`, `SRC-007`, `SRC-008`, `SRC-009`, all `linked_work: null`).
- A mission that depends on SAIOPS materialization is unreachable.
- The only exits are both outside agent authority: edit a protected canonical
  file by hand (forbidden, and would falsify history) or fix the engine.

## How to reproduce (deterministic fixture, for a regression control)

Build a minimal project whose STATE/BOARD/LOG carry the exact trigger shape:

1. `STATE.md`: `schema_version: 3`, `phase: DONE`, `task: T-1`,
   `transition_from: VERIFY`, `last_event` = the `E-##` of a legal-looking
   `RUN`/`DEC` completion line, `next_action: "None"`, `agent: <one seat>`.
2. `BOARD.md`: `## DOING` empty, `## TODO` non-empty, `T-1` under `## DONE`
   with a `| verify: ...` field.
3. `LOG.md`: last two events are non-SAIOPS (no `[op: ...]`) `RUN` and `DEC`
   lines naming `T-1`; the predecessor is a `ticket added via SAIOPS` event.

Then assert the CURRENT tree refuses, and the FIXED tree repairs:

- `saipen recover` returns `REPAIRED` (or `CLEAN`), not
  `VALIDATION_FAILED`/`state-history-binding`;
- after recovery `saipen status --json` returns `ok: true` with a DFA-reachable
  `(transition_from, phase)` pair and a `next_action` starting with
  `WAIT:`/`saipen `/`PHASE `/`RUN:`/`RESUME:`;
- `saipen start --receipt <SRC>` then projects Work instead of returning its
  own `resume_command`;
- a second `saipen recover` is idempotent and writes no further bytes;
- the negative control: a state whose newest phase event IS a canonical
  active-block DEC is untouched by this repair.

## Suggested repair (non-binding; maintainer decides)

Preferred — a bounded reader escape hatch:

1. add `allow_parked_evidence: bool = False` to `_read`
   (`operations.py:207`), guarding the raise at `operations.py:320-322`;
2. enable it **only** in `reconcile.reconcile_protocol_state`
   (`reconcile.py:1671`), beside `allow_malformed_state=True`. The repaired
   proposal is still proven by `validate_texts` before any byte is written, so
   the gate is proven on the result, not waived;
3. confirm `_state_phase_repairs` (`reconcile.py:1192`) then derives the legal
   replacement from the transition chain and clears the ticket-bearing
   violation.

Alternative — a canonical SAIOPS transition that records `VERIFY -> SHIP`,
`task -> none`, `next_action -> saipen continue` through the operation layer.

Related hardening: two structural events after the `[op: ...]` boundary lack
their marker (`OPS.md` § 4a). The validator's `[saio]` check owns that class,
but cannot run while the checkpoint reader refuses the state it inspects.
