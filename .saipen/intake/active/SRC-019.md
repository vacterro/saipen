DEFECT:
ABSENT is overloaded to mean both:
1. genuinely virgin allocator state; and
2. previously-used allocator whose idempotency authority disappeared.

Those states have opposite authorization semantics, but `enqueue()` treats them identically.

Once any prior audit allocation exists, losing/removing the allocator causes a retry of the SAME producer operation to be accepted as a NEW operation. `_reconcile()` correctly avoids numeric collision, so the bug is particularly deceptive: instead of overwriting layer 1, it creates layer 2 containing the same audit and reports normal success.

The implementation already contains the correct diagnosis for CORRUPT but stops one branch too early. A missing authority after history is just as incapable of proving producer-operation uniqueness as a malformed authority.

REPAIR:
Make allocator initialization conditional on a provably virgin audit transport.

Minimum fail-closed repair:

- Before treating ABSENT as virgin, inspect the existing durable witnesses already used by `_reconcile`:

    audit inbox binding/history;
    any other canonical allocation receipt introduced by the implementation.
- If history exists but allocator is absent, return a distinct refusal such as:
    AUDIT_ALLOCATOR_MISSING_HISTORY
  and write nothing.
- Remove the current unsafe remediation that suggests simply deleting a corrupt allocator unless the same command simultaneously reconstructs a complete producer-operation authority.
- If automatic repair is desired, add a redundant immutable allocation receipt that preserves:
    producer
    producer_operation_id
    producer_item_id
    layer
    digest
  so idempotence can actually be reconstructed. Do not infer producer-operation identity merely from matching body digests: two intentional producer operations may legitimately carry identical audit bytes.

- fresh-project ABSENT initialization;
- monotonic non-reuse of layer ids;
- CORRUPT refusal;
- existing same-op/different-body conflict behavior.
