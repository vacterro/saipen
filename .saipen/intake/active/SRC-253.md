SAIPEN

MISSION: Self-Healing Continuation — Automatic Doctor, Recovery and Resume

PRIORITY: P0/P1
MODE: Extended autonomous engineering implementation
PRIMARY OWNER: SAIPEN
INTEGRATION CONSUMER: ZAICODE
REFERENCE PROJECT: Wintage

GOAL

Make SAIPEN-managed projects recover automatically from routine,
deterministic and safely repairable operational failures.

The operator should express intent once.

When the operator sends:

cc
continue
saipen continue
cc all

the system should perform all necessary authorized intermediate steps
without requiring the operator to manually execute routine diagnostic
or recovery commands.

The desired outcome is:

One operator command
-> trusted ingress
-> canonical admission
-> health preflight
-> automatic diagnosis when needed
-> safe recovery
-> validation
-> resumption of the original Work
-> trustworthy final receipt

The operator should not become the maintenance worker for the agent
execution protocol.

This is NOT permission to bypass authority, ignore genuine corruption,
or turn cc into unlimited execution authorization.

The engineering principle is:

"If a system can safely, deterministically and with proper authorization
diagnose and repair an operational problem itself, the human operator
should not have to perform intermediate technical recovery steps."

This principle must become a reusable SAIPEN capability, not a
Wintage-specific workaround.

CURRENT REFERENCE INCIDENT

The operator submitted cc to the Wintage project through ZAICODE.

The SAIPEN launcher refused continuation:

CONFORMANCE_UNHEALTHY

crew convergence requires a CURRENT_PASS canonical conformance receipt

got STALE_PASS

receipt checkpoint hashes invalid:

STATE hash mismatch:
receipt=8b99993300433601
current=efde52c0d1e36de2

Suggested manual action:

saipen validate

The refusal may be correct under existing conformance rules.

The product-level deficiency is that a routine recoverable validation
condition can require the operator to leave the normal cc workflow,
open a terminal, navigate to the project, run validate, return to
ZAICODE and resend cc.

The expected behavior is different:

1. Detect the stale receipt.
2. Determine why it became stale.
3. Verify there is no conflicting active writer or unsafe state.
4. Revalidate through the canonical validator if authorized.
5. Obtain and verify CURRENT_PASS.
6. Resume the original continuation exactly once.
7. Return the normal Work result.

If automatic recovery is not safe, stop with a specific blocker.

Do not assume this incident is merely a stale cache.

The STATE hash mismatch may indicate legitimate canonical mutation,
concurrent activity, incorrect receipt invalidation, faulty checkpoint
hashing, or other defects.

The Doctor must distinguish these cases.

PHASE 1 — DEFINE THE SELF-HEALING CONTRACT

Introduce or extend one canonical contract:

SELF_HEALING_CONTINUATION

The contract should answer:

1. What failed?
2. Is the failure automatically recoverable?
3. Which canonical subsystem owns recovery?
4. Is recovery permitted under current authority?
5. Does recovery risk modifying protected state?
6. Is there another active writer?
7. What proves recovery succeeded?
8. Can the original Work safely resume?
9. What prevents duplicate execution?
10. When must the system stop?

Use a typed classification rather than free-text matching.

Suggested classes:

HEALTHY
RECOVERABLE_READ_ONLY
RECOVERABLE_AUTHORIZED_MUTATION
REQUIRES_OPERATOR_AUTHORITY
REQUIRES_HUMAN_DECISION
CONCURRENT_OWNER
UNSAFE_STATE
IRRECOVERABLE
UNKNOWN

The exact names may follow existing SAIPEN conventions.

Do not create a parallel status taxonomy if the protocol already has
one suitable authoritative owner.

The essential distinction is between a condition that the system can
repair and one that it is merely capable of describing.

The classification must produce a canonical action, not just a message.

PHASE 2 — AUTO-DOCTOR ENTRY POINT

Integrate Auto-Doctor into the normal continuation path.

The operator must not need to invoke a separate command when the
continuation path can safely perform the recovery itself.

Required behavior:

OPERATOR cc
  -> resolve project
  -> establish trusted provenance
  -> check admission
  -> inspect necessary health
  -> execute Work if healthy
  -> otherwise classify failure
  -> perform permitted automatic recovery
  -> verify repaired condition
  -> recheck admission and ownership
  -> resume Work

The original command identity must survive this process.

Preserve:
- Original operator input.
- Source command ID where available.
- Original project binding.
- Trusted carrier.
- Target Work.
- Execution intent.
- Retry identity.
- Session identity where applicable.
- Audit and receipt linkage.

Auto-Doctor must not synthesize a new operator decision.

It must not translate an ordinary cc into unlimited repair,
publication, migration or deletion authority.

If recovery requires additional authority beyond the original
admission, obtain it through the existing canonical mechanism.

If that authority is unavailable, stop.

Do not request confirmation for operations already safely authorized
by the existing protocol.

PHASE 3 — STALE CONFORMANCE RECEIPT RECOVERY

Implement the Wintage incident as the first concrete acceptance case.

Initial condition:

Existing conformance receipt:
STALE_PASS

Reason:
STATE hash mismatch

Required automatic behavior:

A. Capture initial state

Read:
- Current canonical STATE.
- Relevant BOARD and LOG identity.
- Receipt identity.
- Receipt checkpoint hashes.
- Current checkpoint hashes.
- Validation status.
- Active writer/lease.
- Execution phase.
- Applicable recovery restrictions.

Do not mutate anything during diagnosis.

B. Classify the mismatch

Distinguish:

1. Legitimate STATE update after validation.
2. Incomplete or interrupted canonical transition.
3. Another active writer modifying state.
4. Race between validation and transition.
5. Validator or receipt-generation defect.
6. Malformed or unverifiable receipt.
7. Actual canonical integrity failure.

Only the first category and other explicitly proven safe cases should
follow the ordinary automatic revalidation path.

Do not assume every hash mismatch is benign.

C. Check recovery eligibility

Verify:
- The original operator request is authenticated.
- The project identity is unchanged.
- No conflicting writer exists.
- No STOP or NO_GO condition prohibits recovery.
- Current phase permits the operation.
- The validator supports the requested operation.
- No manual decision is required.
- The repair does not modify immutable history.
- The receipt can be regenerated canonically.

D. Run canonical validation

Use the existing validator rather than constructing a receipt manually.

The expected command-level equivalent is:

saipen validate

However, prefer the engine's supported structured invocation when it
provides stronger identity, ownership and result guarantees.

Do not spawn shell commands that accidentally bind a different
project root.

E. Verify the result

Require:
- Validator success.
- CURRENT_PASS.
- Correct canonical checkpoint identity.
- Correct project identity.
- No unresolved integrity errors.
- Stable ownership.
- Current admission still valid.

A process exit code of zero alone is insufficient.

F. Resume

Return to the original continuation through the canonical route.

Do not issue a new independent user request.

Do not duplicate previously admitted or dispatched Work.

If the receipt becomes stale immediately without a legitimate external
mutation, classify the condition as a probable lifecycle or hashing defect.

Do not retry indefinitely.

Preserve a diagnostic trace showing exactly which hash changed and when.

PHASE 4 — PREVENT SELF-INVALIDATING VALIDATION

Investigate whether SAIPEN itself can create a stale receipt during the
normal continuation lifecycle.

Potential failure pattern:

validate
-> CURRENT_PASS
-> SAIPEN writes STATE
-> STATE hash changes
-> receipt becomes STALE_PASS
-> continuation refuses
-> repeat

Determine whether the current code can produce this sequence.

Do not assume that it does.

Build a deterministic reproducer around:

- Validation.
- STATE transition.
- Receipt generation.
- Checkpoint hashing.
- Crew convergence admission.
- Concurrent activity.
- Restart after validation.

Define the authoritative checkpoint boundary.

Ensure that a successful and correctly ordered canonical validation is
not invalidated solely by an unintended bookkeeping mutation.

Do not solve this by ignoring STATE hashes.

Do not exclude security-relevant state from conformance without proving
the legitimacy of that exclusion.

If the underlying issue belongs to receipt generation or checkpoint
ordering, repair that owner.

Do not create a second inconsistent hashing implementation.

PHASE 5 — EXPAND AUTO-DOCTOR TO ROUTINE FAILURE CLASSES

After the initial stale-receipt path is proven, extend the same mechanism
to other safely recoverable cases.

Candidate categories:

1. Stale but otherwise valid conformance evidence.
2. Missing generated cache that can be rebuilt.
3. Stale non-authoritative runtime projections.
4. Temporary filesystem read failures.
5. Interrupted but transactionally recoverable maintenance work.
6. Incomplete recoverable checkpoints.
7. Expired leases with documented safe reclamation rules.
8. Recoverable interrupted validation.
9. Safe host/service reconnection.
10. Retryable transient transport failure before dispatch.

Every category requires:

- A specific diagnosis.
- One authoritative recovery owner.
- Explicit safety prerequisites.
- An authorized mutation boundary.
- An idempotent operation.
- A post-recovery verification oracle.
- A retry limit.
- A deterministic terminal failure response.

Avoid implementing a generic repair engine that edits files based on
error strings.

Do not classify an ambiguous failure as automatically recoverable
merely because retrying might work.

PHASE 6 — NON-RECOVERABLE AND HUMAN-GATED CASES

Auto-Doctor must stop on genuine authority or integrity boundaries.

Examples:

HISTORY_LEDGER_CORRUPT

Never synthesize missing parent events or rewrite immutable history
merely to make validation pass.

OPERATOR_REQUIRED

Never turn model-generated text into trusted operator authority.

NO_GO / STOP

Never clear a deliberate safety barrier without authorized evidence.

CONCURRENT_OWNER

Never steal an active writer's lease to satisfy cc.

RECOVERY_ONLY

Never extend recovery authorization into unrelated feature work.

UNTRUSTED_CARRIER

Never invent SAIPEN_TASK_FILE or SAIPEN_TASK_SHA256 inside an agent
process.

UNSAFE_SOURCE_STATE

Never discard foreign dirty changes or force a reset.

AMBIGUOUS_EXECUTION_ACK

Never blindly dispatch a second execution when the first may have
already started.

UNSAFE_DESTRUCTIVE_ACTION

Never purge user sessions, audit history or backups as a recovery
shortcut.

For these cases, return:

STATUS: BLOCKED
REASON: exact canonical reason
RECOVERY_ATTEMPTED: yes/no
WHY_AUTOMATION_STOPPED: precise safety boundary
NEXT EXACT ACTION: required operator or responsible owner

The human should only be interrupted where human authority or judgment
is genuinely necessary.

PHASE 7 — IDEMPOTENCY, CONCURRENCY AND DUPLICATE PREVENTION

Auto-recovery introduces a serious new risk:

One user command could accidentally trigger multiple executions.

Establish a single continuation identity across:

- Original cc.
- Doctor admission.
- Recovery operation.
- Validation.
- Resumed execution.
- Final acknowledgment.

Required invariants:

1. A recovery retry never creates a second operator command.
2. A second cc cannot duplicate an already dispatched task.
3. Concurrent cc requests respect the canonical writer lock.
4. A crash during recovery can be resumed safely.
5. An ambiguous dispatch result is not blindly replayed.
6. A stale validation receipt is never mistaken for CURRENT_PASS.
7. A recovered project cannot silently change identity.
8. A doctor instance cannot outlive its authorized scope.
9. Recovery evidence survives interruption.
10. Recovery does not consume or renew unrelated operator authority.

Use the existing SAIPEN transaction and idempotency mechanisms where
available.

Do not create independent shadow locks or recovery ledgers unless the
canonical architecture explicitly requires them.

PHASE 8 — RETRY AND BUDGET POLICY

Avoid endless self-healing loops.

Use bounded, cause-specific retries.

A suitable default for the stale-conformance path:

- One automatic canonical revalidation.
- One verified return to the original continuation.
- No unlimited recursive Doctor invocation.

A genuinely new failure may be classified separately, but nested
recovery must have a hard global bound.

Prevent sequences such as:

cc
-> validate
-> cc
-> validate
-> cc
-> validate
-> ...

The operator should receive the actual reason when the loop cannot
converge.

Every attempted recovery must have observable start and terminal
outcomes.

Do not mask repeated systemic defects as transient faults.
