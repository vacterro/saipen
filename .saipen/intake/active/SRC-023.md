# IMPLEMENTATION — SAIPEN Run to Closure Producer

## Target

Primary writable repository: **SAIPEN**

Implement only the SAIPEN producer side of the Run to Closure bridge.

Do not implement OpenCode UI behavior.
Do not modify SAITULS/SAIPATCH.
Do not add a second lifecycle or a new SAIPEN phase.

The output of this wave is a stable, tested, read-only machine contract that a later SAIPATCH/OpenCode consumer can trust.

## Mission

Add an authoritative automation verdict to:

```text
saipen status --json
```

so an external driver can safely decide whether to:

- send another `cc`;
- stop because the project is complete;
- stop because a human/external/blocking condition exists;
- fail closed because state is invalid.

The core requirement is:

> COMPLETE is allowed only after the audit transport is truly quiescent and one fresh convergence pass has completed after that audit-empty boundary.

Do not use assistant prose such as `FULL_DONE` as authority.

## 2. Extend `saipen status --json`

Add one additive object:

```json
{
  "automation": {
    "schema_version": 1,
    "disposition": "...",
    "next_command": "...",
    "reason_code": "...",
    "reason": "...",
    "audit_quiescent": true,
    "audit_epoch": "...",
    "convergence_current": true,
    "closure_complete": true,
    "source_fingerprint": "...",
    "completed_at": "..."
  }
}
```

Closed dispositions:

```text
CONTINUE
COMPLETE
WAIT_USER
WAIT_EXTERNAL
BLOCKED
INVALID
```

Rules:

```text
CONTINUE      -> next_command = "cc"
everything else -> next_command = null
```

`saipen status --json` must write **zero project bytes**.

Unknown/ambiguous state must never become `CONTINUE` or `COMPLETE` optimistically.

---

## 3. Canonical audit quiescence

Do not equate "folder empty" with "audit complete".

`audit_quiescent = true` requires all applicable canonical facts to agree:

1. no NEW audit layer;
2. no ACTIVE audit layer;
3. no CLOSED_PENDING_DELETE layer;
4. no invalid/unreadable audit layer;
5. no audit-inbox residue diagnostic;
6. no numbered `audit/N.md` transport file remaining;
7. no uncaptured/reappeared generation at a previously used path;
8. no active audit-related work that remains live after the source layer was removed.

Historical DELETED intake records are allowed.

Derive a deterministic `audit_epoch` from canonical audit transport identity/generation facts.

Requirements for `audit_epoch`:
- changes whenever a new audit generation arrives;
- deterministic for the same canonical audit state;
- not based on arbitrary LLM prose;
- cheap to compute;
- testable.

---

## 4. Post-empty convergence

This is the critical correctness rule.

`COMPLETE` is forbidden merely because:

- BOARD is empty;
- STATE says DONE;
- `audit/` is empty;
- tests passed earlier;
- an older convergence receipt exists.

Required sequence:

```text
latest audit generation drains
        ↓
audit becomes canonically quiescent
        ↓
ONE fresh full convergence runs
        ↓
convergence is current for live source
        ↓
no new audit generation arrives
        ↓
COMPLETE
```

Reuse the existing convergence authority and existing `converge_target: done` semantics.

Bind the accepted convergence proof to the current `audit_epoch`.

Preferred implementation:
- use existing operation/receipt/journal infrastructure;
- derive the latest audit-empty boundary from canonical audit chronology;
- avoid a new persistent STATE flag.

If a tiny receipt is genuinely required, store machine evidence in an existing canonical operation/runtime area, not as prose.

If a new audit arrives during or after convergence, the previous closure proof becomes invalid and a new post-empty convergence is required.

---

## 5. Disposition derivation

Use existing canonical routing/ownership.

### COMPLETE
Only when the full closure bar is proven.

### CONTINUE
When SAIPEN can make useful autonomous progress and another `cc` invocation is a valid continuation carrier.

### WAIT_USER
When continuation requires user authority/input, including as applicable:
- manual verification;
- destructive authorization;
- first publish;
- explicit user brake.

### WAIT_EXTERNAL
When progress depends on a non-user external condition and another immediate `cc` cannot lawfully advance it.

### BLOCKED
When state is valid but no safe autonomous progress exists.

### INVALID
When corruption, unknown schema/contract, broken audit state, invalid machine evidence, or another unsafe condition prevents trustworthy automation.

Do not map "not complete" to CONTINUE.

---

## 6. Soft safety-valve behavior

Normal manual SAIPEN semantics remain unchanged.

Document one narrow automation rule:

An explicitly operator-armed external Run to Closure driver may treat repeated `cc` issuance as pre-authorized reauthorization of the ordinary soft goal/convergence safety valve.

This does **not** authorize:
- first publish;
- destructive operations needing confirmation;
- manual verification;
- secrets or missing user input;
- policy/product choices owned by the user.

SAIPEN does not need a global persistent `run_to_closure=true` field.

The external driver owns whether repeated continuation has been authorized.

---

## 7. Human-visible terminal line

Optionally render:

```text
SAIPEN_CLOSURE_COMPLETE
```

only when `automation.disposition == COMPLETE`.

Optional compact evidence:

```text
SAIPEN_CLOSURE_COMPLETE audit=<short> source=<short>
```

This is display-only.

Tests and consumers must not parse it as machine truth.

---

## 8. No accidental Improve after closure

Once automation says `COMPLETE`, the external driver must stop before another `cc`.

Do not remove normal manual continue→Improve behavior.

The automation contract should make it unnecessary for an external driver to send one extra `cc` merely to discover that closure already happened.

---

## 9. Deterministic tests

Add tests covering at least:

1. pending audit -> CONTINUE, never COMPLETE;
2. active audit-linked ticket -> CONTINUE;
3. invalid audit -> INVALID/BLOCKED according to canonical owner;
4. audit residue -> not COMPLETE;
5. empty physical audit folder with unsettled canonical intake -> not COMPLETE;
6. quiescent audit + no post-empty convergence -> CONTINUE;
7. convergence older than latest audit generation -> CONTINUE;
8. audit drains + fresh convergence -> COMPLETE;
9. new audit during convergence invalidates closure;
10. new audit after convergence invalidates closure;
11. source mutation after convergence invalidates closure;
12. empty BOARD alone is insufficient;
13. DONE phase alone is insufficient;
14. human confirmation -> WAIT_USER;
15. external dependency -> WAIT_EXTERNAL;
16. structural corruption -> INVALID;
17. manual behavior outside RTC remains unchanged;
18. explicitly armed RTC may cross only the ordinary soft safety valve;
19. first-publish confirmation remains a hard stop;
20. `status --json` writes zero project bytes;
21. `audit_epoch` is deterministic;
22. the same audit epoch + same source produces stable machine output;
23. unknown machine state fails closed.

## 10. Acceptance fixture

Create a disposable test project with:

```text
audit/1.md
audit/2.md
audit/3.md
```

Prove mechanically:

- while audits/work remain -> `CONTINUE`;
- when the transport first becomes quiescent -> still not COMPLETE;
- a fresh convergence happens after that boundary;
- only then -> `COMPLETE`;
- adding `audit/4.md` invalidates the prior closure;
- a new convergence is required after `audit/4.md` drains.

No OpenCode dependency is needed for this producer wave.

## 13. Done when

Done means:

- `saipen status --json` exposes schema v1 automation truth;
- the contract is read-only;
- `CONTINUE` is emitted only when another `cc` can safely advance work;
- `COMPLETE` requires true audit quiescence + fresh post-empty convergence;
- closure is bound to the current audit generation/epoch;
- new audits/source mutation invalidate stale closure;
- human/external/blocking boundaries stop automation;
- deterministic tests pass;
- existing SAIPEN validation/conformance/release checks remain green.

Final report must include:

1. exact files changed;
2. exact JSON contract;
3. disposition derivation;
4. `audit_epoch` algorithm;
5. post-empty convergence binding;
6. source fingerprint behavior;
7. tests and results;
8. read-only proof for status;
9. protocol line/token delta;
10. remaining limitations.
