SAIPEN

SILENT EXECUTION — MAXIMUM ACTIVITY, MINIMUM USER-VISIBLE PROSE

TARGET

Make silent execution the canonical default for active SAIPEN work.

The user can already observe tool activity / host thought surfaces where the host
chooses to expose them.

SAIPEN must therefore stop adding redundant model-authored progress narration
between work steps.

Desired UX:

    user gives work
    -> agent works
    -> tools / host activity continue
    -> no conversational progress prose
    -> one compact final protocol response

The agent should be busy, not chatty.

============================================================
1. DEFAULT EXECUTION MODE
============================================================

Introduce or reuse one canonical execution policy equivalent to:

    SILENT_EXECUTION = ON

Default it ON for normal SAIPEN execution / goal continuation unless the user
explicitly requests progress narration.

This governs USER-VISIBLE MODEL TEXT.

It must NOT suppress:

- internal reasoning;
- tool calls;
- host-native activity indicators;
- host-native thought UI that SAIPEN cannot control;
- machine-readable runtime status;
- canonical blocking diagnostics.

============================================================
2. PROHIBIT INTERMEDIATE NARRATION
============================================================

During executable work, do not emit prose such as:

    "I am reading STYLE.md now."
    "Next I will inspect the board."
    "SCOUT is clear."
    "I found the file, now checking the tests."
    "Build continues."
    "I will run verification next."
    "The tests are running while I inspect..."

These messages add no operator value when work can continue automatically.

They are execution noise.

Canonical rule:

    RUNNABLE WORK EXISTS
    -> DO WORK
    -> DO NOT NARRATE THE WORK

============================================================
3. USER-VISIBLE TEXT DURING EXECUTION IS EXCEPTIONAL
============================================================

Before terminal completion, user-visible model prose is allowed only for one of
these reasons:

A. REAL BLOCKER
   Human input/authority/data is genuinely required and no canonical autonomous
   next action exists.

B. OPERATOR ACTION
   A precise human action is mechanically required.

C. SAFETY / IRREVERSIBLE BOUNDARY
   Explicit approval is required by policy.

D. USER REQUESTED PROGRESS
   The user explicitly asked for periodic/intermediate reports.

E. CAPABILITY BOUNDARY
   The requested action cannot be executed and the protocol requires a bounded
   explanation.

Everything else stays silent.

============================================================
4. FINAL REPORT ONLY
============================================================

Normal successful execution should produce ONE final response after the current
work boundary completes.

Use the existing canonical response contract.

Default final response should be compact:

    STATUS
    RESULT
    BLOCKER
    OPERATOR ACTION
    NEXT EXACT ACTION
    VALIDATION

Omit empty/non-required fields where the current contract permits.

No chronological diary.

Do not recount every command, file read, test invocation, or reasoning step.

Report outcomes, not the travelogue.

============================================================
5. LONG EXPLANATIONS ARE EXPLICITLY AUTHORIZED
============================================================

A long explanation is allowed only when:

- the user explicitly asks for a detailed report/audit/handoff;
- a complex failure genuinely requires explanation;
- protocol evidence requires bounded detail;
- a consequential design decision must be explained.

Even then:

    detail authorization
    -> existing DETAILS budget
    -> canonical response enforcement

No unrestricted prose mode.

"Important" does not mean "write a novel".

============================================================
6. THOUGHT UI IS NOT THE SAME AS MODEL COMMENTARY
============================================================

Keep these concepts separate:

    INTERNAL REASONING
    HOST-NATIVE THOUGHT DISPLAY
    MODEL-AUTHORED USER-VISIBLE PROGRESS TEXT

SAIPEN owns the third category.

If a host independently renders its own Thought blocks and provides no supported
suppression mechanism:

    classify that host capability honestly
    do not pretend SAIPEN can hide it

But SAIPEN must still avoid adding another prose narration layer underneath it.

If a host supports disabling/collapsing intermediate model commentary safely,
use that capability.

Do not interfere with reasoning quality merely to make the UI visually quiet.

============================================================
7. TOOL-TOOL CONTINUATION
============================================================

Allow this execution shape:

    tool
    -> tool
    -> tool
    -> checkpoint
    -> tool
    -> test
    -> tool
    -> final response

without requiring an assistant prose message between actions.

The protocol must never force:

    tool
    -> "Now I will..."
    -> tool

as a lifecycle requirement.

Check current adapters/skills/prompts for instructions that accidentally demand
narrated progress.

Remove or override them at the canonical owner.

============================================================
8. AUTONOMOUS CONTINUATION
============================================================

Silence must increase autonomy, not decrease it.

When the agent reaches:

    SCOUT complete
    BUILD available

it should transition and continue.

When BUILD completes:

    VERIFY available
    -> continue

When VERIFY succeeds:

    REVIEW
    -> continue

No user-facing checkpoint message merely because the phase changed.

Phase transitions belong in STATE/LOG/runtime UI, not conversational prose.

============================================================
9. MACHINE STATUS REMAINS ALLOWED
============================================================

Machine-generated UI/status may expose compact facts such as:

    PHASE BUILD T-1572
    tests running
    92/98
    blocked
    waiting for foreign owner

This is not conversational narration.

Prefer machine status surfaces over model prose for progress visibility.

Where possible, adapters should update structured status instead of emitting
chat text.

============================================================
10. HEARTBEATS MUST NOT BECOME CHAT SPAM
============================================================

If a long-running executor needs heartbeat/progress evidence for watchdogs,
write it to:

- canonical runtime state;
- heartbeat/event channel;
- logs;
- structured host UI;

not to the user conversation.

A watchdog needing evidence is not authorization for prose.

============================================================
11. HOST CONTRACT
============================================================

For every adapter record whether it supports:

    silent_tool_continuation
    intermediate_text_suppression
    structured_progress
    host_thought_visibility_control
    final_response_gate

Do not claim a host feature that is unavailable.

Desired strongest host behavior:

    model reasoning/tool work
    -> no intermediate text emitted
    -> canonical final response gate
    -> one final response

============================================================
12. USER OVERRIDE
============================================================

Explicit user requests such as:

    "keep me updated"
    "show progress"
    "tell me after every phase"
    "explain what you're doing"

may temporarily authorize progress messages.

The authorization is scoped to that request/session as defined by the existing
contract.

Do not infer progress authorization from ordinary phrases like:

    "continue"
    "keep going"
    "finish it"
    "work on this"

Those mean continue WORK, not continue TALKING.

============================================================
13. REGRESSION MATRIX
============================================================

Add deterministic carriers.

A.
Runnable SCOUT work.
Agent emits:
    "I am reading the board now."
Expected:
    intermediate prose rejected/suppressed.

B.
SCOUT -> BUILD transition.
Agent emits:
    "SCOUT is complete. Starting BUILD."
Expected:
    rejected/suppressed; transition continues silently.

C.
Several tool calls succeed.
No user-visible text until final.
Expected:
    PASS.

D.
Real blocker requiring operator authority.
One compact blocker response.
Expected:
    PASS.

E.
User explicitly requests progress updates.
Bounded progress message.
Expected:
    PASS.

F.
User says only:
    "continue"
Expected:
    silent continuation, no narration authorization.

G.
Long-running task emits heartbeat into runtime/log only.
Expected:
    PASS.

H.
Long-running task emits heartbeat prose into conversation.
Expected:
    reject/suppress unless explicitly authorized.

I.
Final successful response after silent execution.
Expected:
    PASS through existing response/style gates.

J.
Detailed audit explicitly requested.
Authorized bounded DETAILS.
Expected:
    PASS.

K.
Host exposes native Thought UI outside SAIPEN control.
Expected:
    capability recorded honestly; SAIPEN adds no duplicate narration.

============================================================
14. ACCEPTANCE
============================================================

DONE only when:

1. Silent execution is the canonical default.
2. Runnable work produces no model-authored intermediate progress prose.
3. Tool-to-tool continuation requires no chat narration.
4. Phase changes require no chat narration.
5. Watchdog heartbeat does not use the conversation.
6. Real blockers still surface immediately and compactly.
7. Explicit user-requested progress remains possible.
8. Final report remains governed by response/style budgets.
9. Host-native Thought visibility is distinguished from SAIPEN-authored text.
10. Major supported adapters declare their actual silence capabilities.
11. Pre-fix narration carriers are RED and repaired behavior is GREEN.
12. Canonical validation is CURRENT_PASS.
13. Required full core returns new_red=0.

PRODUCT PRINCIPLE

    IF THE AGENT CAN CONTINUE WORKING:
        WORK.

    IF THE USER DOES NOT NEED TO ACT:
        STAY SILENT.

    WHEN THE WORK BOUNDARY IS COMPLETE:
        REPORT ONCE, COMPACTLY.
