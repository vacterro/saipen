# User request

priority: P1
verify: the requested change is present and demonstrated against the user own description of it

## Request

SAIPEN

APPEND TO CURRENT OPUS RUN

Record the following as a justified next/future implementation target.

Do NOT derail the currently active repair/lifecycle work to implement this immediately unless the current SAIPEN lifecycle naturally reaches a safe transition point.

TARGET

Unified provider/account-aware `saipen launch` system.

USER INTENT

The operator should be able to open a normal CMD/PowerShell/terminal in any project directory and launch the desired AI agent/account with a short command, without manually preparing environment variables, switching accounts, repairing PATH, selecting profiles, or remembering provider-specific invocation details.

Examples of intended UX:

saipen launch claude
saipen launch claude1
saipen launch claude2

saipen launch codex
saipen launch codex1
saipen launch codex2
saipen launch codex3

saipen launch ag1
saipen launch ag2
saipen launch ag3

Optional explicit form should also exist:

saipen launch claude --account 2
saipen launch codex --account 1
saipen launch antigravity --account 3

The current shell working directory MUST be the default working directory of the launched agent.

An explicit override may be supported:

saipen launch claude1 --cwd "C:\path\to\project"

Do not require --cwd for normal use.

DESIGN GOAL

Make SAIPEN the stable launch/orchestration surface while preserving the provider's native installation, authentication, account model and subscription model.

SAIPEN must not become a second incompatible authentication system.

Integrate with the existing SAITULS / SAI Account system where available, but do not break or replace the existing provider-native account/authentication flows.

ACCOUNT / PROVIDER DISCOVERY

Implement provider capability discovery.

For each supported provider/account, distinguish at minimum:

- provider installed
- executable discoverable
- account/profile configured
- authenticated
- identity known/unknown
- launchable
- connection/provider status
- managed integration available/unavailable
- native/direct launch available/unavailable
- plan/subscription known/unknown
- limits known/unknown

Subscription/plan detection MUST be best-effort.

Only report a concrete plan when the provider exposes trustworthy evidence through an official/local supported mechanism.

Do NOT infer a paid plan from filenames, cached labels, guessed account type, presence of an executable, or stale metadata.

If plan detection is unavailable:

plan = UNKNOWN

must remain a valid launchable state.

Unknown subscription information MUST NOT block an otherwise safe native launch.

AUTHENTICATION

Reuse existing authenticated provider sessions/accounts whenever possible.

Do not ask the user to log in again if a valid native authenticated session already exists.

Do not copy passwords.

Do not duplicate provider secrets into SAIPEN unless strictly required by an established secure account contract.

Do not expose tokens in logs, process arguments, diagnostics, STATE, BOARD or UI.

Prefer provider-native credential stores and existing SAI Account references.

SAITULS / SAI ACCOUNT INTEGRATION

The launcher should be able to consume existing SAI Account definitions such as:

AG1
AG2
AG3

CL1
CL2

CX1
CX2
CX3

or their future equivalents.

The exact human-facing names must not become hard-coded architecture.

Use stable account/provider identifiers underneath aliases.

SAITULS may remain the GUI management surface.

SAIPEN should provide the CLI launch/orchestration surface.

Both should use a compatible/shared account registry contract rather than maintaining divergent account truth.

WORKING DIRECTORY CONTRACT

Default:

launch directory = caller's current working directory.

Example:

C:\work\myproject> saipen launch cl1

must launch Claude account/profile CL1 with:

working directory = C:\work\myproject

unless an explicit override is supplied.

Do not silently replace it with:
- SAIPEN repository root;
- provider installation directory;
- account home directory;
- launcher script directory.

If a provider requires temporary bootstrap execution elsewhere, restore/preserve the intended project cwd for the actual agent process.

ENVIRONMENT CONTRACT

Build provider/account environment automatically.

Environment modifications MUST be scoped to the launched process tree by default.

Do NOT permanently mutate:
- machine environment;
- user environment;
- parent terminal environment;
- global PATH;

merely to launch an account.

Compose child environment from:

1. inherited safe caller environment;
2. provider adapter;
3. selected account/profile;
4. SAIPEN integration variables;
5. working-directory/project context.

Clearly separate:

provider-native environment
SAIPEN-managed integration environment
account-specific environment

Avoid hidden cross-account leakage.

Launching CL1 and then CL2 must not inherit CL1-specific credentials/state merely because CL1 launched first.

PROVIDER ADAPTER MODEL

Do not implement a giant provider-specific if/else pile in the CLI entrypoint.

Provide a stable adapter/registry contract approximately equivalent to:

provider id
aliases
binary discovery
version probe
authentication probe
account discovery
account identity
plan/limits probe
environment builder
native launch command
managed launch command
doctor
repair
capabilities

Existing T-1623/T-1624 Claude host integration should become one provider implementation of the generalized launch model rather than being duplicated.

FAIL-OPEN POLICY

Preserve the operator-access invariant established by the current Claude repair.

If the provider can physically launch safely, internal SAIPEN integration failure should normally degrade rather than deny operator access.

Conceptual states:

MANAGED_AVAILABLE
-> launch with full SAIPEN integration.

MANAGED_UNAVAILABLE_BUT_DIRECT_SAFE
-> launch provider natively/directly with a visible warning and degraded status.

DIRECT_UNSAFE
-> hard block with exact reason and recovery action.

Examples of conditions that should normally be degradable rather than fatal:

- SAIPEN provenance temporarily unverified;
- optional broker unavailable;
- limits probe unavailable;
- plan/subscription unknown;
- optional account metadata stale;
- optional managed hook unavailable.

Examples that may legitimately block a selected account:

- executable absent;
- selected account does not exist;
- authentication explicitly invalid and provider cannot launch unauthenticated;
- account environment is internally contradictory;
- launching would expose/cross-contaminate another account's secrets;
- provider-native launch itself is impossible.

Never convert:

"SAIPEN cannot fully verify this launch"

into:

"operator cannot use Claude/Codex/Antigravity"

when a safe direct/native route exists.

ALIASES

Support short ergonomic aliases without making aliases canonical identity.

Desired examples:

cl1 -> Claude account 1
cl2 -> Claude account 2

cx1 -> Codex account 1
cx2 -> Codex account 2
cx3 -> Codex account 3

ag1 -> Antigravity account 1
ag2 -> Antigravity account 2
ag3 -> Antigravity account 3

Also retain explicit provider names.

Alias resolution must be inspectable:

saipen launch --list
saipen account list

or equivalent.

The user should be able to see:

alias
provider
account
authentication
launchability
managed/direct status
identity
plan if known
limits if known

Do not expose secrets.

DEFAULT ACCOUNT

`saipen launch claude`

may select a configured default account if exactly one/default authority is available.

Do not silently choose between multiple equally valid accounts without an established default rule.

Provide a clear way to set/change default account.

Existing SAITULS account preference may be reused if it is already authoritative.

AUTO-DETECTION

On setup/doctor/refresh, discover existing installations instead of requiring the user to recreate them manually.

Potential discovery sources may include, where appropriate:

- PATH;
- known provider installation paths;
- provider-native CLI/version commands;
- provider-native account/auth status;
- existing SAI Account registry;
- existing SAITULS account definitions;
- existing SAIPEN host integration state.

Discovery must be read-only unless the user explicitly requests repair/import/setup.

Do not rewrite native provider config merely because it was discovered.

IMPORT

If native accounts/installations are discovered, allow safe adoption/import into the SAI Account registry without invalidating their current native use.

The intended result is:

native launch still works;
SAITULS launch works;
saipen launch works;

all referencing the same real provider/account rather than three incompatible copies.

DOCTOR / REPAIR

Generalize the current host doctor/repair direction.

Desired surfaces:

saipen launch --list
saipen host doctor
saipen account doctor

and an appropriate repair command.

Doctor should tell the operator things such as:

Claude:
  CL1
  installed: yes
  authenticated: yes
  identity: ...
  managed: ready
  direct: ready
  plan: known/unknown

Codex:
  CX1
  installed: yes
  authenticated: yes
  managed: unavailable
  direct: ready

Antigravity:
  AG3
  installed: yes
  authenticated: yes
  managed: ready

Exact UI is implementation-owned.

Do not invent information the provider cannot prove.

PROCESS / TERMINAL UX

Preserve normal provider console behaviour.

Interactive agents must receive a usable terminal.

Ctrl+C and normal termination should behave sensibly.

Exit code should propagate where appropriate.

Avoid orphan bootstrap/broker processes.

Avoid duplicate consoles unless the selected launch mode requires one.

A GUI/new-console option may exist, but normal CLI launch should feel native.

MULTI-ACCOUNT ISOLATION

This is mandatory.

Test sequential and concurrent launches of different accounts.

CL1 must not accidentally use CL2 identity.

CX1 must not inherit CX2 environment.

AG1 must not mutate AG2 persistent configuration merely by launching.

Where providers themselves have global-single-account limitations, represent that capability truthfully rather than pretending isolation exists.

Do not work around provider restrictions by destructive account switching behind the user's back.

SAFETY

Never log authentication tokens.

Never place secrets directly in command-line arguments when a safer provider-native mechanism exists.

Redact diagnostics.

Keep process-scoped environment isolated.

Do not automatically upload account information.

Do not publish account identities.

Do not modify Windows user/machine environment without an explicit separate operation.

Do not require Administrator rights for normal launches unless the provider itself genuinely requires them.

COMPATIBILITY

Preserve existing commands and existing Claude work.

The new abstraction must not regress:

saipen launch claude

or the T-1623/T-1624 host-authority/degraded-access guarantees.

Migration should be incremental.

Do not rewrite working Claude integration merely to make the abstraction aesthetically cleaner.

TEST MATRIX

At minimum cover:

1. provider installed + authenticated + managed available;
2. provider installed + authenticated + managed unavailable + direct safe;
3. provider installed + plan unknown;
4. provider installed + limits unknown;
5. provider absent;
6. selected account absent;
7. default account;
8. ambiguous account selection;
9. alias resolution;
10. caller cwd preservation;
11. explicit cwd override;
12. spaces/non-ASCII in cwd;
13. environment isolation between two accounts;
14. concurrent different-account launches;
15. broker unavailable;
16. provider executable moved;
17. stale discovered metadata;
18. native auth expired;
19. native provider still usable without SAIPEN;
20. SAITULS and SAIPEN resolve the same account identity.

Include real-process smoke coverage where safe and practical, not only mocked unit tests.

ACCEPTANCE

A user standing in an arbitrary project directory can execute a short command such as:

saipen launch cl1

and receive the intended Claude account in that project directory without manually preparing environment variables.

Equivalent supported accounts work for Codex and Antigravity.

Already installed/authenticated native provider accounts can be discovered/adopted without breaking their existing native configuration.

Unknown plan/subscription metadata does not prevent safe launch.

SAIPEN integration failure does not deny safe provider access when direct/native launch is possible.

Account-specific environment does not leak between launches.

SAITULS and SAIPEN share compatible account truth rather than diverging.

Existing provider-native launch remains usable.

NON_GOALS

- building a billing/subscription service;
- scraping provider web dashboards;
- bypassing provider authentication;
- bypassing subscription limits;
- fabricating plan information;
- automatically purchasing subscriptions;
- destructive account switching;
- storing plaintext credentials;
- replacing provider-native credential systems;
- forcing all providers into identical capabilities;
- blocking native access merely because optional SAIPEN integration is unavailable.

PRIORITY

Treat this as a bonus/future target after the current access-reliability/security work reaches a truthful lifecycle boundary.

It is strongly aligned with the current host-launch architecture and should preferably reuse/generalize that work rather than create a parallel launcher stack.
