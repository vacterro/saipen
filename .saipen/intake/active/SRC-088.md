## Request

SAIPEN (LIMISAW PROBLEM)

SAIHANDOFF

MISSION

Repair the SAIPEN protocol so an authoritative CURRENT_FAIL conformance state always has a finite, canonical, truthful remediation path when the underlying implementation defect is already fixed or the remaining state is historical/protocol bookkeeping.

This handoff supersedes previous continuation handoffs for this protocol-recovery problem.

Execute the milestones sequentially without asking for continuation between them.

After each milestone:

1. implement;
2. add executable regression coverage;
3. verify;
4. record evidence;
5. close or honestly block that milestone;
6. continue automatically to the next eligible milestone.

Stop only for a genuine hard stop:

* integrity/security P0;
* missing authority that cannot be represented safely;
* destructive migration risk without a reversible path;
* no eligible work remaining.

Do not weaken conformance validation merely to make projects green.

PRIMARY ACCEPTANCE FIXTURE

Use the current LIMISAW repository as a real external acceptance fixture:

V:___VAC__K__CODE_PY_LIMISAW

Current observed state:

* structural gate passes;
* authoritative conformance is CURRENT_FAIL;
* validate --gate core returns exit 1;
* approximately 25 reported problems;
* failures reduce to a small number of protocol root causes;
* LIMISAW product code is not the cause;
* router blocks saipen next / cc with CONFORMANCE_UNHEALTHY.

Known root classes:

A. work_closure_evidence requires current_tree_reverify, but no canonical CLI route exists.

B. stale/invalid ACTIVE source receipt such as SRC-007 cannot be canonically retired when it is neither valid work nor MISROUTED.

C. strict improve cycles can enter states where all useful evidence exists but no canonical cycle deactivation/finalization path exists.

D. locally reported defects that were implemented upstream cannot be truthfully closed because closure provenance assumes local patch ownership.

The protocol currently detects these states but lacks the commands required to repair them.

That is the defect class to eliminate.

GLOBAL INVARIANT

Every validator-produced actionable remediation must satisfy at least one of:

1. an implemented canonical CLI command exists that can perform the remediation safely;

2. the validator reports a stable external/manual dependency with an explicit reason why no local mutation is possible;

3. the state is historical/non-actionable and the validator does not block continuation on it.

The protocol must never emit an actionable instruction naming a command or remediation primitive that does not exist.

The protocol must never require fabricated local provenance for externally implemented fixes.

The protocol must never require historical evidence to be rewritten to achieve current conformance.

MILESTONE 1 — CANONICAL WORK REVERIFY CLI

PROBLEM

Validator remediation currently refers to current_tree_reverify / work reverify semantics.

The engine contains reverify logic, but the public protocol command surface does not expose a canonical operation.

This creates an impossible state:

validator requires remediation
but router/parser/registry cannot execute it.

TARGET

Add a first-class canonical work reverify operation.

Preferred command surface:

saipen work reverify <work-id>

or the nearest naming convention consistent with the existing CLI.

Do not implement a hidden special-case command used only by LIMISAW.

REQUIRED SEMANTICS

The operation must:

* resolve the target work item canonically;
* preserve original implementation provenance;
* preserve historical closure evidence;
* execute the current verification contract against the current tree/environment;
* write a new immutable reverification receipt/event;
* associate the receipt with the original work item;
* distinguish original closure evidence from current-tree verification evidence;
* never pretend the current tree was the original implementation tree;
* never rewrite historical LOG events;
* never rewrite old evidence blobs;
* be idempotent when the same current tree + verification contract has already been reverified successfully.

The reverify receipt should include at minimum:

* work id;
* verification contract identity;
* current project head/tree identity;
* result;
* timestamp/event identity;
* original implementation/provenance reference;
* verifier/oracle identity where available;
* evidence artifact references.

VALIDATOR INTEGRATION

If work_closure_evidence can be repaired by current-tree reverify, validator output must name the exact implemented canonical command.

No pseudocommand.

No Python-only internal function name.

No remediation text that the router cannot dispatch.

ROUTER INTEGRATION

When conformance is blocked only by work items eligible for canonical reverify, router remediation should lead toward the reverify operation rather than dead-ending at generic:

saipen validate

The router must still refuse unrelated product continuation until remediation succeeds.

REGRESSION

Create fixtures covering:

1. work with historical implementation evidence that remains directly valid;
2. work whose historical closure evidence no longer matches current-tree requirements but current-tree reverify passes;
3. current-tree reverify failure;
4. repeated identical reverify;
5. tree changes after a successful reverify;
6. missing verification contract;
7. external implementation provenance;
8. malformed work id;
9. verification command timeout/failure;
10. validator before and after successful reverify.

Acceptance:

* validator emits only executable remediation;
* successful reverify clears the corresponding current conformance defect;
* failed reverify does not mutate the work into a false green state.

MILESTONE 2 — EXTERNAL IMPLEMENTATION / INHERITED VERIFIED RETIREMENT

PROBLEM

A local project can report an engine/protocol defect.

The defect is then fixed upstream.

The local project can verify the installed upstream implementation.

However closure currently cannot represent:

reported locally
implemented upstream
verified locally
no local patch ownership

The resolver instead expects local implementation provenance or an in-repository DONE successor.

This leaves tickets such as T-73, and potentially T-66/T-67, permanently BLOCKED_EXTERNAL even after their defect is demonstrably fixed.

TARGET

Add a canonical closure semantic for externally implemented fixes.

Use a name consistent with the protocol architecture, for example:

external_resolution
inherited_verified
superseded_by_external_implementation

Do not encode the semantic only as free-form blocker text.

CANONICAL OPERATION

Provide a real CLI operation.

Example shape:

saipen ticket resolve-external <ticket> ...

Exact syntax is implementation-defined.

Required fields should include:

* local ticket id;
* upstream implementation authority;
* upstream work/ticket/commit/reference;
* local verification evidence;
* optional installed artifact/version identity;
* resolver reason.

The operation must not require:

* local patch ownership;
* a fake local commit;
* a fake DONE successor;
* rewriting the original report.

PROVENANCE MODEL

Closure provenance must explicitly distinguish:

LOCAL_IMPLEMENTATION

from:

EXTERNAL_IMPLEMENTATION_LOCAL_VERIFICATION

The latter is valid only when:

* local ticket represents the same defect contract;
* external implementation identity is recorded;
* the implementation is observable in the installed/current dependency;
* the local verification contract passes;
* no local implementation is claimed.

If the upstream repository is unavailable locally, a signed/immutable installed-engine identity plus verification evidence may be sufficient according to protocol policy.

Do not silently downgrade provenance requirements.

Represent the external authority explicitly.

REGRESSION

Cover:

1. local defect fixed by local patch;
2. local defect fixed upstream and verified locally;
3. claimed upstream fix but local verification fails;
4. missing upstream identity;
5. mismatching defect contract;
6. external fix disappears after dependency rollback;
7. duplicate external resolution;
8. external implementation with immutable verification evidence;
9. resolver attempts to claim own_patch for external work;
10. current LIMISAW-style T-73 scenario.

ACCEPTANCE FIXTURE

Re-evaluate the actual T-73 case.

If current installed T-1411 still satisfies its verification contract, the new protocol must be capable of truthfully terminalizing the local ticket without inventing LIMISAW implementation provenance.

Then independently evaluate T-66 and T-67.

Do not bulk-close them.

Each must satisfy its own original contract.

MILESTONE 3 — STALE SOURCE / RECEIPT RETIREMENT

PROBLEM

A source receipt can remain ACTIVE even though it is stale, empty, corrupt, superseded, or no longer actionable.

Current recovery supports only limited classes such as MISROUTED.

Cases such as the current SRC-007 state can therefore permanently poison conformance without a canonical tombstone/retirement path.

TARGET

Implement canonical source retirement for stale non-actionable source receipts.

Do not delete source history.

Do not physically erase immutable receipt evidence.

Use a tombstone/retirement state.

ELIGIBILITY

Retirement must be conservative.

A source may be retired only when the operation can prove an allowed reason such as:

* stale credential / digest identity that cannot represent current actionable work;
* empty source with zero actionable requirements;
* superseded source represented by a canonical successor;
* orphaned historical receipt with no reachable active requirements;
* protocol-generated source whose owning operation was canonically abandoned/superseded.

Do not permit retirement while unresolved actionable requirements exist unless a separate explicit migration/supersession transaction moves those requirements first.

SUPPORTED REASONS

Define stable machine-readable reasons rather than free-form prose.

At minimum evaluate support for:

STALE_CREDENTIAL
EMPTY_STALE_SOURCE
SUPERSEDED_SOURCE
ORPHANED_RECEIPT
MISROUTED_PROJECT_BINDING

Names may differ, but semantics must be explicit.

REQUIRED TRANSACTION

The operation must:

* verify source identity;
* inspect requirement count/state;
* verify successor/migration where applicable;
* write immutable retirement metadata;
* preserve original receipt bytes;
* remove the source from ACTIVE gating;
* preserve auditability;
* be idempotent.

If the source has unresolved actionable requirements, refuse with a precise reason and next command.

REGRESSION

Cover:

1. empty stale source;
2. source with VERIFIED-only requirements;
3. source with UNKNOWN requirement;
4. source with BLOCKED requirement;
5. source with successor;
6. corrupt digest but preserved original bytes;
7. orphan-recovery interaction;
8. repeated retirement;
9. wrong project binding;
10. current SRC-007 fixture.

VALIDATOR

After canonical retirement, validator must no longer report SOURCE_CORRUPTION / credential errors as current actionable blockers for that retired source.

Historical evidence may remain visible as historical metadata.

MILESTONE 4 — STRICT IMPROVE CYCLE FINITE EXIT

PROBLEM

A strict improve cycle may enter a state where:

* seats exist;
* some reports/dispositions are complete;
* stale COMPLETE evidence exists;
* abort refuses because dispositions exist;
* normal completion refuses because one seat cannot become current;
* the protocol has no canonical cycle-level terminalization path.

T-1411 added stale COMPLETE seat supersession, but the larger lifecycle can still remain ACTIVE indefinitely.

TARGET

Make every strict improve cycle finite.

A cycle must always have one valid canonical path to one of:

COMPLETE
SUPERSEDED
ABORTED
BLOCKED_EXTERNAL

depending on state.

No ACTIVE cycle may remain permanently undeactivatable after all remaining work has been explicitly resolved, superseded, retired or blocked.

SEAT-LEVEL SEMANTICS

Preserve T-1411 stale COMPLETE behavior.

Ensure seat retirement/supersession can:

* preserve original report bytes;
* attach a replacement seat where required;
* mark the stale seat as superseded;
* prevent the stale seat from blocking cycle completion.

CYCLE-LEVEL SEMANTICS

Add a canonical cycle finalization/reconciliation operation.

Possible shape:

saipen improve reconcile <cycle>

or equivalent.

It must inspect all registered seats and determine whether each is:

* completed current;
* superseded;
* canonically unavailable;
* externally blocked;
* still actionable.

If every seat is terminal under allowed semantics, the cycle may become terminal.

Do not use raw manifest edits.

SWEEP-TICKET LINKAGE

Validator currently reports sweep-ticket-link problems requiring fields such as recurrence/weak_model linkage that may have no canonical mutation operation.

Fix the model in one of two acceptable ways:

A. provide a canonical operation to add/reconcile the required linkage;

or

B. derive the linkage from existing authoritative records so manual mutation is unnecessary.

Do not leave validator-required mutable fields without a writer.

5. cycle abort before dispositions;
