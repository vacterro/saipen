## Request

SAIPEN

APPEND — MANAGED WINDOWS ACCOUNT RUNTIME ACCESS / CROSS-USER BOOTSTRAP

Record a second concrete bootstrap defect observed on a real managed Antigravity Windows account.

This is related to the zero-hunt bootstrap target but is NOT the same defect.

INCIDENT

A managed Windows account was launched through the existing SAI Accounts path:

antigravity_b

The agent could read the target project and its `.saipen/STATE.md`.

STATE exposed the current canonical lifecycle:

phase: DONE
next Work: T-287
saipen_version: 7
schema_version: 3

However the agent could not execute SAIPEN.

Observed state:

- `saipen` command: not found;
- the project-declared SAIPEN home points into the operator's private Windows profile;
- the managed account cannot read:

  C:\Users\vac34\.agents\skills\saipen\BOOT.md

  and the canonical SAIPEN repository/runtime under the operator account;

- access is denied by the intended Windows account isolation;
- the agent correctly refused to mutate BOARD/LOG/STATE manually without BOOT/runtime authority;
- the agent attempted to clone the public repository into its own accessible workspace;
- the public repository layout/version did not match the exact runtime/schema required by the managed project;
- the agent then asked the operator to:
  1. grant cross-user access,
  2. provide another SAIPEN copy,
  3. or bypass SAIPEN and edit Work directly.

None of these should be required during normal operation.

ROOT DEFECT

A SAIPEN-managed project is portable across agent/provider contexts only while those contexts happen to share filesystem access to the original operator's private runtime installation.

That violates the intended managed-account isolation model.

A project may be readable and executable by a managed Windows account while its canonical SAIPEN runtime is inaccessible because:

`STATE.saipen_home`

contains an operator-private absolute path.

This turns valid security isolation into loss of protocol control.

The system must not require granting one managed Windows user broad read access to another user's private profile merely to execute SAIPEN.

SECURITY INVARIANT

Preserve Windows account isolation.

Do NOT solve this by granting:

antigravity_b

or another managed execution account broad read access to:

C:\Users\vac34

C:\Users\vac34\.agents

the operator's complete development tree

or unrelated private configuration.

SAIPEN runtime access must be deliberately provisioned through a least-privilege shared/runtime boundary.

DESIGN GOAL

Any managed Windows account created/adopted by SAI Accounts that is allowed to execute work in a SAIPEN-managed project must have a deterministic compatible way to execute the exact SAIPEN runtime required by that project.

The normal path must require:

zero manual ACL work;
zero public-repository cloning;
zero guessed runtime paths;
zero protocol bypass;
zero operator question.

ACCOUNT-INDEPENDENT RUNTIME SURFACE

Introduce or formalize an account-independent canonical runtime surface.

Prefer one of these architectures, based on the existing control plane:

A. MACHINE-SCOPED READ-ONLY RUNTIME

Example conceptual location:

C:\ProgramData\SAI\SAIPEN\...

or another existing trusted machine-wide SAI runtime root.

Managed accounts receive only the minimum read/execute rights required for the runtime.

The operator's source repository remains private.

OR:

B. CONTROL-PLANE/BROKER EXECUTION

A small account-accessible launcher delegates SAIPEN execution to the trusted SAI control plane/broker, which owns the canonical runtime.

The managed account never requires direct access to the operator's runtime tree.

OR:

C. VERSIONED PER-ACCOUNT RUNTIME PROJECTION

SAI Accounts provisions a verified, read-only compatible runtime into each managed Windows account.

The runtime identity/version is derived from canonical machine authority, not from public Git HEAD.

Choose the architecture that best fits the existing SAI Accounts / SAIPEN runtime system.

Do not create several competing runtime truths.

PROGRAMDATA OPPORTUNITY

The managed account is already launched through infrastructure under:

C:\ProgramData\SAI\Accounts\bin\...

Evaluate whether the existing ProgramData SAI control-plane boundary should become the stable machine-level bootstrap surface for SAIPEN as well.

Do not assume this exact layout if another existing authority already owns machine runtime distribution.

The requirement is architectural:

a managed account must receive a trusted launcher without depending on another user's profile.

LAUNCHER AVAILABILITY

Every managed execution account that can be selected by SAI Accounts should automatically receive a usable SAIPEN entrypoint when SAIPEN integration is enabled.

The entrypoint may be:

`saipen`

or a deterministic internal shim used by the agent bootstrap.

Normal execution must not depend on the managed account inheriting the operator's PATH.

Provisioning should occur as part of:

- managed account creation;
- account adoption;
- SAIPEN integration enablement;
- runtime upgrade/repair.

Do not require users to manually edit PATH.

PATH may be one presentation mechanism, but it must not be the only recovery mechanism.

EXACT RUNTIME COMPATIBILITY

Never repair this situation by cloning arbitrary current public SAIPEN source.

A managed project may require an exact compatible runtime generation.

Bootstrap must mechanically determine compatibility using the project's existing protocol/runtime metadata.

At minimum consider:

- saipen_version;
- schema_version;
- runtime provenance;
- installed runtime identity;
- protocol compatibility;
- project registration metadata.

If exact runtime bytes are required, resolve them from trusted local/machine authority.

Do not silently substitute latest GitHub HEAD.

PUBLIC REPOSITORY IS NOT RUNTIME AUTHORITY

Pin explicitly:

The public repository is a source/distribution origin, not an automatic runtime replacement for a managed project's active canonical installation.

An agent must not clone public HEAD and assume it is compatible merely because the project says "SAIPEN".

If runtime recovery requires fetching/installing a version, use a versioned/provenance-checked installation path.

No opportunistic Git clone during ordinary continuation.

PROJECT PORTABILITY

A project-local absolute path to one human Windows profile must not be the sole means of finding protocol authority.

`saipen_home` may remain useful diagnostics/provenance, but managed cross-account continuation requires a relocatable authority mechanism.

Consider storing/resolving:

- runtime generation/id;
- protocol version;
- machine runtime registration id;
- canonical control-plane endpoint;
- project-to-runtime binding.

Then the current account can resolve the proper runtime through machine authority.

Do not blindly rewrite historical STATE paths without migration/version semantics.

BACKWARD COMPATIBILITY

Existing projects currently containing an operator-private absolute `saipen_home` must continue working.

On a managed-account launch:

1. detect that the declared path exists conceptually but is inaccessible to the current account;
2. do not interpret ACCESS_DENIED as runtime corruption;
3. resolve the same canonical runtime through the machine/account-independent authority;
4. verify compatibility/provenance;
5. continue the exact project Work.

If no compatible runtime exists, return a precise provisioning diagnostic.

Do not ask the agent to guess another path.

SAI ACCOUNTS INTEGRATION

Extend the SAI Accounts contract so account readiness can distinguish:

provider_ready
project_access_ready
saipen_runtime_ready

or equivalent capabilities.

An account marked READY for autonomous SAIPEN execution should not later discover after launch that it cannot access the protocol runtime.

Either:

- provision the runtime before reporting SAIPEN-ready;

or:

- represent SAIPEN runtime capability separately and repair automatically on first use.

Do not incorrectly mark an account fully integration-ready while the protocol executable is unreachable.

ACCOUNT CREATION / REPAIR

When a managed Windows account is created or repaired, verify:

1. SAI Accounts launcher access;
2. provider executable/authentication access;
3. target project filesystem access when configured;
4. SAIPEN bootstrap availability;
5. exact runtime compatibility;
6. BOOT/control-plane accessibility;
7. child-process environment;
8. no dependency on another user's private profile.

Provide a canonical repair operation through the existing account/control-plane management surface.

Do not instruct the user to run manual ACL commands for ordinary repair.

LEAST PRIVILEGE

If machine-scoped runtime files are used:

- read/execute only where possible;
- no write permission to canonical runtime for managed model accounts;
- no access to unrelated operator repositories;
- no access to unrelated user secrets;
- runtime updates performed only by the trusted updater/control plane;
- preserve existing account SID isolation.

A compromised model account must not gain broader operator-profile visibility merely because SAIPEN integration is installed.

PROJECT WRITES

The managed account may continue to write to the target project only according to the existing project access policy.

Runtime read access and project write access are separate capabilities.

Do not conflate them.

BOOT / SKILL ACCESS

The agent reported inability to read:

`.agents\skills\saipen\BOOT.md`

If BOOT/SKILL material is required for execution, it must be part of the same canonical account-accessible runtime projection or obtainable through the control plane.

Do not make a private per-user skill installation a mandatory hidden dependency for machine-managed accounts.

There must be one canonical copy/representation for the runtime generation used by the project.
