DESIRED OUTCOME

The local SAIPEN operator grants standing permission to use the available SAIFREN, SAIRoute, and 9router infrastructure for safe, bounded, auxiliary verification without requesting fresh approval for every routine test.

The permission remains in effect for this operator installation until explicitly revoked.

This is an optional local capability, not a dependency of SAIPEN Core and not a universal permission granted by the protocol to all users.

IMPLEMENTATION

1. Inspect the existing configuration, operator-policy and runtime capability mechanisms.

2. Reuse the closest existing local extension point. Do not build a parallel authorization subsystem.

3. Store this operator's permission in installation-local configuration, separate from portable project protocol rules and release defaults.

4. Support capability discovery at execution time. Do not assume that a historically observed endpoint or model still exists.

5. Permit autonomous, bounded use for:
   - independent hypothesis checking;
   - disputed regression reproduction;
   - secondary code and protocol review;
   - weak-model robustness testing;
   - adversarial negative controls;
   - controlled model comparison;
   - isolated field testing;
   - evidence cross-checking.

6. Prefer the existing tools and provider routing. Avoid duplicating SAIFREN, SAIRoute or 9router functionality inside SAIPEN.

7. Do not change provider configurations or consume unrelated live session ownership.

8. Apply normal ticket ownership, resource limits, concurrency constraints and cancellation behavior to auxiliary verification jobs.

9. Perform potentially destructive tests only in verified disposable workspaces, with explicit target isolation and cleanup.

10. Never forward credentials, private data, unrestricted workspace contents or sensitive operator evidence to third-party models without separate authorization.

11. Record useful verification metadata:
    - provider and model identity;
    - test purpose;
    - execution boundary;
    - relevant input provenance;
    - result and contradictory findings;
    - whether the observation was reproduced independently.

12. Auxiliary model agreement cannot substitute for executable tests, canonical evidence or human-required acceptance.

13. Distinguish provider unavailability from test failure.

14. If the optional pool is unavailable, exhausted or unreliable, continue the primary verification workflow whenever its required acceptance does not specifically depend on that pool.

15. Avoid unlimited retries, excessive polling and recursive agent spawning.

16. Provide an explicit local kill switch or revocation mechanism.

17. Preserve existing user-facing controls and ownership rules.

ACCEPTANCE

A. With the optional pool available, a test agent can run an authorized auxiliary verification without another operator prompt.

B. With the pool disabled or unavailable, ordinary SAIPEN operations retain their existing behavior.

C. A malicious or incorrect auxiliary model response cannot mark a ticket PASS or DONE by itself.

D. Concurrent verification does not overwrite canonical state or take ownership of another active task.

E. Authorization remains local to this installation and is not exported as a default policy in public SAIPEN distributions.

F. A revoked permission prevents subsequent auxiliary launches.

G. A live, bounded end-to-end test confirms that the actual configured route works, not merely that mocked routing tests pass.

H. No new core dependency, required external server or unnecessary WAIT gate is introduced.

STOP CONDITIONS

Stop and report if safe auxiliary execution requires modifying unrelated provider projects, bypassing existing ownership controls or exposing secrets.

Do not silently replace the existing working routing mechanism.
