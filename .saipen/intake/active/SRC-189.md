## Request

SAIPEN

APPEND — EXECUTOR CAPABILITY ADMISSION / NO-DEAD-ON-ARRIVAL HANDOFF

Record a protocol/control-plane defect from a real agent run.

INCIDENT

An implementation agent received a continuation task for a SAIPEN-managed C# project.

Its first reasoning was correct:

- project contains `.saipen/`;
- continuation should begin with `saipen continue --json`;
- the task requires code inspection/modification;
- build/test execution is required.

However the executor exposed only:

- read_tabular
- system_todo_write

No shell.
No filesystem/code editing.
No process execution.
No SAIPEN CLI execution.
No compiler/test runner.

The agent therefore terminated after approximately 14 seconds and reported that it could not execute the task.

This is not primarily an agent-quality defect.

The executor should never have been admitted to this Work.

ROOT CAUSE

SAIPEN currently allows Work to be handed to an executor/model session before proving that the session has the minimum capabilities required by:

- the current phase;
- the current ticket;
- the repository/project type;
- the required validation path.

The result is a DEAD-ON-ARRIVAL handoff:

Work is assigned,
context is consumed,
the model reasons correctly,
then discovers that it cannot perform even the first canonical operation.

This wastes:
- model quota;
- wall-clock time;
- context window;
- operator attention;
- autonomous-run continuity.

GENERAL RULE

Before handing executable Work to an agent, SAIPEN must mechanically prove:

EXECUTOR_CAPABILITIES ⊇ REQUIRED_CAPABILITIES

If not:

DO NOT HAND OFF THE WORK TO THAT EXECUTOR.

Use failover/reselection before the task reaches the model.

CAPABILITY ADMISSION MUST HAPPEN BEFORE MODEL WORK

Do not rely on the model to discover missing tools after receiving the handoff.

The admission layer should classify the executor first.

At minimum model/executor capability inventory should distinguish:

- shell/process execution
- filesystem read
- filesystem write
- code editing / patch application
- recursive repository inspection
- Git read
- Git write
- compiler/build execution
- test execution
- Windows-native process execution when required
- GUI/computer-use capability when required
- browser/web capability when required
- SAIPEN control-plane invocation capability
- file upload/download/materialization if required
- image/visual inspection when acceptance needs it

Exact names are implementation-owned.

PHASE REQUIREMENTS

Define canonical minimum capability requirements by SAIPEN phase.

Example intent:

SCOUT
requires:
- repository/file read
- current Work/context access
- canonical SAIPEN continuation/control access

BUILD
requires:
- repository read
- repository write/edit
- execution/shell when implementation verification requires it

VERIFY
requires:
- test/build/process execution appropriate to project
- repository read
- exact evidence production

REVIEW
requires:
- repository read
- validation/evidence access
- execution where review contract requires dynamic checks

SHIP
requires:
- canonical SAIPEN control access
- required validation/evidence access
- release actions only when explicitly authorized

Do not hard-code only these examples if repository contracts already define richer requirements.

TICKET-SPECIFIC REQUIREMENTS

Phase capability is only the minimum.

A ticket may require additional capabilities.

Examples:

C# source modification:
- filesystem write
- C# build execution
- test execution

Windows ACL/runtime repair:
- Windows-native execution
- appropriate privileged broker/helper route

GUI acceptance:
- GUI/computer-use capability or an explicit operator acceptance boundary

Browser integration:
- browser interaction or supported host automation

Image/layout defect:
- visual inspection capability

Derive required capabilities from:
- phase contract;
- project manifest/runtime knowledge;
- ticket metadata;
- validation contract;
- explicit Work requirements.

Do not ask the model to infer whether it has enough tools after admission.

SAIPEN CONTROL-PLANE ACCESS IS SPECIAL

An active SAIPEN operational run should require a canonical route to:

`saipen continue --json`

or an equivalent trusted control-plane API.

If the agent cannot execute the SAIPEN CLI directly but another trusted control-plane transport is available, that alternative is acceptable.

If no canonical control-plane route exists:

the executor is incompatible with autonomous SAIPEN Work.

Do not admit it and then tell the model to "work manually".

NO PROTOCOL BYPASS

When an executor lacks required capabilities, the model must not compensate by:

- editing BOARD manually;
- editing STATE manually;
- fabricating LOG events;
- implementing code without tests when tests are required;
- reporting completion from static reasoning only;
- bypassing SAIPEN lifecycle;
- asking the operator to reinterpret the Work as a documentation-only task.

The correct action is executor failover.

FAILOVER CONTRACT

If the selected executor is incompatible:

1. reject the executor before Work handoff;
2. preserve current ticket, phase, execution_intent and Work ownership;
3. select the next compatible executor from the configured pool;
4. hand off the same canonical Work;
5. continue automatically.

Do not increment autonomous handback/retry counters as though the Work itself failed.

This is executor admission failure, not project execution failure.

BOUNDED FAILOVER

Failover must be bounded and deterministic.

Avoid infinite provider/model rotation.

Track attempted executors and rejection reasons.

If at least one compatible executor exists:
- continue automatically.

If no compatible executor exists:
- produce one canonical blocker describing the missing capability class.

Example:

NO_COMPATIBLE_EXECUTOR
required:
  shell
  filesystem_write
  csharp_build
available_pool:
  freebuff-1: read_only
  tabular-agent: read_only

Do not present a vague "agent cannot do this" message.

DO NOT ASK THE OPERATOR TOO EARLY

A missing tool on one executor is not automatically WAIT_USER.

Before involving the operator:

- try compatible configured executors;
- try declared provider failover;
- try available local/native execution path;
- try canonical broker/control-plane execution path.

WAIT_USER is justified only when the configured system genuinely has no compatible execution route or a human-owned authorization is required.

HANDOFF GENERATION

Do not generate/send a large implementation handoff to an executor until executor admission succeeds.

This is important for context efficiency.

Preferred sequence:

resolve Work
-> derive required capabilities
-> inspect candidate executor capabilities
-> admit compatible executor
-> generate/attach phase-specific context
-> execute

Not:

generate giant handoff
-> send it
-> model discovers no shell
-> abort after 14 seconds.

CAPABILITY CONTRACT MUST BE MACHINE-READABLE

Do not encode this only in prose instructions.

Introduce a canonical machine-readable capability contract.

Conceptually:

required_capabilities:
  - repo_read
  - repo_write
  - process_exec
  - saipen_control
  - csharp_build
  - test_exec

executor_capabilities:
  - repo_read
  - tabular_read

admission:
  compatible: false
  missing:
    - repo_write
    - process_exec
    - saipen_control
    - csharp_build
    - test_exec

Exact schema is implementation-owned.

HOST / MODEL CAPABILITY DISCOVERY

Capability inventory must reflect the actual current session, not assumptions about a model brand.

Do not assume:

"FreeBuff can code"

therefore:

"this FreeBuff session has shell/edit tools."

The same model/provider may run in:
- read-only environment;
- browser-only environment;
- full coding environment;
- restricted plugin context;
- different host applications.

Admission must use the tools/capabilities actually exposed to the current session.

RUNTIME DRIFT

Capabilities may change between sessions or after provider/runtime updates.

Do not persist them forever as static model metadata.

Cache only with appropriate freshness/version identity.

Re-probe when:
- host changes;
- provider changes;
- session changes materially;
- tool manifest changes;
- runtime version changes.

Create a regression reproducing the incident.

Fixture:

Project:
- SAIPEN managed
- C# repository
- active executable ticket
- phase BUILD
- validation requires compilation/tests

Executor exposes only:
- read_tabular
- system_todo_write

No:
- shell
- file editing
- process execution
- SAIPEN control route

Expected:

1. executor is rejected BEFORE implementation handoff;
2. no model implementation turn is started on that executor;
3. current Work remains unchanged;
4. execution_intent remains intact;
5. no BOARD/STATE/LOG lifecycle mutation is fabricated;
6. compatible executor failover is attempted automatically;
7. if compatible executor exists, Work continues there;
8. operator receives no question;
9. no quota/context is intentionally spent on a doomed implementation handoff beyond bounded admission/probe cost.

INVERSE CONTROL

Fixture:

same ticket,
executor exposes:

- repository read/write
- shell/process execution
- SAIPEN control route
- C# build
- test execution

Expected:

executor is admitted and receives Work.

PARTIAL CAPABILITY CONTROL

Fixture:

executor has:
- read/write
- shell
- SAIPEN CLI

but does not have:
- required Windows GUI/computer-use acceptance capability

If the current phase only requires implementation and automated tests:
- admit it.

If the current acceptance step specifically requires real GUI interaction:
- either route that acceptance step to a capable executor/operator boundary,
  or split the Work according to canonical lifecycle.

Do not reject an executor for capabilities that the current step does not actually require.

READ-ONLY TASK CONTROL

A documentation/read-only audit task should remain runnable on a read-only executor if its validation contract does not require writes or execution.

Do not over-constrain admission.

CAPABILITY ESCALATION DURING WORK

If new evidence changes the required capability set during execution:

example:
SCOUT reveals that BUILD requires a Windows-native acceptance step.

Then:

1. update canonical required capabilities;
2. finish the current safe step;
3. fail over at the phase/work boundary;
4. preserve accumulated evidence/context.

Do not force the current incompatible executor to improvise around missing tools.

RELATION TO T-1619 / AUTONOMOUS HANDBACK

This incident is closely related to the existing autonomous handback problem.

A model saying:

"I cannot continue because I lack shell/edit tools"

is legitimate for that executor.

But the SYSTEM response should not be final handback if another compatible executor exists.

Executor incompatibility must feed the same autonomous continuation machinery:

INCOMPATIBLE_EXECUTOR
-> failover
-> continue Work

not:

INCOMPATIBLE_EXECUTOR
-> model final response
-> operator intervention.

RELATION TO QUESTION-GATE WORK

An incompatible executor must not ask:

"What should I do instead?"

or offer:
- documentation-only mode;
- manual edits;
- skip tests;
- bypass protocol.

Those are not operator decisions when compatible failover remains possible.

RELATION TO `saipen launch`

The future unified launcher/account system should expose executor capability information where relevant.

Launching a provider/account and assigning autonomous Work are related but distinct:

provider/account may be authenticated and launchable,
while the resulting session may still lack required development tools.

Do not equate:
ACCOUNT READY

with:
EXECUTOR CAPABLE FOR THIS WORK.

OBSERVABILITY

Expose a compact diagnostic for executor admission.

Example conceptual output:

executor:
  host: freebuff
  session: ...
  capabilities:
    repo_read: true
    repo_write: false
    shell: false
    saipen_control: false
    build: false
    test: false

work:
  ticket: T-XXXX
  phase: BUILD
  requires:
    repo_read
    repo_write
    shell
    saipen_control
    csharp_build
    test_exec

admission:
  result: REJECT
  missing:
    repo_write
    shell
    saipen_control
    csharp_build
    test_exec
  next:
    FAILOVER

Exact presentation is implementation-owned.

PERFORMANCE

Capability admission must be cheap.

Do not run a full environment audit before every tiny continuation.

Prefer:
- host tool manifest;
- cached session capability fingerprint;
- bounded lightweight probes;
- project requirement metadata.

Expensive real-process probes only when uncertainty matters.

SECURITY

Do not grant missing capabilities automatically by weakening sandbox/security policy.

Do not enable arbitrary shell merely because Work requires it.

Select a pre-authorized compatible executor instead.

Privilege/capability escalation remains policy-controlled.

Do not confuse:
"required capability"

with:
"permission to grant capability."

NON_GOALS

- forcing every executor to have every tool;
- disabling read-only agents;
- bypassing provider sandbox restrictions;
- granting shell/admin rights automatically;
- making model self-reported capability authoritative;
- allowing untested implementation when validation requires tests;
- turning every capability mismatch into WAIT_USER;
- provider-specific string matching.

SUCCESS CONDITION

No implementation agent should receive Work that it is mechanically incapable of executing.

For this exact incident, the expected behavior is:

Work requires code edit + shell + build/test + SAIPEN control
-> current executor exposes only read_tabular + todo
-> executor rejected immediately
-> compatible executor selected automatically
-> same Work continues

not:

handoff delivered
-> 14 seconds of reasoning
-> "I have no tools"
-> autonomous run dies.
