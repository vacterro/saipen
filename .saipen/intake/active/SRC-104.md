## Request

SAIPEN

SAIHANDOFF — PROTOCOLIST: ROBUST HANDOFF INGESTION, APPEND RECONCILIATION, AND MID-MISSION CONTINUATION

EXECUTOR

Claude Opus 5 Max

RECOMMENDED EFFORT

Max

ROLE

You are the SAIPEN protocol implementation agent.

Implement protocol-level support for receiving operational handoffs, handoff fragments, appended requirement files, replacement handoffs, and large multi-milestone handoffs at arbitrary points in an already-running project mission.

The protocol must treat operational handoff material as executable mission input, not merely documentation to summarize.

PRIMARY FAILURE TO ELIMINATE

A user may provide a file such as:

GENERALIZED RECOVERABLE SAIPEN_20260922_1835.md

containing explicit implementation requirements.

A current agent may read it and respond with a summary such as:

"This file outlines a failure recovery policy..."

That behavior is incorrect when the file was supplied as an operational handoff or mission append.

The required behavior is:

READ
-> CLASSIFY
-> RECONCILE
-> PROJECT INTO CURRENT MISSION
-> EXECUTE

Do not stop at summarization.

CORE PRINCIPLE

Operational handoff material is mission state.

Its transport mechanism is irrelevant.

Equivalent operational inputs may arrive as:

- pasted text in chat;
- attached .md file;
- attached .txt file;
- a standalone SAIHANDOFF;
- an append fragment;
- a large multi-milestone handoff;
- a handoff created immediately before /new;
- a continuation handoff created after interrupting an agent;
- several small handoff "bricks" delivered over time;
- one replacement mega-handoff;
- an external auditor or protocolist handoff;
- a file containing only one additional invariant;
- a user message explicitly saying that the attached text should be taken into account and executed.

SAIPEN must normalize all of these into the active mission model.

Do not require one preferred physical format.

MISSION INPUT CLASSIFICATION

Every incoming operational handoff must be classified semantically into one of the following categories.

1. APPEND

The new material adds requirements, invariants, acceptance conditions, milestones, tests, constraints, or implementation details to the current mission.

Effect:

- preserve already-valid current mission state;
- add the new requirements;
- reconcile them against current work;
- continue from the current truthful execution point.

Do not restart completed work unless the append invalidates it.

2. SUPERSEDE

The new handoff explicitly replaces prior continuation instructions for the same mission.

Effect:

- preserve durable implementation evidence and completed work;
- replace obsolete planning/instruction layers;
- retain still-valid requirements that are explicitly preserved or structurally required;
- continue from current machine truth under the new controlling handoff.

Do not rewind implementation merely because instructions were replaced.

3. NEW MISSION

The new material clearly targets a different project, source request, or unrelated objective.

Effect:

- route through normal new-source/new-work intake.

Do not silently merge unrelated missions.

4. CLARIFICATION

The new material explains an existing requirement without adding a distinct deliverable.

Effect:

- update interpretation of the existing requirement;
- preserve the same work identity where possible.

5. CONFLICTING UPDATE

The new material contradicts an earlier active requirement.

Effect:

- prefer the newest explicit user instruction;
- record which prior requirement is superseded;
- reconcile affected work;
- invalidate only evidence that genuinely depends on the obsolete rule.

Do not preserve contradictory requirements simultaneously.

CLASSIFICATION MUST BE SEMANTIC

Do not infer operational importance only from filenames or formatting.

A file does not need to contain the literal word:

SAIHANDOFF

to be operational.

A short file containing:

"Recoverable SAIPEN binding failures must fall back to direct OpenCode launch"

may be just as authoritative as a 2,000-line handoff.

Use conversation intent, explicit user language, file content, and current mission context.

Examples of strong operational signals:

- "add this";
- "append this";
- "update current handoff";
- "take this into account";
- "execute this";
- "this is the new requirement";
- "continue with this";
- "use this in /new";
- "here is the handoff";
- "this supersedes the previous handoff";
- attached operational requirements immediately after a project discussion.

Do not reduce such input to a prose summary.

ARBITRARY CURRENT STATE

Incoming handoff material must be accepted in any normal SAIPEN phase.

Examples:

- DONE with queued source work;
- SCOUT;
- BUILD;
- VERIFY;
- REVIEW;
- SHIP;
- BLOCKED;
- recovery state;
- interrupted cold-recovery state;
- source already ACTIVE;
- task already CLAIMED;
- task already partially implemented;
- project reopened through /new.

The protocol must not require the operator to manually reset the project to a special phase before adding requirements.

STATE RECONCILIATION

When new operational material arrives:

1. inspect current STATE, BOARD, source receipts, active contract, coverage, and relevant recent LOG;
2. identify the active mission;
3. classify the incoming material;
4. derive new requirements or update existing requirements;
5. map them to current Work;
6. preserve completed evidence that remains valid;
7. reopen or extend Work only when the new requirement actually invalidates prior acceptance;
8. select the earliest truthful execution phase required by the delta;
9. continue automatically.

Examples:

If BUILD is active and the append adds one implementation requirement:
- remain in BUILD;
- add/project requirement;
- execute it.

If VERIFY is active but the append adds new product behavior:
- return the affected Work to BUILD through a canonical transition;
- implement;
- verify again.

If DONE is active but an append adds new actionable work:
- create/project the new Work;
- start it canonically;
- do not reject the append because the prior task was DONE.

If BLOCKED contains one external blocker but the new append describes independent eligible work:
- preserve the blocker;
- execute the independent work.

NO HANDOFF-BECAUSE-HANDOFF BLOCKER

Never block merely because:

- a handoff arrived late;
- a handoff arrived during BUILD;
- a handoff is larger than the current ticket;
- the current ticket was created before the handoff;
- requirements are contained in a separate file;
- the handoff was generated by another model;
- the previous agent was interrupted;
- the user used /new;
- the handoff contains several milestones;
- the handoff overlaps existing work;
- some of the handoff has already been implemented.

These are reconciliation problems, not operator blockers.

HANDOFF BRICKS

Support incremental "handoff bricks".

A handoff brick is a small operational fragment that modifies the active mission.

Examples:

- one new invariant;
- one UX requirement;
- one discovered regression;
- one acceptance test;
- one fallback rule;
- one newly observed failure;
- one architectural constraint.

Multiple bricks received across time must accumulate into the mission unless explicitly superseded.

Do not require every brick to become an independent top-level ticket.

Instead:

- attach it to the correct active source/mission;
- derive traceable requirement coverage;
- map it to the relevant Work;
- execute at the correct phase.

Avoid ticket explosion.

MEGA HANDOFFS

Also support large handoffs that contain many milestones and hours of work.

Do not artificially split a large coherent handoff merely because it is large.

A mega handoff may define:

- mission objective;
- many milestones;
- dependency order;
- invariants;
- validation gates;
- closure semantics;
- recovery behavior.

The protocol should project the handoff into traceable requirements and Work while preserving the handoff's orchestration intent.

The implementation agent must be able to work sequentially for hours without asking the operator after each milestone.

SMALL BRICKS AND MEGA HANDOFFS ARE EQUIVALENT INPUT FORMS

The protocol must support both extremes:

A:
10 small append files delivered over several hours.

B:
1 consolidated handoff containing the same requirements.

After reconciliation, both should produce functionally equivalent mission state.

Do not make project behavior depend on how the user grouped the instructions.

INTERRUPT AND /NEW CONTINUITY

The user may deliberately interrupt an active implementation session and immediately start a new conversation using /new.

This is normal operation.

The handoff produced before interruption must be sufficient to resume from cold state.

A new session receiving that handoff must:

1. orient to current project machine truth;
2. read the supplied handoff;
3. reconcile handoff claims with actual STATE/BOARD/LOG/source state;
4. discard stale planning assumptions;
5. preserve valid requirements;
6. continue from the actual execution point.

The new session must not require the previous conversation history when the handoff plus repository state provide enough evidence.

The handoff is not trusted as machine truth when it conflicts with repository state.

Use:

repository/protocol state = execution truth
handoff = mission intent and continuation context

Reconcile both.

OPERATIONAL FILE INGESTION

When an attached or referenced file is identified as operational handoff material:

Do not return merely:

- a summary;
- a description of what it contains;
- a list of its topics;
- "I have read the file."

Instead:

1. parse normative requirements;
2. identify MUST / MUST NOT / acceptance / tests / constraints;
3. derive mission requirements;
4. bind them to the current source/work;
5. record provenance to the input artifact where supported;
6. execute or schedule the resulting work immediately.

A summary may be produced as secondary evidence, but it is never the terminal action when actionable requirements exist.

GENERALIZED RECOVERABLE SAIPEN EXAMPLE

Given an operational append that states:

- the SAIPEN launch layer may fail while direct OpenCode launch still works;
- direct launch is safe when project root, executable, identity, and process safety can still be established;
- classify:
  - MANAGED_AVAILABLE
  - MANAGED_UNAVAILABLE_BUT_DIRECT_SAFE
  - DIRECT_LAUNCH_UNSAFE_OR_IMPOSSIBLE
- avoid fragile error-code allowlists;
- classify semantically from safety preconditions;

the correct agent behavior is:

- recognize this as an architectural requirement;
- attach it to the active launcher/fail-open mission;
- preserve prior related requirements;
- update implementation acceptance;
- implement semantic launch admission;
- add regression coverage;
- continue execution.

Incorrect behavior:

"This file outlines a failure recovery policy..."

and then waiting.

REQUIREMENT PROJECTION

Incoming append requirements must become traceable.

Use the existing SAIPEN source contract / coverage / Work machinery.

However, do not force the operator to manually create a new source receipt for every tiny brick if it is clearly an amendment to an already-active explicit source request.

Implement a canonical append mechanism or equivalent semantics that:

- records append provenance;
- associates it with the controlling source receipt;
- derives requirements;
- updates coverage;
- preserves append ordering;
- supports supersession;
- avoids rewriting immutable historical source evidence.

The original source remains immutable.

Appends are additional durable source events.

Do not silently edit old receipt text.

SUGGESTED SOURCE MODEL

A source receipt may have zero or more ordered append records.

Conceptually:

source:
  SRC-123

appends:
  APP-001
  APP-002
  APP-003

Each append should carry enough identity to recover:

- timestamp/order;
- source artifact or text hash;
- classification;
- supersedes relation if any;
- derived requirement IDs;
- affected Work;
- processing state.

Exact schema may follow existing SAIPEN conventions.

Do not invent a parallel protocol if existing intake structures can represent this cleanly.

IDEMPOTENCY

The same handoff file may be supplied twice.

Reprocessing must be idempotent.

Use stable content identity where appropriate.

Do not:

- duplicate requirements;
- duplicate Work;
- append the same mission fragment repeatedly;
- reopen completed work unnecessarily.

If identical content already exists:
- recognize it;
- report/reuse the existing append identity;
- continue from current mission state.

If the content changed:
- treat the new content as a distinct append/update.

CONFLICT RESOLUTION

When a newer append contradicts an older requirement:

Newest explicit user intent wins.

Record the supersession relationship.

Do not delete historical requirements.

Mark them superseded/obsolete through canonical protocol semantics.

Re-evaluate only implementation/evidence affected by the conflict.

Example:

Old:
"Invalid SAIPEN binding must block launch."

New:
"Recoverable invalid SAIPEN binding must fall back to direct launch."

Result:
- old blocking requirement becomes superseded;
- affected launcher acceptance is invalidated;
- unrelated completed work remains valid.

EXECUTION ROUTING

After reconciliation, automatically determine next exact action.

Examples:

New implementation delta:
-> BUILD

Only new tests/evidence required:
-> VERIFY

Only review acceptance changed:
-> REVIEW

Only packaging/release evidence changed:
-> SHIP

Completely new independent mission:
-> normal intake / claim flow

Do not restart at SCOUT by default.

Use the minimum truthful rewind.

FAIL-OPEN PROTOCOL PHILOSOPHY

SAIPEN itself should follow the same principle where safe.

Protocol imperfections should not unnecessarily prevent productive project work.

Distinguish:

- protocol metadata issue;
- recoverable reconciliation issue;
- genuine integrity/safety ambiguity.

A malformed append index should not necessarily prevent using a valid current Work item if source identity and requirements are recoverable.

A stale planning pointer should not block implementation when canonical project state identifies the active Work.

Hard blocking is reserved for situations where proceeding would risk:

- executing the wrong project;
- executing the wrong source request;
- losing source provenance;
- corrupting immutable history;
- bypassing a real safety/integrity boundary.

OBSERVABILITY

Expose append/reconciliation state clearly.

Status should make it possible to see:

- active source;
- latest append;
- number of active requirements;
- superseded requirements;
- unprojected appends;
- currently affected Work;
- exact next action.

Do not bury a newly received append in LOG only.

CONTINUE COMMAND

`saipen continue --json` must understand pending operational appends.

If an append is durable but not yet projected:

continue must route to the canonical append projection action.

It must not incorrectly report:

- no work;
- mission DONE;
- unrelated old ticket;
- generic manual repair instruction.

Example semantic result:

{
  "ok": true,
  "action": "saipen source apply-append APP-004",
  "reason": "unprojected-source-append",
  "source_receipt": "SRC-123"
}

Exact command/schema may follow the actual implementation.

RECOVERY

Cold recovery must detect:

- durable but unprojected append;
- partially projected append;
- projected append with unfinished Work;
- superseded append;
- duplicate append;
- append whose execution was interrupted.

Recovery must converge to one canonical next action.

Do not rely on previous chat context.

ACCEPTANCE

This protocol work is complete only when SAIPEN can robustly consume both:

- small handoff bricks;
- large multi-milestone handoffs;

at arbitrary normal mission states without requiring operator cleanup or manual protocol choreography.

The following behavior is a regression:

- reading an actionable handoff file and merely summarizing it;
- requiring the operator to restate its requirements manually;
- refusing an append because the current task is already BUILD/VERIFY/DONE;
- restarting the entire mission unnecessarily;
- duplicating Work from repeated handoff content;
- losing append requirements across /new;
- treating every append as an unrelated new mission;
- blocking because planning metadata is stale when machine truth is sufficient to reconcile safely.

FINAL PRINCIPLE

A handoff is not prose decoration.

If the user supplies operational requirements for the active mission, SAIPEN must absorb them into durable mission state and drive them toward execution.

Transport format, conversation boundary, handoff size, and current phase must not make the protocol fragile.
