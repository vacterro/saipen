APPEND — OPERATOR READABILITY / COMPACT CHECKPOINT ENFORCEMENT

Record a human-facing protocol/output defect observed in a real SAIPEN autonomous run.

INCIDENT

An agent completed substantial FastPrompter Work correctly, but its operator-facing checkpoint rendered as a very large dense paragraph occupying most of the application viewport.

The response was technically accurate and evidence-rich, but operationally difficult to read.

Observed characteristics:

- STATUS line contained extensive implementation detail;
- RESULT expanded into many repaired findings and implementation notes;
- validation counts, red controls, performance measurements, filenames, symbols and evidence details were mixed into the main prose;
- important state such as blocker / next action / terminality was visually buried;
- the output behaved like a compressed audit log rather than an operator checkpoint;
- line wrapping alone did not solve readability because semantic density remained excessive.

This is a protocol/presentation defect, not merely a style preference.

ROOT CAUSE

SAIPEN defines compact checkpoint fields, but does not sufficiently constrain how much evidence/models may inline inside those fields.

Therefore an agent can technically satisfy:

STATUS
RESULT
BLOCKER
NEXT EXACT ACTION
VALIDATION

while placing hundreds or thousands of characters into RESULT/VALIDATION.

The result is formally structured but practically unreadable.

CORE PRINCIPLE

Human-facing checkpoint output and machine/evidence output are different surfaces.

The operator checkpoint should answer quickly:

1. What state are we in?
2. What materially changed?
3. Is anything blocked?
4. What happens next?
5. Is validation green?

Detailed evidence should remain available through canonical evidence/log/detail references, not be dumped into the main operator surface by default.

Introduce a canonical rule, e.g.:

OPERATOR-READABILITY-01

or repository-equivalent.

DEFAULT OPERATOR CHECKPOINT

For ordinary autonomous continuation/final checkpoint, render a compact structure equivalent to:

STATUS:
<TICKET> <PHASE> — <short state>

RESULT:
<1-3 short sentences describing the material outcome>

BLOCKER:
NONE
or one exact blocker

NEXT:
<one exact next action>

VALIDATION:
<compact counts / verdict>

Optional:
DETAILS:
<one short pointer to evidence/detail/log if useful>

Do not inline the full implementation history.

HARD READABILITY BUDGET

Define a measurable default budget.

Suggested starting contract:

STATUS:
- one logical line;
- approximately <= 140 visible characters where practical.

RESULT:
- maximum 3 short sentences;
- approximately <= 450 visible characters by default.

BLOCKER:
- one short paragraph;
- NONE when absent.

NEXT:
- exactly one canonical next action;
- one logical line where practical.

VALIDATION:
- one compact line or at most two short lines;
- summarize totals/verdicts, not individual tests.

Whole normal checkpoint:
- target <= 900 visible characters;
- hard soft-limit around 1200 characters before detail extraction is mandatory.

Exact thresholds are implementation-owned, but the contract MUST be machine-testable.

Do not interpret the limits as permission to truncate away safety-critical information.

If critical information exceeds the normal budget, preserve the critical statement and move supporting detail to evidence/detail references.

SEMANTIC COMPRESSION

Do not merely cut text by character count.

Compress semantically.

Bad:

"PERF-001 audio_render.py MAX_RESAMPLE_PHASES=2048 LRU kernel_cache ... 22/22; CORE-001 theme_mixin.py ... 9/9; CORE-002 ..."

Good:

"8 findings repaired; focused regressions 54/55 green, full suite 4999 passed / 23 skipped / 0 failed."

The operator normally needs the verdict, not every internal symbol.

Detailed symbols remain in:
- LOG;
- evidence;
- ticket detail_ref;
- source receipt coverage;
- audit artifact;
- canonical test output.

MACHINE EVIDENCE MUST NOT BE LOST

This is NOT a request to reduce technical evidence quality.

Preserve full evidence in canonical machine surfaces.

The operator checkpoint may summarize:

"4999 passed, 23 skipped, 0 failed"

while canonical evidence retains:
- exact command;
- exact failing/passing tests;
- timestamps;
- fingerprint;
- file/symbol list;
- performance measurements;
- red/green controls.

Human brevity must not weaken machine traceability.

DETAIL POINTERS

When substantial evidence exists, prefer references such as:

DETAILS: E-4520, E-4521; T-1442 detail_ref

or repository-native equivalent.

Do not paste the full contents of those records into the checkpoint unless:
- the operator explicitly requests detail;
- a safety-critical discrepancy must be visible immediately;
- canonical evidence storage failed and the text is the only surviving evidence.

NO IMPLEMENTATION CHANGELOG IN RESULT

RESULT should describe outcomes, not narrate every code change.

Avoid default sequences such as:

- changed function X;
- added constant Y;
- changed cache Z;
- restored font handling;
- changed shutdown ownership;
- repaired importer;
- changed IPC event loop;
- etc.

Instead summarize by outcome/category:

"8 verified defects repaired across audio, shutdown, fonts, persistence and IPC."

The detailed per-defect map belongs in evidence.

PRIORITY ORDER FOR HUMAN OUTPUT

Operator-visible information must appear in this order:

1. current state;
2. success/failure;
3. blocker if any;
4. next action;
5. compact validation;
6. optional evidence pointer.

Do not make the operator scan implementation prose to discover whether Work is DONE or blocked.

TERMINAL / WAIT OUTPUT

When Work is terminal or awaiting the user, readability becomes even more important.

Example target:

STATUS: T-1442 DONE; SRC-101 CLOSED
RESULT: 8/8 findings repaired and verified.
BLOCKER: NONE
NEXT: cc
VALIDATION: 4999 passed, 23 skipped, 0 failed; core red 0.
DETAILS: E-4520..E-4521

That is sufficient for the normal operator surface.

Do not append an unsolicited mini-audit after it.

AUTONOMOUS CONTINUATION OUTPUT

During `/goal cc all`, intermediate ticket completions should be even quieter.

If no operator action is due:

- store full evidence canonically;
- emit only the minimum progress checkpoint required by the host;
- continue automatically.

Do not reward every completed ticket with a full human-facing report when the goal remains active.

The operator did not request a novel between autonomous steps.

QUESTION / WAIT_USER CASE

If operator input is genuinely required:

show:

STATUS
WHY INPUT IS REQUIRED
EXACT DECISION/ACTION

Do not precede the question with a multi-page technical retrospective.

The human should understand the decision within a few seconds.

ERROR CASE

Errors may exceed the ordinary size budget when necessary, but still use progressive disclosure.

First surface:

ERROR:
<exact failure class>

IMPACT:
<what cannot continue>

RECOVERY:
<one exact action>

EVIDENCE:
<reference>

Do not dump stack traces/test logs into the main operator surface unless explicitly requested or no evidence storage exists.

RENDERER OWNERSHIP

Prefer enforcing this in the canonical SAIPEN response/checkpoint renderer rather than relying only on prompt wording.

If `saipen response render` or an equivalent canonical owner exists, extend it so models cannot satisfy the structure while producing effectively unbounded paragraphs.

The renderer should be able to:

- detect excessive field length;
- extract/summarize machine evidence;
- preserve canonical detail references;
- flag operator-surface overflow;
- produce a deterministic compact form.

Do not build a second independent response-formatting subsystem.

OVERFLOW CLASSIFICATION

Introduce a diagnostic such as:

OPERATOR_OUTPUT_OVERFLOW

or equivalent.

It should identify:
- offending field;
- character/line count;
- available detail reference;
- whether compaction succeeded.

This diagnostic should normally trigger automatic compaction, not WAIT_USER.

EXACT REGRESSION — FASTPROMPTER INCIDENT

Create a fixture representing the observed response.

Input contains:

- terminal T-1442 / SRC-101;
- 8/8 findings repaired;
- many individual component/file/symbol descriptions;
- focused red/green evidence;
- performance values;
- full-suite result around 4999 passed / 23 skipped / 0 failed;
- evidence IDs;
- next action.

Pre-fix behaviour:

one large dense checkpoint paragraph containing most implementation details.

Expected post-fix operator rendering:

STATUS: T-1442 DONE; SRC-101 CLOSED
RESULT: 8/8 findings repaired and verified.
BLOCKER: NONE
NEXT: <canonical next action>
VALIDATION: 4999 passed, 23 skipped, 0 failed; required gates green.
DETAILS: <canonical evidence refs>

Exact wording may differ, but semantic density/readability must be equivalent.

Prove that all detailed implementation/evidence information still exists in canonical storage.

READABILITY TESTS

Add machine checks for:

1. normal DONE checkpoint stays within budget;
2. normal CONTINUE checkpoint stays within budget;
3. WAIT_USER presents the decision before technical detail;
4. BLOCKED presents blocker/recovery before evidence;
5. large evidence sets are referenced, not dumped;
6. long file/symbol lists collapse into counts/categories;
7. no single RESULT paragraph can grow arbitrarily;
8. validation summarizes totals;
9. evidence remains lossless in canonical storage;
10. explicit operator request for verbose details can expand output.

EXPLICIT VERBOSE MODE

Do not ban detailed reports.

If the operator explicitly requests:
- details;
- full report;
- audit;
- evidence;
- technical breakdown;
- verbose output;

then a larger response is allowed.

Default autonomous checkpoints remain compact.

Operator-requested verbosity and machine evidence storage are separate from normal checkpoint rendering.

HOST INDEPENDENCE

Apply the same semantic output contract across:

- FastPrompter;
- ZAICODE;
- FreeBuff;
- Claude;
- Codex;
- Antigravity;
- other SAIPEN-compatible hosts.

Host viewport size may influence wrapping, but the semantic compaction rule must remain host-independent.

Do not solve the problem only by increasing widget height or width.

UI width is not the root cause.

STYLE CONTRACT

This rule overrides model tendencies to:
- demonstrate effort;
- enumerate every fix;
- reproduce logs;
- narrate reasoning;
- prove competence through verbosity.

A successful operator checkpoint optimizes for:

time-to-understand

not:

amount-of-evidence-visible-on-screen.

The machine already owns the evidence.

NON_GOALS

- deleting technical evidence;
- hiding failures;
- suppressing safety-critical information;
- forbidding verbose reports when requested;
- reducing audit quality;
- truncating canonical logs;
- changing lifecycle semantics;
- enforcing arbitrary one-line responses everywhere;
- relying only on CSS/text wrapping.

SUCCESS CONDITION

An operator looking at a completed SAIPEN checkpoint should understand in roughly 5-10 seconds:

what finished,
whether it is healthy,
whether they are needed,
and what happens next.

The normal viewport should show a checkpoint, not an embedded audit report.

Technical truth stays complete in canonical evidence.

Human-facing truth stays compact and readable.
