SAIPEN SHORTCUT DECONFLICTION — SS → ST
PROTOCOL MIGRATION / IMPLEMENTATION WAVE

ROLE

Ты implementation agent SAIPEN.

Выполни узкую protocol migration:

    CURRENT:
        ss   -> saipen stop
        sss  -> saipen status

    TARGET:
        st   -> saipen stop
        sss  -> saipen status

Причина изменения:

`ss` и `sss` слишком близки визуально, семантически и для LLM generation.
На практике агенты путают STOP и STATUS.

Это плохой shortcut design, потому что две команды имеют резко различающийся
effect profile:

    STATUS = read-only observation
    STOP   = checkpoint + halt / hand control back

Одна случайная дополнительная или пропущенная `s` не должна превращать
наблюдение в control-flow mutation или наоборот.

Цель этой волны — сделать STOP shortcut явно отличимым:

    st = STOP

и сохранить:

    sss = STATUS

без изменения long-form commands.

DESIRED CONTRACT
============================================================

После миграции:

    `st`
        EXACTLY routes to:
        `saipen stop`

    `sss`

        `saipen status`

============================================================
WHY SS MUST NOT REMAIN A LEGACY ALIAS
============================================================

Не делай:

    ss -> stop
    st -> stop

как permanent compatibility mapping.

Это оставит исходный ambiguity alive.

Главная цель изменения — чтобы модель, которая помнит старый shortcut,
не могла случайно остановить execution.

Поэтому old `ss` должен fail closed.

Предпочтительная semantics:

    input: ss

    result:
        ok: false
        deterministic non-mutating error
        clear migration guidance

Пример смысла:

    Shortcut `ss` was retired.
    Use `st` for `saipen stop`.
    Use `sss` for read-only `saipen status`.

Точную error code / envelope выбери из существующих SAIPEN conventions.
Не создавай новый error framework ради одной команды.

КРИТИЧЕСКИЙ INVARIANT:

    retired `ss` performs ZERO project mutation.

Он не должен:
- checkpoint;
- менять phase;
- менять BOARD;
- писать digest;
- менять intent;
- запускать status side effects;
- запускать producers;
- продолжать work.

============================================================
DO NOT CHANGE STATUS SHORTCUT IN THIS WAVE
============================================================

`sss` остаётся status.

Не переназначай автоматически:

    ss -> status

только потому, что `ss` освободился.

Это снова создаст confusion surface и одновременно сломает существующий
status shortcut.

Target намеренно такой:

    st   STOP
    sss  STATUS

Два visually distinct tokens.

Если во время implementation обнаружится доказанная техническая причина,
почему это невозможно, верни BLOCKED с evidence.
Не импровизируй другой shortcut.

============================================================
RETIRED SS TOMBSTONE
============================================================

Сделай `ss` безопасным migration trap.

Preferred:

    ss
      ↓
    explicit retired-shortcut diagnostic
      ↓
    no mutation
      ↓
    non-success exit/disposition

Сообщение должно различать обе похожие команды:

    st  = stop
    sss = status

Это особенно важно для LLM agents.

Не отвечай только:

    "unknown command"

если existing architecture позволяет дать deterministic migration hint
без расширения public command vocabulary.

Но tombstone НЕ является alias.

Machine semantics должны различать:

    recognized-retired token
    active shortcut

Если для tombstone нужен слишком большой новый mechanism,
используй минимальный существующий deprecation/refusal mechanism.

============================================================
CYRILLIC / UNICODE NORMALIZATION
============================================================

Это отдельная зона риска.

Текущий SAIPEN имеет deliberate codepoint normalization для shortcuts.

Не придумывай keyboard-layout fuzzy matching.

Проверь actual normalization table.

`st` не должен случайно получить неявный Cyrillic twin
из визуального сходства или keyboard position.

Особенно не должно появиться:

    сс -> st
    ст -> st

если это не объявлено canonical registry/codepoint contract.

Существующая защита:

    Cyrillic `сс` -> Latin `cc`

должна сохраниться и НИКОГДА не превращаться в STOP.

Добавь regression, что никакая Cyrillic normalization не resurrects
старый `ss` route.
