Опус, запиши, пожалуйста еще вот это на будущее для реализации такой вот идеи:

SAIPEN

FINAL-REPORT CONDITIONAL EFFICIENCY KPI

TARGET

Add one compact approximate efficiency indicator to the FINAL SAIPEN agent
report.

This is derived telemetry for the operator.

It is NOT:

- lifecycle authority;
- acceptance evidence;
- quality PASS/FAIL;
- a ranking of agents/models;
- permission to optimize speed at the expense of correctness.

Preserve:

    QUALITY > TIME

and the existing principle:

    quality metrics and efficiency metrics remain separate.

============================================================
1. REUSE EXISTING METRICS
============================================================

Do not create a second metrics system.

Inspect and reuse the existing telemetry owners, especially:

    tools/saipen_metrics.py

and the current metrics contracts.

Existing useful families already include:

    throughput
    rework
    human cost
    continuity
    self-directedness
    token/usage cost where available
    acceptance evidence
    runtime/checkpoint timing where available

The new KPI is a DERIVED VIEW over existing evidence.

It must never become a second lifecycle database.

============================================================
2. ADD ONE OPTIONAL FINAL RESPONSE FIELD
============================================================

Extend EXEC-RESPONSE with an OPTIONAL field:

    EFFICIENCY

Canonical ordering:

    STATUS
    RESULT
    BLOCKER
    OPERATOR ACTION
    NEXT EXACT ACTION
    VALIDATION
    EFFICIENCY        optional
    DETAILS           optional, always last

Do not make EFFICIENCY mandatory when evidence is insufficient.

Keep it compact.

Default budget:

    EFFICIENCY <= 1 line
    EFFICIENCY <= 240 characters

Adjust only if existing response-budget architecture requires another bounded
value.

============================================================
3. USER-FACING SHAPE
============================================================

Preferred normal shape:

    EFFICIENCY
    ~85% MED | progress 92 | rework 81 | autonomy 90 | human 95

or an equivalently compact canonical rendering.

Requirements:

- approximate marker must be visible;
- confidence must be visible;
- components must be visible;
- no decimal fake precision;
- preferably round the headline KPI to nearest 5%;
- component scores may use whole integers if mechanically derived.

Examples:

    ~90% HIGH | progress 96 | rework 88 | autonomy 91 | human 94

    ~75% MED | progress 86 | rework 61 | autonomy 79 | human 83

Insufficient evidence:

    UNKNOWN | insufficient ticket-scoped telemetry

Never invent missing values.

============================================================
4. THIS IS A CONDITIONAL KPI
============================================================

Name the machine value clearly, for example:

    conditional_efficiency_kpi

The operator-facing abbreviation may simply be:

    KPI
    EFFICIENCY
    КПД in localized UI

but the protocol/code terminology stays English.

Document explicitly:

    the percentage is an operator-oriented approximation,
    not a physical efficiency measurement.

============================================================
5. DO NOT CREATE ONE OPAQUE SCORE
============================================================

The current metrics contract correctly warns against one opaque "agent score".

Preserve that rule.

The headline percentage is allowed only because its components remain visible.

At minimum derive it from evidence representing approximately:

    useful/progressive execution
    rework overhead
    autonomous continuation / human intervention
    continuity / recovery overhead

Use existing measurable telemetry where possible.

Do not invent a component merely because the formula wants four numbers.

============================================================
6. QUALITY MUST REMAIN OUTSIDE THE KPI
============================================================

Do NOT calculate:

    quality PASS = +20 KPI
    validation FAIL = -30 KPI

Quality remains a separate axis.

The final report may show:

    VALIDATION
    CURRENT_PASS | focused 48/48 | core new_red=0

    EFFICIENCY
    ~85% MED | progress 92 | rework 81 | autonomy 90 | human 95

This is intentional.

A slow but correct agent may have:

    VALIDATION PASS
    EFFICIENCY ~60%

A fast broken agent must NOT receive an attractive efficiency score merely
because it failed quickly.

When terminal validation is not trustworthy, either:

    EFFICIENCY PRELIMINARY ...

or:

    EFFICIENCY UNKNOWN ...

according to the evidence contract.

============================================================
7. PROPOSED COMPONENT MEANINGS
============================================================

Do not blindly hard-code these if better existing metrics already own the
meaning.

Use approximately these semantics:

PROGRESS
    Share of measurable active work that produced durable forward progress.

REWORK
    Efficiency after backward transitions, repeated failed attempts, duplicated
    work and avoidable reruns.

AUTONOMY
    How much execution continued without unnecessary human intervention,
    manual Continue, avoidable WAIT_USER or operator repair.

HUMAN
    Human-friction efficiency: low unnecessary operator cost scores higher.

CONTINUITY may either:

    contribute separately

or:

    be folded into AUTONOMY

if that avoids redundant correlated components.

Keep the model small.

============================================================
8. WEIGHTING
============================================================

Create one versioned canonical formula.

A reasonable starting shape is:

    progress   35%
    rework     25%
    autonomy   25%
    human      15%

but verify this against current telemetry before adopting it.

Requirements:

- weights total 100%;
- formula has one owner;
- adapters do not repeat the formula;
- formula/version appears in JSON telemetry;
- changing the formula changes its version;
- missing evidence must not silently become 100 or 0.

If a component is unavailable, either:

A. renormalize only across sufficiently evidenced components and lower
   confidence;

or

B. return UNKNOWN if too much evidence is missing.

Define this mechanically.

============================================================
9. CONFIDENCE
============================================================

Every headline KPI must carry:

    HIGH
    MED
    LOW

or:

    UNKNOWN

Confidence describes EVIDENCE COVERAGE, not whether the number looks good.

Example:

HIGH:
    ticket-scoped timing, lifecycle, rework and intervention telemetry are all
    available.

MED:
    one secondary component is inferred/coarse.

LOW:
    KPI is based on sparse telemetry.

UNKNOWN:
    deriving a percentage would be misleading.

============================================================
10. TICKET-SCOPED FINAL KPI
============================================================

The final-response KPI should describe the CURRENT WORK/TICKET when possible.

Do not accidentally print a 30-day repository KPI as though it described the
ticket that just finished.

Keep scopes explicit in machine output:

    scope: ticket
    ticket: T-NNN

If ticket attribution is unavailable:

    scope: session

or:

    scope: window

and render that truthfully.

============================================================
11. WAIT / BLOCKED TIME
============================================================

Preserve current metrics semantics:

    WAIT / BLOCKED time is not ordinary active execution when classification is
    available.

Do not punish an agent because:

- the user was asleep;
- another owner held the ticket;
- CI/service was externally unavailable;
- an intentional long soak was required.

Measure avoidable inefficiency, not elapsed calendar suffering.

============================================================
12. SILENT EXECUTION COMPATIBILITY
============================================================

This feature must NOT create intermediate reports.

Do not print KPI updates during SCOUT/BUILD/VERIFY.

Normal behavior:

    work silently
    -> finish boundary
    -> one compact report
    -> EFFICIENCY line included

This integrates with SILENT EXECUTION.

No KPI heartbeat spam.

============================================================
13. NO KPI GAMING
============================================================

KPI must never influence correctness decisions.

Specifically:

- do not skip tests to improve KPI;
- do not reduce checkpoints below recovery needs;
- do not suppress blockers;
- do not avoid REVIEW;
- do not merge tickets artificially;
- do not avoid useful rework;
- do not turn slow progress into failure;
- do not prefer a faster model solely to raise KPI.

Metrics observe behavior.

Metrics do not command behavior.

============================================================
14. MACHINE OUTPUT
============================================================

Expose the derived value through an existing metrics/status surface rather than
making the response renderer calculate history itself.

Conceptual JSON:

    {
      "conditional_efficiency_kpi": {
        "scope": "ticket",
        "ticket": "T-1572",
        "percent": 85,
        "approximate": true,
        "confidence": "MED",
        "formula_version": 1,
        "components": {
          "progress": 92,
          "rework": 81,
          "autonomy": 90,
          "human": 95
        },
        "withheld": null
      }
    }

If unavailable:

    {
      "conditional_efficiency_kpi": {
        "scope": "ticket",
        "percent": null,
        "confidence": "UNKNOWN",
        "withheld": "insufficient ticket-scoped telemetry"
      }
    }

============================================================
15. REGRESSION MATRIX
============================================================

Add deterministic tests.

A.
Complete well-evidenced ticket.
Expected:
    bounded approximate KPI + components + confidence.

B.
Sparse evidence.
Expected:
    UNKNOWN or reduced-confidence result, never fabricated precision.

C.
Long legitimate WAIT.
Expected:
    wait duration does not destroy active-execution KPI.

D.
Repeated avoidable backward transitions.
Expected:
    rework component decreases.

E.
No unnecessary human intervention.
Expected:
    autonomy/human components reflect that evidence.

F.
Required operator authorization.
Expected:
    legitimate human boundary is not classified as avoidable inefficiency.

G.
Validation failure.
Expected:
    KPI cannot masquerade as successful quality evidence.

H.
Silent execution.
Expected:
    no intermediate KPI messages; one final field only.

I.
Detailed report authorized.
Expected:
    DETAILS may explain KPI components, but headline remains one line.

J.
Frozen fixture.
Expected:
    deterministic JSON and deterministic rounded headline KPI.

============================================================
16. ACCEPTANCE
============================================================

DONE only when:

1. One canonical derived conditional-efficiency KPI exists.
2. It reuses existing telemetry rather than building parallel lifecycle state.
3. Quality remains a separate axis.
4. KPI is explicitly approximate.
5. Evidence confidence is explicit.
6. Components are visible; headline is not opaque.
7. Missing evidence produces UNKNOWN/reduced confidence rather than invention.
8. Final EXEC-RESPONSE can carry one bounded EFFICIENCY field.
9. Silent execution remains silent until the final boundary.
10. KPI cannot affect lifecycle/validation/routing decisions.
11. Ticket/session/window scope is explicit.
12. WAIT/BLOCKED semantics remain honest.
13. Focused tests are green.
14. Canonical validation is CURRENT_PASS.
15. Required core family returns new_red=0.
