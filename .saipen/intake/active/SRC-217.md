SAIPEN

MISSION: Enable parallel audit-driven engineering through isolated workers and serialized canonical integration.

MODE: Existing-roadmap continuation, staged implementation.
PRIORITY: Increase verified audit throughput without violating the T-442 stability gate.

OPERATOR INTENT

The operator has multiple pending audit documents and wants a dynamic pool of independent SAIPEN engineering workers.

Each worker should eventually:
- Receive one eligible audit generation.
- Work in an isolated Git worktree.
- Investigate and implement the audit independently.
- Run focused validation.
- Submit an immutable patch proposal.
- Return its slot to the pool.

One canonical coordinator should:
- Control audit assignment.
- Prevent duplicate claims.
- Validate submitted proposals.
- Detect conflicts and stale results.
- Integrate accepted changes sequentially.
- Preserve existing lifecycle and Source authority.

The pool size is configurable, not fixed at 12.

PHASE 0: ADMISSION AND CONFLICT REVIEW

1. Inspect current canonical state, active ownership, pending operations and live audit inventory.
2. Do not interrupt ongoing T-1718 or any successor that currently owns Work.
3. Confirm current T-442 gate status from canonical evidence.
4. Check existing concurrent architecture tickets before proposing new Work.
5. Distinguish read-only parallel evaluation from concurrent source mutation.
6. Preserve the existing sequential saipen crew command semantics.

Never introduce the future saipen concurrent command before its own gate authorizes implementation.

PHASE 1: IMMEDIATE READ-ONLY AUDIT DISTRIBUTION

Design and, where already permitted by existing runtime capabilities, exercise a bounded independent evaluation pilot.

Use three distinct eligible audit generations initially.

The live inventory, not filenames supplied in this instruction, determines eligibility.

Each assignment identifies:

- Worker ID.
- Audit relative path.
- Exact audit content SHA-256.
- Existing Source receipt, if any.
- Existing linked Work, if any.
- Immutable source commit/fingerprint.
- Existing dependency and ownership constraints.
- Assignment generation.
- Read-only authorization boundary.

No worker may claim the same audit generation twice.

No worker may create duplicate Source receipts or tickets.

No worker may modify canonical state, shared audit files or production source during this read-only stage.

Each worker returns:

- Findings.
- Confirmed root causes.
- Exact relevant source symbols.
- Reproduction details.
- Suggested correction.
- Required negative controls.
- Evidence.
- Uncertainty.
- Potential overlap with other workers.

Preserve blocked and invalid audit generations without manufacturing eligibility.

If the current tools cannot provide an independently enforced read-only boundary, do not simulate a successful pilot.

PHASE 2: EXISTING CONCURRENT ENGINEERING DESIGN

Extend the existing T-443/T-444 design, not a competing implementation.

After the T-442 stability gate is genuinely satisfied, the intended worker environment should use isolated worktrees.

Conceptual workspace naming:

SAIPEN_WORKER_001
SAIPEN_WORKER_002
SAIPEN_WORKER_003

Each worker receives its own branch or detached source identity, filesystem scratch and test environment.

Workers must not share writable caches or canonical runtime state without explicit isolation.

The worktree may contain tracked canonical documents for source consistency, but these files carry no independent lifecycle authority.

Prohibit worker writes to:
.saipen/STATE.md
.saipen/BOARD.md
.saipen/LOG.md
shared Source ledgers
shared audit bindings
shared recovery journals
release metadata and publication surfaces

Prevent worker-side SAIPEN commands from silently creating a second authoritative project identity.

PHASE 3: PROPOSAL CONTRACT

Define an immutable handback envelope containing:

- Proposal identity.
- Worker and assignment identity.
- Audit path and exact generation digest.
- Source receipt and Work association.
- Base commit.
- Base source fingerprint.
- Read set and hashes.
- Write set and before-hashes.
- Changed files and logical resources.
- Patch artifact and digest.
- Focused test evidence.
- Required regression coverage.
- Known conflicts.
- Verification limits.

Never treat a worker's own PASS statement as independent acceptance.

Prefer reusing proven ProducerPackage semantics where the authority contracts permit.

Avoid inventing a second package system with different freshness and conflict rules.

PHASE 4: CONFLICT-AWARE INTEGRATION

The coordinator processes accepted proposals through one authoritative integration lane.

Before applying a proposal:

1. Confirm the exact audit generation still exists or remains durably captured.
2. Revalidate Source and Work ownership.
3. Validate the base identity and read/write sets.
4. Detect file-level and logical-resource conflicts.
5. Reject stale proposals without silently rebasing them.
6. Check for conflicting foreign changes.
7. Verify patch integrity.
8. Apply through the authorized integration boundary.
9. Run focused and required complete regression gates.
10. Require independent REVIEW.
11. Complete Work only through canonical lifecycle.
12. Consume the audit file only after exact-generation closure.

A failed proposal returns to its worker for rework or remains blocked.

It never overwrites newer accepted changes.

PHASE 5: DYNAMIC POOL

The desired worker count is configurable.

Evaluate pool sizes:
1, 2, 4, 8, 12, and higher only if resources and observed throughput justify it.

Measure:

- Audits independently evaluated per hour.
- Verified fixes integrated per day.
- End-to-end audit completion time.
- Duplicate investigation rate.
- Merge conflict rate.
- Stale proposal rejection rate.
- Human intervention count.
- Regression failures caused by integration.
- CPU, RAM and test-runner contention.
- Idle time waiting for canonical integration.

Do not run a full core-unit suite independently in every worker by default.

Use focused verification per worker and schedule complete authoritative regression after integration when required.

Maintain no more concurrent heavy test processes than the measured host capacity safely supports.

PHASE 6: WORKER FAILURE AND RECOVERY

Future worker slots must be recyclable.

A worker crash, quota exhaustion or provider change must not destroy the accepted evidence from its completed work.

Require:
- Immutable submitted proposals.
- Detectable expired leases.
- Stale-epoch write refusal.
- Recoverable worker assignment state.
- No automatic ownership theft.
- No duplicate integration.
- No accidental deletion of in-progress worktrees.

Do not equate a worker heartbeat with actual progress.

ACCEPTANCE STAGES

Stage A:
Three independent real audits receive read-only evaluation without duplicate assignment or canonical mutation.

Stage B:
After legitimate Concurrent Mode admission, two independent engineering workers produce isolated verified proposals.

Stage C:
The coordinator integrates both proposals sequentially with no lost updates, stale acceptance or duplicated Source closure.

Stage D:
Repeated real workload demonstrates measurable throughput improvement and acceptable resource contention.

Do not label Stage B, C or D complete based only on synthetic fixtures.

GATE AND STOP POLICY

T-442 remains binding.
Do not close or bypass it to satisfy the operator's desired worker count.

If it is still HELD:

- Reconcile the existing concurrency design.

- Create independent canonical ledgers for worktrees.
- Force-release active claims.
- Give every worker lifecycle-write privileges.
- Automatically merge unknown changes.
- Overwrite foreign work.
- Fabricate Source receipts.
- Rebuild historical evidence.
- Weaken regression or security gates.
- Run conflicting full regression jobs.
- Publish or deploy without authorization.
