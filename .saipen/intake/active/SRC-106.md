======================================================================

1. CORE POLICY — QUALITY > TIME
======================================================================

Add and preserve one explicit SAIPEN design invariant:

```
QUALITY > TIME

```

Expanded:

```
CORRECTNESS > LATENCY

EVIDENCE > MODEL CONFIDENCE

DURABLE PROGRESS > FAST PROSE

ACCEPTANCE QUALITY MUST NOT DECREASE BECAUSE THE CURRENT MODEL IS WEAKER

```

Time is an optimization variable.
Correctness is not.
A slower agent is acceptable.
A slower recovery path is acceptable.
Smaller Work slices are acceptable.
More deterministic scaffolding is acceptable.
Additional focused verification is acceptable.
A weaker model is NOT allowed to obtain a cheaper definition of DONE.
The same Work acceptance applies regardless of:

```
provider
model
price tier
reasoning tier
session
context size
agent incarnation

```

No model receives weaker integrity, review, verification or closure rules merely
because it is cheap, small or slow.
======================================================================
2. IMPORTANT LIMIT — DO NOT CLAIM MAGIC MODEL PARITY
Do not encode the false claim:

```
"every model can perform every task"

```

The real target is:

```
any supported agent that possesses the minimum required operational
capabilities should be able to enter, recover, understand and attempt Work
through the same canonical protocol without protocol drift.

```

A model may still be unable to solve a sufficiently difficult technical
problem.
That is allowed.
What must not happen is:

```
loss of Work

loss of user intent

invented project state

bypassed verification

duplicate Work

duplicate Source

conversational drift

silent acceptance weakening

corruption caused by model weakness

```

SAIPEN should reduce the intelligence required to perform the NEXT SAFE STEP.
It cannot manufacture reasoning ability that the underlying model does not
possess.
======================================================================
3. SAIPEN AS AN EXECUTIVE-FUNCTION EXTERNALIZER
Treat the protocol as externalized execution discipline.
The model should not have to remember:

```
what project it is in

what ticket is active

why the ticket exists

what phase it is in

what was already verified

which expensive test already ran

what must happen next

whether historical input was already consumed

who owns mutation authority

what completion means

```

Those facts belong to machine-readable protocol state.
The model's cognitive burden should increasingly become:

```
understand one bounded problem

inspect the named evidence

make one technical decision

perform one bounded change

prove it

checkpoint it

```

A weaker model may require more such bounded cycles.
That is acceptable.
Do not trade larger speculative leaps for wall-clock speed.
======================================================================
4. MODEL STRENGTH MUST NOT BE PROJECT TRUTH
Preserve the existing runtime boundary:

```
agent != model

```

Provider/model identity remains replaceable runtime telemetry.
Do not persist statements such as:

```
weak model
strong model
premium model
cheap model
smart model

```

into canonical Work truth.
Do not hard-code:

```
GPT-X gets hard tickets
model Y gets easy tickets

```

Canonical state must remain portable across provider/model replacement.
Adaptive execution may eventually use measured runtime behavior.
It must not make project truth vendor-specific.
======================================================================
5. ADAPT THE CORRIDOR, NOT THE ACCEPTANCE
When an agent shows difficulty, SAIPEN may adapt HOW Work is presented.
It must not change WHAT counts as correct.
Prefer a bounded degradation ladder equivalent to:

```
LEVEL 0 — NORMAL
    ordinary bounded Work packet

LEVEL 1 — NARROW
    smaller explicit slice
    fewer relevant files
    explicit non-goals
    exact acceptance clause

LEVEL 2 — GUIDED
    machine-selected next action
    closed command vocabulary
    explicit reproduction
    exact expected observation

LEVEL 3 — PROOF-HEAVY
    focused RED/GREEN controls
    independent read-only verification
    stronger checkpoint before continuation

LEVEL 4 — HANDOVER
    checkpoint exact current truth
    replace agent incarnation
    continue same execution epoch

```

The ladder is conceptual.
Reuse existing runtime/context/recovery owners where possible.
Do not create five new canonical modes merely to encode these names.
======================================================================
6. A WEAK MODEL MUST RECEIVE LESS AMBIGUITY, NOT LESS SAFETY
Protocol outputs intended for an arbitrary successor should prefer:

```
one exact next action

one bounded objective

explicit relevant files

explicit acceptance

explicit non-goals

exact blocker classification

exact known evidence

exact commands where commands are canonical

bounded output from noisy tools

```

Avoid instructions that require the agent to reconstruct hidden orchestration
policy from prose.
Bad:

```
investigate and continue as appropriate

```

Better:

```
inspect X and Y
reproduce condition Z
if Z is true perform canonical action A
otherwise checkpoint evidence B and route C

```

A weak model should be able to follow the protocol mechanically without
inventing missing policy.
======================================================================
7. SLOW PROGRESS IS NOT NO PROGRESS
Do not confuse latency with failure.
The supervisor must distinguish:

```
SLOW_BUT_PROGRESSING

```

from:

```
NO_PROGRESS

```

Existing durable progress semantics are the correct foundation.
Progress remains something real such as:

```
repository diff

newly verified acceptance clause

focused regression turning green

contradiction removed

blocker narrowed by evidence

durable checkpoint advancing

```

A model that takes longer but produces durable progress should not be replaced
merely because another model might be faster.
A fast model repeating the same failed action is worse than a slow model making
measured progress.
Elapsed time alone must never imply model failure.
======================================================================
8. TIME STILL HAS A BOUNDARY
QUALITY > TIME does NOT mean:

```
infinite retries

infinite wall time

unlimited provider spending

repeated identical tests

frozen sessions

endless analysis with no durable result

```

Preserve:

```
NO_PROGRESS_LOOP

provider budget limits

operator gates

checkpoint cadence

host execution bounds

```

When time/runtime limits are reached while progress is real:

```
checkpoint

preserve execution epoch

replace incarnation if necessary

continue from canonical state

```

Do not turn a host timeout into lost Work.
======================================================================
9. HANDOVER MUST BE CHEAPER THAN RECONSTRUCTION
The AUTO_RECALL/AUTO_KICK work now makes model replacement possible.
Push that principle further.
A successor should receive enough machine truth that replacement costs
approximately:

```
load bounded recovery packet
inspect current slice
continue

```

not:

```
reread entire repository
reread entire conversation
rediscover architecture
reinterpret original user intent
rerun all prior verification

```

Persist decision-bearing knowledge, not transcript bulk.
The stronger the recovery packet becomes, the less important the predecessor
model's private context becomes.

If the current incarnation cannot progress:

```

remove unnecessary context

detect repeated identical failure

```

Only then consider replacing the incarnation when another authorized runtime is
available.
Replacement must preserve the execution epoch.
Escalation does not permit:

```
bypassing verification

changing acceptance

discarding failed evidence

starting duplicate Work

```
