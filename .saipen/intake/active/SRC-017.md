# AUDIT DIRECTION -- TEST ORACLE INTEGRITY / ANTI-GREENWASHING

## Goal

Determine whether SAIPEN can wrongly accept a bug fix as VERIFIED/DONE when the
agent, instead of fixing the implementation, changed the test, fixture, expected
output, mock, snapshot, test data or verification command so that the original
bug no longer reproduces.

Defect class:

    BUG EXISTS -> TEST FAILS -> agent changes test/fixture/oracle ->
    TEST PASSES -> false VERIFIED / false DONE

Typical antipattern: "Why are there no failures if there is a bug?" -- "Because
I changed the test fixture to avoid that specific bug."

This must be impossible, or explicitly detected by the protocol.

## Method

AUDIT FIRST, change second. Do not add a norm merely because the wording sounds
useful. First prove whether existing SAIPEN already covers this case.

Check at least: saipen/CORE.md, saipen/phases/verify.md, saipen/phases/review.md,
saipen/phases/validate.md, SPEC.md, saipen/CONFORMANCE.md,
tests/conformance_cases.jsonl, tools/audit_checks.py, tools/run_scenarios.py,
tests/scenarios/, and the related validator / acceptance / evidence contracts.

## Existing hints to test for sufficiency

1. VERIFY: "A fixed bug requires a regression test that failed before the fix."
2. VERIFY / instrument controls: a new or inherited gate must be proven against
   known-bad input and actually go RED.
3. CORE: verification failure must lead to diagnose -> repair -> verify, never to
   success relabeling.
4. REVIEW: re-runs the ticket's verify rather than trusting the VERIFY claim.

Decide whether these are sufficient specifically against changing the test oracle.

## Key invariant to check for

A confirmed bug fix requires a causal A/B comparison:

    SAME regression test
    SAME fixture
    SAME expected result / oracle
    SAME relevant verification configuration

    PRE-FIX implementation  -> FAIL
    POST-FIX implementation -> PASS

The variable between RED and GREEN must be the implementation under repair (or an
explicitly permitted external dependency), never the definition of success itself.

If the fixture/test/oracle changed between FAIL and PASS, the earlier FAIL cannot
be used automatically as evidence of the fix.

## Scenario SAIPEN must catch

1. Implementation with a known bug.
2. Regression test correctly reproduces the bug and FAILs.
3. Implementation is NOT fixed.
4. Agent changes fixture/expected value/test input so the problem path is no
   longer executed.
5. New test PASSes.

Expected: SAIPEN MUST NOT allow VERIFY PASS / REVIEW SHIP / DONE / COMPLETE on
that transition. Verdict should be roughly "verification invalid / oracle changed
/ regression evidence invalidated", and the Work stays unfinished until a real fix
or an independently justified requirement change.

## Greenwashing variants to cover

Not only direct edits to test_*.py: fixture change; deleting the failing case;
skip/xfail; changed expected output; snapshot update; changed mock; narrowing the
input domain; removing an edge case; changed test discovery; changed test command;
excluding a failing directory; continue-on-error / allow_failure; weakening an
assertion; catching/ignoring an exception inside the test; changing seed/data so
the bug path is not executed; changing timeout/tolerance; changing the acceptance
criterion; changing a golden file; replacing a behavioral test with a smoke test;
changing environment/config purely to pass; testing a different code path;
deleting the regression test after the fix; changing production code AND test
together so it is impossible to prove which side made the result green.

## Legitimate test changes must remain possible

Sometimes the test really is wrong, or the requirement changed. A blunt ban
("tests MUST NOT change during bug fixing") breaks real projects. The needed
semantics is: CHANGING THE VERIFIER INVALIDATES PRIOR VERIFIER EVIDENCE. If the
test/fixture/oracle changed, the agent must re-establish the evidence chain:

A. prove an independent reason for the test change (requirement/spec changed; the
   old test contradicted authoritative behavior; the fixture itself was defective);
B. separately prove the original product defect, if it is still claimed;
C. the new regression oracle must have its own RED control;
D. FAIL of the old test version + PASS of the new test version must never be used
   together as bug-fix evidence.

## Preferred norm if the gap is confirmed

Consider a compact rule id such as TEST-ORACLE-01 / VERIFY-ORACLE-01:

"Verification evidence is bound to the verifier that produced it. For a bug-fix
regression claim, the same relevant test, fixture, oracle and verification
configuration MUST demonstrate FAIL against the pre-fix subject and PASS against
the post-fix subject. Changing the verifier invalidates the earlier comparison
unless the verifier change is independently justified and a new red control is
established."

Do not copy that wording mechanically. First find the correct normative owner and
the minimal form inside SAIPEN's architecture.

## Do not create a second mechanism where an existing one can be extended

Preferred order: existing VERIFY regression rule; existing instrument-control
rule; REVIEW independence; conformance scenario / red control; validator
enforcement only where it is genuinely machine-decidable without false confidence.

Do not build a large hash-ledger subsystem for one invariant if the existing
evidence/provenance architecture can already express it. But do check for cheap
evidence binding:

    verifier identity = test command
                      + relevant test/fixture/oracle content identity
                      + subject revision

## A hash is not proof of correctness

A hash proves "verifier changed / did not change", never "verifier is semantically
correct". Both properties are needed: verifier integrity AND red-control
capability.

## Mutation check

A good executable control: take the fixed state; restore the buggy
implementation; do NOT change the regression test; confirm the test goes RED
again. If the restored bug stays GREEN, the regression evidence is invalid. The
fix must be NECESSARY for the green result.

## Acceptance criteria

The audit is complete only with one of two results.

RESULT A -- ALREADY COVERED: show the specific normative rules plus executable
controls that already make this impossible: implementation unchanged, fixture
weakened, failing regression disappears, ticket nevertheless reaches DONE. A
proven chain is required, not "this is probably implied". If genuinely covered, do
not add a duplicate rule.

RESULT B -- GAP CONFIRMED: show (1) the exact missing invariant; (2) why current
rules do not fully close it; (3) the minimal normative owner; (4) a machine-
testable scenario; (5) a negative/red control; (6) the legitimate-test-change
escape path; (7) acceptance criteria; (8) which existing mechanisms are reused.
Then implement the minimal solution and its test.

## Mandatory regression

    buggy subject + original regression fixture = FAIL
    buggy subject + weakened fixture            = PASS   <- MUST NOT count as fix evidence

Positive control:

    buggy subject + original regression fixture = FAIL
    fixed subject + SAME regression fixture     = PASS   <- admissible fix evidence

## Review check

REVIEW must be able to see: whether tests/fixtures/oracles changed; if so, why;
whether the previous FAIL belongs to the same verifier version; and whether the
current verifier is still capable of detecting the original bug. "All tests pass"
is not by itself evidence.

## Report format

STATUS: ALREADY_COVERED | GAP_CONFIRMED | IMPLEMENTED | BLOCKED
EXISTING COVERAGE: file:line, rule, what exactly it prevents
ESCAPE FOUND: minimal reproduction, why SAIPEN currently misses it
DECISION: is a new invariant needed
PATCH: only if the gap is proven
TEST EVIDENCE: buggy + unchanged oracle -> RED; fixed + unchanged oracle -> GREEN;
buggy + weakened oracle -> GREEN BUT REJECTED AS FIX EVIDENCE

No "tests passed, therefore fixed". That is painting over the CHECK ENGINE light
with a black marker and declaring the engine repaired.
