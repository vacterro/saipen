SAIPEN

ROLE: SAIPEN protocol engineering agent
MISSION: Early Architecture Correction and Outcome-First Execution
PRIORITY: P1 SYSTEMIC ENGINEERING QUALITY
MODE: EXECUTION-FIRST, PROTOCOL-NATIVE

OBJECTIVE

Prevent autonomous agents from spending repeated engineering
cycles repairing the symptoms of an unsuitable architecture
while the original user-visible goal remains unfulfilled.

Introduce a lightweight, enforceable engineering convergence
contract into the existing SAIPEN handoff, execution, evidence,
review, and recovery workflows.

This is a systemic prevention task.

It is not permission to rewrite the entire protocol, reopen
historical tickets, introduce an additional controller, or
create a second source of truth.

PROBLEM STATEMENT

A recurring failure pattern has been observed across agentic
development work:

1. A user requests a concrete working capability.
2. An agent selects an implementation mechanism.
3. The mechanism cannot reliably satisfy the actual capability.
4. The agent encounters a failure and patches one symptom.
5. Tests become green for the newly patched condition.
6. The original user-visible capability remains broken.
7. Another audit discovers another symptom.
8. Another ticket is created.
9. More fallback states, guards, recovery paths, and tests are added.
10. The system becomes more complex without becoming more useful.

The agent may be locally correct while the overall engineering
strategy remains wrong.

The protocol must detect this pattern early enough to prevent
wasted cycles.

REFERENCE INCIDENT

FREEBUFF SAI notification audio:

Original user outcome:

Reliable WAV/MP3 playback with volume control, mute, stop,
replacement, and native notification fallback.

Selected implementation:

PowerShell, MCI, COM, and managed SoundPlayer fallbacks.

Repeated engineering work improved:

- Playback lifecycle tracking.
- Stop-before-start guarantees.
- Audio state acknowledgements.
- Codec failure reporting.
- Volume verification.
- Mute handling.
- Native notification fallback.
- Regression coverage.

Yet real Windows evidence showed that the selected MCI WAV
backend could not honor the requested volume.

The resulting application could safely refuse WAV playback
without providing the original WAV playback capability.

This is an example of LOCAL CORRECTNESS WITHOUT OUTCOME
CONVERGENCE.

The desired prevention is an earlier architecture feasibility
decision, not more tests around the unsuitable backend.

OTHER RELEVANT FAILURE CLASSES

Generalize the lesson to:

- Host/runtime integration that cannot reach its required API.
- Desktop UI actions that render but do not execute.
- Packaging that excludes irrelevant files but also loses source.
- Launchers that report success without successful activation.
- Repeated recovery and validation loops without progress.
- Stale test evidence presented as current acceptance.
- False availability inferred from a mock or status marker.
- Incorrect ownership causing protocol tickets to mask host bugs.
- Patch chains that accumulate compatibility modes and fallbacks.

Do not assume these classes all share one implementation defect.

They share an engineering decision-making failure pattern.

PHASE 0: LIVE AUTHORITY AND EXISTING INFRASTRUCTURE

Inspect the live SAIPEN repository, current canonical lifecycle,
ownership, dirty work, existing improvement records, and
handoff/validation/review mechanisms.

Identify the actual source paths and symbols responsible for:

- Handoff admission and interpretation.
- Task acceptance.
- Engineering evidence.
- Regression evidence.
- Review and closure decisions.
- Blocked capability representation.
- Continuation and recovery.
- Repeated work detection, if present.

Reuse existing canonical authority.

Do not create a parallel ticket database or independent
truth authority.

If this improvement already exists in an active owned task,
append the proven missing contracts there.

If SAIPEN is blocked, preserve the requested change through
the authorized improvement queue without bypassing admission.

No unauthorized BOARD, STATE, or LOG edits.

PHASE 1: DEFINE OUTCOME-FIRST ACCEPTANCE

Introduce a compact outcome contract for substantial
engineering tasks.

Required concepts:

USER_OUTCOME

What the operator actually expects to work.

REAL_WORLD_ACCEPTANCE

How the result will be observed in its target environment.

IMPLEMENTATION_ACCEPTANCE

Which implementation invariants must hold.

EVIDENCE_LEVEL

What class of evidence supports each result.

REMAINING_CAPABILITY_GAP

Which user outcome is still unavailable even if engineering
tests pass.

A handoff must not equate these statements:

"The test suite passed."

"The implementation is correct under the tested contract."

"The requested feature works in the real application."

These are distinct claims.

Do not force every trivial typo or cosmetic adjustment through
a heavyweight architectural review.

Use the lightweight existing handoff shape wherever possible.

PHASE 2: EARLY ARCHITECTURE FEASIBILITY

Before committing to a substantial new subsystem, identify:

1. The required user-visible capability.
2. The proposed mechanism.
3. The critical operating-system or host constraints.
4. Fundamental limitations of the mechanism.
5. Existing working components that may be reused.
6. At least one viable alternative when the choice is uncertain.
7. The cheapest safe way to prove feasibility.

Prefer a small working proof over a long speculative build.

For example:

If the task is WAV volume control on Windows, first verify that
the selected audio backend can actually play a WAV at the
requested volume.

Do not build a large playback-state machine before testing
that capability.

If the task is host automation, first prove a supported
communication channel exists.

Do not build ten automation actions against a host API that
cannot be reached.

If the task is UI layout, first inspect the actual available
geometry.

Do not add CSS overrides based only on synthetic DOM fixtures.

EARLY PROOF REQUIREMENTS

The proof should be:

- Small.
- Bounded.
- Reproducible.
- Directly related to the user outcome.
- Non-destructive.
- Appropriate to the real target platform.
- Honest about simulated versus live evidence.

A feasibility proof is not automatically a release acceptance.

If the live environment is unavailable, record that limitation.

Do not fabricate successful capability evidence.

PHASE 3: ARCHITECTURE DECISION RULE

When choosing an approach, evaluate:

CAPABILITY
Can it deliver the actual required behavior?

RELIABILITY
Can it operate repeatedly under normal conditions?

COMPLEXITY
How many special cases are required to keep it working?

MAINTAINABILITY
Can a future agent understand and extend it?

INTEGRATION
Does it fit the application's actual runtime architecture?

SECURITY
Does it introduce new credential, process, or filesystem risks?

DEPLOYMENT
Can the operator actually install and use it?

RECOVERY
Can failures be detected and recovered without corrupting state?

DEPENDENCIES
Does it violate the project's local-first constraints or
introduce unnecessary external services?

REUSE
Can an already working component fulfill the capability?

Favor the simplest proven solution that satisfies the actual
operating requirements.

Do not favor a legacy mechanism merely because previous
tickets invested time in it.

Historical effort is not technical evidence.

PHASE 4: ANTI-LOOP DETECTION

Define an advisory architecture-review trigger when:

- The same user-visible symptom survives two repair cycles.
- The same subsystem accumulates repeated workaround tickets.
- New tests pass but the original capability remains unavailable.
- New fallback states grow faster than useful capabilities.
- An error is repeatedly moved to another layer.
- A real platform limitation is rediscovered by successive agents.
- A task repeatedly returns to BUILD after apparent completion.
- The project alternates between green tests and unusable output.
- A feature only works in mocks while the live route stays blocked.
- Different agents repeatedly repair the same ownership boundary.

These conditions are signals, not automatic proof that the
architecture is wrong.

At two ineffective repair cycles, perform an explicit
architecture review.

At three ineffective cycles, do not continue another
same-mechanism patch without evidence that the approach can
actually deliver the user outcome.

Escalate earlier when the fundamental limitation is already
obvious.

Do not force two wasted iterations before allowing a pivot.

Do not add an unconditional blocking gate to every
SAIPEN continue operation.

The detector must be bounded and inexpensive.

Do not scan complete historical archives or massive ledgers on
every continuation.

Use available canonical ticket, evidence, and outcome metadata.

PHASE 5: PATCH OR PIVOT

After an anti-loop trigger, determine whether the correct action is:

A. PATCH

The architecture is capable.
A local defect has a clear reproducible cause.
Repairing it restores the required capability.

B. REPLACE

The selected component cannot meet a fundamental requirement.
A better mechanism can meet it.
Replace the unsuitable component behind the existing contract.

C. REDESIGN

The subsystem boundaries or ownership model are fundamentally
wrong.
A bounded architectural restructuring is justified.

D. BLOCK

The required external host capability is unavailable.
No authorized implementation can currently provide it.

E. STOP UNSAFE WORK

Further changes would violate authorization, security,
ownership, or data integrity.

Never use BLOCK merely because a preferred implementation
failed when another feasible approach exists.

Never use REPLACE as permission for speculative large rewrites.

Require a small feasibility proof before an expensive pivot.

When a pivot succeeds, stop accumulating compatibility layers
around the abandoned design.

Preserve necessary migration and rollback paths, but do not
retain indefinite competing implementations without a purpose.

PHASE 6: EVIDENCE QUALITY

Distinguish:

SOURCE_INSPECTED
DETERMINISTIC_TESTED
PLATFORM_TESTED
LIVE_INTEGRATION_VERIFIED
USER_VISIBLE_OUTCOME_VERIFIED
EXTERNAL_ACCEPTANCE_PENDING
BLOCKED_WITH_EVIDENCE

These are conceptual evidence classes.

Reuse existing SAIPEN schemas and statuses where possible.

Do not invent additional canonical enum values without
checking existing contracts and consumers.

Evidence must identify the exact tested revision or source
generation when required by the current protocol.

Keep historical evidence immutable.

Do not treat old acceptance as validation of a new tree.

Do not mark a test fixture's playback marker as proof that
physical audio was heard.

Do not mark a successful HTTP response as proof that a
desktop window opened.

Do not mark a rendered button as proof that it performs
the expected action.

Do not turn NOT_RUN into PASS.

PHASE 7: ANTI-OVERFITTING TEST POLICY

Require appropriate tests of the original failure.

A useful regression suite must demonstrate:

1. The previous implementation fails the relevant condition.
2. The new implementation passes it.
3. A deliberately broken implementation is still detected.
4. The actual user-facing behavior is covered when testable.
5. Related negative controls still work.

Favor behavioral contracts over source-text matching.

Do not reward agents for increasing PASS counts while the
requested feature remains absent.

Do not require every fix to introduce a large test framework.

Use the least expensive tests that establish the relevant
behavior and maintain the safety boundary.

For hardware, GUI, audio, and live integrations, identify
what automated tests cannot establish.

Keep human or live acceptance explicit when necessary.

PHASE 8: HANDOFF GENERATION RECONSTRUCTION

Apply the new rules to future SAIHANDOFF preparation.

Each significant handoff should communicate:

PROJECT AND EXACT OWNER

Name the correct project agent.
Separate different owners into independent handoffs.

ORIGINAL USER OUTCOME

Describe the concrete working result in plain language.

CURRENT MACHINE TRUTH

Give the actual verified state and defect boundary.

WHY THE CURRENT APPROACH FAILED

Explain the root cause at the right engineering level.

ARCHITECTURE DECISION

State whether to retain, repair, replace, or investigate the
existing mechanism.

EARLY FEASIBILITY

Identify a small proof that can invalidate the proposed
approach before major implementation.

IMPLEMENTATION CORRIDOR

Specify actual known files, symbols, interfaces, constraints,
and neighboring regressions.

ANTI-LOOP STOP

State what evidence would require changing approach.

REAL ACCEPTANCE

Require the original user-facing outcome rather than only
internal correctness.

NEGATIVE CONTROLS

Preserve security and failure safety.

LIFECYCLE

Respect SAIPEN admission, ownership, checkpoint, review,
recovery, and closure rules.

DELIVERY

Produce specific evidence, changed files, genuine test
results, remaining blockers, and the next actionable item.

Do not send executor agents on broad archival searches.

A prior independent audit should already identify relevant
known source locations and facts.

Avoid generic "investigate everything" tasks when the
defect boundary is already known.

PHASE 9: OWNER SEPARATION

SAIPEN owns:

- Protocol admission.
- Handoff interpretation and lifecycle contracts.
- Evidence integrity.
- Convergence and anti-loop guidance.
- Review and verification semantics.

Consumer project agents own:

- Choice of libraries and runtime implementation.
- Application-specific architecture.
- Product source and tests.
- Application behavior.
- Real platform integration.

Do not route every application architecture mistake into
a SAIPEN engine ticket.

Do not modify consumer projects from this protocol task.

Use product incidents as fixtures for generic protocol
behavior, not as authority to rewrite those products.

Host/runtime-specific defects belong to their actual owners.

A blocked packaging project must not receive duplicate tickets
for the same already recorded finding.

PHASE 10: AUTONOMY WITHOUT BUREAUCRACY

This improvement must reduce wasted work, not add more waiting.

Do not introduce:

- Mandatory architecture documents for tiny fixes.
- New manual approval after every green test batch.
- Additional repeated cc requirements.
- New blocking status for every uncertain design choice.
- A parallel audit queue.
- A second task ownership system.
- Unbounded background feasibility searches.
- Retrospective reclassification of every historical ticket.

Retain existing fail-open progress for independently safe work.

Continue eligible work even if unrelated work is blocked.

Require operator authorization only for genuinely unsafe,
external, destructive, or otherwise gated actions.

When a design is obviously unsuitable, permit an early
architecture decision without wasting two more repair cycles.

PHASE 11: REGRESSION FIXTURES

Create bounded, deterministic protocol-level fixtures.

FIXTURE A: AUDIO PATCH LOOP

Three successive corrective tasks improve internal audio
state tracking, but WAV volume remains unavailable.

Expected:

An early architecture-review signal appears.
The next handoff must examine backend suitability rather than
prescribe a fourth MCI state patch.

FIXTURE B: LEGITIMATE LOCAL DEFECT

A capable backend has one reproducible parser error.

Expected:

The protocol permits a normal narrow patch.
No unnecessary architecture rewrite is demanded.

FIXTURE C: LIVE HOST BLOCKED

Implementation works in simulation, but a host endpoint is
unavailable.

Expected:

The live capability remains BLOCKED.
The protocol does not falsely claim user acceptance.
Independent safe work may continue.

FIXTURE D: STALE ACCEPTANCE

An old green result belongs to a previous source revision.

Expected:

It cannot close the current revision without required
verification.

FIXTURE E: OWNER MISCLASSIFICATION

A GUI runtime fails while protocol admission is valid.

Expected:

The issue is assigned to the GUI/runtime owner, not
automatically to SAIPEN.

FIXTURE F: ARCHITECTURE PIVOT SUCCESS

A minimal replacement backend proves the original user outcome.

Expected:

The handoff can authorize bounded replacement work.
The previous implementation is not endlessly patched.

FIXTURE G: NO DUPLICATE QUEUE

A blocked project already has an equivalent audit finding.

Expected:

The existing finding is reused.
No parallel ticket is created.

FIXTURE H: AUTONOMY PRESERVED

The architecture review finishes successfully and all
necessary authority is present.

Expected:

Execution proceeds without an unnecessary new operator
confirmation.

PHASE 12: ROLLOUT

Implement the smallest generic contract that integrates with
current SAIPEN facilities.

Prefer improving current handoff generation and review
behavior over adding a standalone subsystem.

Do not bulk-migrate historical tickets.

Introduce explicit compatibility handling only where existing
contracts require it.

Validate:

- Existing canonical ticket ownership.
- Valid lifecycle transitions.
- Regression evidence integrity.
- Cold recovery.
- Continuation behavior.
- Review/closure behavior.
- Consumer compatibility.
- No new endless validation loop.

Run focused tests, adjacent regressions, full relevant gates,
and the current canonical validator.

Do not modify frozen historical evidence.

FINAL ACCEPTANCE

1. Significant handoffs define a user-visible outcome.
2. Fundamental feasibility is investigated before expensive work.
3. Repeated symptom repairs trigger an architecture review.
4. Proven dead-end mechanisms can be replaced safely.
5. A capable architecture with a local bug remains patchable.
6. Green tests cannot masquerade as live feature acceptance.
7. External blockers stay honest without blocking unrelated work.
8. Different projects retain correct ownership.
9. No duplicate ticket or authority system is introduced.
10. Existing autonomy and recovery remain functional.
11. No unnecessary manual approval gate is introduced.
12. The protocol is easier to use, not more bureaucratic.

FINAL REPORT

Return:

- Actual SAIPEN admission and ownership.
- Existing mechanisms reused.
- Changed canonical contracts and implementation locations.
- Anti-loop trigger behavior.
- Architecture pivot decision behavior.
- Positive and negative fixture results.
- False-positive and false-negative analysis.
- Full relevant validation results.
- Compatibility and recovery results.
- Remaining limitations.
- Exact next action.

NON_GOALS

No broad protocol rewrite.
No consumer-product code changes.
No new mandatory external servers.
No MCP dependency.
No automatic uncontrolled architecture rewrites.
No arbitrary ticket takeover.
No historical evidence fabrication.
No forced publication.
No mass reopening of completed tickets.
No indefinite architecture analysis without execution.

TARGET STATE

SAIPEN must help agents recognize an unsuitable engineering
approach before they spend multiple cycles perfecting its
failure handling.

The desired optimization target is not maximum PASS count.
