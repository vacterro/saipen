PRIMARY DEFECTS

1. Windows launcher breaks documented compound command syntax.

The canonical SAIPEN command surface documents and supports segments separated by:

` + `

Example:

`saipen push + build ccc`

The internal parser/regression coverage already treats compound commands as supported behavior.

However, through the actual Windows `.cmd` entrypoint, this operator command:

`saipen clean + push`

was forwarded incorrectly and became effectively:

`clean + push`

as arguments to one command, producing an `unknown command` failure instead of executing two ordered segments.

This creates a command-surface split:

- canonical parser says compound commands are supported;
- tests say compound commands are supported;
- actual Windows operator entrypoint does not preserve that syntax correctly.

Treat this as a real SAIPEN defect, not as an operator mistake and not as an unsupported convenience syntax.

ROOT-CAUSE TARGET

Trace the complete Windows invocation path from the real installed/operator-facing `saipen` command through:

- `.cmd` launcher/wrapper;
- argument forwarding;
- PowerShell or Python boundary if present;
- canonical CLI/parser;
- compound segment execution.

Determine exactly where quoting/token preservation is lost.

Do not merely special-case `clean + push`.

Fix the forwarding contract generically so all documented compound commands survive the Windows launcher unchanged.

Required examples include at minimum:

`saipen clean + push`
`saipen push + build ccc`
`saipen status + validate`
`saipen clean + status + validate`

Preserve ordinary single commands and commands with their own arguments.

Add regression coverage at the highest practical real-entrypoint level. A parser-only unit test is insufficient because the defect exists between the operator-facing launcher and the parser.

The regression should prove that a command invoked through the Windows launcher reaches the canonical compound parser as distinct ordered segments.

If direct `.cmd` execution cannot be exercised portably in the normal suite, create the closest deterministic launcher-contract test and document the remaining platform boundary honestly.

2. CLEAN command semantics are ambiguous.

The observed state after:

`saipen clean`

was:

- transition into CLEAN succeeded;
- canonical state remained CLEAN;
- `next_action` remained `PHASE CLEAN`.

That may be correct if `saipen clean` is only the transition/entry trigger.

However, user-facing wording such as:

`clean succeeded`

can incorrectly imply that the CLEAN phase itself has completed.

Inspect the authoritative protocol contract for:

- `saipen clean`;
- CLEAN phase entry;
- CLEAN phase execution;
- CLEAN completion;
- transition to DONE or the next legal state;
- emitted status/result wording.

Establish one unambiguous invariant.

Preferred contract unless authoritative existing design proves otherwise:

`saipen clean` means "enter/start CLEAN", not "perform every CLEAN obligation synchronously and finish it".

If that is the actual intended design, make all command/status/help/output wording precise enough that automation and humans cannot confuse:

CLEAN ENTERED

with:

CLEAN COMPLETED

For example, the runtime may report semantically equivalent wording to:

`CLEAN phase entered; CLEAN execution remains pending.`

Do not hardcode prose unless the project has a canonical messaging layer. Follow existing architecture.

If the intended canonical design is instead that `saipen clean` must execute the complete CLEAN phase, then fix the implementation rather than the wording. Do not choose between these interpretations by convenience. Derive it from protocol authority, state-machine invariants, documentation, tests, and historical behavior.
