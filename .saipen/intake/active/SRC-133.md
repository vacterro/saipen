SAIPEN

Fix the operational response contract at the protocol/runtime level so EXEC-RESPONSE-01 is enforced across all future sessions, cold starts, recoveries, continuation turns, and executor/model changes.

This is not a documentation-only task.

The defect is that SAIPEN already defines an authoritative operational response surface, but agents can still drift into free-form prose and bury machine-relevant state, blockers, operator requirements, and next actions inside narrative text.

The protocol currently has the intended contract, but enforcement is too weak.

OBSERVED FAILURE

A session reached an operational boundary after CLEAN and conformance validation.

The agent returned a prose explanation containing facts such as:

- CLEAN mutations completed;
- current conformance became CURRENT_FAIL;
- 46 work_closure_evidence findings existed;
- a retention blocker remained;
- an operator decision was requested;
- a suggested reverify command existed.

The facts were mostly correct, but the operational control surface was not emitted according to canonical EXEC-RESPONSE-01.

The agent later inspected the protocol and correctly identified that EXECUTION.md defines a mandatory response surface:

STATUS

RESULT

BLOCKER

OPERATOR ACTION

NEXT EXACT ACTION

VALIDATION

DETAILS

with DETAILS optional and last.

The agent also correctly identified the precedence:

user/safety/CORE > execution policy > STYLE

and the autonomy invariant:

if OPERATOR ACTION = NONE and an eligible canonical next action exists, the agent must continue autonomously instead of returning to the operator.

The session therefore exposed a protocol-enforcement defect:

EXEC-RESPONSE-01 exists as specification, but is not reliably binding at the actual response-generation boundary.

GOAL

Make EXEC-RESPONSE-01 a hard operational runtime contract.

Future sessions must not depend on the executor remembering the format.

The protocol/runtime must actively derive, validate, and enforce the response surface before an operational boundary response is returned.

This must survive:

- new chats;
- cold recovery;
- continuation;
- context exhaustion;
- `/new`;
- executor/model replacement;
- style changes;
- pinned reply languages;
- caveman/ded or other STYLE contracts;
- long autonomous runs;
- failures and recovery;
- CLEAN/VERIFY/REVIEW/SHIP boundaries;
- capability blockers;
- operator-only decisions.

PRIMARY INVARIANT

For every SAIPEN operational boundary that returns control to the operator, the response must expose the canonical control surface first and in canonical order.

Required surface:

STATUS
RESULT
BLOCKER
OPERATOR ACTION
NEXT EXACT ACTION
VALIDATION

Optional:

DETAILS

DETAILS must always be last.

No free-form prose may appear before STATUS.

No required operator information may exist only inside DETAILS or prose.

No explanatory prose may substitute for a required field.

STYLE may affect wording inside allowed values where safe, but STYLE must never alter the structure, presence, ordering, semantics, or machine-readability of the operational response surface.

EXECUTION policy wins over STYLE.

RESPONSE MODEL

Establish or reuse a canonical structured representation equivalent to:

- status
- result
- blocker
- operator_action
- next_exact_action
- validation
- details

The exact internal names may follow existing architecture.

Required semantic rules:

STATUS

Must summarize the current canonical operational state.

It must not hide phase/task/blocking truth.

RESULT

Must summarize what materially changed during the completed work interval.

It must distinguish:

- work performed;
- no-op;
- refusal;
- blocked;
- validation failure;
- successful completion.

BLOCKER

Always present.

Allowed semantic forms:

NONE

or:

<canonical blocker code> -- <bounded reason>

Do not emit vague prose such as:

"There is still a problem."

Prefer canonical blocker identity whenever one exists.

OPERATOR ACTION

Always present.

Allowed semantic forms:

NONE

or one exact human action/decision.

This field must describe what the human must do.

It must not contain an agent command disguised as operator work.

Examples of valid operator action:

- Approve deletion of the retained ignored scripts.
- Select whether historical debt should be accepted or repaired.
- Insert the hardware token and touch it when prompted.

Examples of invalid operator action:

- Run the next internal phase.
- Continue processing.
- Execute a command the agent can execute itself.

NEXT EXACT ACTION

Always present.

Allowed forms:

- one canonical command;
- one exact manual step;
- NONE.

Never:

- continue as appropriate;
- investigate further;
- proceed with next steps;
- retry if needed.

If multiple internal actions remain and the agent retains authority, do not return them to the operator merely to expose progress.

Continue autonomously.

VALIDATION

Always present.

Must state the strongest current validation truth concisely.

Examples:

- CURRENT_PASS
- CURRENT_FAIL
- focused tests 17/17; core 3985; new_red=0
- validation unavailable due to <canonical capability blocker>

Do not claim PASS from stale cache when current authority is known to be stale.

DETAILS

Optional.

Must always be last.

Use only when the compact control surface is insufficient.

The operator must never need to read DETAILS to determine whether action is required.

AUTONOMY HARD BINDING

Enforce the following decision before any operational response is returned:

If:

OPERATOR ACTION = NONE

and:

an eligible canonical next action exists

and:

no safety/capability/evidence-authority boundary prevents execution

then:

DO NOT return control to the operator.

Execute the next action.

This must be enforced across phase transitions.

Do not emit a status card merely because:

- SCOUT finished;
- BUILD finished;
- VERIFY finished;
- REVIEW finished;
- CLEAN was entered;
- one ticket closed;
- one regression was fixed.

Return only at a legitimate boundary.

A status response is not a replacement for autonomous continuation.

OPERATOR BOUNDARY RULE

If operator action is genuinely required:

- stop safely;
- emit EXEC-RESPONSE-01;
- put the required human decision in OPERATOR ACTION;
- put the exact post-decision continuation in NEXT EXACT ACTION where deterministic;
- do not bury the decision inside prose;
- do not ask a conversational question after the card if the card already contains the required action.

Resolve this from existing authority rather than inventing a second convention.
