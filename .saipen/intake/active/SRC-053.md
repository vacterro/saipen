======================================================================
PROBLEM
======================================================================

Agents already detect genuine SAIPEN protocol defects correctly, but their
reports are being written to arbitrary locations such as:

    V:\_TEMP_\opencode\...
    V:\_TEMP_\fastprompter_drag\...
    project-local future_gate/
    other ad-hoc paths

This destroys discoverability.

A SAIPEN protocolist should have ONE place to inspect when asking:

    "Which projects are currently blocked because SAIPEN itself failed?"

The protocol report must not depend on the agent guessing a path.

======================================================================
CORE REQUIREMENT
======================================================================

Introduce one canonical USER-LOCAL SAIPEN protocol incident inbox.

Conceptual authority:

    %LOCALAPPDATA%\saipen\protocol_incidents\

Exact final path may follow existing SAIPEN local-state ownership, but:

    ONE OWNER
    ONE ROOT
    ONE FORMAT
    ONE DISCOVERY COMMAND

Do NOT use arbitrary project roots.

Do NOT require the reporting agent to know the SAIPEN source repository path.

Do NOT use scheduled-source/future_gate as the raw incident spool.

scheduled-source is runtime/source distribution.

protocol_incidents is operational evidence.

======================================================================
WHEN AN AGENT MAY EMIT A REPORT
======================================================================

This path is for SAIPEN protocol failures, not ordinary application bugs.

Trigger only when the agent has evidence that progress is blocked because the
SAIPEN protocol/runtime itself has no legal forward route.

Conceptual state:

    BLOCKED_BY_SAIPEN
        -> PROVE
        -> EMIT PROTOCOL INCIDENT
        -> HANDOFF
        -> WAIT / STOP

Examples:

    reconciliation cannot reach its own repair planner
    canonical next command is absent
    repeated same refusal has no state change
    legal recovery command is unreachable
    guard blocks the only engine-required repair path
    scheduler enters a proven non-progress carousel
    cross-project protocol ownership defect
    installed runtime violates its own documented invariant

Not sufficient:

    model is confused
    tests fail
    application code has a bug
    ordinary BLOCKED_EXTERNAL
    user has not answered a legitimate operator decision

======================================================================
FIRST-CLASS PACKET
======================================================================

Prefer a machine-readable incident carrier with a human-readable body.

Conceptual header:

    SAI-DEFECT!1

    incident_id
    created_at
    reporter_project
    reporter_identity
    protocol_version
    runtime_generation
    installed_home
    defect_class
    severity
    state
    blocker
    canonical_next_command
    evidence_digest
    dedupe_key
    source_report_path

Human body may include:

    summary
    deterministic reproduction
    observed commands/output
    root-cause analysis
    impact
    suspected owner
    repair candidates

Principle:

    PROSE MAY EXPLAIN
    PACKET DEFINES

Do not make free prose the machine contract.

======================================================================
CANONICAL STORAGE
======================================================================

Suggested shape:

    %LOCALAPPDATA%\saipen\protocol_incidents\
        inbox\
        claimed\
        resolved\
        invalid\
        evidence\

Example:

    inbox\
        SAI-DEFECT-20260916-<digest>.md

or an equivalent content-bound envelope.

The active inbox must contain only unresolved incidents.

Resolved incidents remain retrievable.

Never silently delete reports.

======================================================================
DEDUPLICATION
======================================================================

Multiple agents/projects may hit the same SAIPEN defect.

Do not create twenty independent reports merely because twenty weak models hit
the same broken branch.

Create a deterministic dedupe identity from stable fields such as:

    defect class
    normalized refusal / failure signature
    protocol generation
    relevant owner/module
    minimal reproduction signature

If the same incident already exists:

    attach occurrence evidence
    increment occurrence count
    record project/model/runtime
    preserve the original incident id

Do NOT dedupe solely on prose equality.

Do NOT merge incidents across materially different protocol generations without
explicit compatibility proof.

======================================================================
PROTOCOLIST DISCOVERY
======================================================================

Provide one canonical read-only discovery command.

Conceptual examples:

    saipen defects
    saipen defects list
    saipen defects show <id>

Exact CLI naming may follow current registry conventions.

The SAIPEN protocolist must be able to immediately see:

    unresolved incident count
    severity
    defect class
    affected projects
    first seen
    last seen
    occurrence count
    protocol generation
    claimed/unclaimed state
    suspected owner
    exact report path / evidence reference

No recursive filesystem archaeology.

======================================================================
CLAIM / OWNERSHIP
======================================================================

A protocolist may claim an incident for investigation.

Conceptual lifecycle:

    INBOX
    -> CLAIMED
    -> RESOLVED

or:

    INBOX
    -> INVALID

Claiming an incident must NOT mutate the blocked project.

Incident ownership and project Work ownership are separate concepts.

A protocolist investigating SAIPEN must not steal the blocked project's seat.

======================================================================
PROJECT-SIDE REFERENCE
======================================================================

The blocked project should retain only a lightweight reference such as:

    protocol_incident: SAI-DEFECT-...

Do not copy the whole incident report into every project.

The central incident packet owns the full evidence.

The project owns only:

    blocker state
    incident id
    resume condition

When the protocol defect is fixed and an installed generation is available, the
blocked project can prove the required generation and resume.

======================================================================
FUTURE_GATE RELATIONSHIP
======================================================================

Do not confuse:

    protocol_incidents/inbox
with
    future_gate/

Their roles differ.

protocol_incidents/inbox:

    raw proven protocol failures awaiting protocolist triage

future_gate:

    accepted future work / follow-up after triage

Desired route:

    AGENT PROVES PROTOCOL FAILURE
        -> protocol_incidents/inbox

    PROTOCOLIST REVIEWS
        -> INVALID
        OR
        -> existing ticket
        OR
        -> new SAIPEN ticket
        OR
        -> future_gate follow-up

Only the protocolist / canonical triage operation promotes an incident into
future work.

======================================================================
WEAK-MODEL UX
======================================================================

When the condition is proven, the agent should not be told:

    "write a report somewhere useful"

The engine should return one exact operation.

Conceptually:

    saipen defect emit --from-current-failure

or an equivalent bounded command.

Expected output:

    incident: SAI-DEFECT-...
    state: RECORDED
    path: <canonical inbox path>
    next: WAIT for SAIPEN protocol repair

The model should not choose filenames, folders or schemas.

======================================================================
SECURITY / INTEGRITY
======================================================================

The incident inbox is evidence.

Required properties:

    atomic write
    content digest
    no path traversal
    no arbitrary absolute destination
    bounded file size
    schema/version validation
    idempotent retry
    append-only occurrence history
    symlink/reparse-safe paths
    no executable payload semantics

A report does NOT grant mutation authority.

A SAI-DEFECT cannot bypass guards.

A SAI-DEFECT cannot authorize its own fix.

======================================================================
ACCEPTANCE CASES
======================================================================

Future implementation must prove at least:

1. genuine unreconcilable SAIPEN deadlock
       -> one canonical incident emitted

2. retry same failure
       -> same incident / new occurrence, not duplicate report

3. same defect from another project
       -> same defect family with second occurrence when generation/signature match

       -> no protocol incident

8. claim does not mutate affected project ownership

9. resolved incident remains historically retrievable

10. project can reference incident id without copying report body

11. runtime-generation mismatch remains visible

12. malformed/tampered incident fails validation
