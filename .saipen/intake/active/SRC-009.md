Да. Я посмотрел именно свежий SAIPEN_30.08.26-T16-21-29.zip. Здесь уже не нужен очередной рефакторинг документации. Нужна **semantic compression**: уменьшить количество текста, который обязан понимать агент, при этом сохранить все переходы, safety-гейты, recovery, continue  improve, HUSH и deterministic routing.

Сейчас картина такая:

* весь saipen/*.md + phases/*.md  **624 KB / 96 300 слов**;
* CONFORMANCE.md  **207 KB / 33 500 слов**;
* CORE.md  **163 KB / 25 000 слов**;
* только CORE 1.10 Command Surface  **36 KB / 5 500 слов**;
* CORE 1.2 File Model  **44 KB / 6 900 слов**;
* все 16 phase docs вместе  **109 KB / 16 900 слов**;
* BOOT + STYLE + INDEX уже  **25.5 KB**, ещё до активной phase.

И главное: движок сейчас местами **парсит сам prose как API**. Например tools/saipen_engine/commands.py вытаскивает shortcut table прямо из CORE.md, а validate.py/audit_checks.py имеют массу cross-doc и phrase-based проверок. Вот этот damn coupling сначала надо убить. Иначе сокращение одного предложения будет считаться изменением протокола, хотя логика вообще не менялась.

Мой конкретный roadmap такой.

1. **Зафиксировать семантику до первого сокращения. Ничего пока не резать.** Сделать protocol semantic baseline: список фаз, переходов, command aliases, shortcut normalization, STATE fields, ticket states, next-action forms, disposition/error vocabularies, destructive gates, checkpoint order, source authority, recovery precedence, goal/autonomy semantics, continue  improve bounded fallthrough и будущий HUSH precedence. Для каждого факта указать текущего owner и тест. Отдельно сохранить golden snapshots для saipen continue, cc, ccc, ship, improve, compound commands, recovery и dry-run. Текущий tools/saipen_engine/continue_fallback.py уже есть, поэтому его поведение сразу объявить invariant: fallback только после исчерпания существующей Work, resume существующего Improve cycle, не создавать бесконечную improve-карусель. Gate этого этапа: нынешние tests/validator/scenarios зелёные и сохранён baseline, с которым будут сравниваться следующие этапы.

2. **Отвязать executable logic от английских предложений. Это P0 всей затеи.** Добавить один machine-owned registry, я бы сделал saipen/REGISTRY.json. Туда вынести только закрытые machine facts: phases, legal transitions, canonical commands, aliases/shortcuts, confusable normalization metadata, next-action forms, disposition vocabularies и другие реально парсящиеся множества. Не пихать туда философию, recovery reasoning или длинные правила. Переделать commands.py, чтобы shortcut table читалась из REGISTRY.json, а не regexом из CORE.md. validate.py должен проверять соответствие docs registry, а не требовать конкретную английскую фразу. Это критично: **prose перестаёт быть database**. Gate: можно переписать описание команды другими словами, и behavior tests остаются byte-identical.

3. **Ввести stable Rule IDs и правило One Rule = One Owner.** Например STATE-ROOT-01, CMD-CONTINUE-04, RECOVERY-03, OPS-EFFECT-02, GOAL-07. Второй документ не переписывает правило, а пишет See CMD-CONTINUE-04. Не надо превращать всё в бюрократическую японскую 電話帳 (でんわちょう, дэнвачо: телефонную книгу), достаточно IDs только для правил, которые реально cross-referenceятся. Это позволит вырезать десятки повторов STATE.md/BOARD.md/LOG.md, Pick Rule, destructive, next_action, saipen_home, USERPERSON, recovery semantics. Gate: validator обнаруживает два normative owners одного Rule ID.

4. **Вынести Command Surface из CORE.** Создать saipen/COMMANDS.md. CORE 1.10, который сейчас весит 36 KB, превращается в короткое: authority, routing invariant, ссылка на COMMANDS.md. В COMMANDS.md оставить compact таблицу input  canonical action  special rule  Rule IDs. Compound parsing, Unicode twin semantics, STOP_ON_FAILURE, HUSH modifier, continue  improve описать там один раз. Не переименовывать команды. В проекте уже есть ratified decision, что saipen x sub и подобная компрессия command surface была rejected. Это правильно: мы сокращаем **описание**, mitte (не) пользовательский vocabulary. Target: COMMANDS.md **1215 KB**, вместо нынешних 36 KB, а обычная команда больше не заставляет загружать 163 KB CORE.

5. **Сжать CORE в настоящий kernel.** Не очередным split ради split, а удалить всё, что не является нормативным решением. Нормативный rule должен иметь форму примерно: Condition  MUST/MUST NOT  outcome  exception  Rule ID. Истории типа это воспроизвели в linked worktree, потому что однажды validator был green про чужую tree... из нормативного bullet убрать. Оставить максимум Evidence: scenario X / incident Y. Причина может жить в test scenario, CHANGELOG или KNOWLEDGE, но агенту не надо каждый раз читать роман о том, почему закон появился. В CORE оставить authority, state model essentials, ownership, state machine, deterministic priority, completion truth и high-level recovery invariants. Target для CORE: **3550 KB**, а не 163 KB. Это реалистичная экономия примерно 70%, не меняя ни одной 規則 (きそく, кисоку: нормы).

6. **BOOT превратить в действительно cold-start kernel.** Сейчас он 12.8 KB и сам начинает повторять source capture, USERPERSON, runtime identity, command precedence, reply language, repair и прочее. BOOT должен отвечать только на вопрос что прочитать и в каком порядке. Я бы оставил примерно: bind root/home  load STYLE  STATE  BOARD/LOG tail  resolve current input mechanically  load only required owner doc/current phase  execute  checkpoint/readback. Все подробности через Rule IDs. Никакой второй command table, второй source contract или второй explanation reply_language. Target: **BOOT 57 KB**. BOOT + STYLE + INDEX после следующего этапа держать около **1520 KB total**.

7. **Не трогать число фаз. Сжимать phase docs по delta principle.** У тебя уже явно зафиксировано решение не схлопывать 16 phases, и оно логичное: lazy loading делает маленькие отдельные phases дешевле жирных объединённых. Поэтому SCOUT/BUILD/VERIFY/... остаются. Для каждой phase один формат: Entry, Reads, Actions, Exit, Forbidden, Evidence, Rule refs. Общие вещи типа checkpoint order, destructive authorization, source receipts, root binding, agent identity в phases больше не повторять. ship.md сейчас 17 KB, translate.md 13.6 KB, markhunt/clean/verify около 1011 KB. Targets: median phase **4 KB**, специализированные ship/translate **810 KB**. Весь phase set можно опустить примерно со 109 KB до **6070 KB**, не меняя state graph.

8. **Отдельно вычистить MAINTENANCE, OPS и IMPROVE.** MAINTENANCE.md особенно подозрителен: всего 97 строк, но 23.5 KB, потому что там bullets размером с железнодорожный состав. 2.4 Goal-Driven Execution один занимает примерно 13 KB. Свести каждый lifecycle к state/trigger/termination tables и Rule IDs. IMPROVE.md уже структурирован лучше, его не рубить агрессивно. OPS.md тоже механический и полезный. Targets примерно: MAINTENANCE 1012 KB, IMPROVE 1518 KB, OPS 1215 KB. Здесь главное не сожрать edge cases ради красивой статистики.

9. **HUSH оформить как маленький EXECUTION.md, а не размазывать по пяти документам.** Там должны жить execution/output policies: default narration, HUSH activation, tool-first rule, silence lock, mandatory-output exceptions, final 20-line report, interaction with audits. CORE знает только precedence: user/safety/core  execution policy  style. STYLE знает голос, но ничего не знает о lifecycle HUSH. COMMANDS знает лишь syntax hush task. Это даст настоящую модульность: kolm asja (три вещи), три owners, никакой каши.

10. **CONFORMANCE перестать считать частью human-readable протокола.** Сейчас это 207 KB и 33.5k слов, хотя INDEX.md уже правильно говорит работающему агенту его вообще не читать. Следующий шаг: вынести scenario rows в machine corpus, например tests/conformance_cases.jsonl, где каждая запись имеет id, rule_id, setup, expected result. CONFORMANCE.md оставить как 510 KB explanation/index/debugging guide, автоматически генерируемый из корпуса или хотя бы проверяемый против него. Ничего из 250+ scenarios не удалять. Мы не теряем доказательства, просто перестаём хранить тестовую базу как огромную pseudo-constitution.

11. **Убрать phrase-based validator hardening.** Это обязательный отдельный этап, а не побочная уборка. Сейчас validate.py местами проверяет буквально наличие формулировок в BOOT, CORE, STYLE, CONFORMANCE. Это исторически понятно, но превращает wording в ABI. Каждый такой check классифицировать: если проверяется semantic invariant, тестировать registry/parsed structure/runtime behavior; если реально нужен exact marker, оставить marker. После миграции validator должен жаловаться Rule CMD-X missing/owner mismatch, а не предложение больше не содержит эти пять слов. See, наконец-то computer проверяет computer facts, а не играет учителя английского.

12. **Ввести CI-бюджеты на context, иначе через 30 версий всё снова распухнет.** Старый T-392 уже сделал правильный RFC split и lazy INDEX, но CORE снова вырос до 163 KB, а CONFORMANCE до 207 KB. Значит, одной архитектурной реформы недостаточно, нужен автоматический brake. Добавить tools/protocol_budget.py, считающий не только total bytes, но и реальные load profiles. Я бы зафиксировал budgets: cold 20 KB protocol prose; ordinary continue 35 KB; command resolution 30 KB; обычная phase execution 40 KB; ship/improve 55 KB; ни один routinely-loaded .md 50 KB; CONFORMANCE исключён из production load graph. Если новый rule превышает budget, автор обязан либо удалить старый duplicate, либо доказать необходимость.

13. **Мигрировать маленькими semantic-preserving waves.** Не делать один commit минус 300 KB, потому что потом хрен поймёшь, где потерялось одно MUST NOT. Порядок такой: registry/decoupling  COMMANDS  CORE compression  BOOT  phases  MAINTENANCE/OPS/IMPROVE  CONFORMANCE  final dedupe. После каждой wave: registry equality, full validator, existing scenario suite, unit suite, command-routing tests, hostile recovery tests, source tests, continue/improve acceptance и golden semantic diff. Только green wave разрешает удалять старый duplicated prose.

14. **Финальный target я бы поставил не экстремальный, а безопасный.** Human-readable protocol сейчас 624 KB. Нормальная первая цель: **250325 KB**, то есть минус примерно **4860%**, при этом machine conformance corpus может остаться отдельными 80150 KB и никому context не жрать. Более важная metric: routine agent execution должен видеть не 100200 KB law, а примерно **2045 KB relevant law**. Вот это даёт реальный token win. Не minify markdown, а уменьшение cognitive working set.

Главное правило всей операции: **не сокращать semantics, сокращать representation**. Не MUST  ну желательно, не объединять разные safety branches, не убирать recovery edge cases. Удаляются история, duplicate wording, narrative rationale, machine data из prose и cross-document restatements. Это tihendamine по-эстонски, а не протокольная лоботомия.

Если разложить по priority, то я бы дал агенту именно: **P0 registry + prose decoupling  P1 COMMANDS/CORE  P1 BOOT  P2 phases  P2 maintenance family  P3 conformance corpus  permanent size budgets**. Пока P0 не сделан, CORE.md лучше вообще не резать. Иначе validator с commands.py начнут орать на формулировки, как бюрократ, которому вместо синей ручки принесли чёрную.
