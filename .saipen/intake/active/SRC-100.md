## Request

Нет, это не фантазия. Но важная поправка: **«агент работает сутками» не должно означать один бессмертный LLM-сеанс, который 36 часов держит контекст и надеется, что Windows, сеть, quota и сам агент не чихнут**. Это была бы архитектура на молитвах.

Реалистичная цель гораздо сильнее:

> **SAIPEN может работать сутками как непрерывная система, автоматически меняя/перезапуская агентные сессии, восстанавливая состояние и продолжая работу с последнего доказанного checkpoint.**

То есть не:

```text
ONE AGENT
    works 72 hours
    never crashes
    remembers everything
```

а:

```text
SAIPEN SUPERVISOR
    ↓
worker session A
    ↓
bounded work
    ↓
verify
    ↓
durable checkpoint
    ↓
worker/session dies or context ends
    ↓
cold recovery
    ↓
worker session B
    ↓
continues exact next action
    ↓
...for days
```

Вот это можно довести до очень серьёзного уровня автономности.

Я бы для SAIPEN поставил отдельную архитектурную цель: **CONTINUOUS AUTONOMOUS OPERATION**.

| Слой               | Что должно быть                                                     |
| ------------------ | ------------------------------------------------------------------- |
| Work selection     | автоматически выбирает следующий eligible Work                      |
| Lease              | один mutating worker на проект, stale lease восстанавливается       |
| Checkpoint         | после каждого bounded slice                                         |
| Crash recovery     | новый агент продолжает без человека                                 |
| Context exhaustion | автоматический cold-agent handoff                                   |
| Tests              | focused first, broad only на meaningful boundary                    |
| Blockers           | один BLOCKED ticket не блокирует проект                             |
| Human gates        | DEFERRED, а не GLOBAL STOP                                          |
| Quotas             | модель/провайдер временно недоступен → fallback или retry later     |
| Deadlocks          | одинаковое действие несколько раз → диагностировать, а не крутиться |
| Evidence           | всё durable, никаких «я помню, что вчера было зелёным»              |
| Publication        | push/tag/release отдельно от обычной автономной работы              |
| Observability      | видно, что делает, почему, сколько времени, что дальше              |

Самая важная часть: **bounded slices**. Я бы вообще запретил continuous worker думать «моя задача закончить весь проект». Пусть его единица работы будет примерно:

```text
recover
→ acquire lease
→ choose one root/milestone
→ reproduce
→ implement
→ focused verify
→ review
→ checkpoint
→ classify next state
→ continue/release
```

Например 15–90 минут на slice. Тогда смерть процесса в 07:43 не превращает предыдущие восемь часов в дым.

Для настоящего режима «оставил вечером, пришёл утром» нужны ещё четыре механизма.

Первый: **automatic cold recovery package**. Перед окончанием каждой сессии SAIPEN сам должен создавать компактное machine-readable состояние вроде:

```text
ACTIVE_WORK: T-1452
PHASE: BUILD
LAST_VERIFIED_ROOT: release_freshness
TREE_IDENTITY: ...
DIRTY_IDENTITY: ...
NEXT_COMMAND: ...
KNOWN_REDS: ...
BLOCKED: ...
DEFERRED: ...
DO_NOT_REPEAT:
  - full scenario run
  - injector repair
```

Новый агент читает это вместо 4000 строк истории.

Второй: **watchdog/supervisor**. Если worker умер, завис, потерял heartbeat или 20 минут повторяет одно и то же состояние, supervisor делает не «ну ладно», а:

```text
worker unhealthy
→ freeze current mutation
→ inspect last checkpoint
→ stale lease recovery
→ spawn/reassign worker
→ continue
```

Третий: **progress invariant**. Это для SAIPEN особенно полезно, потому что он уже умеет выращивать бюрократию как плесень. Каждые N действий должна меняться хотя бы одна измеримая величина:

```text
failure identities ↓
milestone terminalized
new evidence produced
blocker classified
next action changed
```

Если пять циклов подряд:

```text
same state
same blocker
same command
same evidence
```

это `NO_PROGRESS_LOOP`, а не повод попробовать шестой раз.

Четвёртый: **operator-independent scheduling**. Именно то, к чему ты уже подбираешься:

```text
ticket A BLOCKED on human
       ↓
scheduler scans
       ↓
ticket B eligible
       ↓
continue B
not:
ticket A BLOCKED
       ↓
entire civilization stops
```

### Насколько автономно реально

Я бы ставил такие ступени:

```text
LEVEL 0
human says "continue" constantly

LEVEL 1
several milestones autonomously

LEVEL 2
one session autonomously until context/runtime ends

LEVEL 3
automatic session recovery + durable continuation

LEVEL 4
multi-project worker pool + leases + scheduler

LEVEL 5
24-72h unattended operation with watchdog/recovery

LEVEL 6
week-scale operation with budgets, provider failover,
maintenance, compaction and human-gate queue
```

Сейчас SAIPEN, судя по тому, что мы видим, где-то **между L2 и ранним L3**, а отдельные механизмы уже лезут в L4. Есть durable lifecycle, checkpoints, Sources, dependency resume, scheduler concepts, operator gates, recovery. Но пока ещё слишком много случаев, где система может сама создать себе blocker, воскресить старого owner или уйти в мета-ремонт собственного протокола.

Для начала я бы поставил очень конкретный target:

> **SAIPEN 24H AUTONOMY GATE**

Acceptance:

```text
24 hours unattended
0 manual "continue"
0 duplicate semantic mutations
0 stolen live leases
0 fabricated PASS
0 UNKNOWN terminal failures
0 raw STATE/BOARD/LOG edits
0 project-wide stops caused by one deferred ticket

worker crash:
    recovery <= 5 min

context exhaustion:
    cold continuation <= 5 min

provider unavailable:
    fallback/defer without losing Work

every 60 min:
    durable progress checkpoint

every Work transition:
    executable exact next action

human-only gate:
    parked + surfaced
    unrelated work continues
```

После этого уже:

```text
72H AUTONOMY GATE
```

а потом week-scale.

И я бы добавил ещё один очень важный принцип:

> **Agent is disposable. State is not.**

Если это станет фундаментальным правилом SAIPEN, тогда вообще неважно, прожила Astra 35 минут, 5 часов или её прибил provider quota. Следующая Astra/DeepSeek/Sol должна подняться и продолжить с того же доказанного места.

Вот это уже действительно путь к твоей цели «оставил работать и не нужен человек с кнопкой continue». Не идеальная автономия в фантастическом смысле, а довольно инженерно достижимая **fault-tolerant autonomy**. И это, пожалуй, более интересная задача, чем просто заставить одну модель сидеть сутки, пока её контекст постепенно превращается в кашу.
