FINDING P0-1 — GOAL CLI SUBCOMMANDS BECOME NEW GOAL PIVOTS

Independently reproduced from the supplied SAIPEN snapshot
using the actual imported ZAICODE hook module.

The native hook classifies:

saipen goal propose  -> action=goal, objective="propose"
saipen goal status   -> action=goal, objective="status"
saipen goal list     -> action=goal, objective="list"
saipen goal eval     -> action=goal, objective="eval"
saipen goal replenish -> action=goal, objective="replenish"
saipen goal pause ... -> action=goal, objective="pause ..."
saipen goal resume ... -> action=goal, objective="resume ..."
saipen goal authorize --file ... -> action=authorize-goal

The canonical parser excludes "authorize" but fails to exclude
the other real goal CLI subcommands.

The native hook may therefore seal an operator's read-only
inspection command as a NEW goal-entry action and then call
_spend_goal on the original authenticated human message.

This is especially dangerous because the agent's current
recommended operator action is to type "saipen goal propose"
directly into ZAICODE.

REQUIRED REPAIR

Use one canonical grammar shared by CLI and all native host
adapters.

Recognize the complete real subcommand table, not only
"authorize".

A goal-management command is NEVER a goal-entry objective.

Preserve explicitly intended new-goal commands and their
existing security model.

Provide a read-only native preview route for "goal propose",
or direct the operator to a genuinely safe terminal/UI path.

The preview must not trigger:
- goal pivot;
- bounded authority reset;
- Work admission;
- campaign dispatch;
- journal mutation;
- authorization;
- a synthetic operator event.

Do not merely classify inspection as "continue" if that path
has side effects.

Keep genuine authorize-goal as a separate, strictly authenticated
operator action.

Add end-to-end negative controls using the real hook parser
and its dispatch decision, not just source-text assertions.

FINDING P1 — OPERATOR APPROVAL UX IS INCOMPLETE

The current proposed workflow is:

1. Human requests the capsule.
2. CLI prints raw JSON.
3. Human manually saves or transfers it.
4. Human sends a second command naming that file.
5. Native hook and broker attempt to authenticate/apply it.

This is a proposal generator, not yet a completed one-action
native approval surface.

After resolving the binding and parser defects, provide the
smallest real operator-controlled approval workflow.

The operator should be able to inspect the precise requested
grant and explicitly approve it once without manually computing
hashes, editing JSON, or guessing the correct path.

The approval event must originate in a real trusted human
interaction. Do not treat an agent's shell or text as consent.

The native broker must verify exact proposal identity and
revocation/budget scope at commit time.

If a separate trusted approval UI is not supported, expose a
safe and documented manual procedure instead of pretending
that a shell command is authenticated native approval.
