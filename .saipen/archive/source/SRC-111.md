SAIPEN

ADVICE APPEND TO CURRENT PROTOCOLIST MISSION

SAIGPU — FUTURE LOCAL GPU WORKER EXPANSION

Target executor:

```
Claude Opus 5.5
```

Recommended effort:

```
Max
```

This is an advisory append.

It records promising directions for further use of the local GPU / local models.

It does NOT authorize implementing every item immediately.

Do not interrupt higher-priority correctness, closure, field-gate, autonomy or
proof work merely to expand SAIGPU.

Do not create a broad new GPU architecture umbrella unless measured Work proves
one is necessary.

Preserve the architecture already established:

```
SAIPEN engine owns truth, lifecycle, evidence and authority.

Frontier/cloud agents own difficult reasoning and ambiguous engineering.

Local GPU workers perform bounded, replaceable, low-authority support Work.

GPU absence must never reduce protocol correctness.

GPU output is ADVISORY unless a future explicit protocol contract proves a
stronger role safe.
```

======================================================================

1. CURRENT GOOD BASELINE — PRESERVE IT
   ======================================================================

SAIGPU already has two useful classes of local work.

Embedding / recall lane:

```
semantic memory indexing

recall

similarity

near-duplicate advisory
```

Local reasoning lane:

```
qwen3:14b core-unit failure triage
```

Current useful pattern:

```
deterministic code defines the evidence set

local model reasons over the bounded evidence

model returns a hypothesis

frontier agent / canonical protocol verifies the hypothesis
```

This pattern is good.

Prefer extending this pattern before granting the local model mutation or
lifecycle authority.

The preferred formula is:

```
MACHINE SELECTS FACTS
    ->
LOCAL MODEL COMPRESSES / CLASSIFIES / HYPOTHESIZES
    ->
SAIPEN OR FRONTIER AGENT VERIFIES
```

not:

```
LOCAL MODEL DECIDES WHAT IS TRUE
```

======================================================================
2. DESIGN TARGET
================

The local GPU should gradually absorb work that is:

```
repetitive

context-heavy

classification-heavy

summarization-heavy

retrieval-heavy

cheap to verify

expensive in frontier-model tokens

useful in the background

non-critical if unavailable
```

The local GPU should initially avoid work that is:

```
authority-sensitive

destructive

architecturally ambiguous

difficult to verify mechanically

responsible for PASS / DONE

responsible for publication

responsible for mutation ownership
```

The long-term goal is not:

```
"use the GPU because it exists"
```

The goal is:

```
move appropriate cognitive background work away from expensive frontier
agents while preserving the same verified quality floor.
```

======================================================================
3. NEXT SAFE ROLE — LARGE LOG / TRANSCRIPT COMPRESSION
======================================================

Candidate:

```
LOCAL LOG SUMMARIZER
```

Input examples:

```
long unittest output

supervisor history

worker transcripts

long CLI traces

field-soak output

provider/runtime error streams
```

Output:

```
bounded factual summary

error clusters

repeated signatures

first occurrence

last occurrence

likely relevant files/functions when explicitly present

unresolved anomalies
```

The local model must not fabricate missing lines.

Where deterministic extraction is possible:

```
Python extracts counts, timestamps and identities.

Qwen explains/compresses them.
```

Potential value:

```
large reduction in frontier context usage.
```

High priority candidate.

============================

Candidate:

```
LOCAL SCOUT ASSIST
```

Given:

```
Work title

Source requirement

semantic memory index

repository symbol/path inventory
```

Return:

```
likely relevant files

related Work

related previous defects

related KNOWLEDGE

suggested first inspection order
```

Example:

```
T-####

likely first reads:
    tools/saipen_engine/router.py
    tools/test_foo.py
    saipen/COMMANDS.md

related:
    T-####
    SRC-###
    KNOWLEDGE-###
```

This should reduce the amount of blind repository exploration performed by the
frontier model.

Qwen does not choose the final scope.

It prepares candidates.

======================================================================
7. BACKLOG SIMILARITY MINING
============================

Use embeddings plus bounded Qwen reasoning to periodically inspect:

```
TODO Work

BLOCKED Work

FUTURE GATE ideas

incident inbox
```

and suggest:

```
probable duplicates

parent/child relationships

likely common root causes

ideas already implemented elsewhere

stale Work likely superseded by newer mechanisms
```

Output remains:

```
ADVISORY
```

Never auto-close or merge tickets from semantic similarity alone.

This may later reduce protocol/backlog entropy significantly.

======================================================================
8. RECOVERY PACKET COMPRESSION
==============================

Candidate:

```
LOCAL RECOVERY CONTEXT COMPRESSOR
```

AUTO_RECALL already reconstructs canonical execution.

A local model may help compress non-authoritative supporting context:

```
recent relevant LOG events

prior hypotheses

relevant diff summaries

already-read files

failed approaches

DO_NOT_REPEAT material
```

The mandatory recovery fields remain machine-owned.

The local model may only prepare the optional explanatory layer.

The successor must remain able to recover when Qwen is unavailable.

Input:

```

Output:

======================================================================
10. CORE-UNIT FAILURE TRIAGE EXPANSION
======================================

The existing T-1481 role may be extended carefully.

Possible improvements:

```
group explanation quality

rank likely root-cause files

distinguish:
    likely product defect
    likely fixture defect
    likely isolation defect
    likely inherited debt
    likely environment defect

compare current group with previous historical groups

suggest smallest reproduction command
```

Keep mechanical ownership of:

```
test IDs

grouping

coverage count

baseline comparison

PASS / FAIL status
```

Qwen should interpret groups, never define them.

======================================================================
11. FIELD-SOAK WATCHER
======================

Candidate:

```
LOCAL SOAK OBSERVER
```

During long unattended runs, the GPU may periodically inspect a bounded snapshot
of:

```
generations

recoveries

repeated failures

recent Work progression

provider classifications

checkpoint cadence

anomaly counters
```

and produce:

```
anomaly advisory
```

Examples:

```
"generations 18-22 show repeated VERIFY stalls"

"same failure hypothesis has repeated four times"

"recovery latency is rising"

"new failure class first appeared at generation 31"
```

This must not replace deterministic supervisor stop rules.

It is a second pair of eyes, not a second supervisor.

======================================================================

======================================================================
16. CHEAP HYPOTHESIS GENERATION
===============================

Candidate:

```
LOCAL HYPOTHESIS WORKER
```

For a bounded RED reproduction:

```
exact failure

relevant code fragment

exact recent diff
```

ask Qwen for:

```
2-4 candidate root causes

evidence that would distinguish them
```

The frontier agent then tests the hypotheses.

This can reduce expensive exploratory reasoning.

Do not let the local model patch code merely because it produced a plausible
hypothesis.

==================================

Do NOT enable immediately.

Give qwen3:14b a real bounded SAIPEN Work slice with:

```
one narrow defect

one or few files

deterministic RED reproduction

explicit acceptance

no architecture work

no publication

no destructive effects

normal SAIPEN verification
```

Candidate task classes:

```
small parser fix

simple validation bug

stale test fixture repair

deterministic CLI formatting defect

isolated documentation parity fix
```

Measure:

```
acceptance retention

time

retries

protocol drift

manual intervention

escaped regressions
```

This is where SAIGPU could evolve from:

```
advisory worker
```

to:

```
restricted execution worker
```

Do not cross this boundary before measurement supports it.

======================================================================
19. EVENTUAL MULTI-LOCAL-WORKER MODE
====================================

Only if future hardware allows it.

Potential architecture:

```
embedding worker

triage worker

summarization worker

bounded local execution worker
```

These need not be separate models.

They may be roles over the same local runtime.

Do not build a distributed scheduler prematurely.

The RTX 3060 has finite VRAM.

One useful worker is better than four workers fighting over 12 GB and heating
the room.

======================================================================
20. GPU RESOURCE POLICY
=======================

Preserve user-first GPU ownership.

SAIGPU must yield to interactive workloads.

Relevant workloads may include:

```
Cinema 4D

After Effects

rendering

local interactive inference

games

other CUDA workloads
```

Before substantial inference verify:

```
GPU utilization

free VRAM

configured reserve

current SAIGPU ownership
```

For long local inference consider bounded cancellation / preemption.

The user should not discover SAIGPU activity because their interactive workload
suddenly stutters.

======================================================================
21. VRAM RESERVATION
====================

Do not use one universal free-VRAM threshold forever.

Future configuration may distinguish:

```
embedding_min_free_vram

reasoning_min_free_vram

user_vram_reserve

max_saigpu_vram
```

The user reserve should win.

SAIGPU exists to consume genuinely spare compute.

It does not own the GPU.

======================================================================
22. CPU OFFLOAD MUST BE VISIBLE
===============================

Important future hardening:

Detect or bound substantial CPU / system-RAM offload.

A task classified as:

```
GPU worker
```

must not silently become:

```
CPU worker consuming large RAM and Ryzen time
```

Possible runtime states:

```
GPU_NATIVE

GPU_PARTIAL_OFFLOAD

CPU_FALLBACK

CPU_FALLBACK_REFUSED
```

Exact vocabulary may follow existing capability semantics.

The system should be able to refuse expensive hidden fallback when policy
requires GPU-only background work.

======================================================================
25. CACHE REMAINS DISPOSABLE
============================

All SAIGPU memory/index/result storage should remain reconstructable.

Preferred location remains equivalent to:

```
.saipen/cache/gpu/
```

Deleting the cache must never destroy:

```
Work

evidence

Source

checkpoints

acceptance

canonical knowledge
```

At worst:

```
recall is temporarily slower

advisory output must be regenerated
```

======================================================================
26. PRIVACY / LOCALITY
======================

One useful property of SAIGPU is that suitable work remains local.

Prefer local GPU for tasks involving:

```
large repository context

historical logs

indexing

clustering
```

when there is no need to send those bytes to an external provider.

Do not advertise this as absolute security.

It is a deployment/property advantage, not a replacement for data-handling
policy.

======================================================================
27. VALUE MEASUREMENT
=====================

Do not expand SAIGPU based only on novelty.

Measure whether a role produces useful savings.

Candidate measurements:

```
frontier context avoided

frontier tool reads avoided

wall time saved

local inference time

GPU busy time

advisory acceptance rate

hypothesis usefulness

duplicate detection precision

human/frontier corrections required
```

A role that consumes GPU but rarely helps should be removed or narrowed.

A role that saves significant frontier effort should be promoted.

======================================================================
29. RELATION TO QUALITY > TIME
==============================

SAIGPU should support QUALITY > TIME by reducing the cost of maintaining the
same quality.

The ideal result is:

```
frontier agent spends less time on mechanical context processing

local GPU absorbs repetitive cognitive preparation

deterministic SAIPEN machinery preserves truth

final acceptance remains unchanged
```

The local worker may be slower.

That is acceptable if it runs in genuinely spare compute and reduces paid /
scarce frontier cognition.

```

======================================================================
31. ADOPTION RULE
=================

Treat every new SAIGPU role as an experiment.

For each role require:

```
bounded responsibility

input contract

output contract

authority level

failure behavior

GPU/resource budget

measurable value hypothesis

focused regression
```

Adopt one role at a time.

If useful:

```
retain and improve it.
```

If noisy:

```
narrow it.
```

If dangerous:

```
remove it.
```

Do not turn SAIGPU into a second uncontrolled agent framework.

======================================================================
32. FINAL PRINCIPLE
===================

GPU IS A RESOURCE.

LOCAL QWEN IS A WORKER.

NEITHER IS AUTHORITY.

LET THE GPU DO MORE WORK.

LET SAIPEN DECIDE WHAT THAT WORK MEANS.

USE LOCAL COMPUTE WHERE ITS ERRORS ARE CHEAP AND ITS OUTPUT IS EASY TO VERIFY.

MOVE TOWARD MUTATION AUTHORITY ONLY AFTER MEASUREMENT PROVES THE QUALITY FLOOR
SURVIVES.

QUALITY > TIME.

QUALITY > GPU UTILIZATION.

STATE > MODEL.

EVIDENCE > HYPOTHESIS.
