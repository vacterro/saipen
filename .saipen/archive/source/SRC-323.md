TARGET: CURRENT SAIPEN ENGINE

MISSION

Make SAIPEN critically evaluate incoming substantial handoffs before creating implementation work.

When an incoming request describes functionality that already exists, SAIPEN must:

1. Preserve the original request.
2. Identify its exact requirements.
3. Compare them against current implementation and canonical history.
4. Verify existing functionality against the new request's acceptance criteria.
5. Determine the actual implementation delta.
6. Avoid redundant implementation.
7. Canonically settle requirements already proven satisfied.
8. Create Work only for missing, defective or unverified requirements.
9. Resolve mechanically provable duplicate-work relationships without unnecessary operator intervention.
10. Continue the next independent authorized task.

The target behavior is demonstrated by an observed ZAICODE session in which a new A3 Quick3 handoff was critically checked against already implemented Wave 3 functionality.

The agent correctly discovered that the requested functionality was substantially implemented and avoided producing another implementation.

However, the session became blocked by source/work supersession restrictions.

This campaign must preserve the correct analysis and eliminate the unnecessary deadlock.

4. PRE-ADMISSION HANDOFF ANALYSIS
============================================================

Every substantial implementation handoff must receive bounded pre-admission analysis.

The analysis determines:

A. What is actually requested?
B. Which requirements are already implemented?
C. Which requirements are already verified?
D. Which requirements are partially implemented?
E. Which requirements are missing?
F. Which requirements are contradicted by current code?
G. Which requirements require new operator authority?
H. Which requirements are genuinely new objectives?

For compound handoffs, compare individual requirements.

Do not classify the whole handoff as duplicate merely because its title resembles an earlier project.

Use these proposed result classes:

EXACT_DUPLICATE
EXISTING_IMPLEMENTATION_VERIFIED
EXISTING_IMPLEMENTATION_UNVERIFIED
PARTIAL_OVERLAP
NEW_IMPLEMENTATION_REQUIRED
REGRESSION_DETECTED
CHANGED_ACCEPTANCE_CONTRACT

Integrate these classifications with existing SAIPEN types rather than building a parallel status framework.

============================================================
8. AUTHORITY BOUNDARY
============================================================

Automatic equivalence analysis does not grant additional operator authority.

The distinction is:

Already authorized operation, independently verified implementation:
May be mechanically reconciled through an existing permitted lifecycle.

Changed implementation objective:
Requires the applicable admission authority.

New external publication:
Requires the existing publication authority.

Revoked authorization:
Remains revoked.

Unknown implementation equivalence:
Cannot be declared verified.

Genuine repeat request:
Cannot be silently discarded merely because similar work was done before.

Do not permit a model-generated handoff or report to impersonate operator intent.

If a legacy supersession operation requires a separate operator capsule, do not bypass that gate by relabeling the same operation.

Instead, define and prove a narrower canonical settlement operation whose effects are limited to already-satisfied requirements and consume no new authority.

If that cannot be justified under the existing policy, retain the gate and document the precise policy change required.

============================================================
9. AUTOMATIC DUPLICATE ROUTING
============================================================

When a duplicate is detected:

EXACT SAME SOURCE EVENT:
Reuse the existing receipt and operation result.

EXACT SAME BYTES, DIFFERENT EVENT:
Preserve event provenance and apply existing request-identity rules.

SEMANTICALLY EQUIVALENT REQUEST:
Verify each requirement against current code and evidence.

PARTIAL OVERLAP:
Reuse the verified portion; admit the real delta.

CHANGED IMPLEMENTATION:
Treat the changed requirements as new Work.

CHANGED ACCEPTANCE:
Revalidate the stronger or different acceptance contract.

STALE VERIFICATION:
Run bounded relevant verification or classify as unverified.

NEW DEPLOYMENT OR REPEATED ACTION:
Honor the independently authenticated new request.

NO ACTUAL DELTA:
Conclude through canonical verified settlement.

Never equate semantic resemblance with executable permission.
