## FINDING A — no preflight rule before a long declared suite

Problem: `saipen test suite run T-###` is the VERIFY gate. Nothing asks the
agent to run the subset its diff touches first, so a 14-min suite becomes
the compiler error loop.

Required work: add a protocol rule (proposed id SUITE-PREFLIGHT-01, in the
VERIFY phase owner; place it where VERIFY's gates live):
1. Use the last record's duration_s for the declared command. If it is over
   5 min, run the affected subset first:
   - list the changed paths (`git diff --name-only` plus untracked files);
   - grep the suite's scripts and fixtures for each changed file's basename
     and for new or removed qualified symbols (`ns::Function`);
   - include every fixture that asserts a count of a table the change grows.
   Run the full suite only once that subset is green.
2. After a red suite run: rerun only the failing script until it passes.
   Then grep for siblings of the same kind (other fixtures that stub or cut
   the same file), and only then start one full run. Never restart the full
   suite blind.

## FINDING B — a red run is expensive to read and late to fail

Required CLI work (proposals; design inside SAIPEN):
- `saipen test suite run [T-###] --fail-fast`: stop the declared command at
  the first line matching the suite's FAIL grammar (or the runner's first
  failing sub-test), record the partial result as FAIL, and keep the existing
  evidence semantics.
- Record per-sub-script durations when the runner prints them, plus SAIPEN's
  own overhead (pre/post tree hashing, parsing) as separate fields, so "where
  did the hour go" is answered from the record.
- `saipen test suite affected [T-###]`: print the candidate subset (the
  scripts and fixtures that reference the changed paths), for the agent to
  run before the gate.
- `saipen response digest` or `status`: show the last suite run's duration
  and first failure line, so the agent does not dig them out of
  `stdout_tail`.
