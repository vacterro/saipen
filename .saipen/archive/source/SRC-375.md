## Request

SAIHANDOFF — FIX RELEASE APPROVAL CONTRACT END TO END

MODE: 2 — IMPLEMENT AND VERIFY
TARGET: CURRENT LIVE SAIPEN PROJECT
PRIORITY: P0
GOAL: ONE-TIME OPERATOR SETUP FOR AUTONOMOUS VERIFIED GITHUB RELEASES

OPERATOR OBJECTIVE

The operator wants SAIPEN to maintain itself and publish verified,
reviewed updates to its established GitHub repository with minimal
manual intervention.

Ordinary Git and engineering decisions are delegated.
Actual publication authority must remain authenticated,
scope-bound, revocable, and finite.

COLD START

Inspect live SAIPEN source, release engine, operator-origin broker,
authority capture, decision_request, native host integration,
current release candidate, release tests, Git remotes and grants.

Do not use frozen ticket numbers, historical hashes, file counts,
or assumed command contracts.

ROOT CAUSE TO VERIFY

The pending approval packet is a decision_request, not an
operator authorization capsule.

The existing authority capture implementation accepts specific
closed capsule grammars and persists an operator-backed Source.
It does not automatically turn a decision_request into a
release grant.

Broker service availability is not operator approval.

The installed Antigravity native hooks authenticate host
invocations but do not themselves prove explicit human consent
to a protected publication.

The current recommended operator command therefore appears
incomplete or incompatible with the actual release approval path.

MISSION

1. TRACE THE REAL PUBLICATION CONTRACT

Find the exact release admission owner and its accepted grant kind.

Determine whether a complete authenticated release-authorization
mechanism already exists.

If it exists, connect the existing decision-request workflow
to that owner instead of inventing a second authority system.

If it does not exist, implement the smallest integrated,
broker-backed release authorization contract.

Do not use retirement, handoff, goal, gate-decision, or campaign
authority as implicit permission to publish.

2. BUILD AN ACTUAL HUMAN APPROVAL SURFACE

Implement or connect a supported local operator-controlled
approval interaction, usable while Antigravity remains the
primary execution host.

Present the exact repository, remote URL, branch, reviewed
cohort, expected resulting commit, test gate, publication
effects, expiration, and grant limits.

The operator must explicitly approve that exact transaction
through a genuinely authenticated mechanism.

The model must not be able to synthesize the approval event by
running a shell command, editing a file, or invoking a fake UI.

Use real host/broker identity verification, challenge binding,
anti-replay protection and durable revocation.

Do not fabricate signatures, host ancestry, human events or
broker receipts.

3. SUPPORT BOUNDED STANDING RELEASE AUTHORITY

If the canonical authority model supports it, offer one
explicit operator opt-in covering repeated verified releases
to the SAME approved repository and branch.

Bind it to:
- exact project identity;
- fixed remote and repository visibility;
- reviewed SAIPEN-owned code;
- required verification policy;
- finite duration and operation count;
- no force-push;
- no deletion of foreign work;
- revocation and cancellation;
- independent remote verification.

Changes of repository, public/private visibility, protected
scope, or destructive Git operations require new approval.

Do not silently issue or renew a standing grant.

4. FINISH THE ACTUAL RELEASE CANDIDATE

Reconcile the live GitHub branch and the intended integration.

Freeze the real final release commit identity.

Run the mandatory full release gate against those exact bytes.

Focused tests are not a substitute for a mandatory full gate.

If the gate fails, investigate and repair genuine regressions;
never waive the test policy merely to enable publication.

Preserve the shared Git index and all unrelated staged entries.

5. PUBLISH AND VERIFY

Only after genuine operator approval and all required gates:
perform the authorized non-force publication.

Independently fetch the actual GitHub target branch and verify
the exact intended commit or formally permitted merge result.

Store broker and publication receipts separately.

Never call HELD a successful publication.

6. MAINTAIN AUTONOMOUS ENGINEERING

Keep the existing valid maintenance authority independent
of release approval.

Do not stop authorized Work, HUNT, Improve, SAIPAL discovery or
persistent-goal evaluation because GitHub publication is held.

Avoid redundant status polling and artificial tickets.

REQUIRED NEGATIVE CONTROLS

- Raw decision_request is not accepted as a release grant.
- Model-generated JSON cannot authorize a release.
- Model-shell invocation cannot impersonate operator approval.
- A hook event alone cannot prove human publication consent.
- Wrong project, remote, branch, scope or candidate is refused.
- Expired, revoked or replayed grant is refused.
- New public destination requires explicit approval.
- Changed release bytes invalidate incompatible test evidence.
- Focused PASS cannot replace the mandatory full gate.
- Broker restart cannot silently restore unauthorized grants.
- No force-push, foreign-index loss or accidental public leak.
- Valid operator-approved transaction succeeds end to end.
- Antigravity remains the normal engineering host.

SUCCESS CRITERIA

A real operator can approve one precisely explained publication
through a working trusted local interface.

The broker accepts and verifies that genuine approval.

The release engine consumes only the correctly scoped grant.

A verified commit reaches the intended GitHub branch and the
remote SHA is independently confirmed.

Subsequent approved maintenance can continue autonomously
within the finite granted scope.
