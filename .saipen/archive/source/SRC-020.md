ROLE

Implement a bounded strengthening of SAIPEN's EXISTING `.saipen/KNOWLEDGE/`
memory contract.

Do NOT create a new memory subsystem.

The feature is:

KNOWLEDGE DISTILLATION + RETRIEVAL

Core idea:

verified experience
    ↓
distilled reusable lesson
    ↓
small searchable index
    ↓
future relevant task
    ↓
cold agent retrieves lesson
    ↓
lesson materially influences decision

The canonical design principle is:

"A project should be able to tell the next intelligence what the previous
intelligence learned."

This is a functional requirement, not marketing prose.

============================================================

The repository already owns durable memory:

============================================================
2. PROBLEM TO SOLVE
============================================================

The current protocol knows WHERE durable knowledge belongs but only weakly
specifies:

A. when an experience deserves promotion into reusable knowledge;
B. how to encode WHY it matters to a future decision;
C. how a cold agent discovers the relevant knowledge without reading the whole
   KNOWLEDGE tree;
D. how stale/superseded knowledge stops influencing future decisions;
E. how to prove that stored knowledge actually changes later behavior.

This implementation closes exactly those gaps.

============================================================
3. MEMORY PROMOTION GATE
============================================================

Define one small normative promotion rule in the narrowest existing owner,
preferably CORE + the relevant phase docs rather than a new protocol document.

A finding MAY become durable KNOWLEDGE only when ALL are true:

1. VERIFIED
   It is supported by repository evidence, accepted human authority, or an
   already-admitted decision.

2. REUSABLE
   It is likely to matter outside the ticket/session that discovered it.

3. DECISION-BEARING
   Knowing it could materially change a future implementation, debugging,
   architecture, verification, operational, or maintenance decision.

4. NOT CHEAPLY DERIVABLE
   It is not merely a fact trivially and reliably re-read from current
   package.json/config/source in seconds.

5. NON-DUPLICATE
   Existing KNOWLEDGE was searched first.

6. NON-TRANSIENT
   It is not current progress, temporary state, an open task, a retry note,
   a timestamped status report, or an event transcript.

7. SAFE
   It contains no credential, secret, private token, copied sensitive payload,
   or unnecessary personal information.

If any condition is false:
DO NOT PROMOTE IT.

This gate exists specifically to prevent memory inflation.

Default:
- zero new memory items for an ordinary ticket;
- at most one newly promoted lesson per ticket unless the work genuinely
  produced multiple independent reusable truths.

The protocol MUST NOT create a memory entry merely because a ticket finished.

============================================================
4. DISTILLED KNOWLEDGE CARD
============================================================

Introduce an OPTIONAL structured card format under:

.saipen/KNOWLEDGE/cards/

Do not migrate all legacy KNOWLEDGE files.

Existing:
- decisions.md
- traps.md
- harness.md
- ADRs
- architecture notes
- arbitrary durable Markdown

remain legal and authoritative under the existing contract.

A card is for distilled cross-session knowledge whose future retrieval matters.

Use one file per lesson with a stable descriptive slug, for example:

.saipen/KNOWLEDGE/cards/standalone-subtools-in-utility-hubs.md

Do NOT introduce a global K-### counter unless repository inspection proves
there is already a safe reusable identity allocator.
The filename is sufficient identity for v1.

Keep the machine-readable header deliberately tiny and stdlib-parseable.

Required conceptual fields:

kind: lesson | decision | trap | convention
scope: comma-separated bounded retrieval terms
trigger: short description of the future situation in which this matters
status: active | superseded
evidence: one or more durable project references
supersedes: optional relative card path(s)

Then a short human body:

# <title>

<one concise claim>

Why:
<short causal explanation>

The exact syntax may be improved during implementation, but it MUST:
- remain plain Markdown;
- require no YAML dependency;
- be deterministic to parse with Python stdlib;
- remain pleasant to edit manually;
- keep the claim and WHY close together.

Example semantic shape:

kind: lesson
scope: SAITULS, architecture, utilities, subtools
trigger: adding a substantial utility to a utility hub
status: active
evidence: <real repository evidence>
supersedes: none

# Keep substantial utilities standalone

When adding a substantial utility to SAITULS, prefer a standalone subtool with
thin launcher integration rather than embedding its implementation into the hub.

Why:
The LIMISAW extraction demonstrated that embedding substantial tool logic in
the host increases coupling and makes later separation more expensive.

Do NOT fabricate the evidence in this repository if that specific LIMISAW
history is not actually present here.
The scenario below may use a fixture carrying equivalent evidence.

============================================================
5. EVIDENCE CONTRACT
============================================================

Every structured knowledge card MUST have evidence.

Evidence may name existing durable project evidence such as:
- T-###;
- E-###;
- commit hash;
- ADR/path;
- test/repro path;
- explicit human decision already recorded canonically.

Do not require every project to use Git.

Do not require a T/E reference when another durable repository-owned source is
the correct authority.

A bare statement such as:
"agents work better this way"
is not admissible durable memory.

Knowledge is allowed to compress evidence.
It is not allowed to replace evidence.

============================================================
6. COMPACT KNOWLEDGE INDEX
============================================================

Add a deterministic compact index for retrieval:

.saipen/KNOWLEDGE/INDEX.md

The index is a PROJECTION, never authority.

Generate it mechanically from:
- structured cards;
- and, if useful without guessing semantics, the filename/H1 of legacy
  KNOWLEDGE documents.

Do not synthesize LLM-written summaries while generating the index.

For structured cards the index should expose only compact retrieval metadata:

path
kind
scope
trigger
status

For legacy files with no structured metadata, list only mechanically provable
information such as path/title.

Example:

- cards/standalone-subtools-in-utility-hubs.md
  | lesson
  | scope: SAITULS, architecture, utilities, subtools
  | trigger: adding a substantial utility to a utility hub
  | active

The generated index MUST:
- be deterministic;
- have a generated marker;
- carry a content digest or equivalent stale-view check;
- contain no full card bodies;
- stay small relative to the KNOWLEDGE tree.

Deletion of INDEX.md loses no canonical knowledge.
It can always be regenerated.

============================================================
7. RETRIEVAL CONTRACT
============================================================

Strengthen SCOUT/BOOT behavior without increasing cold-start bulk.

Do NOT load the whole KNOWLEDGE tree.

Expected route:

current ticket / explicit objective
       ↓
KNOWLEDGE/INDEX.md if present
       ↓
match scope + trigger + obvious filename/title relevance
       ↓
load smallest relevant set of knowledge files/cards
       ↓
inspect source/code
       ↓
make decision

If INDEX.md is absent:
- preserve current behavior;
- search relevant KNOWLEDGE directly;
- do not fail legacy projects.

If no relevant knowledge exists:
- continue normally.

If several items plausibly apply:
- load the smallest set needed to decide;
- expand only when ambiguity remains.

A future agent must never be told to read every memory file "just in case".

This is a context-reduction feature as much as a memory feature.

============================================================
8. MEMORY MUST BE ABLE TO CHANGE A DECISION
============================================================

Add a narrow rule:

When retrieved durable knowledge materially affects a discretionary decision,
the agent should be able to name the knowledge source in its reasoning/evidence
record.

Do NOT require noisy user-visible citation on every response.
Do NOT LOG "memory used" merely because a file was opened.

Only when it materially changes a decision.

Example:

without lesson:
new substantial tool → tempting direct embedding

with retrieved lesson:
new substantial tool
→ retrieve standalone-subtool lesson
→ choose standalone implementation + thin integration

This is the acceptance target.

Storage without behavioral effect is not successful memory.

============================================================
9. SUPERSESSION / STALE KNOWLEDGE
============================================================

Durable memory must not become an immortal lie.

Structured cards support:

status: active
status: superseded

When new verified evidence invalidates an old card:

- do not silently delete historical reasoning;
- mark the old card superseded;
- point it at the replacement via `supersedes` / replacement linkage using the
  simplest unambiguous design;
- only active cards participate in normal retrieval;
- forensic/manual reading can still inspect superseded cards.

Do not permit two active cards that make directly contradictory claims about
the same scoped invariant when the contradiction is mechanically detectable.

Do not attempt general natural-language contradiction solving.
That would be fake intelligence encoded as a validator.

============================================================
10. KNOWLEDGE MAINTENANCE
============================================================

CLEAN may perform bounded KNOWLEDGE hygiene:

- regenerate stale INDEX.md;
- detect missing card targets;
- detect duplicate card paths/slugs;
- surface orphaned supersession links;
- identify obviously obsolete structured metadata.

CLEAN MUST NOT delete a knowledge card merely because it is old.

Age is not invalidity.

Only explicit supersession or evidence can retire a durable lesson.

============================================================
14. WHERE PROMOTION OCCURS
============================================================

Do not turn every phase into a memory writer.

Preferred ownership:

SCOUT:
- retrieve relevant knowledge before architecture discovery;
- may record newly discovered durable facts when already verified by repository
  authority.

REVIEW:
- bounded promotion check after independent evidence exists:
  "Did this ticket reveal a verified reusable lesson that can change a future
  decision?"
- usually answer NO.
- if YES, upsert one card or update/supersede an existing one.

CLEAN:
- structural memory/index hygiene only.

SHIP:
- should not grow a second memory lifecycle.
- release mechanics remain release mechanics.

Adjust exact owner placement if repository inspection finds a stronger existing
boundary, but preserve the principle:
few writers, targeted readers.

============================================================
15. DO NOT TURN KNOWLEDGE INTO A SECOND LOG
============================================================

Explicitly reject cards whose content is primarily:

- "T-123 was completed";
- "tests passed on Tuesday";
- "agent X tried Y";
- "version 7.x shipped";
- session narration;
- current blockers;
- current next_action;
- complete failure transcripts.

Those belong to BOARD/LOG/STATE/kitchen.

A good card answers:

"What should a future intelligence know BEFORE it makes this class of decision,
and WHY?"

============================================================
16. DO NOT TURN KNOWLEDGE INTO PROTOCOL RULES
============================================================

Project KNOWLEDGE may say:

"This repository uses standalone subtools for substantial utilities because..."

It must NOT become a backdoor place for changing universal SAIPEN semantics.

Universal SAIPEN rules remain under the existing normative ownership map.

Project memory is evidence/context, not a hidden higher-precedence instruction
channel.

Preserve the existing precedence:
current user request
> project/task requirements
> SAIPEN normative rules
> verified evidence
> lower-precedence preferences/context

17. HOSTILE / REGRESSION TESTS
============================================================

Add deterministic tests.

A. Backward compatibility
1. project with no KNOWLEDGE directory behaves exactly as before;
2. project with legacy decisions.md/traps.md but no cards behaves as before;
3. missing INDEX.md is not an error;
4. deleting INDEX.md loses no authority.

B. Card validation
5. valid card parses;
6. missing evidence fails card validation;
7. invalid kind/status fails;
8. self-supersession fails;
9. missing supersession target fails;
10. path traversal in a card link fails;
11. duplicate identity/path fails safely.

C. Index
12. same card tree generates byte-identical INDEX.md;
13. changed card makes existing index stale;
14. regeneration restores exact projection;
15. index contains metadata only, not full card body;
16. superseded cards are visibly non-active.

D. Retrieval
17. unrelated current task does not cause all cards to load;
18. matching scope/trigger selects the relevant card;
19. multiple plausible matches expand only to the needed set;
20. stale/missing index falls back safely without treating projection as
    authority.

E. Promotion
21. task-local completion does NOT produce a card;
22. a verified reusable cross-session lesson qualifies;
23. a guess does not qualify;
24. a duplicate lesson updates/reuses existing knowledge rather than appending a
    semantic twin;
25. contradictory newer verified evidence supersedes rather than silently
    coexisting as active truth.

F. Security
26. secret-like values remain rejected by existing KNOWLEDGE hygiene;
27. INDEX generation never copies secret/body content into the projection.

G. Protocol/context size
28. ordinary cold continuation does not load all knowledge cards;
29. projects with hundreds of unrelated cards still load only index + relevant
    subset;
30. no new state field/phase is required.

18. BEHAVIORAL ACCEPTANCE: PAST EXPERIENCE CHANGES FUTURE DECISION
============================================================

Create a deterministic fixture representing this sequence.

Past episode:
- a utility was embedded directly in a host;
- later evidence showed increased coupling / difficult extraction;
- the verified reusable lesson was promoted:
  substantial utility → standalone subtool + thin host integration.

Cold future episode:
- fresh agent context;
- no chat history;
- new ticket asks to add a different substantial utility to the same class of
  host;
- source tree alone does not force either architecture;
- KNOWLEDGE card is relevant by scope/trigger.

Acceptance requires proving:

1. the cold route finds the index/card;
2. it does not load the whole memory tree;
3. the card's WHY/evidence is available;
4. the resulting planning/scout context carries the standalone-subtool
   constraint/recommendation;
5. removing the card from the fixture removes that memory-derived influence;
6. no hidden conversation/session memory is used.

Do not assert that an LLM will deterministically choose one architecture from
English prose.

Test the deterministic substrate:
the relevant lesson MUST be surfaced in the bounded context supplied to the
decision step.

That is the machine-checkable boundary.
