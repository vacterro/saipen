OBJECTIVE
Determine whether the protocol lacks effective protection against

or whether an operational reconciliation path was skipped.

PHASE 1 — ROOT CAUSE

Inspect the live SAIPEN implementation and existing contracts for:
- Work closure evidence.
- Source receipt closure.
- Code changes after verification.
- Regression invalidation.
- Knowledge and evidence dependencies.
- Verification fingerprinting.
- Active task ownership and admission.
- Current-state reconciliation.

Do not invent source paths before locating the real implementation.

Distinguish:
A. Historical evidence was valid but later became stale.
B. Closure happened without valid evidence.
C. Evidence remained valid but its meaning was overclaimed.
D. Existing regression detection failed.
E. An operator or agent bypassed the supported protocol.

Require evidence before selecting a classification.

PHASE 2 — DESIGN AN ENFORCEABLE GUARD

A previously VERIFIED requirement must not automatically imply that
the current code still satisfies it.

Introduce or repair targeted regression-suspect detection.

Desired behavior:
1. Associate verified requirements with meaningful implementation
   dependencies and reproducible verification evidence.
2. Detect changes that may invalidate those assumptions.
3. Recheck affected requirements with focused tests or behavioral
   invariants where possible.
4. Mark contradictions as CURRENT_REGRESSION or an existing equivalent
   supported state.
5. Preserve original historical evidence unchanged.
6. Attribute newly discovered defects to new legal Work ownership.
7. Prevent duplicate tickets for already active recovery work.
8. Avoid re-running every historic test for every unrelated edit.
9. Keep performance bounded for large repositories.
10. Provide exact reasons for any inability to verify.

Use the existing protocol vocabulary and schemas where possible.
Avoid creating parallel, incompatible state machinery.

PHASE 3 — NEGATIVE CONTROLS

Test at least:

- A verified function is later replaced with an incorrect implementation.
- A required dependency is removed.
- A test is deleted or weakened.
- A harmless formatting change touches the same file.
- A refactor preserves the behavioral contract.
- A closed source has an active successor repair ticket.
- Two agents attempt reconciliation simultaneously.
- A historical receipt is immutable but its current validation is stale.

The guard must detect real contradictions without treating every changed
byte as proof of failure.

PHASE 4 — ADMISSION AND RECOVERY

Prefer fail-open degraded engineering operation when safe.

A suspected historical regression should not freeze unrelated Work,
ordinary diagnostics, or all application development.

Hard-block only an operation that cannot be performed safely or whose
required integrity guarantee is actually violated.

Never silently close a confirmed regression as already VERIFIED.

Do not rewrite source history to make the current snapshot look clean.

PHASE 5 — VERIFICATION

Run focused protocol tests, relevant lifecycle tests, regression controls,
and the supported full verification gates.

Measure the detection overhead.

Document:
- The actual root cause.
- The guard or workflow correction.
- False-positive controls.
- False-negative controls.
- Remaining limitations.
- Migration impact on existing project states.

NON_GOALS

implementation demonstrably regresses, without destroying its historical
closure evidence or blocking unrelated safe engineering.
