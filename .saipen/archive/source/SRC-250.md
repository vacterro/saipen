# User request

## Request

SAIPEN

SOFT APPEND — LONG-TERM RELIABILITY, COMPLEXITY CONTROL AND AUTONOMOUS CONVERGENCE

EXECUTOR: SAIPEN agent
MODEL: Claude Opus Max
MODE: Non-disruptive continuation
PRIORITY: Architectural reliability over short-term throughput

MISSION

Continue the existing authorized SAIPEN engineering mission.

The operator explicitly accepts additional engineering time when that investment demonstrably reduces future failures, manual intervention, repeated recovery, or long-term maintenance costs.

This is not permission for unlimited refactoring, speculative architecture, or endless hardening.

The objective is to make SAIPEN increasingly reliable, predictable, comprehensible, and autonomous across models of different capabilities.

The ultimate target is a system where authorized agents can execute cc, continue, and cc all, recover from ordinary failures, complete legitimate work, and preserve trustworthy state with minimal human involvement.

Do not interrupt the active ticket.
Do not override ownership.
Do not bypass admission.
Do not create a new meta-project.
Integrate these principles into existing admitted work.

============================================================
1. CORRECTNESS BEFORE SPEED
============================================================

Prioritize root causes that can produce:

- Unauthorized lifecycle transitions.
- State or journal corruption.
- Concurrent overwrites.
- Lost or duplicated work.
- Recovery deadlocks.
- Contradictory CLI instructions.
- False success or false completion.
- Stale or fabricated evidence.
- Unsafe filesystem or identity handling.
- Repeated unnecessary operator intervention.
- Divergence between protocol state and actual product behavior.

These defects justify deeper investigation even when the immediate patch appears small.

Avoid cosmetic improvements while fundamental reliability defects remain.

Prefer removing an entire failure class over repeatedly correcting individual symptoms.

Never weaken security, provenance, ownership, or forensic integrity to improve throughput.

============================================================
2. MEASURE THE COST OF THE PROTOCOL
============================================================

Establish a lightweight, reproducible baseline using existing logs, tests, and lifecycle evidence.

Previously observed approximate measurements:

- 350 KB protocol Markdown.
- Approximately 100 CLI subcommands.
- Approximately 6450 tests.
- 27–51 minutes per ticket in the measured sample.
- Approximately 75 parked administrative records.

Treat these as historical observations, not universal performance benchmarks.

Measure the following where reliable evidence exists:

A. Median and P90 lifecycle duration.
B. Time spent performing useful engineering work.
C. Time spent on protocol administration.
D. Validation and regression execution time.
E. Repeated continuation attempts.
F. Number of recovery operations per ticket.
G. Unnecessary manual operator actions.
H. Repeated validation of unchanged evidence.
I. Duplicate administrative records.
J. Number of genuine execution blockers.
K. Rate of successful end-to-end task completion.
L. Complexity added or removed by each correction.

Distinguish elapsed time from actual computational work.

Separate cold starts, ordinary work, recovery work, and release work.

Avoid comparing unrelated ticket classes as though they have identical costs.

Reuse existing evidence and instrumentation.

Do not build an additional telemetry subsystem merely to collect these measurements.

============================================================
3. COMPLEXITY MUST HAVE A JUSTIFICATION
============================================================

For every meaningful architectural correction, evaluate:

- Which failure class does it eliminate?
- Which existing mechanism owns the responsibility?
- Does this introduce another authoritative state?
- Does this add a new mandatory step to ordinary continuation?
- Does this add another compatibility fallback?
- Does this introduce persistent metadata or recovery obligations?
- Could an existing component solve the same problem?
- Can existing behavior be simplified or removed safely?
- What is the regression and migration risk?

Prefer:

One authoritative owner per fact.

One canonical transition per lifecycle operation.

One trusted runtime-resolution policy.

One consistent recovery path per failure class.

One coherent operator-action contract.

One supported completion and reconciliation mechanism.

Read-only projections may exist, but must never become independent competing authorities.

Avoid creating new tickets or protocol layers for problems already represented by admitted work.

============================================================
4. KEEP THE COLD PATH SMALL
============================================================

The observed minimal cold path is:

BOOT
continue --json
phase file

Preserve this architectural advantage.

Ordinary authorized work should not require understanding the complete protocol.

Keep optional machinery outside the normal execution path unless genuinely required:

- Crew coordination.
- Publication and release.
- Advanced recovery.
- Multi-account administration.
- Concurrent execution.
- Legacy migrations.
- Optional audit tooling.

Do not remove the security checks needed for ordinary operations.

Instead, eliminate unnecessary dependencies, duplicated checks, misleading fallbacks, and manual ceremony.

A weaker model must be able to follow the ordinary path deterministically.

Protocol correctness must not depend on exceptional model reasoning ability.

============================================================
5. SELF-HEALING WITHOUT FALSE AUTHORITY
============================================================

Make recoverable failures recoverable automatically when the canonical protocol already authorizes the recovery.

Expected behavior:

1. Detect a concrete recoverable condition.
2. Identify its authoritative owner.
3. Verify current admission and state.
4. Execute a bounded canonical repair.
5. Validate the repair.
6. Resume the ORIGINAL user request idempotently.
7. Report the actual result.

Examples:

- Refresh genuinely stale validation evidence.
- Repair safely reproducible derived metadata.
- Complete deterministic source reconciliation.
- Resume an interrupted authorized operation.
- Resolve a known safe runtime-generation mismatch.

Do not automatically repair conditions involving:

- Untrusted operator provenance.
- Foreign ownership.
- Missing privileged authorization.
- Corrupt forensic history without an admitted recovery route.
- Ambiguous destructive filesystem operations.
- Conflicting authoritative identities.
- Missing explicit cutover approval.

Avoid recovery systems that themselves create unnecessary recovery obligations.

A bounded failure must produce a clear terminal reason, not an infinite retry loop.

============================================================
6. MAKE COMPLETION ACTUALLY COMPLETE
============================================================

An ordinary authorized task should not require a second administrative cleanup mission after its legitimate engineering completion.

Investigate recurring cases where:

- Work is DONE but source receipts remain ACTIVE.
- Verification passes but completion remains unnecessarily blocked.
- continue recommends an operation that claim rejects.
- A completed phase needs redundant manual reconciliation.
- A successful dry-run is mistaken for real execution.
- A recovery operation leaves unexplained pending work.

Where all required evidence and authority already exist, make canonical completion deterministic and self-contained.

Never invent missing evidence or approval.

Do not automatically close genuinely unresolved audit requirements.

============================================================
7. VALIDATE WITH REAL WORKFLOWS
============================================================

Unit-test coverage is necessary but insufficient.

Maintain a small representative acceptance matrix:

1. Clean authorized continuation.
2. Cold start after context loss.
3. Interrupted work followed by resume.
4. Recoverable stale-evidence condition.
5. Unauthorized or foreign-owner refusal.
6. Legitimate work completion with source reconciliation.
7. Windows managed-account execution.
8. Concurrent access conflict without lost updates.

Include real host and operating-system verification where required and authorized.

Use disposable fixtures for destructive testing.

Measure the real user-visible result.

Do not report a simulation as actual Windows acceptance.

Do not consider a successful continue response proof that the product task reached DONE.

Use the established SMART_VAC_CLEANER AG3 scenario as a high-value integration regression when its current project authority permits it.

SAITULS and AUDAPACK must retain independent admission and ownership.

============================================================
8. LONG-TERM MAINTENANCE ECONOMICS
============================================================

The operator is willing to invest additional time now to reduce future maintenance.

Evaluate this investment rationally.

For relevant corrections, compare:

CURRENT COST:
Repeated failures, manual recovery, additional tool calls, validation overhead, wasted model context, and lost engineering progress.

EXPECTED BENEFIT:
Reduced recurrence, simpler control flow, fewer interventions, shorter recovery, or stronger integrity.

IMPLEMENTATION COST:
Engineering time, additional code, migration complexity, regression risk, and future maintenance.

Do not invent numerical savings.

Use observed measurements whenever possible.

An expensive correction is justified when it eliminates a significant recurring failure class.

A speculative refactor without demonstrated benefit is not.

Treat the suggested 40–60% reduction in avoidable protocol overhead as an aspirational optimization target, not an acceptance requirement.

Correctness and security remain mandatory.

============================================================
9. AVOID UNNECESSARY FRAMEWORK GROWTH
============================================================

Do not introduce:

- New orchestration frameworks without proven need.
- New parallel authorities.
- Additional compatibility paths without expiration rules.
- Duplicate registries.
- Redundant lifecycle states.
- Self-repair mechanisms without bounded termination.
- New long-lived protocol metadata for transient observations.

Where practical, simplify existing implementation while performing admitted corrections.

Remove obsolete behavior only after demonstrating that its removal preserves supported consumers and migration guarantees.

Prefer small, independently verifiable architectural corrections over a broad CORE rewrite.

The entire CORE has not yet received a comprehensive architectural assessment.

Do not assume local findings justify replacing the global architecture.

============================================================
10. WEAKER-MODEL ACCEPTANCE
============================================================

The ecosystem must not require Claude Opus Max to perform every ordinary task.

Evaluate whether a less capable agent can:

- Identify the authoritative next action.
- Execute the instructed command.
- Interpret a structured refusal.
- Follow a supported recovery path.
- Resume legitimate work.
- Complete a normal lifecycle.
- Report blockers without fabricating authority.

Prefer concise structured machine-readable responses with one exact next action.

Keep optional diagnostics available without flooding the ordinary agent with administrative details.

The protocol must carry complexity internally rather than transferring it to the model.

============================================================

SAITULS agent:
Account Control Plane, managed accounts, Windows integration.

AUDAPACK agent:

Do not modify a target project based solely on SAIPEN admission.

Do not modify the corrupt original AUDAPACK lineage.

Do not force an operator-paused project into normal execution.

Cross-project integration acceptance must be demonstrated independently by the responsible project.

============================================================
12. CONTINUOUS IMPROVEMENT WITHOUT ENDLESS WORK
============================================================

After each significant admitted correction, record concise evidence of:

- Root cause eliminated.
- Regression coverage.
- Actual workflow improvement.
- Administrative steps removed or added.
- Remaining known risks.
- Whether overall complexity increased or decreased.

Do not create additional permanent reports when existing evidence can carry the result.

Periodically compare against the established baseline.

The desired trend:

- Fewer recurring failures.
- Fewer manual recoveries.
- Fewer contradictory instructions.
- Lower unnecessary protocol overhead.
- Higher successful task-completion rates.
- Stable or decreasing accidental complexity.
- Preserved security and integrity.

Do not pursue arbitrary test-count growth or ticket-count growth as success metrics.

Do not wait for every parked or future-gated ticket to close.

When core workflows are genuinely reliable, prefer stabilization and normal project operation over speculative hardening.

============================================================
13. STOP AND ESCALATION RULES
============================================================

Continue autonomously within verified authority.

Do not request operator intervention for routine, safely recoverable conditions.

Request operator involvement only for genuinely required decisions or permissions.

Stop the affected operation on:

- Missing admission.
- Foreign active ownership.
- Untrusted provenance.
- Unsafe destructive action.
- Unresolved forensic corruption.
- Required privileged approval.
- Repeated ineffective recovery.
- A proposed correction that cannot pass real acceptance.

Continue unrelated independently authorized work where possible.

Never bypass a gate to improve performance statistics.

============================================================
14. DEFINITION OF SUCCESS
============================================================

The mission is not to make SAIPEN infinitely sophisticated.

The mission is to make SAIPEN boringly reliable.

Success means:

An ordinary authorized task begins predictably.

The agent receives an exact next action.

Valid work proceeds without unnecessary administrative friction.

Recoverable failures are handled canonically.

Unrecoverable or unauthorized operations refuse safely.

Evidence remains trustworthy.

Completion reconciles automatically where authorized.

Interrupted work resumes correctly.

Different model capabilities do not change protocol correctness.

The operator rarely needs to intervene.

And every substantial architectural investment produces a measurable improvement in reliability, safety, simplicity, or maintenance cost.

FINAL DIRECTION

Finish the currently admitted Work.

Continue existing priorities without forced ownership changes.

Focus on systemic causes rather than isolated symptoms.

Preserve the minimal cold path.

Make the system simpler whenever evidence justifies it.

Invest engineering time now where doing so prevents substantially greater future costs.

Do not introduce complexity merely to manage complexity.

The final measure of success is not how many protocol mechanisms exist.

It is how reliably autonomous agents accomplish legitimate work without human babysitting.
