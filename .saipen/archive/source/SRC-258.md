HOW THE HOST PICKS ONE

PATH resolves the shim, not the project:

  $ cat /c/Users/vac34/bin/saipen
  #!/bin/sh
  exec ".../python.EXE" "V:\...\_SAIPEN\tools\saipen.py" "$@"

So bare `saipen` runs the V install, while the project records the C install:

  .saipen/STATE.md:  saipen_home: "C:\\Users\\vac34\\.agents\\skills\\saipen"

The engine already detects this and says so, in `saipen validate --json`:

  install_identity.mismatch: "the RUNNING install is V:\...\_SAIPEN but
  STATE.saipen_home names C:\Users\vac34\.agents\skills\saipen -- two
  divergent installs answer to the same VERSION (8.1.0). Evidence produced
  now is attributable to the running one, not the named one. Run saipen
  through the install STATE names, or repoint the state with
  `saipen rebind-home`."

MEASURED CONSEQUENCE (SMART_VAC_CLEANER T-198/T-195)

`saipen transition REVIEW` refused:

  INCOMPLETE_TICKET: VERIFY -> REVIEW: STALE_REGRESSION_EVIDENCE:
  verifier or subject bytes changed

At that moment, with the pairs freshly re-executed against the current tree,
direct calls into BOTH engines' decision code answered admissible:

  C engine  sr.regression_execution.evidence_gate(root,'T-198',docs,state) -> None
  V engine  sr.regression_execution.evidence_gate(root,'T-198',docs,state) -> None
  C engine  sr.operations._regression_gate(docs,'T-198')                 -> None
  V engine  sr.operations._regression_gate(docs,'T-198')                 -> None

and the CLI succeeded on the next invocation:

  $ python V:/.../_SAIPEN/tools/saipen.py transition REVIEW --project-root .
  -> TRANSITIONED, E-318

So the refusal was not a stable product or evidence verdict; it was
route-dependent on which install answered and on the T-1771 clause-derivation
step running first. A gate whose answer moves with the caller's PATH cannot be
trusted by an unattended goal run, because the run cannot tell a real failure
from an install-skew artefact.

SECOND-ORDER RISK

`saipen validate --json` reports install_identity.mismatch as a DIAGNOSTIC and
still returns verdict PASS / repair_status HEALTHY. A goal executor reading
only the verdict proceeds on evidence attributable to an install the project
never named. The mismatch is well-written prose in a field most callers never
read.

REQUESTED PROTOCOL ACTION (SAIPEN Core owner decides, not this executor)

1. Make the running-install vs STATE.saipen_home mismatch BLOCKING for any
   mutating verb, or auto-route to the named home, or auto-rebind under the
   operator's existing authority. Do not leave a silent two-install split.
2. Make VERSION insufficient as an install identity. Both installs say 8.1.0
   while 16 engine files differ; the version alone cannot distinguish them.
   A content fingerprint (the mechanism `install_identity.install_fingerprint`
   already computes) should be the compared value.
3. Reconcile the two trees, or declare one canonical and retire the other, so
   `C:` and `V:` cannot answer differently to the same command.
4. Decide whether T-1771 `_derive_request_clauses` belongs in the C install;
   today the closure path differs by install.
