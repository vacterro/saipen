======================================================================
A. PROBLEM STATEMENT
====================

A cold or scheduled SAIPEN host can currently read the projected startup instructions:

BOOT.md
STYLE.md
EXECUTION.md

but may still fail before reaching canonical SAIPEN machine truth because the execution transport is unresolved.

Observed failure pattern:

```
python -m saipen status --json
    -> No module named saipen

where saipen
    -> executable not found
```

The model then has incentive to improvise alternate invocation forms.

This is the defect.

The logical SAIPEN command surface and the physical executable transport are insufficiently separated for cold hosts.

A model MUST NOT have to guess:

* whether SAIPEN is installed as a Python package;
* whether `saipen` is available on PATH;
* where the canonical repository is;
* whether `tools/saipen.py` should be invoked directly;
* whether a launcher is stale or canonical;
* which Python interpreter owns the runtime;
* whether a discovered runtime is admitted for mutation.

======================================================================
E. REQUIRED RESOLUTION STATES
=============================

Define a structured resolution result.

Exact internal naming may follow existing project conventions, but it must distinguish at least the following meanings:

PATH_LAUNCHER

```
A canonical admitted launcher is available through the normal command path.
```

DIRECT_LAUNCHER

```
A canonical launcher exists and can be invoked directly even though PATH resolution is unavailable.
```

DIRECT_ENGINE

```
The canonical engine can be invoked through a proven Python interpreter and canonical tools/saipen.py path.
```

RUNTIME_REBOUND

```
Existing persisted runtime binding was stale, but a canonical recovery/rebind path successfully established a valid replacement.
```

HUMAN_REQUIRED

```
Runtime exists but a required human-only authorization or setup boundary prevents continuation.
```

HOST_UNSUPPORTED

```
Runtime is discoverable but the current host is not admitted for the requested operation.
```

PROJECT_UNBOUND

```
No canonical project binding can be established safely.
```

RUNTIME_UNAVAILABLE

```
No valid executable runtime can be established.
```

Do not collapse these states into one generic failure.

======================================================================
F. ENTRY RESOLUTION CONTRACT
============================

Provide one machine-consumable resolver boundary.

Conceptually:

```
resolve_entry(
    project_root,
    host,
    environment
) -> EntryResolution
```

The concrete API may differ if existing architecture already provides a better integration point.

A successful resolution should carry enough structured information to execute the requested logical command without additional model inference.

Possible fields include:

```
ok
code
transport
argv_prefix
project_root
saipen_home
runtime_identity
host_admission
diagnostics
```

Do not expose fields that cannot be proven.

Do not use environment variables alone as authority.

======================================================================
G. RESOLUTION ORDER
===================

Derive the exact order from the existing bootstrap implementation.

The expected policy is approximately:

1. establish project binding;
2. inspect persisted canonical SAIPEN home if present;
3. validate provenance / identity of that runtime;
4. prefer an admitted canonical PATH launcher when available;
5. otherwise use a canonical direct launcher;
6. otherwise use a canonical direct engine invocation;
7. if persisted binding is stale, use the existing canonical recovery/rebind mechanism;
8. otherwise return a structured unavailable or human-required state.

Do not perform disk-wide discovery.

Do not pick the first executable named `saipen`.

Do not trust an arbitrary PATH hit solely because its filename matches.

Do not search unrelated repositories.

======================================================================
L. SECURITY AND AUTHORITY INVARIANTS
====================================

The resolver must preserve current SAIPEN authority boundaries.

A reachable engine does NOT automatically imply mutation authority.

A valid launcher does NOT automatically imply host admission.

A discovered repository does NOT automatically become canonical.

A stale persisted SAIPEN home must not silently win over a newly proven canonical runtime.

A same-name executable from another installation must not be trusted without provenance.

A host that is unsupported for mutation must remain blocked from mutation even when direct engine invocation is technically possible.

Do not weaken host admission to improve launch success.

Do not confuse runtime discovery with runtime authorization.

======================================================================
M. FAIL-OPEN / FAIL-CLOSED POLICY
=================================

Follow the existing generalized recoverable SAIPEN policy.

If the project can physically and safely launch through another canonical transport:

```
continue through that transport and report degraded resolution if relevant.
```

Hard-block only when:

```
no valid runtime exists;
project binding cannot be established;
host authority is insufficient;
required provenance cannot be proven;
continuing would be unsafe.
```

PATH failure by itself is not a hard blocker.

Missing Python package installation by itself is not a hard blocker when the canonical engine is otherwise executable.

no `saipen` executable on PATH

CASE 2 — CANONICAL PATH LAUNCHER AVAILABLE

Given:

Expected:
launcher is not trusted as canonical

CASE 4 — DIRECT LAUNCHER AVAILABLE, PATH EMPTY

Expected:
direct canonical launcher succeeds

CASE 5 — DIRECT ENGINE ONLY

Given:
launcher unavailable

Expected:
direct engine transport succeeds

CASE 6 — STALE PERSISTED HOME

Given:
persisted saipen_home is dead or invalid
a canonical recoverable replacement is provable

Expected:
canonical recovery/rebind path executes
stale binding does not remain authoritative

CASE 7 — RUNTIME REACHABLE, HOST UNSUPPORTED

Expected:
discovery may succeed
mutation remains refused
HOST_UNSUPPORTED or equivalent structured result

CASE 8 — PROJECT UNBOUND

Expected:
no arbitrary repository selection
structured PROJECT_UNBOUND result

CASE 9 — NO RUNTIME

Expected:

no repeated command guessing

CASE 10 — SCHEDULED COLD START

Given:
scheduled-source contains BOOT / STYLE / EXECUTION

host reaches canonical `status --json`

Run the same read-only logical command through every supported canonical transport:

```

```

CASE 12 — MUTATION AUTHORITY

Resolve the engine from a host that is not mutation-admitted.

Expected:

Q. ACCEPTANCE
=============

This append is accepted only when:

1. A cold scheduled host with empty PATH can still reach canonical SAIPEN status when a valid direct runtime exists.

2. No normal runtime path requires the LLM to guess an executable invocation.

3. `python -m saipen` is not used as a fallback unless the project intentionally becomes an installable Python package and canonical policy explicitly supports it.

4. Foreign/stale same-name launchers are not trusted as canonical solely by PATH discovery.

5. Runtime discovery remains separate from mutation admission.

6. Unsupported hosts remain unable to mutate canonical state.

7. Stale persisted runtime binding has a deterministic recovery/rebind path where recovery is possible.

8. No disk-wide scanning is required.

9. Resolution failure is structured and bounded.

10. Existing canonical launcher/direct-engine behavior remains regression-green.

11. BOOT / EXECUTION cold-start instructions describe logical command invocation without requiring brittle transport assumptions.

12. Scheduled execution reaches canonical machine truth without human intervention when the required capabilities are genuinely available.
