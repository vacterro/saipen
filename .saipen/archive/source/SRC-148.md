PRIMARY FINDING — RECONCILIATION RECOVERY GUIDANCE IS MISLEADING

Observed sequence:

`saipen improve cycle-complete <cycle>`

refused completion because six improve seats had stale `source_head` values relative to the current project HEAD.

The protocol/tool error guidance suggested effectively re-running or re-sweeping findings.

That path was not viable.

The sweep ledger is append-only and rejects another entry for an already existing:

    (finding_ref, report)

pair.

Therefore the suggested recovery route cannot repair this class of stale improve-seat state.

The actual working recovery was:

    saipen improve reconcile <cycle>

Reconcile correctly:
- classified the stale seats;
- matched them against one CURRENT_COMPLETE replacement with equivalent scope;
- superseded the six stale seats;
- preserved all report bytes by SHA-256;
- did not rewrite or delete historical reports;
- allowed the cycle to converge.

Required investigation:

1. Reproduce this lifecycle in a controlled fixture.

2. Identify the exact code path producing the misleading recovery guidance.

3. Determine whether:
   - `cycle-complete` should directly recommend `improve reconcile`;
   - reconciliation should be invoked automatically where deterministic and safe;
   - or another explicit recovery command is intended.

4. Ensure the suggested recovery action is executable under the append-only sweep-ledger contract.

5. Do not weaken append-only history guarantees merely to make the old guidance work.

Acceptance:

Given stale improve seats whose original finding/report ledger entries already exist, SAIPEN must provide a valid recovery path that can actually converge the cycle without rewriting history.

SECOND FINDING — AUDIT REPRO STATUS LABEL CAN REPORT THE OPPOSITE OF REALITY

This behavior was observed repeatedly during the SAILEARN improve cycle.

Several audit reproduction scripts classified a case as:

    REPRODUCED

when the tested operation raised an error.

However, in these cases the error was the newly correct protective behavior.

The actual defect condition was something such as:
- secret escaped sanitization;
- unsafe package path escaped package root;
- invalid candidate bypassed a promotion gate.

After repair, the system raised/refused correctly.

The reproduction helper nevertheless interpreted:

    "an exception / gate rejection happened"

as:

    "the original vulnerability reproduced"

rather than evaluating the actual defect predicate.

This occurred in multiple independent reproduction scripts.

Required investigation:

1. Locate the common audit/reproduction helper contract responsible for result classification, if one exists.

2. Define reproduction semantics around the actual defect predicate:

    REPRODUCED
        original unsafe/broken behavior occurred

    NOT_REPRODUCED
        protective/correct behavior prevented it

    BLOCKED / INVALID
        the reproduction itself could not establish either outcome

3. Do not infer REPRODUCED merely because the target command raised.

4. Add controlled fixtures for:
   - unsafe behavior succeeds -> REPRODUCED
   - guard rejects unsafe behavior -> NOT_REPRODUCED
   - harness itself fails -> BLOCKED/INVALID

5. Preserve enough evidence in the result to explain why the classification was chosen.

Acceptance:

A protective rejection can never be labeled REPRODUCED solely because an exception or non-zero result occurred.
