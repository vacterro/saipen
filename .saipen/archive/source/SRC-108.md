SAIPEN
APPEND TO CURRENT SAIPEN PROTOCOLIST MISSION
EXECUTION TIME / CHECKPOINT / DAILY PROGRESS TELEMETRY
Target executor:

```
Claude Opus 5.5

```

Recommended effort:

```
Max

```

This is a bounded append to the current SAIPEN mission.
Do not create another broad architecture umbrella.
Do not interrupt higher-priority active correctness / closure / field-gate work.
Capture this append through the canonical Source append mechanism.
Integrate it at the correct lifecycle point.
The intent is simple:

```
make SAIPEN able to show where execution time goes

```

without:

```
turning telemetry into another source of truth
adding heavy observability infrastructure
creating ceremonial logging
weakening QUALITY > TIME
slowing ordinary Work materially

```

The desired operator experience is:

```
"What happened today?"
"How long has this Work taken?"
"How long since the last checkpoint?"
"Where did the time go?"
"Was the agent progressing, waiting, verifying, or recovering?"

```

The answer should be available immediately and in a compact form.
======================================================================

1. CORE PRINCIPLE
======================================================================

Add one derived observability principle:

```
TIME IS OBSERVED.
TIME DOES NOT DEFINE TRUTH.

```

Execution telemetry may describe:

```
duration
pacing
waiting
checkpoint frequency
recovery cost
phase cost
Work throughput

```

It must never independently decide:

```
Work state
acceptance
PASS
DONE
Source ownership
mutation authority

```

Canonical truth remains owned by the existing SAIPEN state / event / evidence
owners.
Metrics are derived telemetry.
If the metrics cache disappears, SAIPEN must be able to reconstruct the useful
statistics from canonical durable events where practical.
Do not create a second lifecycle database.
======================================================================
2. RELATION TO QUALITY > TIME
This append exists partly to make QUALITY > TIME measurable.
Preserve:

```
slower != worse

faster != better

```

A weak or inexpensive model may take longer while preserving the same acceptance
quality.
Therefore keep QUALITY metrics and TIME / EFFICIENCY metrics separate.
Do not create one opaque "agent score".
Example:

```
Agent A:
    verified quality: PASS
    elapsed: 18m

Agent B:
    verified quality: PASS
    elapsed: 47m

```

Both may be valid successful executions.
The time difference is useful telemetry.
It is not permission to weaken B's acceptance.
======================================================================
3. USE DURABLE CHECKPOINTS AS THE NATURAL TIME BOUNDARY
SAIPEN already has meaningful durable checkpoints.
Use them as the primary pacing boundary.
For every durable checkpoint, derive or record enough timestamp identity to
calculate equivalents of:

```
checkpoint_at

previous_checkpoint_at

elapsed_since_previous_checkpoint

work_started_at

elapsed_on_current_work

phase_started_at

elapsed_in_current_phase

```

Do not create checkpoints solely to improve statistics.
Checkpoint semantics remain owned by progress/recovery requirements.
Metrics consume checkpoint events.
Metrics do not drive checkpoint spam.
======================================================================
4. MINIMUM ACTIVITY CLASSIFICATION
Keep activity classes intentionally small.
Prefer reuse of existing phase/runtime vocabulary.
The operator should be able to distinguish approximately:

```
SCOUT
BUILD
VERIFY
REVIEW
RECOVERY
WAIT
BLOCKED

```

Do not invent dozens of micro-categories.
If existing canonical phases already provide the required classification, derive
from them.
Do not duplicate them into another independent taxonomy.
Where execution time cannot be classified reliably:

```
classify UNKNOWN

```

Do not guess.
======================================================================
5. DISTINGUISH WALL TIME FROM USEFUL EXECUTION
At minimum expose separate concepts equivalent to:

```
wall time

active execution time

wait / external-tool time

blocked time

```

Exact accounting may be approximate where the host cannot provide trustworthy
signals.
Truthful approximation is better than fake precision.
Do not attempt to infer private model "thinking time" unless the host exposes a
reliable measured value.
The useful question is not:

```
"how many seconds was the neural network thinking?"

```

The useful question is:

```
"how much elapsed time did this Work consume, and what state was the
execution in?"

```

======================================================================
6. TIME TO DURABLE PROGRESS
Add one particularly useful derived metric:

```
TIME_TO_DURABLE_PROGRESS

```

Meaning:

```
elapsed time from the beginning of a bounded execution slice until the first
new durable progress evidence

```

Durable progress should reuse existing progress semantics.
Examples:

```
repository diff created

acceptance clause newly verified

focused regression changed RED -> GREEN

blocker narrowed by evidence

durable checkpoint advanced meaningfully

terminal lifecycle transition completed

```

Do not count:

```
repeated reads

repeated unchanged commands

repeated identical tests

prose confidence

model claims of progress

```

This metric should help compare execution methods without changing acceptance.
======================================================================
7. CURRENT WORK SUMMARY
Provide a compact read-only current Work view.
Target information:

```
active Work
phase
Work elapsed
phase elapsed
current bounded-slice elapsed
time since durable checkpoint
time since durable progress
current wait/block state

```

Example presentation:

```
CURRENT WORK
  T-#### VERIFY
  Work elapsed          1h 07m
  Phase elapsed           21m
  Current slice           12m
  Since checkpoint         6m
  Since progress           4m
  State              progressing

```

Exact wording may follow existing CLI style.
Do not expose misleading precision when data is unavailable.
======================================================================
8. TODAY SUMMARY
Add a simple daily rollup based on the user's / host's local day boundary where
the runtime already has a trustworthy timezone.
Target fields:

```
observed execution time

active execution time

wait time

blocked time

Work touched

Work completed

checkpoints

verified slices

recoveries

worker generations

agent incarnations

model/provider replacements where known

manual interventions

regressions found

regressions fixed

```

Keep this compact.
The goal is operator orientation, not accounting software.
Example:

```
TODAY
  Observed            6h 24m
  Active              4h 38m
  Waiting             1h 28m
  Blocked                18m

  Work touched             8
  Work completed           5
  Checkpoints             23
  Verified slices         17
  Recoveries               3
  Agent incarnations       4
  Manual interventions     0

```

If a field cannot be reconstructed reliably:

```
omit it

```

or:

```
report UNKNOWN

```

Do not synthesize a value.
======================================================================
9. CHECKPOINT PACE
Expose basic checkpoint pacing:

```
checkpoint count

average checkpoint interval

median checkpoint interval

longest checkpoint interval

```

Optionally:

```
shortest meaningful checkpoint interval

```

Avoid averages alone.
One 3-hour gap hidden inside many 2-minute checkpoints should remain visible.
Example:

```
CHECKPOINT PACE
  Count              23
  Average         11m 42s
  Median           8m 16s
  Longest         37m 09s

```

This is observability.
A long interval is not automatically failure.
Existing NO_PROGRESS / checkpoint policy remains authoritative.
======================================================================
10. WORK-LEVEL SUMMARY
Allow an operator to inspect one Work item's time distribution.
Equivalent command shape may be:

```
saipen stats --work T-####

```

Target output:

```
total observed duration

phase durations

checkpoint count

time to first durable progress

recoveries

agent incarnations

worker generations

verification time

blocked/wait time

terminal result

```

Example:

```
T-1475

  Total observed          41m 33s
  Time to first progress   6m 12s

  SCOUT                    8m
  BUILD                   14m
  VERIFY                  18m
  RECOVERY                 1m

  Checkpoints                5
  Agent incarnations          2
  Recoveries                  1

```

Do not require every historical ticket to have perfect telemetry before the
feature can ship.
Forward-correctness is acceptable when older events lack sufficient timestamps.
======================================================================
11. CLI SURFACE
Prefer one small read-only command family.
Candidate:

```
saipen stats

```

Default:

```
concise current-day summary

```

Useful options:

```
saipen stats --work T-####
saipen stats --days 7
saipen stats --json

```

Potential:

```
saipen stats --today

```

only if required for clarity.
Do not create many overlapping commands.
Do not make the command mutating.
Do not make metrics collection depend on the operator calling `stats`.
======================================================================
12. STATUS INTEGRATION
Add only a very small telemetry line to normal status/context output if it can
be done without noise.
Example:

```
TODAY: 5h42 active | 24 checkpoints | 6 Work done | 0 manual recovery
CURRENT: T-1344 VERIFY | 14m | checkpoint 5m ago

```

Do not dump the full dashboard into:

```
saipen status
saipen continue
AUTO_RECALL

```

AUTO_RECALL must remain bounded and execution-oriented.
If telemetry materially increases recovery payload size:

```
keep it out of AUTO_RECALL

```

except for the minimal progress timing already required by supervisor logic.
======================================================================
13. DERIVED DATA, NOT NEW AUTHORITY
Prefer deriving metrics from existing sources such as:

```
LOG events

checkpoint records

Work transitions

supervisor events

worker generations

recovery events

provider/runtime events

```

If performance requires a cache/materialized rollup:

```
make it explicitly reconstructable

version its schema

never make canonical lifecycle correctness depend on it

```

A deleted metrics cache must not prevent:

```
continue

recovery

claim

ship

finish

Source integrity

```

The system must degrade to:

```
telemetry unavailable

```

not:

```
protocol unavailable

```

======================================================================
14. CLOCK / TIMESTAMP RULES
Use one stable machine timestamp convention internally.
Prefer existing SAIPEN timestamp conventions.
Do not introduce mixed naive/local timestamp semantics.
Daily grouping may render in the configured/local timezone, but duration
calculation must not break across:

```
midnight

timezone offset changes

process restart

model replacement

supervisor restart

host restart where durable timestamps survive

```

Duration must come from durable timestamps, not conversation order.
======================================================================
15. MODEL / PROVIDER COMPARISON PREPARATION
This telemetry should later support the already planned quality-retention
matrix.
Do not build a leaderboard now.
But make the data sufficient to compare same-task runs on dimensions such as:
QUALITY:

```
acceptance result

regression escape

protocol violations

manual intervention

```

EFFICIENCY:

```
wall time

time to durable progress

checkpoint interval

Work duration

verification duration

repeated actions

recoveries

agent incarnations

provider/runtime usage where trustworthy and already available

```

Keep quality and efficiency fields separately queryable.
======================================================================
16. MANUAL INTERVENTION METRIC
Track operator intervention only where there is a deterministic event.
Examples:

```
manual re-kick

explicit operator gate response

manual continuation required

user repair required

```

Do not count ordinary new user requests as "manual recovery".
The particularly useful autonomy indicator is:

```
manual_recovery_count

```

Target for unattended execution:

```
0

```

This should align with existing T-1446 field metrics rather than create a
different meaning.
======================================================================
17. REGRESSION / DEFECT COUNTS
Where current Work lifecycle already records defects discovered/fixed during
execution, allow lightweight daily counts:

```
regressions_found

regressions_fixed

```

Do not attempt semantic defect mining from prose.
Count only durable classified events / Work transitions that can be identified
reliably.
If that cannot yet be done cleanly:

```
defer these two counters

```

They are useful but lower priority than timing/checkpoint telemetry.
======================================================================
18. PERFORMANCE BUDGET
The metrics layer must be cheap.
Ordinary mutation operations must not perform expensive historical scans merely
to maintain statistics.
Prefer:

```
lightweight event timestamps

incremental derived cache where justified

on-demand aggregation for larger windows

```

Do not turn every checkpoint into a full LOG replay.
Set and test a reasonable overhead budget.
The feature violates its purpose if measuring execution becomes a meaningful
part of execution time.
======================================================================
19. NO TELEMETRY-DRIVEN MODEL PREJUDICE
Do not introduce semantics such as:

```
model X is slow -> replace it

provider Y used more time -> lower quality

cheap model -> lower tier

```

Telemetry observes.
Current supervisor behavior remains based on:

```
durable progress

capability

liveness

actual failure

no-progress state

```

not raw wall-clock comparison.
A slow incarnation producing durable progress remains valid under:

```
QUALITY > TIME

```

======================================================================
20. FUTURE USE — QUALITY-NORMALIZED TIME
Leave room for later derived metrics such as:

```
acceptance retention rate

manual-intervention rate

protocol-drift rate

recovery success rate

repeated-action rate

quality-normalized wall time

```

Do not make these required for the first implementation.
First ship understandable raw metrics.
Derived scoring can come after the measurement model proves trustworthy.
======================================================================
21. ACCEPTANCE — MINIMUM USEFUL VERSION
Do not overbuild.
A first complete version should provide at least:

```
checkpoint timestamps

elapsed since previous checkpoint

current Work elapsed

current phase elapsed

time since durable progress

today's observed/active/wait/blocked time where measurable

Work touched today

Work completed today

checkpoint count

recovery count

worker generation count

agent incarnation count

manual recovery count

compact `saipen stats`

JSON output

one Work drill-down

```

Required invariants:

```
metrics are read-only

metrics are derived

metrics loss does not affect protocol correctness

durations survive model replacement

durations survive supervisor restart where durable timestamps exist

QUALITY > TIME semantics remain unchanged

slow progress is not converted into failure

```

======================================================================
22. TESTS

```

worker generation replacement does not reset Work elapsed

phase change starts new phase duration

project day rollup crosses multiple Work items

WAIT / BLOCKED time is not counted as active execution where classification

metrics cache deletion/rebuild does not alter canonical state

stats command performs zero canonical mutation

JSON output is deterministic for a frozen fixture

unknown timestamps produce UNKNOWN/omission rather than invented values

midnight/day-boundary handling

slow-but-progressing execution remains successful regardless of elapsed time

```

======================================================================
23. DO NOT DERAIL CURRENT WORK
This feature is useful but is not automatically higher priority than current
correctness, field-gate or closure work.
Capture it durably.
Then integrate it when canonical scheduling makes the bounded implementation
eligible.
If the current supervisor / checkpoint architecture is already being modified,
it is acceptable to lay minimal timestamp/event foundations now where doing so
prevents later duplication.
Do not pause an active critical corridor to build a dashboard.
======================================================================
24. REQUIRED RESULT
The operator should eventually be able to run:

```
saipen stats

```

and understand in a few seconds:

```
how long SAIPEN has been working today

what it spent time on

what is active now

how long the current Work has taken

when durable progress last happened

how frequently checkpoints occur

how many Work items finished

how many recoveries/replacements occurred

whether human recovery was required

```

without:

```
reading raw LOG

counting timestamps manually

inspecting model transcripts

trusting model self-report

```

```
WHAT IS BEING DONE

WHY IT IS BEING DONE

```

```
HOW LONG DID IT TAKE?

```
