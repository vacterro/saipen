# User request

## Request

SAIPEN

RECOVERY TARGET: HOST BOOTSTRAP / RUNTIME BINDING / FREEBUFF ADAPTER

This is a recovery and hardening wave for SAIPEN host autonomy.

Observed real failure:

* A SAIPEN-managed project was opened in a FreeBuff-style isolated Linux/bash host.
* The repository contained `.saipen/`.
* `saipen continue` failed with `saipen: command not found`.
* Python environment did not expose `saipen` / `saipen_engine`.
* The model did not recognize `cc` as a SAIPEN command.
* Despite missing SAIPEN runtime and activation semantics, the host still allowed consequential product edits.

This must not remain possible.

PRIMARY INVARIANT

A SAIPEN-managed project must never silently degrade into an unmanaged writable session because the current host cannot resolve the `saipen` executable or Python package.

Required lifecycle:

1. Detect `.saipen/`.
2. Activate SAIPEN semantics before ordinary model work.
3. Recognize protocol commands such as `cc` independently of PATH/runtime availability.
4. Resolve the canonical SAIPEN runtime through the project/state bootstrap contract.
5. Recover the runtime binding automatically when possible.
6. Continue the canonical SAIPEN lifecycle.
7. If the canonical runtime is genuinely unreachable from the current host, fail closed before consequential project mutation.

Do not solve this by teaching FreeBuff one hard-coded local Windows path.

The solution must be host-agnostic and based on canonical SAIPEN state/configuration.

RECOVERY WORK

Audit the existing host/bootstrap architecture first and locate:

* activation/instruction injection;
* host adapters;
* OpenCode bootstrap path;
* runtime discovery;
* `.saipen` project detection;
* `STATE` / canonical `saipen_home` resolution;
* direct Python/runtime entrypoints;
* command recognition for `cc`;
* mutation gates protecting SAIPEN-managed projects;
* existing host acceptance tests.

Use OpenCode's working integration as reference behavior, not as code to blindly duplicate.

Implement one canonical bootstrap resolver shared by supported hosts.

Expected resolution order should conceptually be:

A. Detect SAIPEN-managed repository.

B. Load the activation contract immediately.

C. Resolve an already available canonical SAIPEN command/runtime.

D. If the command is not in PATH, obtain the canonical SAIPEN home/runtime location from SAIPEN-controlled project/bootstrap state.

E. Attempt the supported direct canonical entrypoint without requiring the model/operator to manually locate or install SAIPEN.

F. If the host is isolated but a supported host bridge/proxy exists, use the supported bridge rather than inventing another lifecycle implementation inside the host.

G. If no legitimate runtime path is reachable, enter structured runtime-unavailable state and prohibit consequential writes.

Do not scan arbitrary disks for SAIPEN installations.

Do not guess installation paths.

Do not create a second independent implementation of SAIPEN lifecycle logic inside FreeBuff.

Do not allow host-specific state to become lifecycle authority.

CC ACTIVATION CONTRACT

`cc` must remain recognizable even when the executable itself is temporarily unavailable.

The activation layer must establish enough protocol semantics that:

* `cc` is interpreted as canonical SAIPEN continue;
* the model does not ask the user what `cc` means;
* runtime recovery is attempted;
* if runtime recovery succeeds, canonical continue executes;
* if runtime recovery fails, the response is structured runtime remediation instead of conversational fallback.

The same principle applies to other protocol activation commands that must be known before runtime invocation.

FAIL-CLOSED WRITE GATE

When all of the following are true:

* `.saipen/` exists;
* SAIPEN activation is expected;
* canonical runtime binding cannot be established;

the session must enter a host-runtime-unavailable state.

In that state:

ALLOWED:

* repository inspection;
* safe reads;
* diagnostic commands;
* runtime/bootstrap discovery;
* evidence collection required to repair the binding.

DENIED:

* product source edits;
* canonical lifecycle mutations;
* manual BOARD mutation;
* manual STATE mutation;
* manual LOG mutation;
* ticket transitions;
* implementation work that bypasses SAIPEN.

Return one stable structured diagnostic similar in semantics to:

SAIPEN_HOST_RUNTIME_UNAVAILABLE

It must contain enough deterministic information for either the adapter or operator to recover, including the attempted canonical runtime source and the exact unsupported boundary.

Do not spam repeated diagnostics every turn if nothing changed.

FREEBUFF SUPPORT

Treat FreeBuff as a first-class host acceptance surface.

Determine what execution boundary FreeBuff actually provides:

* filesystem visibility;
* shell type;
* environment isolation;
* host/container boundary;
* ability or inability to execute the Windows-side canonical runtime;
* availability of bridge/proxy mechanisms.

Then implement the narrowest correct adapter/bootstrap solution.

The goal is not to make FreeBuff special.

The goal is:

FreeBuff receives the same SAIPEN protocol semantics, runtime bootstrap behavior, continuation behavior, mutation protection, and recovery guarantees as other supported hosts.

If FreeBuff cannot execute the canonical SAIPEN runtime directly because of sandbox isolation, implement or reuse a supported bridge/proxy boundary rather than silently disabling SAIPEN.

ACTIVATION DELIVERY

Audit why the activation contract was not visible in the failing session.

A repository containing `.saipen/` must not depend solely on a global shell installation for protocol recognition.

Ensure the relevant host gets the canonical activation instructions early enough that protocol commands are understood before conversational interpretation.

Do not create divergent FreeBuff-specific protocol wording if the canonical activation block can be reused/generated from one source.

HOST REGISTRY / ACCEPTANCE MATRIX

The current host coverage is insufficient if FreeBuff can execute SAIPEN-managed repositories without being represented in acceptance testing.

Add FreeBuff to the canonical host/support matrix or otherwise make unknown writable hosts fail closed.

The system must not assume that "all registered hosts are healthy" implies "every host capable of opening the repository is protected."

Add a regression that covers an unregistered or incompletely bootstrapped host.

REQUIRED TESTS

Add deterministic tests for at least:

1. `.saipen/` present + `saipen` available in PATH.
   Expected: normal activation and continue.

2. `.saipen/` present + executable missing from PATH + canonical runtime reachable through configured SAIPEN home.
   Expected: automatic runtime recovery and continue.

3. `.saipen/` present + Python package absent from local isolated environment + canonical external/bridge runtime available.
   Expected: adapter uses supported binding and continues.

4. `.saipen/` present + runtime completely unreachable.
   Expected: structured runtime-unavailable state and write denial.

5. `cc` received while PATH/runtime is temporarily unavailable.
   Expected: recognized as SAIPEN continue request, never interpreted as unknown conversational text.

6. Missing activation injection regression.
   Expected: host startup detects the violation before consequential work.

7. Attempted product edit while runtime binding is unavailable.
   Expected: denied before mutation.

8. Attempted manual BOARD/STATE/LOG mutation while runtime binding is unavailable.
   Expected: denied.

9. Runtime restored after an unavailable state.
   Expected: bootstrap rebinds cleanly and canonical continuation resumes without manual project repair.

10. Stale handoff lifecycle state such as a handoff naming an already-DONE ticket while runtime is available.
    Expected: canonical SAIPEN state wins; no destructive rollback to the stale handoff.

11. FreeBuff acceptance.
    Reproduce the real shell/environment shape as closely as practical.

12. Existing OpenCode behavior.
    Expected: no regression.

AUTONOMY REQUIREMENT

This repair is incomplete if the final workflow still requires the user to manually type installation paths, manually explain `cc`, manually edit SAIPEN files, manually reinstall SAIPEN inside every temporary host, or manually repair lifecycle state after bootstrap failure.

The host should self-recover whenever sufficient canonical information exists.

A human should only be required when the execution boundary truly prevents access to any supported SAIPEN runtime/bridge.

OBSERVABILITY

Expose enough diagnostics to distinguish:

* activation missing;
* executable not in PATH;
* local Python package unavailable;
* canonical SAIPEN home resolved;
* canonical runtime reachable/unreachable;
* bridge reachable/unreachable;
* host unsupported;
* mutation gate engaged;
* runtime successfully rebound.

Do not dump secrets or irrelevant environment data.

COMPATIBILITY

Preserve existing working behavior for:

* OpenCode;
* existing SAIPEN CLI execution;
* canonical Windows install;
* project state resolution;
* continue loop;
* queue/bridge behavior;
* activation semantics.

Do not turn AUDAPACK, SAIPAL, or another neighboring project into a mandatory dependency for core SAIPEN bootstrap.

They may provide optional integration or evidence, but SAIPEN must retain its own canonical ability to start and protect a managed repository.

SCOPE CONTROL

Stay on this root cause.

Do not expand into unrelated lifecycle cleanup, project feature work, UI work, or old backlog unless a directly blocking defect is discovered.

If several defects collapse into the same bootstrap/runtime-binding root cause, fix them together and document the shared cause.

VALIDATION

Run focused regression tests first, then the appropriate SAIPEN Core suite.

Provide concrete evidence for:

* FreeBuff-style recovery;
* `cc` recognition without PATH availability;
* fail-closed mutation protection;
* successful canonical runtime rebinding;
* OpenCode non-regression.

If practical, add a small host bootstrap diagnostic command/test fixture so future adapters can validate themselves without performing product work.

SUCCESS CONDITION

The recovery is complete only when this sequence works:

SAIPEN-managed repository
→ arbitrary supported host starts
→ `.saipen` detected
→ canonical activation semantics loaded
→ `cc` understood
→ canonical runtime located or bridged
→ lifecycle continues automatically
→ product work proceeds under SAIPEN

and this sequence fails safely:

SAIPEN-managed repository
→ host starts
→ runtime genuinely unreachable
→ structured SAIPEN runtime-unavailable state
→ safe reads allowed
→ consequential writes blocked
→ exact recovery boundary reported

There must be no third state where SAIPEN disappears and the host silently continues as an ordinary writable coding session.

When complete, return:

* IMPLEMENTATION
* HOST BINDING MODEL
* FREEBUFF RESULT
* TEST EVIDENCE
* OPENCode REGRESSION RESULT
* FAIL-CLOSED EVIDENCE
* REMAINING RISKS
* STATUS

Do not mark COMPLETE merely because FreeBuff recognizes the word `cc`.

The runtime binding and mutation enforcement must both be proven.
