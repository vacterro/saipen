# SAIPEN CONTINUE — AUDIT INBOX WAVE

## `cc` AUTO-INGEST → WORK → EVIDENCE → CLOSE → DELETE

ROLE

Implement a native SAIPEN Audit Inbox integrated with:

`saipen continue`

and therefore its shortcuts:

`cc`
`ccc`

The supplied project already contains the intended external inbox form:

`<project-root>/audit/1.md`
`<project-root>/audit/2.md`

AUDAPACK already uses the same basic convention:

`audit/`
+
canonical numbered Markdown layers:

`^[1-9][0-9]*\.md$`

Reuse that simple filesystem contract.

Do NOT depend on AUDAPACK at runtime.

SAIPEN must implement the behavior natively and remain standalone.

---

# PRIMARY USER INTENT

The desired operator workflow is:

1. An audit/instruction handoff appears in:

   `project/audit/N.md`

2. The user types only:

   `cc`

3. SAIPEN automatically notices the audit before selecting ordinary queued BOARD work.

4. SAIPEN captures the audit as durable source authority.

5. SAIPEN derives/links normal Work from it.

6. SAIPEN executes all actionable audit requirements.

7. Every closed requirement receives real evidence and verification where required.

8. The audit source is CLOSED only when the existing Source Receipt closure contract proves it complete.

9. Only after that closure is proven may the original:

   `audit/N.md`

   be deleted.

10. The next `cc` naturally proceeds to the next audit layer or ordinary project Work.

The user should not need to copy paths, run:

`saipen source capture`

manually, or remember which audit was already processed.

# DO NOT USE MTIME AS SOURCE TRUTH

A "fresh" audit is NOT defined by filesystem modification time.

mtime may change because of:

* archive extraction;
* copying;
* sync tools;
* checkout;
* backup restore.

Freshness is content-bound.

Identity of one audit inbox generation is:

`relative_path`
+
`SHA-256 of exact file bytes`

Example:

`audit/2.md`
+
`4264...eeb2`

If `audit/2.md` is later edited in place and its SHA changes, that is a NEW audit generation.

Never delete new bytes because an older generation under the same filename was completed.

# CONTINUE PRIORITY

Extend `saipen continue` routing carefully.

Required high-level order:

1. recovery / corrupt journal / conflict handling;
2. required WAIT / mandatory human interaction;
3. finish currently active DOING / phase-owned continuation;
4. resume other protocol-owned immediate continuation;
5. AUDIT INBOX;
6. ordinary BOARD Pick Rule;
7. normal maintenance routing;
8. bounded `continue -> improve` fallback.

The important semantic is:

> Audit Inbox outranks selection of unrelated queued BOARD TODO, but does not preempt already active legitimate Work.

This is what "check the fresh audit before the board" means.

Do NOT interrupt an active BUILD/VERIFY/REVIEW transaction merely because a new file appeared.

Capture may happen safely at a boundary, but execution ownership stays with active Work until that legitimate unit yields control.

# AUDIT PICK RULE

When SAIPEN reaches the Audit Inbox routing stage:

1. scan canonical numbered audit layers;
2. classify their current generations;
3. choose the topmost WORKABLE audit layer.

Default deterministic ordering:

lowest numeric layer first.

Example:

`1.md`
`3.md`
`7.md`

order:

1
→ 3
→ 7

Deleted gaps are normal.

Never renumber.

However:

a permanently/non-actionably BLOCKED audit layer must not starve later workable layers forever.

Apply the same principle as BOARD Pick Rule:

> select the lowest-numbered WORKABLE audit generation.

A blocked/invalid earlier layer remains visible and retained.

It does not erase or silently discard later work.

# CURRENT-REPOSITORY MIGRATION CASE — EOL-ONLY LEGACY DUPLICATES

The supplied repository already contains a migration edge case:

an audit layer may be textually identical to an existing active Source Receipt while differing only because the external `audit/N.md` uses CRLF and the previously captured receipt uses LF.

Do NOT weaken Source Receipt byte identity.

One-byte changes must remain distinct source identities.

However, for Audit Inbox migration only, support a narrow operational compatibility binding:

If ALL are true:

1. no exact-digest receipt exists;
2. exactly one existing active receipt is otherwise eligible;
3. UTF-8 decoded text is identical after LINE-ENDING normalization only;
4. no characters other than CR/LF differ;
5. the source is an audit/implementation mission class;
6. there is no ambiguity;

then the inbox adapter may bind the file to the existing receipt as:

`legacy_transport_equivalent`

Record BOTH hashes.

Do NOT rewrite the source receipt digest.

Do NOT call them byte-identical.

Do NOT generalize this to whitespace trimming, Markdown normalization, case folding, punctuation, Unicode normalization or semantic similarity.

If there are multiple matches or any other difference:

capture a new Source Receipt.

This compatibility rule prevents the current repository from manufacturing duplicate Work for already-captured audit material while preserving strict source identity.

# SOURCE CLOSURE IS THE DELETE GATE

Original audit file deletion is permitted only after:

1. exact source integrity PASS;
2. Source Contract bound to its receipt digest;
3. every actionable clause terminal;
4. required evidence exists;
5. required verification exists;
6. linked parent Work is DONE;
7. `close_receipt()` succeeds;
8. canonical tombstone/archive evidence exists;
9. the current bytes of `audit/N.md` STILL match the generation that was captured.

Only then:

delete the external inbox file.

This is the core invariant.

---

# NEVER DELETE A MODIFIED AUDIT

Before deletion:

re-open/rebind the exact audit path safely and compute SHA-256 again.

If:

`current_sha != captured_file_sha`

then:

DO NOT DELETE.

The old receipt may remain correctly CLOSED.

But the file now represents a NEW generation.

Record conceptually:

old generation:
`CLOSED`

current generation:
`NEW`

and immediately make the new generation eligible for normal inbox intake.

This protects the classic race:

agent finishes audit
→ user replaces `2.md` with a new audit
→ old cleanup deletes new file.

That must be impossible.

---

# DELETE MUST BE JOURNALED / RECOVERABLE

Deleting the original audit file is an irreversible filesystem effect.

Do not use naked:

`Path.unlink()`

after closure.

Use SAIPEN's canonical operation/journal machinery.

Before first destructive effect persist enough evidence to recover:

* operation type;
* canonical relative path;
* expected file SHA-256;
* receipt ID;
* linked Work;
* source CLOSED evidence/tombstone;
* before state;
* expected after state.

Conceptual operation:

`audit_inbox.consume`

Stages:

`PREPARED`
→ `APPLYING`
→ `VERIFIED`
→ `COMMITTED`

If crash occurs:

### crash before delete

file remains;
recovery may safely retry after verifying hash + source closure.

### crash after delete before commit marker

file absence + matching prepared operation is idempotent success;
recovery settles COMMITTED.

### file changed before recovery

CONFLICT;
never delete changed bytes.

Use existing journal/plan infrastructure rather than inventing another recovery subsystem.
