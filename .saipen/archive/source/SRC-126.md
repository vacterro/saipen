# SAIPEN guard refusal: improve-cycle writes are wedged by the one-DOING admission gate

Reported by an auditing seat while reconciling a project's post-DONE SAIPEN
ledger. Every claim below is reproduced against the installed protocol.

## Environment

- installed saipen_home: `C:\Users\vac34\AppData\Local\saipen\scheduled-source`
- git source home: `V:\___VAC\__K\__CODE\_AI_STUFF_AGENTIC\_SAIPEN`
- VERSION: `8.0.1` (protocol major 8)
- writer: `tools/saipen_engine/admission.py` (`protocol_snapshot` / `evaluate_admission`)
- reporting project: `V:\___VAC\__K\__CODE\_PY\_9router_extra`
  (lineage-6c27dab147d645d19f103379d2be4d76), source_head `105d3d6`
- evidence cycle: `imp-vacterro-9router_extra-20260916-2`, seat `opencode-01`

## Defect class

`PROTOCOL_VIOLATION`.

## Summary

The mutation admission gate requires exactly one `BOARD.DOING` ticket bound to
`STATE.task` in a ticket-bearing phase. That is correct for ordinary Core Work.
It is applied with NO exemption to the Improve meta-control write surface, even
though `saipen continue` routes to `saipen improve` **precisely when `BOARD` has
no workable `TODO`** — i.e. exactly the state in which the gate refuses. An
admitted improve cycle therefore cannot append its findings, and the only
mutation it can perform is the destructive `improve abort`.

Worse, the same gate refuses honest ledger reconciliation work: a seat with
completed local work and no `DOING` ticket cannot run `source close`,
`source disp`, `audit enqueue`, or any other consequential operation, because
admission is keyed on the `DOING` count rather than on whether the operation
mutates Core execution state.

## Finding IMP-001 [P1] [PROTOCOL_VIOLATION] [reproduced] [ticket]

expected: `saipen improve submit <cycle> <seat> <project> <findings.json>` is
admitted while an active improve cycle exists with this seat registered, because
the cycle is admitted precisely when `BOARD` has no workable `TODO` and its
whole purpose is to append evidence without project mutation.

actual: with `BOARD.DOING` empty and `STATE phase DONE / task none`, the guard
refuses `improve submit` with `SAIPEN_GUARD_REFUSAL NO_ACTIVE_WORK`. The same
invocation SUCCEEDS as soon as an unrelated ticket is placed in `DOING`,
proving the gate is the project `DOING` count and not the improve surface.

evidence: reproduced at source_head `105d3d6`. Two refusals on cycles
`imp-...-20260916-1` and `-2` with an empty BOARD; then `saipen start` claiming
a ticket made the same submit reach `append_run` and return a content-level
`VALIDATION_FAILED` instead of `NO_ACTIVE_WORK`.

## Finding IMP-002 [P2] [PROTOCOL_VIOLATION] [reproduced] [ticket]

expected: guard admission is uniform across the improve lifecycle, so a mutator
is either admitted or refused by ONE rule and the least-privilege choice is
preserved.

actual: in the SAME empty-BOARD state, `saipen improve abort <cycle>` was
ADMITTED and COMMITTED (cycle active -> archived), while `improve submit` was
refused `NO_ACTIVE_WORK`. The destructive mutator passed; the
evidence-appending mutator was blocked — the inverse of least privilege.

evidence: live sequence at source_head `105d3d6`: `improve abort
imp-...-20260916-1` printed `code: COMMITTED` (manifest then read
`cycle_status: archived`), while `improve submit` returned the `NO_ACTIVE_WORK`
refusal.

## Finding IMP-003 [P1] [LOGIC_ERROR] [reproduced] [ticket]

expected: one `saipen status --json` payload states ONE conformance verdict
matching a live validation run at the same source_head.

actual: the same payload carries both flat `conformance: "PASS (10.09.26 19:14)"`
and structured `conformance_status.status: CURRENT_FAIL` with
`validator.verdict: FAIL` and `receipt.exit_code: 1`, while a live
`saipen validate` returns `code: VALID`. A consumer keying on the flat label
reads PASS where the structured verdict says FAIL.

evidence: `saipen status --json` fields `conformance`, `conformance_status`,
`conformance_status.receipt`; `saipen validate` output `code: VALID`.

## Finding IMP-004 [P1] [LOGIC_ERROR] [reproduced] [ticket]

expected: the validator's `[sweep-ticket-link]` reasoning gates (IMPROVE.md
section 13) are satisfiable through some canonical operation, so a compliant
seat can record `recurrence:` and `weak_model:` on the ticket the finding names.

actual: no canonical SAIPEN operation can write an arbitrary BOARD field. The
CLI ticket surface is `add|done|block|block-for|unblock|verify|compact|retire`;
none accepts a free field, and the engine's `board.set_ticket_field` has no
command path. The gate therefore cannot go green without hand-editing
`BOARD.md`, which `OPS.md` section 4a and the host guard both forbid. A
`PROTOCOL_VIOLATION` ticket is permanently red.

evidence: grepped the CLI and engine for any ticket-field writer reachable from
the command surface; the only writer is the internal function. Confirmed the
validator fails a `PROTOCOL_VIOLATION` ticket without both fields while no verb
can add them.

## Finding IMP-005 [P2] [PROTOCOL_VIOLATION] [reproduced] [ticket]

expected: a canonical, non-interactive fallback exists when the host search tool
is unavailable, so classification does not depend on a third-party binary.

actual: on this host the agent's ripgrep-backed search tool fails with a
transport error while SAIPEN state is valid, and the guard independently refuses
every shell invocation with `NO_ACTIVE_WORK`, so an agent cannot grep the
protocol to diagnose its own refusal. The documented read-only transport
`saipen search --hex <hex>` works, but nothing routes an agent to it when the
guard is the thing blocking the shell.

evidence: repeated `NO_ACTIVE_WORK` refusals on a legitimate read (`git status`,
`python tools/coverage_board_check.py`) in a state with no `DOING` ticket;
`saipen search` and plain file reads succeeded.

## Root cause

`admission.protocol_snapshot` gates on `len(doing) != 1` for EVERY consequential
tool, with no distinction between (a) mutation of active Core execution state
and (b) legitimate operations that do not touch that state: Improve
meta-control writes, source-receipt closure/disposition, audit enqueue, and
post-DONE ledger reconciliation. `checkpoint` and `stop` happen to be admitted
because they are read-mostly, but the family above is not.

## Why this must be repaired in the protocol, not the project

IMPROVE.md section 12 (writer boundary, T-557) forbids an improve seat from
touching Core protocol. CORE.md sections 1.1/1.9 confine a project to its own
root/lineage. A local patch would diverge every consumer install. The fix
belongs in the installed protocol.

## Required regression

A red control: in an empty-BOARD `phase: DONE` / `task: none` state with an
active improve cycle and a registered seat, `improve submit` succeeds and
`append_run` commits; `improve abort` remains admitted; an inactive or absent
cycle still refuses. More generally, the one-`DOING` gate must not refuse
operations that do not mutate Core execution state — the exemption must be
explicit and tested, not a side effect of which verbs a seat happened to try.

## Suggested direction (non-binding)

Either exempt the Improve cycle write surface (and source/audit intake) from the
`DOING` requirement, or admit a registered improve cycle as its own authorization
scope, or route improve-cycle admission through a dedicated token distinct from
`BOARD.DOING`. The weak-model test: a compliant weak model that honestly reads
the protocol still cannot proceed today, because the refusal is mechanical and
no state field or command exposes an exemption.
