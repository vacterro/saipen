============================================================
1. MISSION
============================================================

SAIPEN development is becoming economically unsustainable.

The operator reports that verification consumes approximately
98% of available development time.

This percentage is an operator observation, not yet an
independently measured process statistic.

The repository evidence nevertheless confirms severe
verification costs.

The mission is NOT to make tests pass faster by weakening
them.

The mission is to redesign when, why, how, and how often
tests execute, so engineering work can proceed without
repeatedly paying the full verification cost.

CORE PRINCIPLE:

QUALITY MUST REMAIN INTACT.
REDUNDANT EXECUTION MUST DISAPPEAR.

Reduce verification cost through architectural changes,
not through artificial PASS verdicts.

============================================================
5. WAVE 1 — ELIMINATE REDUNDANT VERIFICATION
============================================================

Investigate why full core-unit evidence is regenerated
so frequently.

Current reuse is fingerprint-based.

Determine:

- Which changes invalidate an existing PASS.
- Which changes genuinely require full reruns.
- Whether callers unnecessarily request fresh execution.
- Whether equivalent evidence is missed by lookup paths.
- Whether test records are repeatedly regenerated for
  identical source generations.
- Whether verification is invoked multiple times along
  one lifecycle route.
- Whether failed and interrupted runs are retried
  without a meaningful change.

Introduce canonical single-flight execution:

If multiple authorized consumers request identical
verification for an identical immutable source generation,
one execution should satisfy all compatible requests.

Concurrent callers must share the same trustworthy result
rather than launch duplicate suites.

Preserve:

- Ownership isolation.
- Authority boundaries.
- Evidence integrity.
- Complete provenance.
- Deterministic failure propagation.
- Crash recovery.
- Cancellation semantics.

Never reuse FAIL as PASS.

Never reuse evidence whose tested source, relevant runtime,
test environment, baseline or required verification
configuration no longer matches its declared identity.

Do not assume that identical source fingerprints alone
prove environmental equivalence.

6. WAVE 2 — PROGRESSIVE VERIFICATION
============================================================

Introduce a risk-aware verification strategy.

Proposed levels:

LEVEL 0 — STATIC

Syntax, imports, schema and fast deterministic checks.

LEVEL 1 — FOCUSED

Tests directly covering the changed behavior.

LEVEL 2 — IMPACT

Affected modules, dependency boundaries and essential
integration tests.

LEVEL 3 — FULL

The entire canonical suite against an immutable source
generation.

LEVEL 4 — RELEASE

All required release, portability, distribution and
security acceptance gates.

These names are conceptual until mapped onto existing
contracts.

The objective is:

Ordinary implementation iterations should primarily
consume Levels 0–2.

Level 3 must execute at justified verification boundaries
rather than automatically after every trivial edit.

Level 4 must preserve publication safety.

IMPORTANT:

The existing SHIP gate currently requires full core-unit
evidence for the current VERIFY cycle.

Do not bypass it by quietly treating a focused PASS as
equivalent to a full PASS.

First determine whether batching, shared generation
evidence or a canonical lifecycle amendment can reduce
the number of full executions without weakening
the original safety property.

If a protocol amendment is necessary:

1. Document the old invariant.
2. Specify the new invariant.
3. Prove equivalent or stronger protection.
4. Write adversarial regression controls.
5. Migrate the canonical implementation.
6. Verify that no ordinary route bypasses the policy.

A narrow test result must always retain its declared scope.

Unknown impact must conservatively escalate.

9. WAVE 5 — SANDBOX AND DISCOVERY COST
============================================================

The extracted repository includes a large .saipen tree.

The canonical test process copies project state into
disposable sandboxes.

Parallel execution can multiply this cost.

Measure:

- Copy duration.
- Total copied bytes.
- File-count overhead.
- Redundant shard copies.
- Windows filesystem behavior.
- Antivirus-related overhead when measurable.
- Cleanup duration and retained sandbox leakage.

Investigate immutable-generation snapshots with safe
copy-on-write or equivalent mechanisms.

Hardlinks are acceptable only where mutation cannot
corrupt another consumer or the original project.

Every parallel worker must observe the same tested
generation.

Preserve current project-state consistency protections.

Investigate redundant discovery work.

The current shard runner discovers the whole family
inside each shard before filtering its selected tests.

Determine whether a verified shared discovery manifest
can remove this repeated work.

Any optimized partition must prove:

- All required tests are included.
- No required test is skipped.
- No unintended duplicate executes.
- Import errors remain visible.
- Fixture semantics are preserved.
- New tests enter the selected inventory.
- Windows and Linux behavior remain equivalent.

Count equality alone is insufficient proof of identical
test membership.

15. REGRESSION ACCEPTANCE
============================================================

Build adversarial controls proving:

1. Same source and compatible environment:
   duplicate callers share one valid execution.

2. Changed relevant source:
   old PASS cannot authorize the new generation.

3. Changed verification configuration:
   incompatible evidence is rejected.

4. Previously failed run:
   no false PASS reuse.

5. Interrupted execution:
   no orphaned authority or permanently stuck owner.

6. Parallel runs:
   each consumer receives the correct immutable verdict.

7. Narrow verification:
   cannot impersonate full-suite evidence.

8. Shared dependency changes:
   appropriate broader tests are selected.

9. Unknown dependency:
   selection escalates conservatively.

10. Newly added tests:
    discovery and partitioning cannot silently omit them.

11. SHIP and publication:
    required safety gates remain effective.

12. Injected runtime:
    behavior remains consistent with source layout.

13. Windows and Linux:
    no hidden platform-dependent bypasses.

14. Test failure reporting:
    all failures remain diagnostically visible.

15. Fault injection:
    stale, forged, incomplete or mismatched evidence
    fails closed.

16. Performance instrumentation:
    reports actual measurements, never estimated PASS.

Include RED controls demonstrating that the old failure
mechanisms are detected.
