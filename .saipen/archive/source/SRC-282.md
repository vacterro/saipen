## 1. Why this handoff exists

The operator asked why SAIPEN leaves stuck `.saipen/locks/core.lock` /
`WRITER_BUSY` failures behind, and asked for a handoff to the protocol owner
if this is a protocol hole. It is one. Two incidents in the reporting project
required killing an orphaned Python child by PID before a checkpoint or
transition would run again. The investigation below separates what is
by-design (a persistent zero-byte lock file; fail-fast contention) from what
is not (no holder identity, no bounded wait, and multi-minute critical
sections that run an external validator while holding the only writer mutex).

## 2. What the lock actually is (measured)

- `.saipen/locks/core.lock` is a permanent, zero-byte file. In the reporting
  project it has existed since 2026-10-15 00:27 and every successful write
  leaves it in place. Its existence is NOT a stale-lock marker and deleting it
  does not release a held lock: the real mutex is the OS byte-range lock on
  that file (`msvcrt.locking` on Windows, `fcntl.flock` on POSIX,
  `saipen_engine/lock.py:196-213`).
- The OS lock is released by process death. Fixture proof: a holder process
  took the lock, a second `WriterLock.acquire()` refused in 0.00 s, and after
  killing ONLY the holder by PID the next acquire succeeded in 0.000 s.
- `saipen status` is lock-free and stays usable during a hold: with a foreign
  holder alive, `saipen status --json` exited 0 (73.4 s, dominated by source
  freshness hashing, not by the lock).

## 3. Observed failure chain

1. A mutation enters a critical section and holds the project writer lock.
2. Another mutation starts. `WriterLock.acquire()` fails immediately with
   `PermissionError("WRITER_BUSY")`; the CLI renders a structured refusal
   (`ok:false, code:WRITER_BUSY`) in about 0.4 s. Measured: `saipen checkpoint
   RUN ...` under a fixture holder exited 1 in 378 ms with
   `{"code":"WRITER_BUSY","message":"another live writer holds the project
   lock"}`.
3. The operator (or agent) cannot tell who holds it, what command is running,
   how long it has run, or whether waiting will help. The refusal carries no
   PID, no command, no lock age and no retry budget. The lock file's contents
   are empty by design.
4. On Windows the agent harness can kill the shell/parent while the Python
   child survives. The surviving child keeps the byte-range lock. The only
   recovery that worked was locating the orphan by command line with
   `Get-CimInstance Win32_Process` and killing that PID — which is not a
   protocol surface and is not documented anywhere.

## 4. Root cause: the critical sections are far too long for a fail-fast lock

The worst holder is the required SCOUT -> BUILD path:

`operations.transition_phase` (`saipen_engine/operations.py:2499`)
-> `_establish_pre_build_baseline` (`operations.py:2526`)
-> `debt.ensure_debt_baseline` takes `with project_writer_lock(root)`
   (`saipen_engine/debt.py:496`)
-> `_create_snapshot_apply`
-> `debt.capture_findings` (`debt.py:380`)
-> `_run_validator_capture` runs `validate.py` as a subprocess with
   `timeout=VALIDATOR_CAPTURE_TIMEOUT` = 1800 s (`debt.py:58`, `debt.py:121`)
while the writer lock is held for the entire capture.

Measured on the reporting project (70,050 changed/untracked Git entries,
mostly an unrelated site clone):

- `validate.py --gate core --no-receipt`: exit 0, 74.6 s.
- `saipen transition BUILD T-135 ...`: 240.6 s wall clock, and an independent
  watcher polling `WriterLock.acquire()` every 0.2 s recorded the lock as
  continuously busy for 240.2 s across 1,195 failed attempts.
- The resulting baseline is `DEBT-000134` (`reason: pre-BUILD debt baseline
  for T-135`, `bound_work_phase: SCOUT`, created 2026-10-19T22:13:41Z,
  journal op `debt.snapshot-fcd5ce8f9228`).
- `debt.reverify_work` holds the same lock across the same capture
  (`debt.py:1581` and `debt.py:1613`), so a DONE-Work re-verification can hold
  the only writer mutex for up to the 1800 s timeout.

Because the next SCOUT checkpoint legitimately moves BOARD/STATE/LOG, the
baseline dedup cannot fire, so the FIRST BUILD transition of every Work pays
this cost and holds the lock throughout. That is exactly when an agent is
most likely to issue another SAIPEN command.

## 5. Contract mismatch

`saipen/CORE.md:268` states: "A second writer uses the project writer lock;
lock timeout refuses rather than races." The engine has no timeout and no
retry budget for this lock: acquisition is non-blocking. The sibling locks do
have one, so this is an inconsistency inside SAIPEN, not a missing feature of
the OS:

- `saipen_engine/audit_enqueue.py:120-160` implements a bounded wait with
  `SAIPEN_AUDIT_ENQUEUE_LOCK_TIMEOUT` (default 30 s) and returns WRITER_BUSY
  only after the deadline.
- `saipen_engine/watchdog.py:34-56` retries for 5 s before raising
  WRITER_BUSY.

Additionally `WriterLock.acquire()` is documented as "Blocking exclusive
lock" (`lock.py:334`) while it calls `_os_lock(self._handle)` without
`blocking=True` (`lock.py:349`), so it uses `LK_NBLCK`. The docstring
describes behavior the code does not have.

## 6. Proposed directions (protocol owner decides)

These are options, not a prescribed patch:

A. Bounded acquisition. Give `project_writer_lock` a deadline (env-overridable,
   default a few seconds) matching `audit_enqueue`'s pattern, so a short
   legitimate hold resolves by waiting and a long one still refuses in
   bounded time.

B. Holder identity in the refusal. Best-effort write `{pid, started_at,
   command}` into the lock file (or a sidecar) after acquiring, and include
   it in the WRITER_BUSY payload, plus a diagnostic read-only command that
   reports "lock held by pid N since T running <command>" or "free". The
   empty file is why operators guess "stale lock".

C. Shorten the critical section. The pre-BUILD capture can run OUTSIDE the
   lock with `--no-receipt` (the read-only capture the dry-run path already
   uses), then acquire the lock and re-validate the three project-state
   fingerprints the snapshot already records (`board_sha256`, `state_sha256`,
   `log_fingerprint`) before journaling; retry the capture if they moved.
   That preserves the "baseline predates BUILD" invariant without holding
   the mutex across a subprocess. The same split applies to
   `reverify_work`.

D. Parent-death hygiene. If the host can kill a parent shell, the child
   writer should notice. A cheap guard is a heartbeat/staleness check like
   the watchdog lease, or documenting the exact orphan-cleanup procedure in
   the WRITER_BUSY remediation text.

## 7. Acceptance criteria for a fix

1. `saipen transition BUILD` on a fixture with a 60 s validator hold does not
   refuse a concurrent short mutation arriving 1 s later (it waits within the
   declared budget) and still refuses an unbounded holder in bounded time.
2. `WRITER_BUSY` names the holder PID and command when the holder is a SAIPEN
   process, or states plainly that the holder is unknown.
3. No protocol operation holds the project writer lock across an external
   process for more than a declared small bound.
4. `saipen status` remains lock-free (regression guard).
5. A held lock is still released by process death (do not regress the OS-lock
   property; no PID-file lease that outlives its owner).

## 9. Explicit non-goals / do not

- Do not delete `.saipen/locks/core.lock` as a "stale lock" cure; it is
  recreated and its existence is normal. It is not the mutex.
- Do not add retries to the validator capture under the lock as the only
  fix; that lengthens the hold.
- This report changes no protocol file. The reporting project performed no
  edits to the protocol home; this file is the only artifact placed there,
  via the audit-inbox ingress (SOURCES.md).
