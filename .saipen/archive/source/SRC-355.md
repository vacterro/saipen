In `.saipen/LOG.md`, ticket T-1975 exhibited an elapsed lifecycle of approximately 179 minutes (08:50 to 11:49). Four separate `CORE-UNIT-EVIDENCE` executions were recorded against 8,548 tests under `jobs=6`:

| `2788077a4ad27cc1` | PASS | 1554.0 s | Retried with `--fresh` on **identical** source bytes |

- **Share of ticket lifecycle:** ~58.6% of total wall clock was consumed by full test suites.
- **Root Bottleneck:** Repeated invocations of the monolithic 8,548-test core unit family when source bytes had not changed or when focused suites sufficed.

Profiling across typical ticket lifecycle stages reveals the following resource distribution:

| SAIPEN CLI bootstrap | 0.12 – 0.25 s | Python import time | Negligible; no batch daemon needed |

The critical path is dominated entirely by the **1,500+ second execution time of the 8,548-test suite**. Accelerating ticket completion requires reducing *redundant* runs of this suite without weakening safety gates.

## 2. Invalidation and Reuse Invariants (T-1953 / T-1835)

Verification reuse (`core_unit.reusable_record()`) operates under strict, cryptographically enforced invariants:
1. **Fingerprint match:** Exact match on `fingerprint` (SHA-256 over git tracked content).
2. **Baseline digest match:** Exact match on `baseline_sha256` of `tools/core_unit_baseline.json`.
3. **Verification identity match:** Exact match on Python version, OS platform, tool flags, and environment parameters (`verification_identity`).
4. **Latest outcome wins:** If the most recent compatible record is `FAIL`, an older `PASS` cannot be resurrected.
5. **No oracle relaxation:** Baseline red count must match; no unadjudicated failures may be silently converted to passes.
6. **Immutable citation:** Tickets cite the durable evidence record path and SHA-256; test results are never synthesized in prose.

## 3. Before / After Performance Proof

### Case A: Single Representative Ticket (1–3 Files Modified, e.g. T-1967)
- **Baseline (Before):**
  - BUILD: full core-unit run (1,550 s)
  - SHIP: full core-unit run (1,550 s)
  - Total full runs: 2 (3,100 s / ~51.7 min)
- **Optimized (After):**
  - BUILD: focused unit test (192 tests, 4.2 s) + negative control
  - SHIP: exactly 1 full core-unit run (1,550 s) cited across ticket completion
  - Total full runs: 1 (1,554.2 s / ~25.9 min)
  - **Savings:** **1,545.8 seconds (~25.8 minutes, 49.8% reduction)**.

### Case B: Two-Ticket Cohort Sharing Final Immutable Generation
- **Baseline (Before):**
  - Ticket 1: 2 full runs (3,100 s)
  - Ticket 2: 2 full runs (3,100 s)
  - Total full runs: 4 (6,200 s / ~103.3 min)
- **Optimized (After):**
  - Ticket 1 & 2 develop with focused suites.
  - Final coherent generation verified once at cohort release boundary (1,550 s).
  - Both tickets cite the identical compatible PASS record via `core_unit.cite_evidence()`.
  - Total full runs: 1 (1,550 s / ~25.8 min)
  - **Savings:** **4,650 seconds (~77.5 minutes, 75.0% reduction)**.

### Case C: Documentation, Metadata, or Knowledge-Only Ticket
- **Baseline (Before):** Full core-unit run triggered unconditionally (1,550 s).
- **Optimized (After):** Source tree fingerprint for code is identical; `reusable_record()` retrieves previous compatible PASS in 0.08 s.
- **Savings:** **1,549.9 seconds (>99.9% reduction)**.

## 4. Flaky Test and Order-Dependence Diagnosis

1. **Foreign Baseline Reds:** The 3 known failing tests in `core_unit_baseline.json` belong to external provenance inventory fixtures (`t1816`). These are accounted for in the baseline and do not represent flakiness.
2. **Order-Dependence:** The transient `RUNTIME_DRIFT` failure documented in AUT31-008 arises from environment variable leakage and global module state in sequential test suites. Looping full suites until green is strictly prohibited; order-dependent tests must be isolated.
3. **External Script:** `Close-Ticket.ps1` was verified absent from the SAIPEN project repository. Claims regarding its 10–12 CLI calls and 16-check overhead are external host issues documented under external handoff requirements.
