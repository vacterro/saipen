## Request

SAIPEN

APPEND — OPERATOR QUESTION AUTHORITY / FREEBUFF AUTONOMY GAP

Record and repair a protocol-level autonomy defect.

INCIDENT

A FreeBuff agent received the existing operator intent:

/goal cc all

and displayed an interactive question:

"What should I do for '/goal cc all'?
The keeper work is complete and verified save for live-machine acceptance, and the local session state files aren't readable from here, so I won't guess at an execution target."

It offered choices including:

- Continue verification
- Live acceptance guide
- Something else

This question was not justified by canonical SAIPEN state.

MEASURED CANONICAL STATE FROM THE SAME PROJECT SNAPSHOT

STATE:

phase: BUILD
task: T-1624
blocker: none
execution_intent: goal

`saipen status --json` reports:

automation.disposition = CONTINUE
automation.next_command = cc
automation.operator_action_due = false
automation.closure_complete = false

and:

claimed_ticket = T-1624
computed_next_action = PHASE BUILD T-1624
cold_route.search_required = false

`saipen continue --json` reports:

ok = true
action = PHASE BUILD T-1624
ticket = T-1624
reason = finish
load = saipen/phases/build.md
execution_intent = goal

Therefore the correct behavior was autonomous continuation of BUILD T-1624.

There was no operator decision due.

The model-generated recommendation "Continue verification" was additionally wrong because canonical phase authority said BUILD, not VERIFY.

ROOT DEFECT CLASS

T-1619 protects against premature final handback, but an agent can still escape autonomous continuation by invoking an interactive Question / AskUser / choice UI before producing a final response.

That is the same authority violation through a different transport.

A Question UI must not become a side door around:

- execution_intent: goal
- automation.disposition: CONTINUE
- AUTO_KICK
- canonical continuation routing
- executor failover
- cold recovery

Create a generalized protocol rule rather than a FreeBuff-only wording patch.

Suggested rule identity:

OPERATOR-QUESTION-01

or the repository's canonical equivalent.

CORE RULE

An agent may solicit an operator decision during an operational SAIPEN turn only when canonical machine authority says an operator decision/action is actually due.

At minimum, an interactive question is eligible only when the canonical state resolves to a genuine operator boundary such as:

automation.disposition == WAIT_USER

and/or the canonical response/autonomy owner explicitly reports:

operator_action_due == true

or an equivalent declared safety/authorization boundary.

When:

automation.disposition == CONTINUE

an interactive operator question about what to do next is INVALID.

The agent MUST continue canonically.

MODEL UNCERTAINTY IS NOT OPERATOR AUTHORITY

The following are not sufficient reasons to ask the operator what to do next:

- local chat/session state unavailable;
- transcript unavailable;
- conversation cache unavailable;
- model memory unavailable;
- keeper prose says work is complete;
- the agent is unsure which phase to run;
- the agent forgot the current target;
- the agent cannot infer an execution target from conversation text;
- a previous model stopped;
- an agent handoff is incomplete;
- provider context was compacted;
- the model would prefer confirmation;
- verification "seems like" the next step.

These are recovery/routing conditions, not human decision boundaries.

CANONICAL RECOVERY ORDER

If local conversational/session context is missing or unreadable:

1. resolve project root;
2. use canonical cold-route/project memory;
3. read or invoke `saipen status --json`;
4. consume the `automation` block;
5. invoke `saipen continue --json` when disposition is CONTINUE;
6. open `load_path`;
7. execute the returned canonical action in the same turn.

Do not reconstruct lifecycle state from chat prose.

Do not guess a phase.

Do not ask the operator to select a phase that SAIPEN already owns.

The existing rule in COMMANDS.md that state should be read rather than asking the user to define a registered command must be strengthened to cover interactive Question/AskUser tool calls as well as final textual handback.

SESSION STATE IS NOT CANONICAL STATE

Preserve the existing architecture:

chat/session JSONL, provider-local session files, transcript caches and keeper narration are not canonical project authority.

Loss of those surfaces must not erase persisted execution intent.

If canonical `.saipen` project state remains readable, cold recovery continues from that state.

A model must never convert:

"I cannot read my local session"

into:

"I need the operator to tell me what SAIPEN should run."

KEEPER / WORKER OUTPUT

"Keeper complete", "worker complete", "verification complete", assistant summaries, model handoffs and similar prose are observations only.

They do not override:

STATE
BOARD
LOG
automation disposition
current phase
claimed Work
canonical continuation result

If keeper prose conflicts with the automation block, machine truth wins and the conflict should be recorded diagnostically.

QUESTION TOOL GATE

Audit all supported agent/host paths for interactive question mechanisms.

Examples include:

- AskUser / Question tools;
- multiple-choice control surfaces;
- provider-native clarification widgets;
- generated "what should I do?" prompts;
- premature STOP/handback translated into a question.

Where the host provides an interceptable question/tool-call boundary, enforce OPERATOR-QUESTION-01 before delivery.

Where a host does not provide a blocking question hook, make the strongest available admission/instruction/final-response enforcement and record the capability honestly.

Do not falsely claim HARD enforcement on advisory-only hosts.

QUESTION REFUSED / AUTONOMOUS_CONTINUATION

No operator question is emitted.

TRUE WAIT CONTROL

Add the inverse control.

Fixture:

operator_action_due = true
canonical reason identifies an actual operator decision.

Expected:

the agent may present exactly the canonical operator control surface.

It must not invent additional choices.

Prefer the existing canonical response renderer:

saipen response render

or its owning API.

The question text/options must derive from canonical facts, not model improvisation.

EXECUTOR CAPABILITY

If the current executor cannot read files, invoke shell, or otherwise execute the canonical action, do NOT ask the operator what Work should run.

Apply the T-1619 executor-admission contract:

- reject incompatible executor before handoff where possible;
- bounded failover to a compatible executor;
- preserve current Work and execution_intent;
- only expose a human boundary if all canonical compatible recovery/failover routes are genuinely exhausted and machine authority classifies it accordingly.

Do not manufacture a project blocker from provider/runtime incapability.

AUTOMATION DISPOSITION BEHAVIOR

Pin host-independent behavior:

CONTINUE
-> no operator question; execute next canonical action.

COMPLETE
-> no "what next?" question; render canonical completion.

WAIT_USER
-> canonical operator question/action surface is allowed.

WAIT_EXTERNAL
-> report external wait; do not ask the operator to choose arbitrary next Work unless a separate operator action is explicitly due.

BLOCKED
-> report the canonical blocker/recovery action; no generic menu.

INVALID
-> report canonical diagnostic/recovery route; no model-generated lifecycle menu.

UNKNOWN/UNREADABLE LOCAL SESSION
-> attempt canonical cold recovery; it is not automatically WAIT_USER.

Do not map inability to recall chat context to WAIT_USER.

T-1619 RELATION

Treat an unjustified interactive question while executable autonomous Work remains as semantically equivalent to AUTONOMOUS_HANDBACK.

It should feed the same continuation authority / AUTO_KICK semantics rather than bypass them.

Avoid two independent definitions of "autonomous work remains".

Reuse the canonical automation/iteration verdict owner.

T-1494 RELATION

Do not accidentally weaken persistent `/goal` authority.

This repair should compose with T-1494:

an explicit persisted `/goal` remains authoritative across:

- model changes;
- provider changes;
- session compaction;
- local session loss;
- cold restart;
- keeper completion;
- handoff boundaries.

Only a canonical terminal condition or genuine operator boundary may return control.

ACCEPTANCE MATRIX

At minimum prove:

   zero question, autonomous continuation.

7. WAIT_EXTERNAL:

8. COMPLETE:
   no "what should I do next?" menu.

   persisted goal survives.

10. FreeBuff exact incident regression:
    attempted Question UI is refused/autokicked.

11. another host with an interactive question facility:
    same semantic result.

12. advisory-only host:
    capability is represented truthfully; no false HARD claim.
