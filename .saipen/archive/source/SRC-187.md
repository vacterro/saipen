# User request

priority: P1
verify: the requested change is present and demonstrated against the user own description of it

## Request

SAIPEN

APPEND — ZERO-HUNT FIRST-TURN BOOTSTRAP / CONTROL-PLANE DISCOVERY

Record this as a protocol/runtime hardening target discovered from a real downstream agent cold-start.

Do not interrupt an active higher-priority lifecycle slice merely to implement it. Preserve it as concrete Work/finding and execute at the next justified boundary.

INCIDENT

A downstream AUDAPACK agent received:

/goal cc all

Its initial reasoning was semantically correct:

- SAIPEN is active;
- the first operational action should be `saipen continue --json`;
- SAIPEN FAST PATH / CMD-CONTINUE-01 owns routing before generic skill/bootstrap work.

However the first command failed:

saipen: command not found

The agent then manually searched the known SAIPEN repository, discovered its launcher, exported SAIPEN_HOME and invoked the launcher by absolute path.

Only after this manual discovery did the canonical route return:

PHASE SCOUT T-288

The project `.saipen/STATE.md` itself already contained:

saipen_home: V:\___VAC\__K\__CODE\_AI_STUFF_AGENTIC\_SAIPEN

After routing, the agent also manually grepped BOARD for T-288 and adjacent tickets and separately searched the filesystem for SRC-124, even though the control plane already knew the claimed Work and its source_receipt.

This worked, but success depended on model improvisation and remembered filesystem topology.

DEFECT CLASS

A registered SAIPEN command / active autonomous intent does not yet have a fully deterministic zero-context bootstrap when:

- `saipen` is not on PATH;
- the executor starts in Git Bash or another shell;
- local conversational/session context is absent;
- generic agent instructions conflict with SAIPEN first-turn routing;
- the current Work requires its source receipt/detail context.

The agent can recover today, but only by filesystem hunting and instruction interpretation.

That is unnecessary autonomy friction.

DESIGN GOAL

For a SAIPEN-managed project, a cold agent should be able to go from:

current project directory + `/goal cc all`

to:

canonical next executable Work

without:

- knowing the global SAIPEN installation path in advance;
- scanning arbitrary directories;
- asking the operator;
- guessing instruction precedence;
- reading large portions of BOARD;
- reconstructing current Work from prose;
- remembering a previous session.

BOOTSTRAP AUTHORITY

Pin one explicit precedence rule.

For a registered SAIPEN operational command or persisted active SAIPEN execution intent:

1. canonical control-plane routing owns the first operational action;
2. generic style/personality/skill bootstrap MUST NOT delay or replace routing;
3. style authority still governs communication and implementation behaviour after routing;
4. a generic instruction such as "load skill X first" must not outrank CMD-CONTINUE-01 unless that skill is mechanically declared as a prerequisite of the returned action.

The agent should not need to reason about whether:

"generic skill first"

or:

"SAIPEN continue first"

wins.

SAIPEN must state the precedence mechanically and consistently.

LAUNCHER DISCOVERY

Provide a deterministic fallback when `saipen` is not resolvable through PATH.

Desired recovery order:

1. Attempt the canonical launcher normally.
2. If the executable is genuinely not found, inspect only the current project's bootstrap metadata.
3. If `.saipen/STATE.md` is readable and contains `saipen_home`, resolve the canonical launcher from that home.
4. Invoke that launcher in the current project directory.
5. Continue normal machine routing.

Do not perform broad filesystem discovery before consulting project-owned bootstrap metadata.

Do not hard-code the operator's current V: path.

Do not require PATH installation merely to make an already-managed project resumable.

Support the actual Windows shell surfaces in use, including:

- cmd.exe;
- PowerShell;
- Git Bash / POSIX-like shell on Windows.

Path conversion/launcher selection must be deterministic.

If different launcher artifacts are canonical for different shells, expose that fact through one bootstrap resolver rather than requiring model knowledge.

PROJECT STATE BOUNDARY

Reading `saipen_home` for bootstrap recovery does NOT make arbitrary STATE prose a substitute for the control plane.

The bootstrap read may discover the control-plane launcher.

Lifecycle truth still comes from the canonical command result.

Do not let an agent manually derive current lifecycle decisions from STATE when `continue --json` is available.

NO-HUNT RULE

When a valid managed project is already open, the following must not be necessary for ordinary recovery:

- `ls` across the global SAIPEN repository;
- drive-wide `find`;
- guessed installation directories;
- remembered user-specific paths;
- shell history;
- previous chat/session memory.

A failed PATH lookup should become one bounded project-local recovery step, not a discovery exercise.

STRUCTURED CURRENT-WORK CONTEXT

Reduce the second manual discovery sequence as well.

A successful `continue --json` for actionable Work should expose, directly or through one canonical referenced context object, enough machine information to enter the returned phase without scanning BOARD.

At minimum make readily resolvable:

- project_root;
- ticket id;
- phase;
- load_path;
- execution_intent;
- blocker/operator-action state;
- ticket detail_ref when present;
- source_receipts when present;
- exact current Work record or canonical locator for it.

If the phase needs the user source behind the Work, the agent should receive a deterministic locator for that source.

Do not require:

grep BOARD for T-###
find .saipen -name SRC-###
scan neighbouring ticket ids

merely to rediscover facts the control plane already resolved.

It is acceptable for SCOUT to inspect one relevant neighbour when the phase contract explicitly calls for it.

That architectural exploration is different from hunting for the identity of current Work.

PREFER ENRICHING EXISTING AUTHORITY

Prefer extending the existing:

`saipen continue --json`

and/or its canonical context owner rather than creating a second competing routing command.

If a separate context command is architecturally cleaner, it must be mechanically referenced by the continue result.

Do not make agents memorize another undocumented command.

EXACT REGRESSION — PATH-MISSING COLD START

Fixture:

- Windows managed project;
- `.saipen/STATE.md` contains a valid `saipen_home`;
- active `execution_intent = goal`;
- current phase/ticket are valid;
- shell is Git Bash;
- `saipen` is deliberately absent from PATH;
- no prior conversational/session state is available.

Input:

/goal cc all

Expected:

1. normal launcher lookup reports not found;
2. bootstrap reads only bounded project-owned bootstrap metadata;
3. canonical launcher is resolved from declared SAIPEN home;
4. `continue --json` executes successfully from the original project root;
5. returned phase/ticket is obeyed;
6. zero operator question;
7. zero broad filesystem scan;
8. zero guessed installation path.

RED control must demonstrate that the pre-fix bootstrap cannot meet this contract without manual discovery.

INSTRUCTION-PRECEDENCE REGRESSION

Fixture includes both:

- generic agent instruction requiring a style/skill bootstrap first;
- active SAIPEN operational command whose FAST PATH requires canonical continuation first.

Expected:

- control-plane routing occurs first;
- no ambiguity/question;
- the required style/skill is loaded afterwards if the returned phase actually needs it;
- behavioural/style requirements remain respected.

Do not solve this by ignoring generic instructions globally.

Pin only the operational-routing precedence.

CURRENT-WORK CONTEXT REGRESSION

Fixture:

- `continue --json` resolves `PHASE SCOUT T-288`;
- T-288 owns source_receipt SRC-124.

Expected:

the agent can resolve the T-288 Work description and SRC-124 through bounded canonical machine references without scanning the whole BOARD or searching all of `.saipen`.

Neighbour inspection requested by SCOUT remains allowed after current Work identity is established.

FAILURE SEMANTICS

If:

- project bootstrap metadata is missing;
- declared saipen_home does not exist;
- launcher is absent;
- launcher bytes are unusable;

return one exact bootstrap/integration diagnostic.

Do not silently guess another installation.

Where a safe managed/native recovery route exists, preserve the existing fail-open philosophy.

Do not turn optional bootstrap metadata trouble into loss of unrelated provider access.

SECURITY

Do not execute a launcher merely because an arbitrary text file names it.

Use the existing project/bootstrap trust boundary.

Do not search writable untrusted directories and execute the first `saipen` found.

Do not mutate user or machine PATH during ordinary recovery.

Do not persist shell-specific temporary environment changes globally.

NON_GOALS

- forcing SAIPEN onto global PATH;
- hard-coding the current operator's SAIPEN_HOME;
- making chat/session state canonical;
- replacing phase-specific SCOUT exploration;
- loading the entire BOARD into every first turn;
- making STATE the lifecycle decision engine;
- weakening provenance/security checks;
- creating a second parallel control plane.

SUCCESS CONDITION

A fresh compatible agent opened in any already-managed project can receive `/goal cc all` and deterministically reach the exact current phase/ticket even when `saipen` is absent from PATH and no prior session context exists.

The first-turn path should be boring:

resolve -> continue -> load phase -> execute Work

not:

guess -> search filesystem -> resolve instruction conflict -> grep BOARD -> find source -> finally begin Work.
