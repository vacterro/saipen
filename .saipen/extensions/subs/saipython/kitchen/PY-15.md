## Baseline

The exact TEST-15 concurrent-checkpoint scenario was reproduced in the pen
copy before the patch. Two checkpoint calls read the same uncounted closure;
one completed while the other returned `GC_MAINTENANCE_FAILED` with
`ValueError: GC state ... changed before atomic replacement`. The durable
counter still matched canonical history, but one maintenance failure was
recorded.

## Patch

The patch serializes the complete post-closure checkpoint through a separate
`.saipen/locks/gc-maintenance.lock`. It reuses `FileWriterLock`, which already
provides the platform-specific OS lock and same-process reservation. Contention
retries every 20 ms up to the existing project writer-lock timeout. The lock
covers counter sync, due assessment, collection and debt recording; the
collector's existing project writer lock remains independently owned and is
never nested recursively.

If maintenance-lock acquisition exceeds its bounded wait, the wrapper uses
the existing durable maintenance-failure recorder and leaves the committed
closure untouched.

touches only `tools/saipen_engine/gc.py`. T-2062 still depends on T-2059, so
Core must wait for that dependency before integration and repeat the patch
