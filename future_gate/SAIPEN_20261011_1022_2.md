PURPOSE

Investigate a future SAIPEN-compatible memory interoperability layer that allows independent agents and tools to exchange useful, verifiable project knowledge without gaining unauthorized lifecycle authority.

The layer must reduce repeated context reconstruction while preventing memory poisoning, stale-state promotion and cross-project authority leakage.

CORE PRINCIPLE

Memory is descriptive.
Canonical SAIPEN state is authoritative.

No memory record, regardless of source, may directly grant ownership, admission, completion, recovery, publication or operator consent.

PROPOSED CAPABILITIES

FG-1: PORTABLE CONTEXT ENVELOPE

Define a minimal transport-neutral envelope containing:

- Stable record identity.
- Project and task scope.
- Record type.
- Created and updated timestamps.
- Producer identity.
- Session identity.
- Source references.
- Evidence references.
- Source fingerprint where applicable.
- Schema and envelope versions.
- Content digest.
- Freshness and validation state.
- Sensitivity classification.

Unknown optional fields should survive safe round-trip operations.

Unsupported critical semantics must be explicitly refused.

FG-2: KNOWLEDGE TRUST CLASSES

Investigate explicit distinctions between:

- PROPOSED: an unverified statement.
- OBSERVED: supported by an observation.
- VERIFIED: validated against admissible evidence.
- STALE: no longer proven current.
- REVOKED: explicitly invalidated or withdrawn.

Treat these as proposed memory classifications, not new canonical lifecycle phases.

Never infer VERIFIED from an agent's own success claim.

FG-3: CROSS-AGENT CONTINUITY

A receiving agent should recover:

- Confirmed previous work.
- Current unresolved problems.
- Accepted decisions.
- Applicable constraints.
- Source and evidence references.
- Immediate next recommended action.
- Known blockers.
- Remaining uncertainties.

The receiver must recheck current canonical state, ownership and relevant live prerequisites before performing any state-changing operation.

A portable handoff is not a substitute for admission.

FG-4: SCOPE AND AUTHORIZATION

Memory must distinguish:

- User.
- Organization.
- Workspace.
- Project.
- Session.
- Task.

Cross-scope access must be explicit and authorized.

Read permission must never imply write permission.

Project ownership must never imply authority over another project.

Sensitivity labels alone are not sufficient access controls.

FG-5: CAPABILITY NEGOTIATION

Explore portable capability discovery for:

- Memory retrieval.
- Provenance verification.
- Handoff support.
- Evidence reference resolution.
- History.
- Export.
- Optional transport adapters.

Capability claims must be verified or explicitly marked unverified.

Unavailable capabilities must not be silently fabricated.

FG-6: CONFORMANCE CONTRACT

Investigate a transport-independent observable test suite.

Required negative controls:

1. Unknown record type survives round trip.
2. Stale records cannot override fresh canonical state.
3. Memory cannot grant Work ownership.
4. Memory cannot fabricate operator consent.
5. Memory cannot authorize recovery or publication.
6. Cross-project retrieval is denied without authorization.
7. Forged producer identity is rejected or marked untrusted.
8. Unauthorized scope expansion is refused.
9. Missing evidence cannot produce VERIFIED status.
10. Superseded decisions cannot silently become current rules.
11. Corrupt or incomplete context fails safely.
12. Capability claims cannot exceed verified implementation support.
13. Secrets cannot leak through exported memory.
14. Read-only access cannot mutate canonical state.
15. Concurrent updates cannot silently erase another writer's knowledge.

Conformance claims require executable evidence, not documentation-only test descriptions.

An independent implementation must not depend on a particular AI model, storage engine, vector database or transport.
