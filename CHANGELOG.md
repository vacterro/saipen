## 7.217.0 -- 2026-08-08 -- optional USERPERSON preference meta-control, off by default

`saipen userperson` is a new optional meta-control: with no `.saipen/USERPERSON.md` it adds nothing to a cold start -- no warning, no boot failure, no placeholder, no onboarding, no cold-start cost. Invoked while absent it runs lightweight onboarding (at most three broad questions, prefer two, or a free-form paste), then writes the canonical profile only after explicit user activation. USERPERSON means default direction, not order: precedence is current explicit request > project/task requirements > SAIPEN > verified evidence > USERPERSON, used only where a valid implementation choice remains unspecified. `add` merges semantically (an equivalent preference is a no-op, never appended history), `remove` drops the matching preference, `reset` requires explicit destructive confirmation, and only explicit user input modifies the profile -- no passive profiling, no mining LOG/chat. When a preference materially influenced a decision the task did not specify, the agent reports `USERPERSON alignment:` once at completion; a deliberate override by stronger constraints is reported as `USERPERSON deviation:`; neither trace appears when USERPERSON had no material effect. SubSaipen handoffs project a relevant subset only (saiui, saitranslate, saiwiki, saihunt) and never dump the whole profile. Implemented before the Improve wave so Improve can classify `USERPERSON_MISS` separately from protocol/project/logic violations. Mechanical core in `tools/userperson.py` (parse/render/merge/remove/validate/projection), the five commands resolve in CORE.md section 1.10, and a present profile is validated structurally. 15 probes plus the `userperson-valid`/`userperson-malformed` fixtures prove the semantics; the shortcut key-count sweep is unchanged (no new key). (T-574)

## 7.216.0 -- 2026-08-08 -- capability-measured platform probes + the active-task/DOING binding

The three runtime files that reached CI for the first time in v7.215.0 (`tools/freshness.py`, `tools/sub_clean.py`, `tools/hardening_controls.json`) were swept for the platform assumptions the manifest-staging paradox let ship untested. `tools/run_scenarios.py`'s tracked-mode-change probe had asserted the source fingerprint moves when `core.fileMode` is true by editing the INDEX (`git update-index --chmod`) while the fingerprint model reads the HEAD-vs-working-tree delta -- it was measuring git's fallback, not the fingerprint, and the fixed probe now records the original mode, chmods on disk, re-stats, asks Git what delta resulted, and SKIPs out loud only where no executable-bit transition can be represented. Symlink and junction capability are now MEASURED probes (`symlinks_available`, `junctions_available`, lazy at first use) wired into every probe that creates such an object; a host that cannot create them gets an explicit SKIP with the capability named, never a crash that hides every later check. The freshness sweep grew nine measured probes: spaces in filenames, Unicode filenames, case-distinct filenames (inode-verified -- a case-insensitive host silently aliases instead of raising, so the naive try/except capability test would have passed vacuously), FIFO objects, a project nested inside another Git repository, no-Git executable bits, and a Windows junction hashed as link identity instead of recursed. `tools/sub_clean.py` closes the reparse boundary: junction/reparse-point directories are never recursed, evidence digests never follow a symlink (a symlink's digest is its link identity), and symlink/reparse recovery evidence is rejected as non-preserved -- an outside file can no longer hash like preserved evidence. `tools/hardening_controls.json` gets mechanical structural checks (list shape, exact keys, unique contiguous IDs, unique names and anchors, canonical repository-relative owners that exist as files). The same Windows run reports 29 role-freshness behaviors executed and 5 SKIPs named by capability; Linux CI reports the complementary set. (T-572)

The v7.215.0 crash exposed a Core state invariant the validator could not see: a checkpoint claimed `STATE.task: T-572` in a ticket-bearing phase while BOARD carried no `## DOING` claim and T-572 sat in `## TODO`, and the tree validated. `tools/validate.py` now binds them -- a ticket-bearing phase (SCOUT, BUILD, VERIFY, REVIEW, SHIP) whose `task:` names a real ticket requires that ticket in `## DOING`, a `task: none` with a self-claimed or unclaimed `## DOING` ticket is the opposite interruption, and a `PHASE`/`RESUME:` `next_action` naming a different ticket than `task:` is a contradiction. A stranger's `## DOING` claim stays legal (`task: none` while another agent holds the ticket), because that is the multi-agent shape the Pick Rule already handles. Two checked-in crash fixtures (`active-task-not-claimed`, `state-behind-board-self-claim`) go red with one focused diagnostic, two audit mutations cover both directions, and a recovery probe performs RFC section 1.5's Recovery on each interruption and proves the rebuilt state validates and that a repeated Recovery is byte-idempotent. ## 7.215.0 -- 2026-08-08 -- gate context: a stale producer package stops blocking an unrelated Core ship

The wave's centre is an ownership fix. `tools/validate.py` answered two different questions with one severity, so a stale, malformed or unrefreshed EE/QQ package produced by another model failed the global validator and blocked ordinary Core commits -- seven of ten live FAILs were external producer state. `--gate` now names why the validator is running: bare or `--gate core` is structural conformance; `--gate ship` is everything needed to ship THIS tree, where producer readiness is a visible WARN and blocks nothing; `--gate collect:<producer>` makes exactly that producer hard (malformed, incomplete, stale, wrong `role_revision`, wrong source identity, not ready, or nothing to collect are each a FAIL) while leaving other producers soft; `--gate converge` adds CONVERGE.md stage M's fresh EE and QQ, where missing is also a FAIL. An unknown or misspelled gate exits 2 rather than falling back to the soft default. The validator stays read-only under every gate. CORE.md's collect row, CONVERGE.md stage M and `phases/ship.md` each name the gate they invoke. 14 probes covering all six required red controls, red-tested in BOTH directions -- forcing every gate hard turns five soft rungs red, forcing every gate soft turns three hard rungs red (T-568).

`phases/ship.md` step 6b is reordered around that gate: read the index and working tree, attribute every file, preserve anything the user staged, stage ONLY the reviewed files by explicit path (`git add .` and `git add -A` are forbidden), prove the staged set equals the reviewed scope, THEN run the ship gate, then `git diff --cached --check`, then commit exactly that scope, then push. Before this, the gate ran before any staging existed, so a required runtime file added by the ticket being shipped could never satisfy the tracked-runtime check without an undocumented staging step -- three MANIFEST entries were live in exactly that state, green locally and red in CI. A gate failure now names its rollback: no commit, no push, only this run's staging undone, pre-existing staged state untouched. `[ship-stage-before-gate]` pins stage < gate < commit by position (T-569).

`check_against_schema` claimed to interpret everything `state.schema.json` uses and did not: `minimum` sat on four fields unenforced, so `goal_waves: -1` passed the gate and handed the safety valve a budget below its own floor. `minimum` and `items` are enforced, and `audit_schema_keywords` now FAILs any keyword the schema declares that no enforcer interprets, and any `type:` value outside the four this validator knows -- the class guard, not just the instance (T-565).

The ccc I -> SHIP -> J proof compared raw hash strings, so one commit written at two abbreviation widths read as two commits and the check meant to catch a SHIP that changed nothing concluded it had. `canonical_commit()` resolves every reference through `git rev-parse --verify <ref>^{commit}` and compares full OIDs; the OID pattern widened from `{7,40}` to `{4,64}`, because the old one did not skip a SHA-256 OID -- it matched the first 40 characters and compared a truncated string. Evidence naming a commit the repository lacks now FAILs; a project with no Git at all WARNs rather than failing an unperformable proof. 10 probes including a real `--object-format=sha256` repository (T-566).

`saipen/SKILL.md` still routed readers to bare "RFC" -- "it points into RFC only when a rule question comes up", "before RFC" -- and instructed BOOT twice. Every RFC-trap pattern required the literal string `RFC.md`, so none of it was visible. The loader now says exactly: read BOOT once, BOOT loads STYLE before output, INDEX routes rule questions, CORE answers the exact one, RFC is a compatibility redirect no step sends you to. A semantic rung FAILs a routing verb aimed at RFC in any adapter, SKILL or injector, sentence-scoped so naming RFC as a redirect stays legal (T-549).

Also: the OUTBOX producer/consumer contract closes -- nonempty package text that parses as zero entries FAILs, and every charter's `output_contract` cites canonical PROTOCOL.md § 2 instead of publishing a local field list its own consumer rejects (T-564). `tools/audit_checks.py` gained an optional per-case gate after review found that its deliberate habit of keeping WARN lines would have let every producer control go on passing -- on a warning -- while proving no refusal; a gated case matches FAIL lines only, and an OUTBOX case naming no gate is refused before the suite starts. Re-verified on the final tree: T-562 distribution, T-563 cleanup fail-closed, T-567 Golden Default. audit_checks 221 of 221 with zero not-evidence, up from 211.
