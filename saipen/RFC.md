# SAIPEN Protocol (RFC)

## Part 1: CORE (Continuation Protocol)

### 1.1 Normative Rules
The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119.

- Agent MUST read `STATE.md`, `BOARD.md`, and tail of `LOG.md` before execution. All three, and `KNOWLEDGE/`/`kitchen/`, live under `.saipen/` at the project root -- later mentions in this document may drop the prefix for brevity, the location never changes. **Unqualified means exactly `.saipen/STATE.md` (and siblings) at the project root, never a nested one.** Since v7.35.0, `.saipen/extensions/subs/<name>/STATE.md` and (during a parallel TRANSLATE run) `.saipen/saitranslate/STATE.md` are real files with the same names, nested deeper in the same tree -- each is that *other* instance's own state, distinguished by its full path, never substituted for or confused with the project's own. Do not `find`/glob for a bare filename and act on whatever turns up first; use the exact path. **No `.saipen/` at the project root and git is available?** Before concluding "not initialized" and defaulting to `saipen set` (which would create a second, disconnected `.saipen/` -- orphaning the real one): check whether the current directory is a *linked* git worktree, not the main one -- `git rev-parse --git-common-dir` returns a bare `.git` when it is the main worktree, and an actual path ending in `/.git` when it is a linked one (e.g. `/path/to/main-repo/.git`). `.saipen/` is gitignored by design, and git populates a linked worktree from tracked content only -- so it never arrives there, however healthy the main worktree is (`tests/scenarios/linked-worktree-not-uninitialized/`). Strip the trailing `/.git` to get the main worktree's root and look there; only genuinely absent at *that* path does "not initialized, run `saipen set`" hold.
- **Bind the project root before the first checkpoint read, and keep that binding for every read and write in the session.** An explicit project-root argument wins deliberately; otherwise a Git checkout resolves through `git rev-parse --show-toplevel` plus `--git-common-dir`, and a non-Git project resolves to the nearest ancestor already carrying `.saipen/`. A linked worktree whose common directory belongs to the main worktree uses that main worktree's gitignored `.saipen/`; it MUST NOT create a local second copy. Root resolution identifies the directory only; missing or corrupt `STATE.md` is then diagnosed by normal validation/Recovery, never misreported as an unowned cwd. After binding, unqualified checkpoint names are shorthand for absolute paths under that one root -- changing cwd never retargets them. Before a write from a changed cwd, resolve again: a different repository/common Git directory is a mismatch and the agent MUST refuse the relative write, return to the bound root, or explicitly bind a new target. `saipen_home` is the protocol installation, not the project root; STATE deliberately stores no absolute project path because moving or cloning a valid project must not make its memory corrupt. `tools/validate.py --project-root PATH` is the explicit form and may be invoked from another cwd; without it, a cwd with no owning memory FAILs instead of guessing or creating `.saipen/`.
- **If any document disagrees, RFC.md wins.** `BOOT.md`, `phases/*.md`, `STYLE.md`, `CONFORMANCE.md`, `state.schema.json` and `KNOWLEDGE/*.md` all change across versions and can disagree, with each other or with a stale copy of this one. `RFC.md` resolves it, always -- not even `BOOT.md`'s "execute, don't ask" overrides a normative rule here, being a loading-speed optimization. Phase docs may tighten a rule for their own scope (verify.md's 3-hypothesis cap on top of § 1.6's table); they may never relax one. `extensions/schemas/state.schema.json` is the machine-readable mirror of STATE's field set and types -- authoritative for what a *machine* checks (`tools/validate.py` reads it directly), and the place to look for a field's type or enum. It is not a second opinion about what is required: **§ 1.2's nine-field required set is the normative list**, and the schema's own `required` array is deliberately narrower, because a JSON Schema `required` array cannot express "except on a fresh INIT" or "only when `goal_mode: true`". A field absent from that array is therefore either genuinely optional or conditionally required and checked in `tools/validate.py` instead -- the schema's `description` says which, every time. Read the two together, never the array alone. The schema's descriptions are summaries of § 1.2's semantics, never overrides. This paragraph itself is a rule, not a comment: document hierarchy is load-bearing for every validation and every agent session, and an agent that encounters a conflict and resolves it in favor of the non-RFC document is in violation.
- Agent MUST NOT rely on chat context for project state.
- **A returning agent MUST distrust its own memory before acting on it.** The rule above is usually read as advice for a *cold* agent, which is the harmless case -- it has no memory to mislead it. The dangerous case is the warm one: an agent that worked this project earlier, remembers plausible specifics, and is wrong because somebody else moved the project in between. Its recollection looks like knowledge, so nothing prompts a re-read. This is mechanical to catch and costs one comparison: before acting on anything you believe you already know, check `STATE.md`'s `agent:` and `updated:`. **`agent:` is not you, or `updated:` is newer than your own last write -> your memory is stale by definition.** Re-read `STATE`/`BOARD`/the `LOG` tail from disk and treat every prior belief -- versions, ticket states, what you think you shipped -- as unverified until the file says so. (`tests/scenarios/returning-agent-stale-memory/` records the incident.) Confident staleness is worse than ignorance, because ignorance asks.
- Agent MUST degrade capabilities if host tools are missing.
- Agent MUST NOT write secrets (API keys, tokens, passwords, private credentials) into `STATE.md`, `BOARD.md`, `LOG.md`, `KNOWLEDGE/`, `.saipen/kitchen/`, `.saipen/extensions/`, `.saipen/saitranslate/kitchen/`, `.saipen/recovery/`, or `.saipen/logs/` -- every one of these is scratch or committed content meant to be read by other agents, kitchen files included. `.saipen/recovery/` and `.saipen/logs/` matter most, because nothing writes them deliberately: Recovery copies a corrupt `STATE.md` **verbatim** (§ 1.5) and sealing moves LOG lines verbatim (§ 1.2), so a secret reaching either original is faithfully archived by a mechanism whose job is not to alter content. Redact at discovery, before it can be archived: a Recovery copy of a state containing a secret MUST be redacted in the copy (the redaction is the one content change Recovery is allowed to make, and it MUST be noted in the accompanying LOG line), and a secret found in an already-sealed segment is a rotate-the-credential incident first -- append-only forbids quietly editing the segment, so redact it only as a deliberate, LOGged `DEC` repair, never as a silent rewrite. A secret discovered mid-task gets redacted in whatever gets written (`sk-***`, not the real value) and the user gets told to rotate it, same as any other finding. This covers any credential shape -- `ghp_`, `AKIA`, a `postgres://user:pass@host` string, a bearer token, anything that would let someone else authenticate as this project -- never just the one prefix easiest to name.
- Agent MUST NOT perform a destructive operation without explicit user confirmation, unless the active ticket itself pre-authorizes it AND the operation is reversible. Destructive includes at minimum: force-push, branch deletion, history rewrite, schema/database drop, mass file deletion, user data deletion, and any irreversible migration. This governs SAIPEN's own operation (SHIP, CLEAN, and any phase that touches disk or git) -- it does not relax or replace whatever confirmation discipline the operating agent's own platform already enforces, it is the floor every SAIPEN-conformant agent MUST meet regardless of vendor.
- **Reply Language**: The agent MUST detect the language the user themselves typed and reply in that language immediately. If the user starts communicating in English, reply in English. Never infer the user's language from OS/IDE locale, platform UI, or repository files. When no prose is present (a bare command), default to English.
- **Chat Voice & Compression**: The agent MUST apply `saipen/STYLE.md` (`caveman-дед` voice: structural compression, cut filler/articles/pleasantries/hedging, blunt/street-smart tone, zero preambles/postambles, zero corporate apologies) to EVERY response from the first token. `BOOT.md` MUST mandate loading `STYLE.md` on boot, and MUST NOT defer it solely to a rule-question escalation.

### 1.2 File Model
- **STATE.md**: MUST contain frontmatter: `phase`, `task`, `next_action`, `blocker`, `agent`, `saipen_version`, `mode`, `updated`, `transition_from`. **These nine are THE required set -- the single place it is written down.** § 1.5's checkpoint self-check, `BOOT.md`'s post-checkpoint re-read, and `CONFORMANCE.md` row 44 all point here instead of restating it, -- five copies of this list once drifted into five different answers, so `tools/validate.py` now FAILs any document that re-enumerates it (CONFORMANCE 58). Anything not on this nine-field list is not required, however emphatically another document phrases it. Three conditional additions, and no others: `transition_from` is omitted **only** on a fresh `INIT` (no previous phase exists to name); when `goal_mode: true` the counters `goal_waves` and `goal_tickets` are additionally REQUIRED and MUST be integers (§ 2.4); and a Core `STATE.md` at `schema_version: 2` MUST carry `last_event` whenever its LOG contains an `E-###` event. `schema_version` is deliberately NOT on the list -- it SHOULD be present and current, but absence or v1 is readable legacy, not corruption: it WARNs and MUST upgrade to v2 at the next checkpoint. `saipen_version` (integer) records which protocol version wrote this state, and doubles as the version guard below -- one field. It is the MAJOR component only of the SAIPEN home's own `VERSION` file (semver `X.Y.Z` -- `saipen_version` is `X`, e.g. `7` for `7.46.0`, never the full string). "Current" for the version guard below means whatever `X` this agent's own `<saipen_home>/VERSION` currently reads -- RFC.md itself intentionally carries no version number of its own; the `VERSION` file at the saipen_home root (one directory above RFC.md) is the single source of truth for that. `saipen_home` (string) is a recognized MAY field: § 1.7's bootloader pointer, the absolute path to the SAIPEN home on the machine that last checkpointed -- MAY be absent on states written before v7.25.0. `next_action` MUST be an immediately executable command -- this includes the exact form `WAIT: <the specific question or decision needed>`, which counts as executable because "ask this exact thing and stop" is itself an unambiguous action. `next_action` MAY carry a compact trailing progress tag -- a single bracketed `[...]` suffix at the very end, informational only, never altering the command in front of it (e.g. `PHASE SCOUT T-154 [3/7 done, 1 blocked]`). An example that fails the rule below is worse than no example: a weak model copies the example and never reaches the rule. **`WAIT:` carries a category token, and the set of tokens is closed.** The shape is `WAIT: <category> -- <the exact question>`, where `<category>` is one of exactly seven words: `manual-verify`, `destructive-op`, `first-publish`, `user brake`, `blocked`, `safety valve`, `init`. `tools/validate.py` FAILs any `WAIT:` that does not open with one of them. This exists because § 1.11 names the guessing agent as the one failure this protocol cannot detect after the fact -- and the stopping agent is its twin: a vague `WAIT: need more context` is byte-identical in shape to a legitimate gate, passes every prefix check while saying nothing, and parks the project on a question nobody can answer. Naming the category is what makes the two mechanically separable, and it costs one word. The category is not decoration: it tells the human *what kind of answer unblocks this*, which is the difference between a `WAIT:` someone can clear in ten seconds and one that sits for a week. The seven, in full -- `WAIT:` is legal ONLY for a manual-verify gate, a destructive-operation confirmation, a first-publish confirmation, the user's own explicit brake, a session-level `BLOCKED` unblock request (`phases/blocked.md`: a specific credential, decision, or manual intervention needed to resume -- the question itself must be concrete, never "what's blocking us?"), a tripped § 2.4 safety valve (the run hit its 3-wave/20-ticket ceiling and MUST stop until the user re-authorizes: `WAIT: safety valve reached (N waves / M tickets) -- run 'saipen goal' to continue`; without this category the one place § 2.4 explicitly orders a stop-and-wait would have no legal way to express it), or -- narrowly -- `INIT` bootstrap when `BOARD.md` is empty and no project goal exists anywhere yet (`phases/init.md`): that bootstrap `WAIT:` MUST ask for the first goal or raw backlog only, never for context `STATE.md`/`BOARD.md`/`LOG.md` would otherwise already provide. Never a stand-in for "figure out project context," which the agent is already required to get from `STATE.md`/`BOARD.md`/`LOG.md`, not the user. **Narrower still at `phase: DONE` with an empty `## TODO`**: only two categories survive there, because every other one names a question about work in flight and there is none. Both MUST be written in a fixed, machine-recognizable form, since an agent arriving cold has no way to tell a legitimate pause from a previous agent's drift by reading free prose:
  - the § 2.4 safety valve -- `WAIT: safety valve reached (N waves / M tickets) -- run 'saipen goal' to continue`
  - the user's own explicit brake -- `WAIT: user brake -- <what the user asked to hold for>`

  **This restricts `WAIT:` only.** A `WAIT:` in that exact state that matches neither fixed form is non-conformant, `tools/validate.py` FAILs it, and § 1.11's UNBLOCK exception says to auto-transition instead of stopping. The other four `next_action` prefixes (`saipen `, `PHASE `, `RUN:`, `RESUME:`) are governed by their own rules and are **not** restricted here -- read the other way round, this paragraph would forbid the `PHASE HUNT` that § 2.1 requires from precisely this state, i.e. it would ban the only conformant exit. The fixed wording is the whole mechanism: a brake nobody can distinguish from drift gets treated as drift. `mode` is written per § 1.3 capability negotiation. `task` MAY be the literal string `none`. `blocker` MUST be non-empty when `phase: BLOCKED` -- a blocked state with no stated reason is not conformant. `updated` MUST be ISO-8601 **UTC** specifically (`Z` suffix or `+00:00`, never a local offset) -- Recovery's "STATE stale vs LOG/BOARD" comparison (§ 1.5) silently miscompares across agents in different timezones otherwise. MAY contain `goal_mode: true|false` (default `false`) — see § 2.4. While `goal_mode: true`, MUST also carry `goal_waves` and `goal_tickets` (integers, both start at `0`) — the persisted safety-valve counters § 2.4 defines; absent/cleared once `goal_mode` returns to `false`. MAY contain `human_note` (string) — an optional one-line human→agent nudge ("last time you did X, don't"), read on the next continue (`BOOT.md`'s `human_note` step) and cleared once applied. It is a lightweight feedback channel, NOT a ticket or a goal: it never queues work, it just colors how the agent approaches the next action, then it's gone. A `human_note` that actually implies work still gets turned into a real `TODO` ticket, not left living in `STATE.md`. "Cleared once applied" MUST leave a trace, not just an empty field where text used to be -- LOG one line (`DEC: applied human_note: <the text>`, or `DEC: human_note -> T-###` when it became a ticket) in the same checkpoint that clears it, so a later Recovery or a human skimming `LOG.md` can see what the nudge actually changed, instead of just knowing one existed at some point. `transition_from` (string) is REQUIRED on every state except a fresh `INIT` (which has no previous phase to name): the previous `phase` value before the last transition. It is what makes CONFORMANCE row 14's transition checking possible at all. Set on every phase transition -- the agent reads current `phase`, sets `transition_from` to that value, then writes the new `phase`. Absent on fresh INIT bootstrap or legacy states written before v7.83.0. Combined with `phase`, it makes phase transitions machine-checkable: `tools/validate.py` asserts every non-self transition against RFC § 1.6's table, and the five user-command phases (VALIDATE, MARKHUNT, CLEAN, TRANSLATE, PREPARE) are accepted from any origin.
- **Version guard**: If a project's `saipen_version` is HIGHER than what this agent's own copy of RFC.md defines as current, a newer protocol wrote this state and this agent is running a stale copy -- it MUST NOT silently proceed or rewrite the value downward. Degrade to `mode: read-only` and report the mismatch, or `BLOCKED` if even reading isn't safe, until the RFC copy is refreshed. Symmetric failure at the other end: if `<saipen_home>/VERSION` is missing, unreadable, or holds no parseable semver major, the guard's "current" is undefined and cannot be evaluated at all -- the agent MUST NOT silently proceed or write `STATE.md` on a guessed value (that write would stamp a `saipen_version` nothing verified). Degrade to `mode: read-only`, report the missing/unreadable `VERSION`, and refuse to downgrade or invent `saipen_version` until it is restored.
- **Executable `next_action`**: `next_action` MUST begin with one of `WAIT:`, `saipen `, `PHASE `, `RUN:`, or `RESUME:`. **Each prefix has exactly one argument shape, and a cold agent MUST be able to act on it without interpreting anything**  -- a prefix that passes every shape check while saying nothing about what to do is not a command:
  - `WAIT: <the exact question or authorization needed>` -- output that exact question verbatim and stop. Legal only in the categories enumerated below.
  - `saipen <command>` -- a command § 1.10 defines, or one an active project extension defines (§ 1.9). Route it there. A verb matching neither is non-conformant even though the shape is legal (`CONFORMANCE.md` row 49): `saipen hunt` looks perfect and names a phase only § 2.1 may enter autonomously.
  - `PHASE <phase-enum> [T-###]` -- enter that phase (a value from § 1.6's phase enum, uppercase) for that ticket, loading `<saipen_home>/phases/<lowercase-phase>.md` for its rules. **The ticket ref is REQUIRED for exactly the five phases this section already names as ticket-bearing** -- `SCOUT`, `BUILD`, `VERIFY`, `REVIEW`, `SHIP` -- and omitted for every other phase. A complement, not a second list: a hand-kept list here drifts from the one above the moment either changes, and its v7.92.0 version silently excluded `INIT`/`ADD`/`TRANSLATE`/`PREPARE`, leaving § 2.1's mandatory `HUNT -> ADD` with no legal `next_action` to write.
  - `RUN: <the exact shell, validator, or test command>` -- execute it as written and record the result in `LOG.md` as a `RUN:` line. Not a description of a command; the literal command.
  - `RESUME: T-### <phase-enum>` -- re-enter that phase on that specific ticket, picking up work already in flight (check `kitchen/` first, § 1.2). Distinct from `PHASE` only in intent, identical in obligation.
  Any of the five MAY carry the trailing `[...]` progress tag described above; nothing else may follow the argument. Vague continuation phrases are non-conformant, including `continue work`, `proceed`, `do next`, `review stuff`, `keep going`, `maybe`, and `if needed`. A question mark outside `WAIT:` is also non-conformant: questions belong in the explicit wait gate, not in a fake command. When `phase` is `SCOUT`, `BUILD`, `VERIFY`, `REVIEW`, or `SHIP`, `task` SHOULD reference a concrete `T-###`; `task: none` in those phases is allowed only for an explicitly named ticket-less maintenance exception in `next_action`.
- **STATE freshness marker**: Core `last_event: N` stores the numeric `N` from the highest `E-N` in the complete LOG sequence at the checkpoint that produced `STATE.md`. It is REQUIRED when `schema_version: 2` and at least one event exists; a fresh bootstrap with an empty LOG omits it because there is nothing truthful to name. Absence or `schema_version: 1` is readable legacy and WARNs rather than trapping an existing project, but the next checkpoint MUST write schema v2 plus the marker. A present marker is always enforced, including in legacy state: lower than the LOG tail means stale, higher means corrupt or from an incompatible branch. Recovery upgrades legacy state and writes the actual tail; it never guesses a value from `updated:` or BOARD.
- **BOARD.md**: MUST track ticket status via section headings `## DOING` / `## TODO` / `## DONE` / `## BLOCKED`. Every ticket line MUST follow this exact shape: `- [ ] T-### description`, checkbox `[ ]` open / `[x]` done / `[/]` in-progress. **The checkbox MUST agree with the section it sits under**: `[x]` only under `## DONE`, `[/]` only under `## DOING`, `[ ]` under `## TODO` or `## BLOCKED`. The section is the status; the checkbox is how a human skims it, and a board where the two disagree gives two different answers to "is this done" depending on which one the reader trusts. `tools/validate.py` FAILs a mismatch. Ticket lines MAY be optionally followed by any of ` | needs: T-###,T-###`, ` | owner: AgentID`, ` | claim_time: ISO8601 UTC` (same `Z`/`+00:00` requirement as `STATE.md`'s `updated`, § 1.4 -- the 15-minute staleness window in § 1.4 silently miscompares across agents in different timezones otherwise, identical failure mode to `updated`), ` | blocker: facts + dead ends`, ` | verify: <command or criterion>` (`phases/plan.md`'s "independently verifiable" ticket shape, made concrete on the ticket itself) as space-pipe-separated fields -- only the fields that apply, in any order. **Changing a ticket's status MUST move its line: cut from the old heading, paste under the new one. A ticket MUST NOT appear under two headings at once, and MUST NOT be left duplicated under its old section.** `T-###` IDs MUST be unique and MUST NOT be reused once assigned, even after the ticket is `DONE` or pruned. **The board alone cannot tell you what has been assigned**: `phases/clean.md` prunes `DONE` tickets, so the highest ID visible is routinely lower than the highest ever issued and "max on board + 1" silently reuses a pruned ID. The next ID is one above the highest `T-###` across `BOARD.md` **and** `LOG.md`, walking back into sealed segments when the active tail does not reach far enough (the same walk § 1.5 does for goal counters). A literal `|` inside `description` MUST be escaped as `\|` -- unescaped, it is indistinguishable from a field separator. `## BLOCKED` holds ticket-level blocks only (`phases/verify.md`'s debug cap: facts + dead ends noted via the `| blocker:` field) — distinct from session-level `STATE.phase: BLOCKED` (§ 1.6, `phases/blocked.md`), which is reserved for when no ticket anywhere on the board is workable. The Pick Rule (§ 1.6) only ever selects from `## TODO`, so a `## BLOCKED` ticket is automatically excluded without extra filtering logic. **Keep it readable.** `BOARD.md` is read on every cold start, so an unbounded board is context a cold agent spends before doing any work. It is not append-only, so it needs no sealing -- `phases/clean.md`'s scrub is the whole mechanism, and pruned tickets lose nothing, their events living permanently in `LOG.md`/`CHANGELOG.md`. `tools/validate.py` WARNs past a ~16 KB soft cap; a `## DONE` section holding more prose than the active work is the usual cause, scrubbed at the next `CLEAN`. **Cyclic `needs:`** (CONFORMANCE.md requires the graph stay acyclic): on detection, the agent MUST move every ticket in the cycle to `## BLOCKED` with `| blocker: dependency cycle: T-###,T-###,...`, LOG a `DEC` line, and continue with other workable tickets -- never pick from inside a known cycle. **Dangling `needs:`** (a referenced `T-###` exists nowhere on the board) is worse than a cycle, not milder: a cycle is caught by the acyclic check, while a reference to a ticket that was never real leaves the Pick Rule permanently unsatisfiable with no signal at all. Same remedy: move the ticket to `## BLOCKED` with `| blocker: needs nonexistent T-###`, LOG a `DEC` line, keep working other tickets.
- **Board must reflect shipped work.** Before SHIP (§ 1.10), the agent MUST ensure every work unit done this session has a ticket in `## DONE`. Work performed inline without a ticket (maintenance fixes, mechanical sweeps, doc corrections) MUST get a new `## DONE` ticket before `saipen ship` proceeds. A board whose `## DONE` section omits visible or LOGged work is stale and blocks SHIP until corrected -- the board is the project's work surface, not an incomplete index of it.
  **That ticket still has to earn `## DONE`, and until v7.92.0 this rule read as permission to skip that.** § 1.6 is unconditional: a ticket MUST NOT be marked `DONE` without a successful `VERIFY`. Read together with the paragraph above, an agent under ship pressure could conclude the protocol was *ordering* it to manufacture `[x]` tickets for work nothing ever checked -- turning `## DONE` from a record of verified work into a receipt printer, which is exactly the "finished is not verified" confusion `saipen status` (§ 1.10) exists to expose. It never meant that. Inline work reaches `## DONE` only with a verify trace, meaning at least one of:
  - a `| verify: <command or criterion>` field on the ticket line whose criterion actually ran, or
  - a `LOG.md` `RUN:` or `H:` line proving the check passed, referenced by that ticket.

  For a doc, config, or maintenance sweep with no test of its own, `tools/validate.py PASS` is an acceptable minimum criterion -- low, but real, and it is the same check the pre-commit hook runs. No verify trace and none obtainable -> the ticket stays `## TODO` or moves to `## BLOCKED` with the reason, and SHIP stays blocked. Blocking the ship is the correct outcome here, not a problem to route around: the alternative ships unverified work under a green checkbox.
- **BOARD shape is validated as a whole, not just ticket lines.** The four section headings (`## DOING`, `## TODO`, `## DONE`, `## BLOCKED`) MUST each appear exactly once. Duplicate headings split the work surface and are non-conformant even when ticket IDs remain unique. `review_passes: N` is a recognized optional ticket field used by `phases/review.md` to enforce its two-pass cap mechanically instead of from memory.
- **The ticket-field list is closed, and this is it.** After the description, a ticket line MAY carry ` | field: value` pairs drawn only from: `needs:` (T-### dependencies), `owner:` and `claim_time:` (§ 1.4's claim pair -- both or neither), `blocker:` (why a `## BLOCKED` ticket is stuck, with evidence), `verify:` (the command or criterion that decides the ticket is done -- `phases/plan.md` asks for it while the goal is still fresh, rather than as an afterthought during VERIFY), and `review_passes:` (above). Anything else is non-conformant and `tools/validate.py` FAILs it; a literal `|` inside a description MUST be escaped as `\|`. This list existed in the tool and in that FAIL message from the start, and `verify:` -- which 72 of this repository's own tickets carry -- was named nowhere in this document until v7.122.0, while `plan.md` and the validator both cited § 1.2 for it.
- **LOG.md**: Append-only event graph. Every line MUST follow this exact
  shape, in this order: `- DATE [E-###] [parent: E-###] [T-### | T-none] [agent: <id>] TAXONOMY: text`.
  This skeleton line is a quick-reference shape, not a second source of
  truth -- `[E-###]` alone is MUST, every other bracketed slot here is MAY
  exactly as detailed in the bullets below; a conformant line may omit
  `parent:`, `agent:`, and even the ticket ref (bare `T-none`) entirely.
  - `DATE` MUST be human-readable `DD.MM.YY HH:mm` and MUST be UTC (not
    ISO-8601 -- ISO-8601 UTC lives only in `STATE.md updated`; `DD.MM.YY
    HH:mm` here is also UTC). Agent MUST use the real current UTC time,
    never a placeholder (`XX`, `TODO`, etc. are non-conformant).
    CONFORMANCE #42 enforces this via validate.py's 3-hour drift check.
    LOG timestamps SHOULD be monotonically non-decreasing within the active
    LOG and across sealed segments. A timestamp earlier than the previous
    event by more than 5 minutes is a WARN-level anomaly unless a later DEC
    line explicitly documents it as historical clock drift. A timestamp more
    than 3 hours in the future from current UTC is a FAIL-level anomaly.
    U+FFFD replacement characters in LOG are a FAIL-level corruption signal:
    repair the shape/readability explicitly and add a new DEC line naming the
    repaired event; never hide the repair by silently rewriting history.
  - `[E-###]` (numeric Event ID) is MUST, always -- phase names
    (`[HUNT]`, `[BUILD]`) are NOT a substitute and MUST NOT appear here.
    IDs MUST be unique and MUST increase monotonically -- never reused,
    never assigned out of order.
  - `[parent: E-###]` is MAY (links the event graph; omit for a fresh root). When present, it MUST reference an `E-###` that already exists earlier in the file -- a dangling parent breaks the graph Recovery (§ 1.5) depends on.
  - `[T-###]` (ticket reference) is MAY -- omit for ticket-less events
    (HUNT sweeps, SHIP, session-level DEC/RUN), or write the literal
    `[T-none]` to mark ticket-lessness explicitly (equally legal -- it
    distinguishes "no ticket" from "forgot the field", and established
    practice already used it; ratified v7.24.0). Any other non-numeric
    value in this position is non-conformant.
  - `[agent: <id>]` (writer identity, same id convention as `STATE.md
    agent:`) is MAY, placed after the ticket ref and before the taxonomy.
    Single-agent sessions SHOULD omit it -- `STATE.md agent:` already says
    who's working, repeating it per line is noise.
  - `TAXONOMY` MUST be exactly one of: `RUN` (command executed, result),
    `DEC` (decision made, why), `H` (hypothesis, test, verdict). No other
    label is conformant -- a phase name is not a taxonomy value.
  - Commentary voice (STYLE.md) wraps AROUND this exact skeleton; it never
    changes the skeleton's shape.
  - When a phase doc instructs "LOG exactly `RUN: X`" (or `DEC:`/`H:`) as a
    fixed format, that fixed text is the `TAXONOMY: text` portion only --
    the full skeleton above (`DATE`, `[E-###]`, etc.) always still applies.
    No phase doc's fixed-format instruction is ever license to write just
    the bare taxonomy:text fragment as the whole line.
  - **Segmentation (keep it small, CPU/RAM/disk-friendly).** Append-only
    does not mean one ever-growing file. A multi-thousand-line `LOG.md` is
    slow to read on weak hardware and can overflow a context window --
    breaking § 1.1's "read the tail of `LOG.md`" before it even starts.
    So `LOG.md` MAY be **segmented**: when it grows past a soft cap
    (~300 lines / ~64 KB), at the next checkpoint *seal* it -- move its
    current content verbatim into `.saipen/logs/LOG-<NNN>.md` (`NNN`
    zero-padded, ascending: `001`, `002`, ...) and start a fresh `LOG.md`
    that continues the very same `E-###` sequence. Sealing MOVES whole
    lines, it never rewrites them, so append-only holds across the segment
    boundary -- history is relocated, never edited. `E-###` stays globally
    unique and monotonic across every segment; `[parent: E-###]` resolves
    against the concatenation of all sealed segments (in `NNN` order)
    followed by the active `LOG.md`. Only the active `LOG.md` is ever read
    for normal operation -- § 1.1's tail read and § 1.5 Recovery both touch
    it alone and stay cheap no matter how long total history gets; sealed
    segments are cold storage, read only when a `parent:` chain or an audit
    actually walks back into them. `tools/validate.py` reads sealed
    segments + active `LOG.md` as one sequence, so the graph checks are
    unchanged by where the boundary falls. Sealing is a natural `CLEAN`
    step (`phases/clean.md`) but MAY happen at any checkpoint once the cap
    is crossed. **Sealing MUST be crash-safe**, same temp-file-plus-rename
    discipline § 1.5 already requires for `BOARD.md`/`STATE.md`: (1) write
    the sealed segment to `.saipen/logs/LOG-<NNN>.md` via temp file + rename
    first; (2) only once that succeeds, replace the active `LOG.md` with a
    fresh empty one, also via temp + rename; (3) never delete or truncate
    the original content before the sealed copy is confirmed on disk. A
    crash between steps 1 and 2 leaves the pre-seal `LOG.md` still intact
    and readable -- worst case the next agent re-attempts sealing on a file
    that's already safely duplicated, never a lost history. **Sealing MUST NOT begin
    unless the cap is actually crossed** -- that precondition is the outer
    guard, and the idempotency check below cannot substitute for it. The two
    protect against different things: after a *successful* seal the active
    log is a brand-new file, not a prefix of any segment, so a second run
    sails past the prefix test and seals a nearly-empty log into its own
    segment. Observed exactly once, in v7.93.0, from re-running a seal script
    to test its idempotency; the stray segment was folded back and the repair
    LOGged. Check the cap first, every time. **The re-attempt after a crash
    MUST also be idempotent, not a blind second seal**: before writing a new
    segment, compare the active `LOG.md`'s content against the
    highest-numbered existing `.saipen/logs/LOG-<NNN>.md`. Already identical
    (or a prefix of it) -> the seal already succeeded and only step 2 was
    lost: just replace the active `LOG.md` with a fresh empty one, do NOT
    create another segment. Skipping this check writes the same `E-###`
    lines into two segments, which breaks the global uniqueness the whole
    scheme rests on -- the exact wreckage sealing exists to avoid.
  - **A plain append is not automatically crash-safe either.** `LOG.md`
    grows by appending, which is cheap and normally atomic enough at these
    sizes -- but a crash mid-append can still leave a final line truncated
    mid-text. Such a line is debris, judged the same way § 1.2's kitchen
    rule judges a half-written scratch file: the *last* line of the active
    `LOG.md` failing to match the skeleton, when every line before it
    matches, is a crashed append, not history to preserve. Move it to
    `.saipen/recovery/<timestamp>-LOG-tail.md` and continue from the last
    intact line -- never guess at what the truncated line meant to say, and
    never treat it as license to reshape *earlier* lines (`phases/validate.md`'s
    shape-only rule still binds: a malformed line that isn't the last one
    is real history with a bad shape, a different problem entirely).
- **KNOWLEDGE/**: Directory for durable truths. MUST NOT contain event histories -- that is the actual constraint, not the filename. Two valid shapes, pick whichever fits the content: a living reference doc with a descriptive name (`architecture.md`, `traps.md`) that gets edited in place as understanding improves, or a numbered ADR (`ADR-001.md`, `ADR-002.md`, ...) recording one immutable decision + its reasoning, never edited once written. Either way: durable truth, never a log of events.
- **kitchen/**: Directory for intermediate, half-finished files, scratchpads, and work-in-progress data. Agents MUST store temporary work here to avoid cluttering the project root. If an agent terminates mid-task, the successor MUST inspect `kitchen/` to resume work seamlessly -- this means `.saipen/kitchen/` specifically, the Core project's own scratch. `TRANSLATE` (§ 2.1) keeps its own, separate `.saipen/saitranslate/kitchen/` — never shared with this one. Each subSaipen (`extensions/subs/`) likewise keeps its own `kitchen/` under `.saipen/extensions/subs/<name>/` — a crashed subSaipen's half-done work is that subSaipen's own concern to resume (or the main agent's, via the Handoff/OUTBOX procedure that extension defines), never something the main agent inspects looking for its own crashed work. **Kitchen writes are not required atomic** (unlike `STATE.md`/`BOARD.md`, § 1.5) -- so a kitchen file whose last record ends mid-line was truncated by a crash mid-write, and is debris, not resumable state: the successor MUST treat such a file as corrupt and restart that piece of scratch clean, never resume from a half-written kitchen file as if it were whole. The authoritative trio (`STATE`/`BOARD`/`LOG`) is protected by § 1.5's write-order; kitchen scratch trades that guarantee for cheapness, so integrity is checked on read, not assumed.

### 1.3 Capability Negotiation (Two-Way Handshake)
1. **Protocol Demands**: `STATE.md` MAY define `requires: [filesystem, git, shell, python]`.
2. **Agent Capabilities**: Agent MUST evaluate host against requirements.
3. **Mode Lock**: Agent MUST write operating mode to `STATE.md` (`mode: full | read-only | no-publish | manual-verify`). **`read-only` is the one mode that cannot record itself** -- it is set precisely because filesystem writes are unavailable, so "write `mode: read-only` to `STATE.md`" is unsatisfiable by construction. Resolve it the honest way, never by quietly skipping the capability check: report the detected mode in chat instead, work under it for the whole session, and leave whatever `mode:` the file already carries untouched (a stale `mode: full` on disk is not a lie the agent told -- it is simply the last value a writing agent left, and the next agent with write access re-negotiates it from its own host anyway). A later agent MUST NOT read a `mode:` value as proof of the *current* host's capabilities; § 1.3's handshake is re-run every session, this field records its last outcome, not a standing fact.
   - **A `requires:` entry with no mapping below** (e.g. `python`) is not a licence to ignore it: missing, and the work genuinely needs it -> degrade to the nearest mode that describes what's actually lost (no `python` means `tools/validate.py` can't run, so VALIDATE falls back to the frozen portable floor `tests/validate.sh`/`.ps1` per `phases/validate.md`, and only if *that* is also unavailable does the conformance check become impossible -> `BLOCKED` rather than a silent skip). Never proceed pretending an unavailable required tool was merely optional.
   - Missing Git: `mode: no-publish`. Agent MUST NOT perform any git-dependent step (commit, tag, push) -- but SHIP itself stays reachable: `phases/ship.md` defines a no-publish branch that still does everything that doesn't need git (version bump, CHANGELOG, digest) and closes straight to `DONE`. A blanket ban on entering `SHIP` at all would leave a git-less project unable to ever close a ticket (`phases/review.md` makes `SHIP` mandatory before `DONE`, no exception) -- degrading git-dependent steps only, same treatment as `read-only`/`manual-verify` degrade their own missing capability instead of dead-ending the whole phase (v7.66.0; a real, previously-unresolved gap here until then).
   - Missing Shell: `mode: manual-verify`.
   - Missing Filesystem Write: `mode: read-only`. **The rule is the principle, and the list is only its most common instances: every phase whose work product is a file write is out of reach.** **Read-only banned phases**: `INIT`, `PLAN`, `ADD`, `BUILD`, `SHIP`, `CLEAN`, `TRANSLATE`. The agent MUST NOT transition to any of them, nor make any `ADD`/`HUNT` change beyond reporting findings. `INIT` creates `.saipen/` and `PLAN` writes tickets, so both were always unreachable; naming only four made the list look exhaustive and left a read-only agent apparently free to stamp tickets it could not save. When a phase is not listed, apply the principle rather than assuming permission. `MARKHUNT`, `PREPARE`, and `VALIDATE` are the audit/validate phases that quietly also write, so read-only reaches them only in **report-only** form: run the audit / freshness-pack / conformance check and report the result in chat, but MUST NOT record it -- no `## BLOCKED` tickets from `MARKHUNT`, no `kitchen/` or handoff payload from `PREPARE`, no structural repair from `VALIDATE` (report the corruption, leave it as-is). The agent MAY still read, analyze, and report; it advises, it does not act. A **subSaipen**'s `mode: read-only` is a *scope* lock, not this capability lock: it writes its own folder freely and is barred only from the shared tree, so its phase ban is four phases rather than these seven -- `extensions/subs/PROTOCOL.md` § 1 states it, and the two lists are cross-checked. Claiming the two contracts were identical is what let a document forbid `PLAN` while every subSaipen legitimately planned its own backlog.
4. **Optional Parallel Execution**: `subagents` (parallel task/agent
   spawning) is never required and never gates a phase or sets `mode`.
   Its trigger is independence, not speed -- `HUNT`'s 6 signal categories
   (`phases/hunt.md`) don't depend on each other's results, so where
   subagents are available they MAY run concurrently instead of in turn.
   Absence MUST fall back silently to sequential execution -- same result.

### 1.4 Claim & Ownership
- Claiming a ticket = moving it to `## DOING` with `owner: <AgentID>` and `claim_time: <ISO8601 UTC>` set on its line. When one agent is provably alone on a project (the common single-agent case), the fields are OPTIONAL -- but any agent that even suspects it is not alone MUST set both on every ticket it picks.
- **Active claim**: `claim_time` less than 15 minutes old. The owner MUST refresh `claim_time` before it goes stale while holding the ticket: at every checkpoint (§ 1.5), AND as a standalone `BOARD.md`-only touch at least every 10 minutes of continuous mid-ticket work. Checkpoints alone cannot carry this duty -- § 1.5 checkpoints fire after tickets, so a 40-minute ticket would starve its own claim mid-work and make theft of a live ticket legal (v7.28.0 tied refresh to checkpoints only; fixed v7.30.0). Liveness is decided by reading `BOARD.md` alone; a recent `LOG.md` line stamped `[agent: <owner>]` (§ 1.2) MAY serve as supporting evidence, never as the primary test. (The pre-v7.28.0 "or actively writing to LOG.md" test was undecidable -- a shared file's mtime can't attribute activity to any particular owner).
- **Stale claim**: `claim_time` 15+ minutes old -> forfeit. The next agent MAY take the ticket over: LOG a `DEC` line recording the takeover (old owner, observed staleness), set its own `owner:`/`claim_time`, and inspect `kitchen/` for the predecessor's half-done work (§ 1.2) before redoing anything from scratch.
- A `## DOING` ticket carrying NO `owner:`/`claim_time` at all is unclaimed by definition (a crashed single-agent session, or pre-claim history): any agent MAY adopt it the same way -- LOG the `DEC`, check `kitchen/`, continue the work.
- **Conflicting claim writes**: the first write that lands in `BOARD.md` wins -- but whole-file saves mean a concurrent second save can silently clobber the first, so "landing" MUST be verified, never assumed: after writing a claim, re-read `BOARD.md` and confirm your claim actually survived. Your claim is absent or overwritten -> you lost, whatever the wall-clock order was; re-read and pick a different ticket -- never re-assert a claim over the winner's.
- **`agent:` names the SEAT, not the model build -- and a returning agent inherits it.** Every rule in this section compares `agent:` against "itself", and until v7.125.0 nothing said where an agent gets its own value, so each session invented one: this repository's own history carries six for what were two or three actors (`claude-opus`, `claude-sonnet-5`, `opencode`, `antigravity`, `antigravity-gemini`, `gemini-pro`), and one LOG line reached disk reading `[agent: id]` -- a placeholder, not a name. A comparison with one side undefined is not a safety mechanism; it is noise that fires both ways. **False alarm**: a model upgrade renames the seat, the next session sees a stranger and assumes a live concurrent agent. **Missed alarm**: two genuinely different actors both writing the same generic value are indistinguishable. So: **read `STATE.md`'s existing `agent:` and keep it** -- that value is the seat, and continuing another session's work in the same seat is what this protocol is for. Change it only when you are genuinely a different actor (a different person's tooling, a different platform driving the project, a subSaipen writing its own state), and when you do, LOG a `DEC` naming the old value and the new one so the graph shows a handover rather than an unexplained stranger. A model version change is NOT a different actor: `claude-opus` upgrading is still `claude-opus`. Placeholders (`id`, `<name>`, `AgentID`, `unknown`) are never valid values -- `tools/validate.py` FAILs them.
- **Concurrency boundary**: Core's safety model is claim-serialized tickets with ONE agent writing `.saipen/` at any instant. Two-plus agents making uncoordinated concurrent checkpoints is outside Core's envelope -- `E-###` allocation races and last-writer-wins `STATE.md` are exactly why (the validator catches that wreckage after the fact; nothing in Core prevents it up front, by design -- SPEC.md: a state protocol, not a distributed consensus algorithm). An agent that observes `STATE.md` with `agent:` other than itself and `updated:` fresher than the claim window MUST assume a live concurrent session: work only tickets it claims under this section's rules.
- **Whole-STATE phase claims go stale the same way, not just BOARD tickets.** A parallel instance (`TRANSLATE`'s own dedicated-agent mode, § 2.1/`phases/translate.md`) is explicitly told not to write the shared `phase:` field -- but that rule is textual, same as every other isolation rule in this document (§ 1.9's extension boundary, the subSaipen boundary `extensions/subs/PROTOCOL.md` § 1 states), so a weak or confused instance can and does violate it anyway. (`tests/scenarios/parallel-translate-isolation/` records the incident.) Finding `STATE.md` in a phase you never personally entered, under an `agent:` you don't recognize as yourself, with no matching `LOG.md` activity since -> treat it exactly like a stale `## DOING` claim above: LOG a `DEC` line naming the old agent and the observed staleness, inspect what it actually produced (`.saipen/saitranslate/kitchen/` for a real partial bundle, or the shared files themselves for direct damage) before rebuilding `STATE.md` to reflect your own real continuation -- never silently overwrite without recording the takeover, and never silently keep working under a phase you never set yourself.

### 1.5 Checkpointing & Recovery
- **Checkpointing**: MUST checkpoint after every ticket, after every phase transition, and before session termination. The phase-transition trigger is not redundant with the per-ticket one: a single ticket walks `SCOUT -> BUILD -> VERIFY -> REVIEW`, and without it a crash anywhere in that walk leaves `STATE.phase` naming a phase the work has already left, which Recovery then has to reconstruct from the LOG instead of simply reading. Three separate files cannot be written as one atomic transaction, so order stands in for atomicity: **(1)** append the `LOG.md` event, **(2)** write `BOARD.md` (temp file + rename), **(3)** write `STATE.md` (temp file + rename) *last* -- `STATE.md` is the commit pointer. That last write MUST use current `schema_version: 2` and set `last_event` to the highest `E-###` now present across sealed plus active LOG; only a fresh empty LOG omits it. A crash between any two steps always leaves `STATE.md` truthfully behind `LOG.md`/`BOARD.md`, never ahead of them, which is exactly the condition Recovery below already knows how to fix. Writing `STATE.md` first (or in any other order) can leave it claiming something `BOARD.md` doesn't yet reflect -- a crash Recovery would not reliably catch.
- **Every one of the three writes is confirmed by reading it back, not just `STATE.md`.** § 1.4 already requires re-reading `BOARD.md` after writing a *claim*; the same duty covers writing *content* -- a new ticket, a status move, a `## DONE` line. After step (2), re-read `BOARD.md` and confirm the tickets you meant to write are actually on it; after step (1), confirm the LOG line is the last line of the file. A real incident, in the session that shipped this rule: an agent wrote fourteen tickets to `BOARD.md` through a pattern substitution whose anchor did not match the file, then printed its own hardcoded success message and moved on. Eleven tickets of work were done with the board silently unchanged -- every edit landed, only the bookkeeping vanished, and nothing noticed for an hour because the *validator* stayed green: an empty `## TODO` is perfectly conformant. This is the general shape and it is worth naming: **a write you did not read back is a claim, and a success message your own tool printed is not evidence.** The three-file order (§ 1.5) protects against a crash between writes; it does nothing about a write that quietly did not happen.
- **Confirm the checkpoint you just wrote, don't assume it landed well-formed.** After step (3), re-read `STATE.md` and check it still carries **every field § 1.2's required set names** -- go read that list there, do not work from a copy held anywhere else, including a copy in your own context from earlier in the session. This section deliberately does not restate the fields -- its own copy once omitted `transition_from`, so an agent self-checking against it confirmed states the validator then failed. Where a validator is reachable, `tools/validate.py` IS this check and running it is both cheaper and more trustworthy than reading nine field names off a page. This is the same re-read-after-write discipline § 1.4 already mandates for a claim ("after writing a claim, re-read `BOARD.md` and confirm your claim actually survived"); the failure mode is identical, and until v7.84.0 only one of the two had the guard. A checkpoint written without `next_action` fails TEST-001 outright -- the one guarantee this protocol exists to make (`tests/scenarios/checkpoint-self-confirmation/`). Missing or empty required field -> fix it before doing anything else; a checkpoint that cannot be resumed from is not a checkpoint. Where a validator is reachable, running it is the cheapest way to do this check and SHOULD be preferred over eyeballing.
- **Dirty tree on continuation**: uncommitted project changes at cold-start are a NORMAL protocol state, never an anomaly to warn the user about -- work commits at `SHIP`, not per checkpoint, so an in-flight ticket's edits are uncommitted by design. Before touching anything, the agent MUST attribute them: cross-reference `git status`/`git diff --stat` against the open `DOING` ticket's scope, the `LOG.md` tail, and `kitchen/`. No git available (`mode: no-publish`, or no repo at all) -- there is no "uncommitted" concept to diff against, but the same attribution question still matters (did *I* leave this mid-edit, or did someone else touch it between sessions): fall back to filesystem modification timestamps on the changed-looking files themselves, cross-referenced against `STATE.md`'s own `updated:` and the open `DOING` ticket's scope, the same mtime heuristic Recovery below already uses for the no-git case. Attributable to the in-flight ticket -> that IS its work so far: continue or adopt it (§ 1.4) and let the changes fold into its eventual commit, no ceremony. Not attributable to any ticket (the user's own edits, another tool's output) -> the agent MUST NOT commit, revert, stash, or clean it: reverting is user-data deletion (§ 1.1), committing stamps authorship over changes nobody reviewed. Only when unattributed changes sit in the very files the next action must touch does the agent stop and ask -- that is § 1.1's existing destructive-op confirmation gate, not a new `WAIT:` category.
- **Recovery**: **Under `mode: read-only`, Recovery MUST NOT write anything** -- rebuilding `STATE.md` is a file write, and that mode is set precisely because writes are unavailable, so the whole procedure below is unexecutable there. Report the stale or corrupt state in chat, name the exact repair that would be required (which field, rebuilt to what value, from which evidence), and stop. Do not perform a partial repair, and do not report a rebuild that did not happen. This is the same resolution § 1.3 gives for `mode:` itself and § 1.10 gives for `saipen stop`'s digest: the honest branch, not a silent skip. With writes available: if `STATE.md` is stale but `LOG.md` or `BOARD.md` is newer, `git status` is ground truth where git is available. Without git (`mode: no-publish`, § 1.3, or no repo at all) -- fall back to filesystem modification timestamps on `LOG.md`/`BOARD.md`/`STATE.md` themselves: whichever of the three was written most recently, cross-referenced against the Checkpointing write order above (LOG, then BOARD, then STATE last), tells you how far a crash got without needing git at all. One § 1.4 caveat on that heuristic: a standalone `claim_time` refresh legitimately touches `BOARD.md` with no `STATE.md` write after it, mimicking a crash between checkpoint steps 2 and 3 -- before rebuilding anything, check whether `BOARD.md`'s difference from what `STATE.md`/`LOG.md` imply is claim fields only; if so, that is a live claim being kept fresh, not a crash. **Recovery MUST be idempotent -- running it twice changes nothing the first run did not already do.** `continue -> crash -> continue -> crash -> continue` is the expected life of an autonomous run, so every step here has to be safe to repeat: rebuilding an already-rebuilt `STATE.md` yields the same file, re-adopting an already-adopted ticket is a no-op rather than a second claim, and the recovery copy below is written under a timestamped name precisely so a second pass adds a file instead of overwriting the evidence the first pass saved. Recovery that is only safe the first time is worse than none, because the crash it exists to survive is exactly what invokes it repeatedly. Where a step cannot be made naturally repeatable, it MUST be made *detectably* repeatable -- check whether the work is already done before doing it, the same shape as the sealing idempotency check in § 1.2.
Before overwriting a corrupt or stale `STATE.md`, copy it to `.saipen/recovery/<timestamp>-STATE.md` -- Recovery reconstructs from evidence, it does not destroy evidence. Rebuild `STATE.md` based on latest `LOG.md` entry and open DOING ticket. **Neither input is guaranteed present, and the checkpoint order is why**: LOG is written first, so a crash between steps 1 and 2 leaves a LOG line about a ticket `BOARD.md` still shows in `## TODO`. An absent `## DOING` therefore does not mean nothing was in flight -- scan the LOG tail for the most recent `[T-###]` with no later `DONE`/ship line closing it, and resume that, re-claiming it properly (§ 1.4). **A live `## DOING` ticket outranks the LOG tail, whatever the tail says.** Check `BOARD.md` first: any ticket in `## DOING` is the thing that was in flight, and Recovery rebuilds around it (adopting it per § 1.4 if unclaimed) -- the LOG-tail heuristics here exist only to answer "what was in flight" when `## DOING` cannot. Ordering matters because the two disagree in the ordinary case, not a rare one: the checkpoint writes LOG first, so any session-level event after a ticket's last line makes the tail look ticket-less while the board still holds the real answer. And when `## DOING` is empty *and* the latest LOG entry is session-level rather than ticket-level (`T-none`: a `SHIP`, `CLEAN`, `MARKHUNT`, `VALIDATE`, or a bare `DEC`), there is no ticket to infer and none should be invented: rebuild to `phase: DONE` with `task: none` and let `phases/done.md`'s own priority logic pick the next real work from `BOARD.md`, which is the same place a clean session would have landed anyway. If the recovered `STATE.md` shows (or `LOG.md` shows a `DEC` pivot line for) `goal_mode: true`, `goal_waves`/`goal_tickets` MUST be rebuilt too -- count wave/ticket-completion events since the NEWEST goal marker, never assume `0`. Two lines are markers, not one: the `DEC` pivot line for `saipen goal <text>`, and the `DEC: goal reauthorized` line § 2.4 requires from a bare `saipen goal`. Counting from the pivot alone rebuilds every bump a later re-authorization already cancelled, which hands the run back a tripped valve the human cleared. Only increments are completion events -- a marker's own `N->0` records the reset, it is not a wave or a ticket. The pivot line itself may have been sealed away (§ 1.2) if enough LOG activity happened since -- the active `LOG.md` alone is not guaranteed to still contain it, so Recovery MUST walk back into `.saipen/logs/LOG-<NNN>.md` segments (in `NNN` order) when the pivot line or the required count isn't found in the active file alone; this is exactly the "parent chain or an audit actually walks back into them" case § 1.2 already carves out as the reason sealed segments exist at all. Losing the count on recovery is exactly the failure § 2.4's safety valve exists to prevent.

Any Recovery rebuild MUST also migrate the Core state to `schema_version: 2` and set `last_event` to the highest real `E-###` found across sealed plus active LOG, omitting it only when that complete sequence is empty. The value comes from evidence, never from `updated:` or BOARD; rebuilding the same evidence therefore produces the same marker and remains idempotent.

### 1.6 Core State Machine & Ticket DAG
`INIT → PLAN → SCOUT → BUILD → VERIFY → REVIEW → SHIP → DONE | BLOCKED`

`SHIP` has one narrow backward edge: a fixable preflight failure found before
commit/tag/push returns the current ticket to `BUILD`, then repeats
`VERIFY -> REVIEW -> SHIP`. It is not a retry path for a failed publish and
never permits editing after a successful push (`phases/ship.md`).

- **Ticket DAG**: Tickets MUST define dependencies using `needs: [T-XXX]`. **Pick Rule**: a `## TODO` ticket is *workable* when all its `needs:` are marked `DONE` and it is not under another agent's active claim (§ 1.4). **Agents MUST take the topmost workable ticket, reading `## TODO` from the top.** Eligibility alone left the actual choice open, which is a hole in a section named Determinism Invariants: two conformant agents handed the same board could pick different tickets and both be right. Board order is priority -- § 2.4's Entry already relies on exactly that when it inserts a new objective's tickets at the top -- so the first workable line wins, and re-prioritising means moving lines, not arguing about them.
- **VERIFY**: MUST be executed. Failure retries within VERIFY itself, not a phase transition -- `phases/verify.md`'s own cap (3 dead hypotheses or 2 failed fix cycles) moves the ticket to `## BLOCKED` on `BOARD.md` and the agent picks up other workable tickets instead. Success transitions to `REVIEW`.
- **MANUAL-VERIFY**: If `mode: manual-verify`, `VERIFY` MUST block and await human confirmation. Agent MUST NOT auto-transition to `REVIEW`.
- **DONE**: A ticket MUST NOT be marked `DONE` without a successful `VERIFY` (or human `MANUAL-VERIFY`).

**Phase enum**: `INIT`, `PLAN`, `SCOUT`, `BUILD`, `VERIFY`, `REVIEW`, `SHIP`, `DONE`, `VALIDATE`, `HUNT`, `MARKHUNT`, `ADD`, `CLEAN`, `TRANSLATE`, `PREPARE`, `BLOCKED`. These sixteen are deliberately factored, not accidentally many: the 2-tier loader (`KNOWLEDGE/decisions.md`, v5.0.0) loads only the active phase's own `phases/*.md`, so the *count* is nearly free — merging them into fewer fat docs raises per-call tokens, it doesn't lower them. Recurring "collapse the phases into 4/5/8" proposals have been rejected with full reasons; read `KNOWLEDGE/decisions.md` before re-proposing one.

**Transition table** -- a quick-reference index, not a second source of truth. Each phase's own `phases/*.md` is authoritative; if this table and a phase doc ever disagree, the phase doc wins and this table is the one that's wrong. **`BLOCKED` here is always the session-level `STATE.phase: BLOCKED`** (`phases/blocked.md`) -- the DFA this table describes has no other kind of state. `## BLOCKED` on `BOARD.md` (§ 1.2) is a completely different, ticket-level concept that shares the name but never appears as a `phase:` value anywhere; do not conflate the two just because this table's bare word "BLOCKED" doesn't repeat the distinction every time it's used:

```text
INIT      -> PLAN | BLOCKED
PLAN      -> SCOUT | BUILD | DONE | BLOCKED
SCOUT     -> BUILD | BLOCKED
BUILD     -> VERIFY | BLOCKED
VERIFY    -> REVIEW | SCOUT | BUILD | BLOCKED
REVIEW    -> SHIP | BUILD | SCOUT | BLOCKED
SHIP      -> DONE | BUILD | BLOCKED
DONE      -> SCOUT | PLAN | HUNT | BLOCKED
VALIDATE  -> SCOUT | PLAN | DONE | BLOCKED
HUNT      -> ADD | PLAN | SCOUT | BLOCKED
MARKHUNT  -> DONE | BLOCKED
ADD       -> BUILD | PLAN | SCOUT | DONE | BLOCKED
CLEAN     -> DONE | BLOCKED
TRANSLATE -> DONE | BLOCKED
PREPARE   -> DONE | BLOCKED
BLOCKED   -> PLAN | SCOUT | DONE
```

- **From-any-phase set**: `CLEAN`, `TRANSLATE`, `PREPARE`, `VALIDATE`, `MARKHUNT`, `PLAN`.
  These six are entered by explicit user command (§ 1.10) from ANY phase, so the transition table's FROM row does not restrict them -- the same way `saipen stop` isn't chain-specific. Once entered, their own row above governs what they can transition to next. `PLAN` is `saipen plan`, and also the `PLAN` that § 2.4's goal-mode Entry mandates on every pivot.

  **A command recognized from any phase is not the same thing as a phase reachable from any phase, and `SHIP` is where the two must not be confused.** `saipen ship` is recognized from anywhere (§ 1.10), but `phase: SHIP` is enterable **only from `REVIEW`** -- this table's single route into it, which § 1.10 states in the same words. `SHIP` was listed here as an any-phase transition from v7.83.0 (validator) and v7.92.0 (this text) until v7.94.0, so the two halves of the protocol disagreed about whether an agent could jump straight to publishing: one said run the gates, the other said the jump was a legal transition. Invoking the command from outside `REVIEW` means "take this work through the missing gates, then ship", and the `next_action` it writes is the next gate on that ticket's Core chain -- never `PHASE SHIP` until `REVIEW` has actually passed.
  This list said five until v7.92.0 while § 1.10 had listed seven the whole time, and the gap was not cosmetic: `saipen goal` MUST run `PLAN` for the new objective from wherever the pivot happens, so a pivot out of `REVIEW` -- a phase whose row allows only `SHIP`/`BUILD`/`SCOUT`/`BLOCKED` -- produced a `STATE.md` that `tools/validate.py` correctly rejected while the agent was doing exactly what § 2.4 ordered. Two rules, both followed, one invalid state. Found by the validator on a live pivot, which is the check working, not failing.
- `HUNT -> PLAN | SCOUT` (the findings case, distinct from the clean-board case which always goes to `ADD`) is stated explicitly in `phases/hunt.md` itself: findings that get ticketed go to `PLAN`, or straight to `SCOUT` for a small/obvious one.
- `DONE` never targets `ADD` directly -- `phases/done.md` itself says plainly "`ADD` itself is only ever reached autonomously via a clean `HUNT`" (§ 2.1). The only door into `ADD` is `HUNT`'s clean-sweep result; an earlier version of this table listed `ADD` as a direct `DONE` target, which no phase doc ever actually implemented.
- `ADD` never targets `HUNT` either -- the direction is `HUNT` -> `ADD` (a clean sweep opens `ADD`), never the reverse. `phases/add.md` states outright that bouncing `ADD` back to `HUNT` is illegal (it would just re-derive HUNT's "no new signal" result and loop): a bug `ADD` spots goes `RETURN SCOUT`, not `RETURN HUNT`. `ADD` begins again only after the *next* clean `HUNT` (§ 2.2), which is `HUNT` reaching `ADD`, not `ADD` reaching `HUNT`. An earlier version of this table listed `HUNT` as a direct `ADD` target -- the same phantom as the `DONE -> ADD` one above, no phase doc ever implemented it, removed for the same reason.
- **A repeated attempt MUST be able to name what changed.** Before trying the same thing a second time -- a failed build, a failed `verify:`, a push that did not land, a hypothesis already rejected -- the agent MUST be able to state, in the LOG line that records the attempt, what is different from last time: new evidence, a changed input, a different environment, a narrowed hypothesis. **If the honest answer is "nothing", the retry is forbidden** -- move the ticket to `## BLOCKED` with `| blocker:` naming the dead end, or pick different work. Counters alone do not carry this: `phases/verify.md`'s 3-hypothesis/2-fix-cycle cap and `phases/ship.md`'s retry-once both bound how MANY times an attempt repeats, and neither asks whether the second attempt could possibly go differently. `phases/verify.md` has said "never re-test without new evidence" of debugging hypotheses since long before this clause; it was true of every repeated attempt and stated for one of them, which is the same fixed-where-noticed shape this protocol keeps finding in itself. Identical retries are the cheapest way for an autonomous run to burn its whole budget while producing nothing, and `goal_mode` makes them free to start and invisible to the human until the valve trips.
  - This is behavioural: no artifact in `.saipen/` witnesses whether the agent actually had new information, so `tools/validate.py` cannot enforce it, and CONFORMANCE records it as a stated limit rather than an implied guarantee. What it can do is refuse the excuse -- the LOG line for a repeated attempt names the delta, so a human or a later agent reading the graph can see whether one existed.
- `VERIFY -> SCOUT | BUILD` and `REVIEW -> SCOUT | BUILD` do NOT mean the ticket that just failed VERIFY or REVIEW bounces back for a retry -- both phase docs send that specific ticket to `BLOCKED` when their own cap trips (`phases/verify.md`'s 3-hypothesis/2-fix-cycle cap, `phases/review.md`'s 2-pass cap), then pick up a *different*, unblocked `TODO` ticket, landing in `SCOUT` or `BUILD` for that one. `v7.18.0` removed a real same-ticket bounce-back bug from this exact row; these targets are the later, distinct "switch to other work" addition, not a regression of that fix.
- **`-> BLOCKED` is universal, not per-phase vocabulary.** Every row above ends in `| BLOCKED` because *any* phase can turn out to be genuinely stuck, not because each phase doc separately invents its own trigger for it. Several docs do name a concrete one (`phases/clean.md`'s unsafe deletion candidate, `phases/prepare.md`'s unrepairable staleness, `phases/done.md`'s all-tickets-unworkable, `phases/verify.md`/`review.md`'s caps); the ones that don't (`add.md`, `hunt.md`, `markhunt.md`, `translate.md`) are not thereby forbidden from reaching it -- a phase that cannot proceed and has no other workable ticket goes `BLOCKED` with the facts, which is `phases/blocked.md`'s own entry condition and needs no per-doc restatement. Do not read a phase doc's silence here as "this phase must push through no matter what."
- `saipen status` MUST NOT change `phase` -- it is read-only (§ 1.10).
- `saipen stop` checkpoints and halts; it is not itself a phase transition (§ 1.10).
- Maintenance phases (`HUNT`/`ADD`/`CLEAN`/`TRANSLATE`) MUST NOT be required for Core continuation -- the Core chain (`INIT` through `DONE`/`BLOCKED`) is fully self-contained; a cold agent running Core alone never needs to reach them.

### 1.7 Workspace Hygiene
The protocol lives in the SAIPEN home; the project holds work, not protocol copies.
- `saipen set` in project root MUST NOT copy phases or scripts into the project. It MUST write a bootloader to `.saipen/STATE.md` pointing to the canonical `saipen/` home path -- concretely, the `saipen_home` frontmatter field (§ 1.2): the absolute path this bootstrap read the protocol from. A successor agent on the same machine finds the protocol through it; a successor on a different machine that finds the path dead clones github.com/vacterro/saipen and updates the field at its next checkpoint. (This field existed only as an unimplemented sentence in this section until v7.25.0 -- states written before then legally lack it.)
- Phase transitions MUST load the authoritative Markdown files directly from the global `saipen/phases/` directory via absolute path.

### 1.8 Batch Input Parsing (The "No Rush" Rule)
If the user provides a raw list or backlog of multiple features, tasks, or bug reports, the agent MUST NOT attempt to implement them all in a single pass. The agent MUST parse the list into individual `TODO` tickets on `BOARD.md` and execute them surgically, strictly one by one. "One by one" governs BUILD scope -- one ticket's changes per edit pass, never several tickets' code mixed into one -- not cadence. It does NOT mean pausing between tickets: under `goal_mode` (§ 2.4) tickets still flow without stopping; outside `goal_mode`, the normal per-ticket checkpoint (§ 1.5) still applies exactly as always.

- **Trailing Extrapolation ('etc.')**: If a user prompt, backlog list, or feature request contains "etc.", "etcetera", "and so on", "и т.д.", or similar phrasing, the agent MUST interpret it as an explicit instruction for "similar additions" — inferring and creating tickets for obvious missing workflow steps, complementary features, or logical extensions required to complete the pattern (aligning with § 2.3).

### 1.9 Extension Discovery
- `.saipen/extensions/<name>/` **inside the consuming project's own `.saipen/`** is an optional, project-attached phase hook (e.g. `security`, `performance`) that the project's own author creates and maintains -- `saipen set` / `init.md` and the injector do NOT auto-populate it, the same way they never auto-populate a project's `tests/`. Each extension's own `README.md` states which phase it attaches to and what it requires there. Everything protocol-shaped a project carries lives under one `.saipen/` roof -- not scattered as sibling dot-and-plain folders across the project root (v7.35.0; before then the attachment point was a root-level `extensions/`). **Legacy**: a project bootstrapped earlier MAY still carry root-level `extensions/<name>/` -- agents MUST recognize it as equivalent, and MAY migrate it (`git mv extensions .saipen/extensions`, one LOG line) at a convenient checkpoint; never maintain both locations at once. **Both exist at once** (a partial/failed migration, or two agents disagreeing) is a conflict, not a merge job: treat `.saipen/extensions/<name>/` as authoritative, the root-level copy as stale, ticket its removal, and do not silently combine or guess which copy is newer.
- On entering a phase, the agent MUST check whether the *project's* `.saipen/extensions/<name>/` (or legacy root `extensions/<name>/`) exists for that phase before proceeding. If it exists, its README's instructions apply for that phase. If it is absent, the phase proceeds exactly as its `phases/*.md` doc describes, with zero extension overhead. Absence MUST NOT block a phase transition -- extensions layer on top of Core, they never gate it.
- If an extension IS present but its own stated requirements aren't met on this host (a scanner binary missing, an API key unset) -- and Core's own safety/correctness isn't at stake -- the agent MUST degrade: skip what that requirement blocks, note it plainly in the phase's findings, and continue. If proceeding without it would be genuinely unsafe (the extension exists specifically because this project needs that check, and it silently can't run), the agent MUST go `BLOCKED` instead of pretending the check happened. Either way, an extension MUST NOT overwrite or weaken Core normative behavior -- it can only add checks on top of Core, never relax what Core already requires.
- The `extensions/security/` and `extensions/performance/` folders inside the SAIPEN home itself are reference *examples* for a project author to copy and adapt -- the same role `extensions/templates/` plays for `.saipen/` boilerplate. The home's top-level `extensions/` is the shipped LIBRARY (what the injector distributes and `saipen sub spawn` bootstraps from) and keeps that location; only the *attachment point inside a consuming project* is `.saipen/extensions/`. They are not live hooks the SAIPEN home reads on its own behalf; nothing discovers them unless a project author has replicated the pattern into their own project.
- `extensions/schemas/` is a distinct, non-behavioral case: descriptive JSON Schemas held for a future external validator (see `extensions/schemas/README.md`). It is not a phase hook and this section does not apply to it. **Exception**: `state.schema.json` is live, not reference -- `tools/validate.py` reads it directly to check `STATE.md`'s shape (CONFORMANCE.md § 1). `board.schema.json`/`log.schema.json` remain descriptive-only, unread by any agent today; don't assume the same of `state.schema.json` just because they share a directory.
- An extension MAY define its own bare-command vocabulary (e.g. `saipen sub spawn <name>`) in its own README/PROTOCOL doc -- recognized ONLY while that extension's folder exists in the project, and MUST NOT collide with a § 1.10 name. These commands are never registered in § 1.10's closed list; § 1.10 alone still governs what's recognized with no extension present. This is the general mechanism -- no extension gets bespoke Core wording for its own commands. **Two active extensions defining the same word** (both attached to this project, e.g. two independently-authored phase hooks that happened to pick an identical bare-command) is never silently resolved by picking whichever loads first -- decline, name both extensions and the colliding word, and ask the user which one they meant. This is the same "never guess" floor § 1.9's own degradation rule already applies elsewhere, just for a collision between two extensions instead of one extension against Core.

### 1.10 Command Surface
The complete set of recognized user-facing commands. Phase-affecting ones are defined in full where cited; `status` and `stop` are defined here because they are meta/control operations, not phase transitions -- they can be invoked from any phase and MUST NOT be treated as work themselves.
- `saipen set` / `saipen init` -- bootstrap `.saipen/` (§ 1.7, `phases/init.md`).
- `saipen continue` / bare `saipen` -- read `STATE.md`/`BOARD.md`/tail of `LOG.md`, execute `next_action` immediately, no rebriefing (§ 1.1, § 2.1 DEFAULT BEHAVIOR, `CONFORMANCE.md` TEST-001). **A resume MUST also name what is stuck**, in its reply, in one line: every ticket in `## BLOCKED`, any untriaged `[MARKHUNT]` finding, and a live `WAIT:` if one is being carried. Report only -- no new field, no state change, nothing queued. `.saipen/kitchen/digest.md` carries this at `saipen stop` and `SHIP` and nowhere else, so a blocked ticket could sit unmentioned across an unbounded number of sessions while every one of them truthfully reported the work it did do. The human's whole view of what is parked came from a file written only when the run ended.
- `saipen goal <text>` -- pivot to a new objective, run to completion (§ 2.4). Bare `saipen goal` (no text) is also recognized, but ONLY to resume an already-paused `goal_mode: true` run (§ 2.4 Entry) -- it is never a way to start a new objective without stating one. **With `goal_mode: false` it is not a command at all**, and the failure mode worth naming is the tempting one: bare `saipen goal` resets `goal_waves`/`goal_tickets` to `0`, so an agent that treats it as a generic "start goal mode" hands out a fresh safety-valve budget for a run nobody authorized. It MUST NOT set `goal_mode`, MUST NOT write or reset either counter, MUST NOT plan, and MUST NOT guess an objective from `BOARD.md`. It replies exactly `Use: saipen goal <objective text>` and stops -- one line, no state change, which also satisfies § 1.11's "a session that did nothing MUST say exactly that."
- `saipen plan [text]` -- explicit trigger for PLAN phase (`phases/plan.md`). If run bare without text, agent MUST generate an autonomous proposal plan (next steps, missing features, refactoring) and populate `BOARD.md` with tickets.
- `saipen clean` -- explicit CLEAN trigger (`phases/clean.md`).
- `saipen translate` -- isolated translation build (`phases/translate.md`).
- `saipen markhunt` -- dry exhaustive audit, records findings to BOARD.md, never fixes anything (`phases/markhunt.md`).
- `saipen prepare` -- package the current work (or a subSaipen's) for handoff to the next agent: freshness-check it against current HEAD, format the result, write injection instructions (`phases/prepare.md`).
- `saipen ship` -- explicit SHIP trigger (`phases/ship.md`); SHIP also fires implicitly per that phase's other stated conditions. Explicit invocation does NOT waive the correctness gates in front of it: the transition table's only route into `SHIP` is from `REVIEW`, and `phases/review.md` states plainly that `SHIP` is mandatory before `DONE` with no `REVIEW -> DONE` shortcut. So `saipen ship` from a phase that hasn't been through `VERIFY`/`REVIEW` for the work in question means "take this work through those gates and then ship," never "skip to the push" -- run them, then ship. Concretely, that means the `next_action` it writes is the next unmet gate on that ticket's own chain -- `PHASE SCOUT`/`BUILD`/`VERIFY`/`REVIEW` with the ticket ref -- and `PHASE SHIP T-###` only once `REVIEW` has passed. With no in-flight and no reviewed work to ship at all, it is `WAIT: blocked -- saipen ship has no verified work to ship`. Nothing already-shipped needs re-gating; this is about work that has never passed them.
- `saipen hunt` -- explicit `HUNT` trigger (`phases/hunt.md`): run the defect/improvement sweep now instead of waiting for § 2.1 to reach it, then follow that phase's own exits (findings -> `PLAN` or `SCOUT`, clean -> `ADD`). It forces the sweep, it does not skip anything: a ticket in `## DOING` still outranks it under § 1.11 step 3, and switching phase with one claimed carries the same checkpoint duty as every other phase-switching command below -- ordering and checkpointing are two rules, and naming only the first is how this command shipped in v7.148.0 as the one phase switch that could leave half-finished work unwritten. `HUNT` was reachable only by auto-transition or a `PHASE HUNT` `next_action` until v7.148.0, so the `hh` shortcut pointed at a phase name with no command behind it -- a shortcut routing to something the command surface never defined.
- `saipen validate` -- explicit VALIDATE trigger (`phases/validate.md`): run the conformance script, fix structural corruption if found (shape only -- a malformed line, missing frontmatter field, wrong heading; never a rewrite of `LOG.md`'s historical event content or any other file's real content), transition to `PLAN` or `SCOUT` per that phase's own rules.
- `saipen status` -- MUST read `BOARD.md` and `STATE.md` and report current phase, the in-flight ticket, and what's queued next. MUST NOT write to any file or perform any work -- read-only, no exceptions, regardless of `goal_mode`.
  **It MUST also answer the question the human is actually asking**, which observation says is rarely "what phase am I in" and almost always "is this in good shape, and does anything need *me*". Those two need different facts, and the second set is the one an agent otherwise reconstructs from memory -- which a cold agent cannot do at all, making it exactly the kind of thing that belongs in state rather than in a chat scrollback. So the report MUST additionally carry, each in one line, and each omitted entirely when it is empty rather than padded with "none":
  - **Waiting on you.** Every open `WAIT:` and every `## BLOCKED` ticket whose blocker names a human decision, quoted as the concrete question. This is the human's to-do list and it is the single most useful line in the report.
  - **Claimed but unproven.** Work that is done but whose `| verify:` never ran, or ran only as `conf: low`/`med` (`phases/verify.md`). "Finished" and "verified" are different states and conflating them is how a project feels healthier than it is.
  - **Conformance.** The result of the last `tools/validate.py` run if one is recorded in `LOG.md`, with its timestamp -- or plainly that none is, which is itself the answer. Never re-run it: `status` is read-only, and a validator run is work.
  - **Staleness.** How old `STATE.updated` is, when that gap is large enough to matter. A tidy-looking board that nobody has touched in three weeks is not the same as a tidy board from an hour ago, and the difference does not otherwise show.
  This is a *report*, never a verdict: state what is and is not established, let the human conclude. It MUST NOT pronounce the project "healthy", "ready", or "good to ship" -- an agent grading its own work is the least valuable opinion in the room. Where `.saipen/kitchen/digest.md` is a snapshot *left behind* at `ship`/`stop`, this is the same picture *asked for* live; if the digest exists and disagrees with what `status` reads off `BOARD`/`STATE` now, say so and trust the live files -- the digest is by definition older.
- `saipen stop` -- MUST checkpoint immediately per § 1.5 (flush `LOG.md`, update `BOARD.md`, set an explicit resumable `next_action`), then (over)write the 3-line human digest `.saipen/kitchen/digest.md` (`done:`/`remaining:`/`awaiting:` — same snapshot `phases/ship.md` writes, so the human reads one small file instead of the LOG), and halt and return control to the user. **Under `mode: read-only` (§ 1.3) the digest write is not merely skipped, it is impossible** -- that mode exists precisely because filesystem writes are unavailable, so this line ordered something unsatisfiable by construction until v7.92.0, and an agent that took "MUST write" literally would either fail the stop or fabricate a success. Resolve it exactly as § 1.3 resolves the identical problem for `mode:` itself: emit the same three lines (`done:`/`remaining:`/`awaiting:`) into chat instead, leave whatever `digest.md` already exists untouched, and say plainly that it was not updated. The checkpoint clause above is under the same constraint and gets the same treatment -- a read-only session cannot checkpoint at all, so it reports the resumable `next_action` it *would* have written rather than pretending one landed on disk. MUST NOT leave a ticket mid-edit. **Overrides autonomous continuation** -- it is the user's manual brake and always wins. It does NOT change `goal_mode`, and it does not touch the safety-valve counters. It once read "Overrides `goal_mode`" two clauses above the paragraph saying `goal_mode` is untouched; a weak model acts on the first clause it can execute and makes the bare `saipen goal` resume illegal under this same section. **A tripped valve outranks the brake in one respect**: if `goal_mode: true` and `goal_waves`/`goal_tickets` are at or over § 2.4's caps, `saipen stop` MUST write the § 2.4 safety-valve `WAIT:`, never a `user brake` one -- stopping may pause a run, it may not disguise a tripped valve as a routine pause, which would hide the fact that continuing requires re-authorization. **This is a pause, not an exit**: `goal_mode` (if `true`) is left exactly as-is -- § 2.4's Exit list is exhaustive and `stop` is not on it -- and the safety-valve counters (`goal_waves`/`goal_tickets`) are left untouched by the stop itself too. How a *later resume* treats those counters depends on which command resumes, and the two paths are NOT equivalent: `saipen continue` or bare `saipen` resumes the *same* paused invocation with its counters exactly as they were -- precisely as if the stop had never happened. Bare `saipen goal` also resumes under the same still-`true` `goal_mode`, but it is the one resume path that deliberately does NOT preserve the counters: per § 2.4 Entry it resets `goal_waves`/`goal_tickets` to `0`, granting a fresh safety-valve budget. That reset is the whole point of re-invoking `saipen goal` to continue past a tripped valve (§ 2.4) -- it is a re-authorized fresh batch, never a neutral counter-preserving resume, so "as if the stop had never happened" describes the `continue`/bare-`saipen` paths only, never bare `saipen goal`.

**Any recognized phase-switching command (`clean`, `translate`, `markhunt`, `validate`, `prepare`, `plan`, `ship`, `hunt`) invoked while a ticket sits in `## DOING` MUST checkpoint that ticket first** (§ 1.5's normal LOG -> BOARD -> STATE, plus a refreshed `claim_time` if the ticket stays claimed) before switching phase. `saipen stop` already says this explicitly; the others inherit the same duty rather than each restating it, because the failure is identical either way -- switching phase out from under an in-flight ticket abandons it mid-edit, leaves an unrefreshed claim that goes stale in 15 minutes (§ 1.4), and strands whatever `kitchen/` work it had going. The ticket may legitimately stay `## DOING` across the switch (you're coming back to it) or be demoted to `## TODO` with a resumable `next_action` (you're not) -- what's forbidden is neither: leaving it claimed, unlogged, and unrecorded while the session goes and does something else.

**Repeated-letter shortcuts.** Identical keystrokes, no shift — a repeated letter cannot begin an English word, and a shortcut is the ENTIRE message rather than a prefix of one, so it is never mistaken for prose. **Length is collision order, not cost**: where two commands want the same first letter, the doubled form goes to one and the tripled form to the next (`cc`/`ccc` for continue and its shipping chain, `ss`/`sss` for stop and status). Length said 'this one reaches a remote' for exactly one release, until `sss` arrived and made that false -- so `ccc` states on its own row that it is the only shortcut whose chain pushes, which is a fact the table carries rather than an inference the reader has to draw from counting keys. **Doubled is safe, tripled reaches a remote**: `ccc` is the only three-letter form and the only shortcut whose chain pushes, so the length of the shortcut tells the user what it costs before they finish typing it. `gg`, `cc` and `hh` are the doubled first letter of their canonical command (E-1415); the rest are user-assigned by fiat to resolve collisions among commands sharing a first letter (`s` alone covers `stop`/`set`/`ship`/`status`/`scout`, `ss` goes to the brake and `sss` to status, both by the user's own assignment, since the three-letter form is reserved for the chain that reaches a remote). The table is authoritative; each shortcut routes to its canonical command's definition above (or to its subSaipen extension's own command vocabulary, § 1.9).

| Shortcut | Routes to | Notes |
|----------|-----------|-------|
| `gg` | `saipen goal` | Goal Mode pivot / re-authorization |
| `hh` | `saipen hunt` | Autonomous defect/improvement scan (§ 2.1) |
| `cc` | `saipen goal` | Mapped by user request to trigger goal mode; originally resume/continue |
| `ccc` | `saipen continue` then `saipen ship` | Everything `saipen continue` does, then the commit/tag/push chain through its own gates. **The only shortcut whose chain reaches a remote** -- stated here because the table carries the fact, not because length implies it: `sss` is tripled too and touches nothing outside the repository. It waives nothing -- `saipen ship` still routes through `VERIFY`/`REVIEW` per its own definition |
| `ss` | `saipen stop` | The brake: checkpoint, write the digest, hand control back |
| `sss` | `saipen status` | Where the run stands, caveman-дед short |

| `qq` | `saipen sub spawn saiwiki` | Wiki: spawn / maintain / update / refresh / analyze |

**A shortcut typed in Cyrillic is the same shortcut.** On a Russian layout the visually identical letters carry different codepoints, so the recognizer resolves through the lowercase confusable set `а→a е→e о→o р→p с→c у→y х→x` before matching. Five rows have twins that way -- `сс`, `ссс`, `аа`, `ее`, `рр` -- and the other six have none, which is why this is a normalization step and not a second column of aliases. Answering `unrecognized command` to a key the user pressed correctly, on the layout they actually type in, is the worst available response and the most-used shortcut is the one it hits. The table itself stays Latin: it is the canonical spelling, not the only accepted one.

A shortcut not in this table is unrecognized — same handling as any unrecognized `saipen <word>`. The table is maintained here, never duplicated elsewhere; CONFORMANCE and `tools/validate.py` point here by reference.

Any command not listed here that appears in a `phases/*.md` doc without a matching definition in this section is non-conformant; add it here before relying on it. If the user types `saipen <word>` and `<word>` matches none of the above, the agent MUST check any active project extension's own bare-command vocabulary (§ 1.9 -- e.g. `saipen sub spawn <name>`) before concluding anything: a match there is recognized and governed by that extension's own doc, never rejected just for being absent from this section's closed list. Only once extensions are checked and still nothing matches, and the word isn't plausibly free-text for `goal`/bare `continue`, MUST the agent decline to invent behavior for it -- list the recognized commands (this section's, plus any active extension's) and stop.

### 1.11 Determinism Invariants

Everything above defines what an agent MAY do. These four define what any two conformant agents MUST do *identically*, given the same `.saipen/`. They add no new files or fields -- they close the places where a rule said "the agent decides" and two models would decide differently.

- **Action priority is fixed, not a judgement call.** When more than one thing looks doable, resolve strictly in this order, first match wins, no weighing:
  1. **RECOVER** -- `STATE.md` is unreadable, missing a required or conditionally-required field, carries a `next_action` that fails § 1.2's prefix or `WAIT:` category checks, or is contradicted by `LOG.md`/`BOARD.md` (§ 1.5 Recovery). The `next_action` clause matters because without it the priority list had a hole exactly where it hurts: `next_action: continue work` is present, non-empty, and passes every RECOVER trigger, so a conformant agent would fall through to FINISH or START and *execute* a value § 1.2 calls non-conformant. One exception routes elsewhere rather than here: the `DONE` + empty `## TODO` + invalid-`WAIT:` case is UNBLOCK's, below, which auto-transitions instead of rebuilding. Nothing else may run first; acting on a state you have not repaired is how a small corruption becomes a large one.
  2. **UNBLOCK** -- `STATE.phase: BLOCKED`, or `next_action` is a `WAIT:`. Restate it and stop. This outranks work by design: § 2.1's autonomous transitions are explicitly barred here, so a blocked session never quietly finds something else to do.
     **One exception, and it is not a judgement call.** `phase: DONE` **and** `## TODO` empty **and** `next_action` starting `WAIT:` in any form other than the **two** § 1.2 whitelists for exactly that state (the § 2.4 safety valve, or `WAIT: user brake -- <reason>`) is a non-conformant state, not a legitimate stop -- § 2.1 requires an empty board at `DONE` to auto-transition into `HUNT` with no human asked, so that `WAIT:` is something a previous agent wrote in violation of the rule. Obeying it deadlocks the project permanently: UNBLOCK says stop, nobody is coming, and the `WAIT:` names no answerable question. So do NOT stop. LOG a `DEC` line quoting the invalid `WAIT:` verbatim, then transition `DONE -> HUNT` per § 2.1 (a legal edge in § 1.6's table). `tools/validate.py` has flagged this state since v7.86.0 while this section still ordered the stop -- the validator was right and this text was wrong until v7.92.0. Every other `WAIT:`, at `DONE` or anywhere else, still stops: this exception is exactly three conditions wide, and a `WAIT:` at `DONE` that IS one of § 1.2's two whitelisted forms -- the safety valve (§ 2.4) or a `user brake` -- is a real pause that MUST be honoured. § 1.2 and this section were shipped in the same release (v7.92.0) naming a different number of legal forms, two versus one; they now name the same two, and if a future edit changes the whitelist it changes in § 1.2 and this sentence defers to it.
  3. **FINISH** -- a ticket sits in `## DOING` and is **either yours or unclaimed**. Carry it to its next phase before touching anything else; adopt an unclaimed one first, per § 1.4 (LOG the `DEC`, check `kitchen/`, set your own `owner:`/`claim_time:`). Half-finished work outranks new work, always. The rule means "don't steal a live claim" (the § 1.4 staleness test, still binding), never "abandon orphans": a crashed session's ownerless `## DOING` read as "not mine" sends the agent to START, and the board ends with two `## DOING`, which `tools/validate.py` FAILs.
  4. **START** -- no `DOING`, workable `TODO` exists: apply the § 1.6 Pick Rule.
  5. **MAINTAIN** -- board empty: § 2.1's `HUNT` -> `ADD`.
  A tie inside a step is impossible by construction: steps 1-3 are single-valued, step 4 defers to the Pick Rule, step 5 to § 2.1.
- **One ticket at a time.** In Core, `BOARD.md` MUST carry at most one `## DOING` ticket **in total** -- not one per agent. Core's concurrency model is one agent writing `.saipen/` at any instant (§ 1.4 Concurrency boundary), so "per agent" and "in total" describe the same board, and stating it per-agent invited a weak model to reason "the other DOING ticket isn't mine, so I may add a second." It may not. This was already the enforced rule -- `tools/validate.py` FAILs any board with two (`CONFORMANCE.md` row 50, v7.90.0) -- while this line said "an agent" until v7.92.0; the enforcement was the correct half. Multi-agent concurrency is outside Core: if an extension explicitly enables it (§ 1.9), every `## DOING` ticket MUST carry a distinct `owner:` with a non-stale `claim_time:` (§ 1.4), and a board with two unowned or same-owner `DOING` tickets is invalid under that extension too. Finish it, block it, or demote it to `## TODO` before claiming another -- and demoting is a real act with a `LOG` line, not just walking away. Without this a weak model ticket-hops (claim T-12, drift, claim T-27, drift, claim T-53) and leaves a log nobody can read and three tickets nobody can tell the state of. Related tickets that genuinely must move together are one ticket, or are sequenced with `needs:`.
- **A session MUST leave a trace.** Every session that did anything at all ends having produced at least one of: a new `LOG.md` line, a `BOARD.md` change, a `STATE.md` change, or a change to the project's own files. If none of those happened, the session did nothing, and it MUST say exactly that rather than summarising activity in chat -- thinking is not progress, and a run whose entire output lived in a conversation is indistinguishable from one that never ran. **Under `mode: read-only`** -- or any mode where the write this session needed is impossible -- the trace is an explicit chat report naming what was checked and which file was deliberately not written. That is a different statement from "I did nothing" and both are honest; what is forbidden is a read-only session narrating work as though it had landed on disk. Thinking is still not progress. This is also the honest form of "I could not proceed": say it, and write the `WAIT:` that names why.
- **Insufficient information is a stop, not a guess.** When the next step depends on a fact the agent does not have and cannot obtain from `STATE`/`BOARD`/`LOG`/`KNOWLEDGE`/the project's own files, the agent MUST stop and ask -- `next_action: WAIT: <the exact missing fact>`, within § 1.2's legal categories. It MUST NOT infer the project's intent, invent a requirement, pick a plausible-looking default for a decision the user never delegated, or proceed on "probably". The test is mechanical: if writing the next action requires a sentence starting "presumably", "I'll assume", or "it probably wants", the information is insufficient by definition. Guessing is the one failure mode this protocol cannot detect afterwards -- a wrong guess produces confident, well-formed, fully-logged work that looks exactly like right work.

## Part 2: MAINTENANCE (Autonomous Evolution)

### 2.1 Autonomous Transitions
When the Core state machine reaches a halt, the Maintenance layer MAY take over.

**"Halt" has one definition, used identically everywhere in this section: no *workable* `## TODO` ticket AND no `## DOING` ticket.** A **workable** `## TODO` ticket is one the § 1.6 Pick Rule would allow you to claim right now -- open checkbox, every `needs:` satisfied, not under another agent's active claim. `## DONE` and `## BLOCKED` tickets never count against the halt. Neither does a `## TODO` ticket that is permanently unpickable: a cyclic or dangling `needs:` puts it in `## BLOCKED` with the reason (§ 1.2), it does not sit in `## TODO` as ballast that blocks the halt forever while looking like work.

**`## DOING` counts too, and that half was missing until v7.93.0.** "No open TODO" alone is satisfied by a board whose only ticket is in flight, which would send an agent into `HUNT` while holding a half-finished ticket -- exactly the abandonment § 1.11's FINISH priority forbids. FINISH outranks MAINTAIN; a `## DOING` ticket is finished, blocked, demoted, or (if unclaimed) adopted, and only an empty `## DOING` opens the maintenance door.

Two phrasings of this test once coexisted here, and a ticket with unsatisfied `needs:` passed one and failed the other -- two conformant agents could disagree about whether the project had halted at all.

- **DEFAULT BEHAVIOR**: The bare command `saipen` is an alias for `saipen continue`. If the board has not halted (a `## DOING` ticket, or any workable `## TODO`), the agent MUST resume work -- via § 1.11's action priority, which decides *which* of them.
- **ZERO-PROMPT AUTO-TRANSITION**: If the user runs the protocol and the board has halted as defined above, the agent MUST NOT ask the user for instructions or permission (e.g., "Should I hunt or add?"). It MUST silently and autonomously transition to the `HUNT` phase. If `HUNT` finds nothing (clean), the agent MUST immediately transition to `ADD`. **Exception -- a session already sitting at `STATE.phase: BLOCKED` is not eligible for this.** A board holding only `## BLOCKED` tickets satisfies "no open `TODO`" on a literal reading, which would let a session that stopped for a credential or a human decision quietly slip into autonomous `HUNT`/`ADD` and start unrelated work while the actual blocker sits unanswered -- exactly the "wait for facts, don't spin" discipline `phases/blocked.md` exists to enforce. `BLOCKED` is left only by the user resolving the blocker (`phases/blocked.md` step 5), never by this transition.
- **HUNT**: Transition to `HUNT` MUST occur strictly when `BOARD.md` has halted as defined above, or when explicitly signaled by a failed verification loop. Agent MUST NOT hallucinate tasks during `HUNT`.
- **CLEAN**: Transition to `CLEAN` occurs when explicitly triggered by the user via `saipen clean` (or just `clean`). The agent MUST instantly set `phase: CLEAN` in `STATE.md`, load `saipen/phases/clean.md`, and execute it. Agent MUST audit and prune stale tickets, orphaned files, and broken paths before returning to `DONE`.
- **MARKHUNT**: Transition to `MARKHUNT` occurs when explicitly triggered by the user via `saipen markhunt` (or just `markhunt`). The agent MUST instantly set `phase: MARKHUNT` in `STATE.md`, load `saipen/phases/markhunt.md`, and execute it.
- **TRANSLATE**: Transition to `TRANSLATE` occurs when explicitly triggered by the user via `saipen translate` (or just `translate`). The agent MUST instantly set `phase: TRANSLATE` in `STATE.md`, load `saipen/phases/translate.md`, and execute it. Agent MUST operate exclusively within a `.saipen/saitranslate/` folder to build, maintain, and update the 32-language core translation system + bonus voice Legacy projects MAY still carry it at root-level `.saitranslate/`; agents MUST recognize that as equivalent and MAY migrate it (`git mv`, one LOG line), never maintaining both. Both present at once is a conflict, not a merge job -- `.saipen/saitranslate/` is authoritative, the root copy stale, its removal ticketed; the same resolution § 1.9 gives extensions. It MUST treat the main software strictly as a read-only reference. **Exception**: a separate, dedicated agent instance sent to run TRANSLATE in true parallel with the main agent (which keeps building elsewhere) MUST NOT set the shared `phase: TRANSLATE` -- that would stomp on the main agent's own active phase. It keeps its own progress in `.saipen/saitranslate/STATE.md` instead, per `phases/translate.md`'s parallel-instance rule. This parallel mode requires the project's `.saipen/` to already exist (`saipen set` already ran) -- the same precondition `saipen sub spawn` requires (`extensions/subs/PROTOCOL.md`); TRANSLATE, parallel or not, is never a substitute for INIT.

### 2.2 Evolutionary ADD
- **ADD**: Agent MUST NOT invent speculative, experimental, or unrelated features. Agent MUST evaluate additions strictly using the following logic:

  ```pseudocode
  FOR priority IN [
    "bugfix", 
    "complementary_feature (Bold->Italic)", 
    "workflow_step (Open->Save_As)", 
    "ux_consistency", 
    "platform_convention"
  ]:
    IF exists(priority):
      IF priority == "bugfix":
        TICKET(priority)
        RETURN SCOUT
      IF satisfies(minimal_delta) AND satisfies(existing_design_language):
        TICKET(priority)
        CLAIM(ticket)
        RETURN BUILD
      ELSE:
        TICKET(priority)
        RETURN PLAN_or_SCOUT
  
  RETURN DONE
  ```
  
  **`RETURN <X>` is a decision this pseudocode makes, never a literal to
  copy into `next_action`.** There is no `RETURN` prefix in § 1.2's five
  legal forms, so `next_action: RETURN PLAN_or_SCOUT` is non-conformant
  garbage that a cold agent cannot execute -- and `PLAN_or_SCOUT` is not
  even a phase. Translate it: `PHASE PLAN T-###` when the ticket needs
  planning, `PHASE SCOUT T-###` when it does not, `PHASE BUILD T-###`
  for the claimed minimal-delta branch.

  `bugfix -> TICKET; RETURN SCOUT`, not `RETURN HUNT` -- ADD does not
  improvise a fix inline, but bouncing back to HUNT is illegal too: if
  HUNT's own 6 mechanical signals (`phases/hunt.md`) didn't already catch
  this bug, sending ADD back to HUNT just re-derives the same "no new
  signal" result and loops forever. ADD tickets it and claims it itself.
  ADD-created tickets follow the normal Core flow from there:
  `BUILD -> VERIFY -> REVIEW -> SHIP -> DONE` (§ 1.6) -- ADD itself never
  implements anything directly or short-circuits to `VERIFY`. `ADD` may
  begin again only after a clean `HUNT` (§ 2.1); it does not run on a
  fixed cadence after every ticket.

### 2.3 The Industrial Completion Rule
When the user requests one step of a well-known user workflow, the agent SHOULD evaluate whether the remaining steps are expected by modern software conventions -- this evaluation is a judgment call, not mechanical. If the evaluation concludes yes, the agent MUST implement the minimal coherent set rather than the isolated feature -- once triggered, this is a discipline requirement, not optional.

- **Evaluate over blindly adding**: If asked for "Apply", the agent evaluates "Save", "Cancel", and "OK". It rejects irrelevant additions (e.g., "Save As").
- **The smallest complete solution wins**: The agent MUST complete the minimal coherent set for the requested workflow. It MUST NOT expand into massive related epics (e.g., "Export" justifies "Import", but does NOT justify building "Cloud Sync").
- **Complete before you extend**: Finish the requested workflow to its logical end before proposing a different one (e.g., "Login" implies "Logout" and wrong-password handling — not OAuth or SSO). Completion is preferred over expansion — the agent SHOULD preserve user expectations before introducing new capabilities.

### 2.4 Goal Mode (Autonomous Execution)
`saipen goal <text>` is an explicit, run-scoped opt-in that (a) sets a new high-level objective, superseding whatever was queued, and (b) runs that objective to completion with minimal interruption — through the Maintenance layer (§ 2.1), not just the current ticket wave. "Run-scoped," not "session-scoped": the persisted `goal_waves`/`goal_tickets` counters (below) mean a `saipen goal` run survives a crash or a fresh chat session mid-run — it ends only via this section's own Exit conditions, never by a session simply restarting. It is NOT the default — `saipen <text>` and bare `saipen continue` retain today's behavior.

- **Entry (the pivot)**: `saipen goal <text>` sets a new objective: a `DOING` ticket in flight MUST be checkpointed cleanly, not abandoned mid-edit — LOG a `DEC` line noting the pivot, then leave it `TODO`. Existing `TODO` tickets MUST NOT be deleted; they are demoted below the new objective's tickets (board order = priority = law, § 1.6). `PLAN` runs for the new objective and inserts its tickets at the top. Agent MUST set `goal_mode: true`, `goal_waves: 0`, `goal_tickets: 0` in `STATE.md`, then proceed directly into `SCOUT` for the first new ticket without pausing. **The Entry `PLAN` is wave 1, not wave 0.** It is a `PLAN` running for a genuinely new wave, which is exactly what the counter counts -- so once it completes, write `DEC: goal_waves 0->1` and checkpoint before entering `SCOUT`. Reading the `goal_waves: 0` initialization as the final value for the first wave costs the run a third of its wave budget and is the easiest way to sail past the valve: three waves would be counted as two. If the user invokes `saipen goal` (bare, no text) to resume a paused run, the agent proceeds immediately to the next workable ticket via `SCOUT` without re-planning or demoting anything. **Whether it also resets the counters depends on the valve, not on the command**: it resets `goal_waves: 0`, `goal_tickets: 0` only when they are at or over § 2.4's caps -- the tripped condition this command exists to clear. With the valve untripped there is nothing to re-authorize, so the counters carry over exactly as `saipen continue` would leave them, and no re-authorization line is written. Resetting unconditionally made the most convenient key silently hand out a fresh 3-wave/20-ticket budget to anyone who typed it out of habit mid-run -- the same failure § 1.10 already names for the `goal_mode: false` case, and it happened here (E-1468 dropped three tickets of accounting against a valve that had never tripped). This is also what makes the shortcut safe to type at any time, which is the point of having one. **A reset that does happen MUST leave its own countable line** -- `DEC: goal reauthorized -- goal_waves N->0, goal_tickets M->0`, this exact text after the taxonomy, with the real pre-reset counts substituted. Without it the drop is invisible: the bumps it cancels are still in the LOG, the newest pivot line is the older `saipen goal <text>` one, and § 1.5's rebuild therefore counts a budget the human already re-authorized away -- re-tripping the valve while this section forbids tidying the counters back down. A re-authorization nobody can count is a re-authorization that expires at the next crash. **No workable ticket to proceed to?** That is not a dead end and not a reason to ask the user anything: fall through to § 2.1 exactly as the Board-empty rule below already requires -- `HUNT`, then `ADD` if clean -- under the still-`true` `goal_mode`. A resume that lands on an empty board is the same situation as a wave finishing on one, and it gets the same answer.
- **Continuation**: While `goal_mode: true`, the agent MUST advance `SCOUT → BUILD → VERIFY → REVIEW → SHIP → DONE` across successive tickets without stopping between them, subject to the caps below. `DONE` MUST transition to `SCOUT` for the next ticket, or re-run `PLAN` automatically for the next wave if the board defines one.
- **Board-empty is not exit**: When `BOARD.md` empties (a wave finishes), the agent MUST NOT stop or wait for a human — it falls straight through into the § 2.1 Autonomous Transitions exactly as under bare `saipen`: `HUNT`, then `ADD` if clean, then `HUNT` again, indefinitely. `goal_mode` remains `true` across this whole loop; a clean `HUNT` or one completed `ADD` ticket is a *waypoint*, never a stopping point.
- **SHIP exception**: The `saipen ship` gate in the SHIP phase is satisfied by an active `goal_mode: true` for subsequent ships to an existing `origin`. Agent MUST auto-push without re-confirming per ship. **First publish of a brand-new repository still MUST confirm name and public/private with the user** — creating a new public artifact is a one-way door goal mode does not waive. "Brand-new" means no `origin` yet, OR an `origin` that exists but has never actually received a commit or tag (`git remote add` run early, nothing pushed since) — the same one-way door either way, not just the narrower "no remote configured at all" case (`phases/ship.md` § 7).
- **Safety valve counters MUST persist, not just live in context**: a long `goal_mode` run spans crashes, restarts, and other agents, so an in-context count is lost on every restart -- defeating the valve for exactly the long runs it protects. `STATE.md` MUST carry `goal_waves` (increment by 1 each time `PLAN` runs for a genuinely new wave -- a `PLAN` entered directly from `ADD`'s `RETURN PLAN` is NOT a new wave, that cycle was already counted at ADD's own RETURN below, so `phases/plan.md` skips the increment in exactly that case; without the carve-out one `HUNT`→`ADD`→`PLAN` chain would count the same wave twice and trip the valve early -- and each time a `HUNT`→`ADD` cycle completes -- "completes" means the moment `ADD`'s own § 2.2 evaluation reaches a `RETURN`, whether that tickets-and-claims a `BUILD`, tickets a `PLAN_or_SCOUT`, or concludes `DONE` outright; the wave is counted there, not deferred until whatever ticket `ADD` just created eventually finishes its own `BUILD → VERIFY → REVIEW → SHIP` run, which `goal_tickets` tracks separately) and `goal_tickets` (increment by 1 each time a ticket passes `VERIFY`) — both bumped and checkpointed (§ 1.5) at the moment they change, so any agent resuming this run reads the true count directly from `STATE.md`, never by re-deriving it from `LOG.md` scrollback. **Each bump MUST also leave an identifiable LOG line** -- `DEC: goal_waves N->M` or `DEC: goal_tickets N->M` (this exact text after the taxonomy) -- because § 1.5's Recovery is required to rebuild these counters by "counting wave/ticket-completion events in `LOG.md` since the pivot line," and that instruction is only executable if those events are actually distinguishable in the log rather than inferred from prose. `STATE.md` stays the fast path every normal resume reads; these lines are what makes the crash path work at all.
- **Safety valve**: A single `saipen goal` invocation MUST NOT process more than 3 waves (`goal_waves`, planned tickets and HUNT/ADD cycles counted together) or 20 tickets (`goal_tickets` counts VERIFY-passes, so a ticket that bounces `REVIEW` -> `BUILD` -> `VERIFY` and re-passes consumes budget more than once -- this is deliberate and conservative: the valve trips slightly early, never late, so it can only ever be safer than the "20 distinct tickets" reading, never looser), whichever comes first. On hitting this ceiling, the agent MUST stop, write a full BOARD/STATE checkpoint, and report progress — the user re-invokes bare `saipen goal` to continue.
  **A tripped valve is a pause awaiting re-authorization, NOT an exit, and `goal_mode` stays `true` through it** (see Exit below, which deliberately does not list the valve). This matters because the alternative deadlocks: § 1.10 recognizes bare `saipen goal` ONLY while `goal_mode: true`, so flipping the flag to `false` here would make the very command this line tells the user to run illegal in exactly the state it just created — leaving no legal way to continue the objective at all, only `saipen goal <text>` to replace it, which demotes the board and re-plans. That is a substitution, not a continuation.
  **The tripped state has one exact shape, and every field of it is load-bearing.** On tripping, checkpoint (§ 1.5) with:
  - `goal_mode: true` — unchanged; the valve is a pause, not an exit (see above).
  - `goal_waves` / `goal_tickets` — unchanged, left at or over the cap. These ARE the tripped condition; "tidying" them is what lets a restart walk straight past the valve.
  - `next_action: WAIT: safety valve reached (N waves / M tickets) -- run 'saipen goal' to continue` — the § 1.2 safety-valve wording, verbatim, with the real counts substituted.
  - `phase` — **left exactly as it is.** Do NOT set `phase: BLOCKED`. This is the one field an agent is most tempted to "fix" here, and setting it is a self-inflicted deadlock: § 2.4's Exit list makes `STATE.phase: BLOCKED` an exit condition, so writing it flips `goal_mode` to `false`, which makes bare `saipen goal` illegal under § 1.10 — and bare `saipen goal` is the only command the `WAIT:` line just told the user to run. The valve would destroy its own continuation path. Same reasoning that kept the valve off the Exit list in v7.86.0; it applies to `phase` too.
  - `blocker` — the tripped valve is not a session-level block, so `blocker: none` stays correct. A budget pause and a blocked project are different states and `saipen status` reports them differently.

  **The counters are what stops a restart, not the phase.** `goal_mode: true` with `goal_waves >= 3` or `goal_tickets >= 20` *is* the tripped condition — no new field. Any agent resuming into that state MUST NOT continue the run: it re-states the stop, with `next_action` in § 1.2's safety-valve `WAIT:` form (`WAIT: safety valve reached (N waves / M tickets) -- run 'saipen goal' to continue`), and waits. Bare `saipen goal` is precisely the human's re-authorization: per Entry it resets both counters to `0`, which is what clears the tripped condition and grants the next budget. Counters at or over the cap are therefore load-bearing, not merely historical — never "tidy them up" without an actual re-authorization.
- **Unchanged under Goal Mode**: All existing caps still apply verbatim (3 dead hypotheses / 2 fix cycles per ticket in VERIFY; 2 review passes per finding in REVIEW). Goal Mode MUST NOT skip `VERIFY` or `REVIEW` — autonomy applies to *continuation between steps*, never to the correctness gates themselves. Destructive ops outside the ship/publish path (force-push, schema drop, deleting user data) still require explicit confirmation unless the ticket itself pre-authorizes them.
- **Exit**: `goal_mode` MUST be set back to `false` in `STATE.md` ONLY when: `ADD` itself gracefully concludes because the product is mature and logically complete (`phases/add.md`), or the agent reaches `STATE.phase: BLOCKED` (not just a single ticket moving to `## BLOCKED`). **A tripped safety valve is NOT on this list** -- it was until v7.86.0, and that was a deadlock: the valve tells the user to re-invoke bare `saipen goal`, § 1.10 recognizes that command only while `goal_mode: true`, so exiting on a trip made the one documented continuation path illegal in the state the trip itself produced. The valve is a budget pause, the same shape as `saipen stop` (which is likewise not on this list); the two real exits above are the objective ending, which a valve trip is not. What stops a restart from silently continuing is the counters, not the flag -- see Safety valve above. A momentarily empty `BOARD.md` is never, by itself, an exit condition. On exit, `goal_waves`/`goal_tickets` MUST be cleared -- they describe the run that just ended, not a running lifetime total. Final report: tickets done/verified/shipped, any blocked, next action -- distinguish tickets that came from the user's original ask from ones picked up along the way (pre-existing backlog demoted below it, or `HUNT`/`ADD` findings), so the user can tell what actually happened without re-deriving it from `LOG.md`. No new persisted field is needed for this -- board order at Entry already carries it; it only needs to make it into the report.
